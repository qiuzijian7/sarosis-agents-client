渠道页 · 9 个方案

2 个按你最新要求做的方案（F1/F2：以表为主、点行展开） + 3 个 B×D 融合（E1/E2/E3）+ 4 个基础方案（A/B/C/D）。 同一份真实数据模型：4 个平台 / 3 条绑定 / 2 条待批准 / 3 条失败。点任意截图可打开交互版。

先看 OpenClaw 怎么组织对照基准

OpenClaw 的层次（官方文档导航）

  • 渠道本身：每平台一页，只讲怎么连上（bot token / QR / Socket Mode / app 凭据）
  • Configuration 是独立分组：Pairing、Access groups、Groups、Broadcast groups、Channel routing、Troubleshooting
  • 即：准入与路由是共享配置层，不塞进单个渠道页
  • 31 个渠道 ⇒ 必须有「目录 + 过滤」，不能是长表单

我们的现状与这 7 个方案的分歧点

  • 现状：凭据 / 入站 / 绑定 / 配对 / 死信 / 最近会话全堆一页
  • 策略字段（dmPolicy / groupPolicy / rooms）已实现但页面无入口
  • 只有 2 个平台还能看，加到 5 个就崩
  • ⇒ 真正的分歧只有两个：「异常数字放哪」 与 「详情怎么出来」

F1 · 窄表 + 行内展开按最新要求贴合 dsh 设置弹窗

一张表，点行就地展开

弹窗总宽 620px − 左导航 128px ⇒ 内容区只有 约 492px。所以主表压到 5 列，展开区把「入站」并成一行工具条，下面才是凭据 / 绑定 / 待批准 / 失败。

取舍展开时其余平台仍在视野内；无抽屉、无跳页
代价一次只展开一行；展开内容纵向堆叠，需小幅滚动

同一套组件与数据；宽容器下主表加「凭据 / 入站」两列，展开区 `.dwrap` 换成两列网格 ⇒ 展开高度约为窄版一半。

取舍信息最全；展开后仍能看到其余所有平台

E1 · 主从 + 运维摘要头B×D 融合

异常在最上面，切平台也不丢

D 的四联 KPI（已接入 / 已连接 / 待批准 / 失败）固定在顶部；B 的左列选平台（带数字徽标）；右详情每一块都是 D 的表格。

取舍全局异常始终可见；单平台操作最顺手
代价顶部条 + 详情里的数字重复一次（否则切走就失参照）

E2 · 表为主 + 抽屉详情B×D 融合

默认就是一张运维表

D 的骨架（一行一平台、异常可数、筛选 chip）；点行从右侧滑出 B 的详情抽屉（430px，可关闭）。

取舍平台再多也不涨高度；窄屏下抽屉自动全屏
代价改凭据多一次点击；抽屉遮住表格右半

E3 · 双表并行B×D 融合

左表选平台，右表看明细

左表只有 4 列（平台 + 绑定/待批准/失败三个数字，352px 宽）；右侧全部内容也是表 —— 不需要抽屉、不跳页。

取舍视觉最统一（两张表）；一屏内完成所有事
代价左表看不到“已连接/未启动”文字；窄屏上下堆叠

方案骨骼异常怎么看见加第 5 个平台改动量
F1 窄表+行内展开表 + 手风琴顶部 KPI + 行内数字只多一行中（无新布局）
F2 宽版同构同上（两栏展开）同上 + 凭据/入站列只多一行中
E1 主从+摘要头B 的左列表 + 右详情顶部 KPI 常驻 + 左列徽标只多一行中偏大
E2 表+抽屉D 的运维表表格列（可排序/筛选）只多一行中
E3 双表并行左窄表 + 右表左表三列数字 + 颜色只多一行中
A 目录式平台卡片 + 策略独立分组卡片上的状态 pill只多一张卡大
B 主从式左列表 + 右详情左列状态点只多一行中偏大
C 工作台式上状态条 + 下分段 tabtab 上的徽标tab 内列变多小
D 运维表一行一平台待批准/失败列高亮只多一行中

我的建议：F1（弹窗内）／F2（将来独立面板）

F1 是唯一真正适配 dsh 设置弹窗的方案 —— 内容区只有 492px 时，主从/双表都放不下，只有「表 + 行内展开」能既不横向溢出、又保留全局视野。

F2 是同一套结构在 880px 下的样子：主表多两列、展开两栏。若以后渠道页从弹窗升成独立面板，直接换宽度即可，组件不变。

两者都把「异常」放在行内数字（待批 / 失败）与顶部 KPI 上，不牺牲 D 的可数性；展开内容按「入站 → 凭据 → 绑定 → 配对 → 失败」顺序，与用户排查顺序一致。

告诉我 F1 或 F2，我按它重写 client.channel.js。 重写时要一起改守卫与探针（现有断言钉的是 data-vssaros-inbound / data-vssaros-pairings / data-vssaros-dlq，换布局会让它们静默失效）。

取舍异常可数，平台多了仍稳定
