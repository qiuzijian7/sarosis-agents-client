01结论摘要

不满足要求。框架能保证「节点名一致」与「产物数据同源」， 但展示内容与进度的覆盖是残缺的 —— 存在 3 处结构性缺口：
  1. 图标/副标题两套体系：聊天卡只有 4 个硬编码图标，而画布卡有完整注册表（约 230 个节点类型）； 业务节点的副标题直接显示机器类型名（如 comfyStage）。
  2. 进度只覆盖 1 类节点：node_progress 全仓只有一个发射点， 在 Comfy 节点执行器内 → 脚本 / Agent / Saros 逻辑节点在聊天卡上永远没有进度条。
  3. 产物通道三处不对称：脚本节点产物只到画布、Agent 节点产物只到聊天卡、绿幕原片被聊天卡刻意过滤。

02架构真相：聊天卡不在 webview 里渲染

这是理解全部覆盖问题的前提。项目里存在两条并行的 trace 消费链，但只有一条真正渲染聊天卡：

host WorkflowExecutionService │ _onDidExecutionTrace.fire(...) ▼ agentStudioWebviewController:504 ← host→webview 的唯一转发点 │ _sendEvent('workflow.executionTrace', trace) ├─────────────────────────────────────────────┬────────────────────────────────────── ▼ ▼ 【链 A】webview React 侧 【链 B】native browser 侧（真正的聊天卡） index.tsx:70-206 routeWorkflowTrace workflowTraceController.ts:220-273 _handleTrace │ │ 写 _subAgents / _askUsers / _nodeInteractions / _events ▼ ▼ useChatStore（liveWorkflowExecutions） chatPanel.updateMessage(msgId, {...}) │ │ ▼ ▼ ✗ 无任何渲染器消费 agentChatPanel.workflowCards.ts:42-159 （ExecutionTimelinePanel 定义存在 _createNodeCard(sa, interaction) ← 每个节点一行 但全仓无 import → 死代码） :955-1212

P2 — 一致性 / 健壮性

#问题说明
P2-1 picker_select 是死契约 契约表有定义（traceContract.ts:30-31,50-51,64）、controller 有处理分支 （workflowTraceController.ts:251-256, 633-667）、单测有 fixture， 但全仓没有任何发射端。2026-09-11「单链路改造」后已由 node_interaction 的 applyMode==='snapshot' 取代，契约却未清理。

健壮性7 / 10 ✓ 多项防回环设计到位：node_values_changed 单向、 applyNodeControl 的 origin 开关、快照增量去重、取消短路 （_bailOutIfCancelled）、mergeSnapshotMedia 幂等合并。 ✗ 但失败路径过滤不对称、静默丢弃、状态归一化把未知 status 一律折成 'error'（workflowTraceController.ts:499）。
可观测性6 / 10 ✓ 有 traceContract.ts 运行时断言、 snapshotResult/stageRunResult 的 unknown-id warn、 多处「不静默」的注释约定。 ✗ 但 if (!sa) return 这类静默分支仍在， execution_end 无统计使「为什么这次跑了 3 分钟」无从回答。
总体：约 5 / 10 —— 「核心链路可用，但一致性与覆盖是半成品」。
框架的骨架是对的（单一转发点 + 契约层 + 产物同源 + 防回环）， 问题集中在「元数据/覆盖没有统一到一处」： 标题对齐了、产物同源了，但图标、副标题、进度、产物可见性各自为政。

06改进建议（按性价比排序）

序动作成本收益
1 聊天卡改读节点描述符
把 subagent_start 的 trace 载荷从 task: node.type 换成描述符摘要 （host 已有 _nodeDisplayName + STAGE_TITLE_BY_TYPE， 再补一个 icon/brand 字段即可）。		 低 一次性解决 P0-1 + P0-2：图标与副标题都变成与画布一致的人类可读文本。 改动集中在 workflowExecutionService.ts:1169 + workflowCards.ts:987-997。
2 把进度提升为「所有执行节点」的通用能力
在 _executeScriptNode / _executeAgentNode 也接 onProgress → 发 node_progress（脚本的进度源已存在， 只是没接成 trace）。		 中 解决 P0-3。脚本节点是重灾区（长任务、无反馈）。
3 清理死代码 / 死契约
① 删或标记 webview/src/index.tsx 的 trace 状态机分支（保留 workflow.executionUpdate 等画布用事件）； ② 从契约 + controller + 单测中移除 picker_select。		 低 减少「改错地方」的风险；契约与实现重新一致。
4 失败路径过滤对齐
catch 分支的 subagent_end 也加 _nodeOnFlowChain 判断；或至少在 controller if (!sa) 处打一行 debug 日志。		 低 消除静默丢弃（P2-3），排障有迹可循。
5 补齐产物通道
① _executeScriptNode 收集 store.byNode() 写入 nodeState.snapshot； ② Agent 节点同理写画布 cardStateStore（或明确文档化为「画布不反映 Agent 结果」）。		 中 解决 P1-1 / P1-2，消除「同一个节点两处显示不同产物」。
6 建立单点「卡片可见性规则表」
把 FLOW 链 + 类型排除 + port 过滤收敛成一张 声明表（如 cardVisibility.ts），供 host 与渲染层共用。		 中 解决 P2-6，新增节点类型时「是否出卡」有唯一答案。
7 聊天卡显示「已隐藏 N 项产物」提示
对 port:'video' 等被过滤项， 渲染一行说明而非完全静默。		 低 消除 P1-3 的「用户不知情」。
8 execution_end 带统计
补 durationMs / doneCount / errorCount（真实起止由 host 记录）。		 低 解决 P2-2，让「这次跑了多久/几个节点失败」可直接回答。
