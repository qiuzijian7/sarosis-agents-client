工作流数据传递机制用户输入如何流到节点 · 参数如何生效 · 运行机制

工作流里「用户填的值」和「上游产出的数据」走的是两条完全不同的通道： 参数走 属性（properties / data），媒体产物走 快照总线（MediaSnapshotStore）； 而连线只决定拓扑顺序与「谁是谁的上游」，数据本身从不沿连线直传。 理解这三句话，就能解释绝大多数「参数没生效 / 下游拿到空值」的问题。

01总览：五段式数据流

① 用户输入Start 卡片 / 节点控件 / 弹窗 / 聊天工具
五个入口，但最终都归一到「某个节点的某个属性」或「图级 args」两种形态。
② 存储：双层双写LiteGraphCanvas.tsx · useWorkflowEditorStore
node.properties 是画布真源（序列化保存到工作流文件）；store.nodes[].data 是执行链路真源。 两者必须同时写 —— 历史 bug「提示词 two apple 未注入」就是只写了 properties。
③ 调度：谁执行、什么顺序、带什么值executionGraph.ts · workflowRun.ts
拓扑排序 + Start 作用域裁剪 + 分支路由 → 逐节点合成 values（三层优先级）并注入全局 args。
④ 执行：把值注入 ComfyUI 图stageWorkflowExecutor.injectWorkflowValues
按 bindings（node_id.input_name → from）从 values / upstreamValues 取值，cast/prefix/suffix 后写入 api_json 的对应 input。
⑤ 产物：写回快照总线MediaSnapshotStore.put
执行产物按 {sessionId}::{nodeId}:{port}:{index} 归档；下游节点靠 upstreams 列表去总线取用，形成链式传递。

关键代码：卡片控件的双写（历史 bug 的修复点）

// LiteGraphCanvas.tsx — handleNodeControl
const handleNodeControl = (e: Event) => {
	const detail = (e as CustomEvent<{ nodeId: string; name: string; value: unknown }>).detail;
	const node = graph.nodes.find(n => String(n.properties?.['__sarosId'] ?? n.id) === detail.nodeId);
	node.properties[detail.name] = detail.value;          // ① 画布真源（保存用）
	useWorkflowEditorStore.getState().updateNodeData(detail.nodeId, {
		[detail.name]: detail.value,                       // ② 执行真源（运行用）
	});
	graph.change?.();
	graph.setDirtyCanvas?.(true, true);
};
只写一半 = 参数永不生效 原版只写 node.properties → 执行链路读的是 store 的 node.data → 用户输入被丢弃（实测：提示词 "two apple" 未注入，生成默认图像；batch_size=2 永远不生效）。任何新增的控件/编辑入口都必须双写。

03存储双层模型与同步方向

A node.properties（LiteGraph）

画布引擎的真源。工作流保存时由 graph.serialize() 序列化；加载时 configure() 恢复。 卡片的显示值直接从这里读（getNodeCardMeta(spec, node.properties)）。

B store.nodes[].data（zustand）

执行链路真源。调度器 runGraphExecution 从 nodes 参数（= store 快照）读节点数据； collectStartArgs / collectOrchestrationValues 也都读它。

两个同步方向

// 方向 ①：store → graph（节点增删/连线变化时全量重建）
// LiteGraphCanvas.tsx — useEffect([nodes, edges]) → syncStoreToGraph → graph.configure(...)
// 效果：弹窗保存后 → store 变 → 触发重建 → node.properties 更新 → 卡片摘要刷新

// 方向 ②：graph → store（用户拖拽/连线/改属性）
// graph.on_change → syncGraphToStore → store.setNodes/Edges
// 效果：画布上的操作被 store 感知 → 自动保存（2s debounce）

// 方向 ③（点对点）：控件事件直接双写，不等全量同步
// wf-node-control / wf-node-prompt / onValuesCommit → 同时写 properties 与 store
为什么要双层？ 画布引擎需要 properties 做序列化与原生渲染；执行链路需要纯数据（不依赖 LiteGraph 实例）以便在无画布场景（headless / 脚本导出）复用同一套调度代码。双写是这两套世界之间的桥。

04运行时输入合成：三层优先级

每个节点执行前，调度器用下面这一行合成它的 values（workflowRun.ts L362）：

const values = {
	...collectOrchestrationValues(runNodes, step.upstreams),  // ① 上游编排节点的文本
	...(nodeValues?.[step.id] ?? {}),                            // ② 用户编辑过的值（覆盖 ①）

const r = await runNodeOrStage({
	runner, nodeId: step.id, snapshotKey: snapshotKeyOf?.(step.id),

	inbound: runEdges.filter(e => e.target === step.id),      //    端口级明细（sheet/text 等）
	nodes: runNodes, store: snapshotStore,
	/* … */
});

值最终如何注入 ComfyUI

// stageWorkflowExecutor.ts — injectWorkflowValues(apiJson, bindings, values, upstreamValues)
for (const [nodeId, node] of Object.entries(apiJson)) {
	for (const [inputName, spec] of Object.entries(bindings?.[nodeId] ?? {})) {
		const key = spec.from ?? inputName;
		const resolved = resolveBindingValue(key, values, upstreamValues);  // values 优先，其次上游快照
		let raw = resolved.has ? resolved.value : spec.default;               // 都没有 → 用绑定默认值
		if (spec.cast) applyCast(raw, spec.cast);                            // int / float / string / boolean
		if (spec.prefix || spec.suffix) v = interpolate(prefix) + v + interpolate(suffix);
		inputs[inputName] = v;   // ← 真正写进 api_json 的 inputs
	}
}

bindings 是 ComfyTV stage 的「参数声明表」，形如 { "3": { "text": { from: "prompt" }, "seed": { from: "seed", cast: "int", default: 0 } } }。 没被 binding 覆盖的 input 保持 api_json 原值 —— 这是「节点有参数但改了没用」的常见原因之一（绑定表里没声明该参数）。

05上游数据传递：快照总线（不是连线直传）

归档键规则（mediaSnapshotStore.put）

key = `{sessionId}::{nodeId}:{port}:{index}`
//  - index 由存储层按同 (nodeId, port) 前缀单调递增**自动分配**，
//    调用方传的 index 被忽略 → 多轮执行不会互相覆盖（历史全保留）
//  - nodeId 实际是 **stageUid**（画布为每个 stage 节点分配的稳定归档键）
//  - port：'output'（最终产物）| 'sheet'（整图集）| 'image' | 'video' | …

下游如何取数

读取函数用途取数规则
collectUpstreamValues(store, upstreams)按媒体类型收集上游产物，喂给 stage 的 binding遍历 upstreams → byNode() → 每种 kind 取第一个 ref
resolveUpstreamSnapshotText(store, upstreams)取上游文本（供 {{input}}）第一个 meta.sarosJson==='1' 或 kind==='text' 的 ref
collectUpstreamCandidates(store, upstreams)picker / loader 的候选列表收集上游全部快照供用户挑选
collectUpstreamTexts(...)多上游文本聚合（如多 Prompt 合并）按顺序拼接
collectOrchestrationValues(nodes, upstreams)编排节点（Prompt/Start）的文本注入读 node.data，不走快照
最容易踩的坑：upstreams 必须映射成归档键 store.byNode(x) 查的是 stageUid。若把 nodeId 直接传下去，就是「写 uid、读 nodeId」→ 下游永远拿不到上游刚生成的图（静默失败）。 所以调度器统一走 mapSnapshotKeys(step.upstreams, snapshotKeyOf)。 另有 registerAlias(nodeId → uid) 别名表兜底，让两种键都能命中。

06模板占位符：文本参数里的动态引用

所有「文本类」参数（prompt、questionText、绑定 prefix/suffix…）在物化前会过一遍 resolveTemplateVars：

占位符数据来源说明
{{input}}第一上游快照文本兼容语义，取 resolveUpstreamSnapshotText 的结果
{{input.a.b}}上游快照 JSON 的点路径先 JSON.parse 再逐段 probe；对象/数组用 JSON.stringify 物化（避免 [object Object]）
{{args.key}}Start 节点 args（含运行时覆盖）图级参数的主通道；支持点路径 {{args.a.b}}
{{标签}}具名引用：按节点 label 查快照resolveNamed(label) → label 匹配节点（重名取首个）→ 归档键 → 快照文本
{{标签.field}}同上 + 点路径对具名节点的快照做字段级取值
设计要点：未解析不静默 解析不到的占位符 原样保留，同时 findUnresolvedPlaceholders(text) 会返回残留名单，执行器据此告警 —— 避免「带着 {{args.topic}} 字面量去生成图」这种静默错误。

07谁执行：调度计划与路由

拓扑排序 computeExecutionOrder
Kahn 算法对全部节点排序（上游优先）；有环 → 整体中止并提示。
Start 入口作用域 resolveStartScope
scope = Start 正向可达闭包 ∪ 可达节点的上游闭包。第二项不可省：媒体链的数据源（LoadImage / 素材节点）通常挂在 stage 上游、不在 Start 下游，只取第一项会把它裁掉 → stage 报「无上游图像」。
Start 无出边或只连 End → 判定「未编排」，退化为全图执行（存量图零迁移）。
可执行过滤 buildExecutionPlan
分出三类：steps（要执行）、skipped（类型不可执行，如纯编排）、outOfScope（可执行但未接入 Start，标 idle 非 error）。
分支路由 computeInactiveNodes
gate 节点（IfElse / Switch）执行后返回 branch → 记入 branchOf → 每步执行前重算激活表：所有入边都未激活的节点 → skipped（非错误）。AskUser 同理由 answer / option-N 端口路由。
值合成与注入 values / args / upstreams
见第 4 节的三层优先级；同时把 args、upstreams（归档键）、inbound（端口明细）一并交给执行器。
执行与回写 runNodeOrStage → store.put
声明式节点查表分发（getNodeDefinition）→ 未命中走既有分支；产物写快照总线 → 供下游取用；卡片状态 cardState.set(...) 驱动 UI。

数据上游 vs 控制上游（FLOW）

控制流端口（flowIn/flowOut，type=FLOW）的边是纯控制依赖，只参与拓扑排序，不进 step.upstreams（否则 executor 会按 nodeId 无差别取快照，把上游 Agent 的文本当图像用）。 由 makeFlowEdgeClassifier 在构计划时分离，ExecutableStep.flowUpstreams 单独记录。

09一次全图 Run 的完整时序

点「▶ 运行」
handleRun 判断图里是否含编排节点 → 选全图 Run 或脚本路径。
预检
buildExecutionPlan 用与执行器同一个 Start 作用域算计划；steps.length === 0 则提示而非空转；有环则中止。
参数面板
promptStartArgs(nodes) 读所有 Start 的 data.args 键 → 弹窗 → 返回 startArgsOverride（取消 = 中止）。
构建执行计划
拓扑序 + Start 作用域 + 数据/控制上游分离 → plan.steps；outOfScope 标 idle。
逐节点循环
① 分支路由判定（未激活 → skipped）→ ② cardState.set(running) → ③ 合成 values → ④ runNodeOrStage
执行器内部
查 getNodeDefinition → 命中即 definition.run(input)；schema 节点走 runStageWorkflow → injectWorkflowValues 把 values 写进 api_json → 提交 ComfyUI / 调 Provider RPC → 轮询进度。
产物归档
store.put({ nodeId: snapshotKey, port, media }) → 触发媒体库导入（onAsset）→ 通知订阅者（卡片 OUTPUT 刷新）。
下游取数
下一个节点的 collectUpstreamValues(store, mappedUpstreams) 从总线取到刚归档的产物 → 继续链式传递。
收尾
成功 → cardState.set(success)；失败 → result.failed 记录首个失败节点并停止；提示「执行完成（从 Start 起）· N 个节点 · 未接入 Start M」。

10排错对照表：参数/数据「没生效」的 8 个典型原因

现象根因检查点
卡片上改了参数，运行时没用 控件只写了 properties 没写 store（或反之） handleNodeControl 是否双写；执行读的是 nodeValues
弹窗改了参数，卡片显示不变 卡片读 properties，弹窗写 store，未触发同步 onValuesCommit → updateNodeData → syncStoreToGraph
卡片与弹窗显示的是两套不同字段 节点有两个字段源：spec.widgets（卡片控件）vs VSSAROS_FIELDS（弹窗） 两处字段名必须一致；否则出现「卡片显示旧字段、弹窗显示新字段」
改了 prompt 但生成的还是默认图 只写 properties 未写 store（历史 bug） wf-node-prompt 处理器是否双写
{{args.x}} 原样出现在结果里 该路径没有注入 args（画布有、headless 缺） 画布：collectStartArgs；headless：_injectStartArgs
下游 stage 报「无上游图像」 upstreams 未映射成 stageUid，或数据源节点被 Start 作用域裁掉 mapSnapshotKeys；resolveStartScope 的上游闭包补全
参数在节点上能看到，但生成时没传进去 stage 的 bindings 里没声明该参数（未绑定 → 不注入） 该 stage 的 bindings[nodeId][inputName].from
某些节点「没跑」但没报错 三种正常情况：分支未激活（skipped）/ 未接入 Start（outOfScope）/ 类型不可执行（skipped） 看提示文案里的「跳过 N / 未接入 Start M」，区分是设计还是 bug
一句话总结 参数：双写入 properties + store.data → 运行时按「用户值 > 上游编排文本 > 上游快照」合成 values → 经 bindings 注入 api_json。
数据：产物写进快照总线（键 = stageUid:port:index）→ 下游按 upstreams 取用；连线只决定顺序与上游关系，不搬数据。
args：Start 的 data.args 是整图输入契约，画布/脚本/聊天三条路径都归一到 {{args.key}} 模板。
