二、三种触发路径：全量 / 增量 / 条件Full · Incremental · Conditional

平台层覆盖 = 行为不一致根因

四、Cluster 簇优化：整簇判定UObjectClusters · O(1) reachability

❌ 无 Cluster：逐个对象遍历
引用图庞大时遍历成本随对象数线性增长。
✅ 启用 Cluster：强关联对象打包
整簇可达 → O(1) 跳过；整簇不可达 → 直接 DissolveCluster 解散回收。
GR 项目 Cluster 配置
gc.CreateGCClusters=1（引擎默认 1）、gc.MinGCClusterSize=2（引擎默认 2）、gc.ActorClusteringEnabled=True、gc.BlueprintClusteringEnabled=True、gc.AssetClustreringEnabled=True（均为默认开启）。Cluster 根索引 ClusterRootIndex 把强关联对象当单节点，降低可达性遍历规模。

六、GR 自研 GC 改造（高价值）project-specific patches

① 结构体数组时间片化（@qiuzijian）
UE5 原生 GC 对 TArray<FStruct> / FInstancedStruct 的遍历常作为不可中断大块。GR 新增：
  • gc.StructArrayBoundaryTimeCheck：在结构体数组边界检查时间预算，超时即让出当前时间片。
  • gc.TraceStructObjects：改为逐数组追踪而非一次性遍历，把成本摊薄到多帧。
② 增量迭代上限（@yanghuang）
gc.ReachabilityIterationsLimit（GR 自研）：限制增量可达性的迭代轮次，防止引用图极深时单帧迭代失控。
③ 大世界流送增量 GC（@LQTech shannonliu）
GarbageCollection.cpp 中插入 GIsLevelStreamingGCIncrementalPreparing (5844)，并在 PerformReachabilityAnalysisAndConditionallyPurgeGarbage 内主动 ReleaseGCLock() 并提前返回 (6634-6644)，避免大世界流送/加载期间 GC 长时间持锁阻塞主线程。

七、优化建议（按优先级）P0 / P1 / P2

P0
统一各平台增量可达性策略
复核 Windows/WindowsEngine.ini:10 的 =1 与 DefaultEngine.ini 的 =0 冲突。明确 Windows/主机/移动目标策略；对关闭增量的平台评估引入受控增量（配合 IncrementalReachabilityTimeLimit + ReachabilityIterationsLimit）。
P0
确保结构体数组时间片改造全平台开启
确认 gc.StructArrayBoundaryTimeCheck / gc.TraceStructObjects / gc.ReachabilityIterationsLimit 在目标平台均被正确设置，这是压制 Reachability 峰值的主手段。
P1
控制 Rerun 整图重跑成本
监控 Rerun 阶段单帧耗时；若引用图过大，降低 gc.TimeBetweenPurgingPendingKillObjects 触发频率，或拆分大 Actor / 大 DataTable。
P1
GC 帧错峰：避免同步批量 Spawn / 流送
GC 前高频生成会放大 MarkUnreachable + Gather + Purge 成本，建议与 GC 周期错峰。
P2
验证多线程销毁与 Gather 并行度
gc.MultithreadedDestruction=1 默认开启；结合 EGatherOptions::Parallel 确认 Purge/Gather 在多核充分并行，避免主线程退化。
