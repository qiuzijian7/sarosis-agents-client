架构差异总览

agentmemory 激活模型

  • 4 条路径: Claude Code Hooks → HTTP POST → events → functions
  • 级联链: SessionStart→context, Stop→summarize→reflect, End→consolidate
  • 5 个定时器: auto-forget(1h), lesson-decay(24h), insight-decay(24h), consolidation(2h), recent-searches(1h)
  • 9 个事件触发器: session.started/stopped/ended, observation 等
  • 所有 timer 都 unref(): 不阻塞进程退出

vssaros 激活模型

  • 2 条路径: AgentDriver finally 块 + memoryProvider 定时器
  • 级联链: loadContext → session_start → writeMemory → hooks → sweep
  • 1 个定时器: sweatTimer(6h) — 所有定期任务集中在此
  • 代理驱动 (Agent Turn): 每轮对话前后触发主要逻辑
  • 无事件中间件: 直接调用而非 pub/sub

6 项优化建议

高优先级

R1: 添加 per-tool-call 级别的观察 (observe)

差异: agentmemory 在每次 PostToolUse 时都调用 mem::observe 创建 CompressedObservation；vssaros 仅在 turn 边界写入一次 assistant + tool summary。

方案: 在 agentOSService._executeToolCalls 每个 tool result 推送后，fire-and-forget 调用 writeMemory 写入工具结果观察（内存内，不持久化到 KV 以减少开销）。

// agentOSService._executeToolCalls, after result push:
void memProvider.writeMemory(agentId, {
  type: 'working', content: `Tool ${tc.name}: ${summary}`,
  metadata: { toolCallId: tc.id, toolName: tc.name, observe: true }
});
高优先级

R2: 让 LLM 可以通过 memory_remember 编辑 Slots

差异: agentmemory 暴露 memory_slot_set 工具给 LLM，可在对话中编辑槽位。vssaros 的 memory_remember 工具不支持 slot_id 参数。

方案: 在 builtinToolProvider.ts 的 memory_remember handler 中添加 slot_id 参数。当 LLM 传入 slot_id 时，调用 slots.set(agentId, slot_id, content) 而非 writeMemory。

高优先级

R3: Lesson extract 改为 session_end 触发 + 缩短间隔

差异: agentmemory 在每次 session 结束（summarize 后）触发 reflect → 立即提取教训。vssaros 的 lesson extract 仅在 6h sweep 定时器之后调用，新经验延迟最多 6 小时才能被纳入上下文。

方案: (A) 在 _endSession 后立即触发 le.extract()；(B) 在 ConsolidationPipeline.consolidateEpisodic 后触发；(C) 保持 sweep 中的 extract 作为兜底。

中优先级

R4: 简化 Consolidation 双触发为单一路径

差异: agentmemory 在每次 session 结束时通过 SessionEnd Hook → consolidate-pipeline，2h 定时器兜底。vssaros 有两条路径：agentOSService 每 3 轮 + sweep 每 6h。虽然 ConsolidationPipeline 有 1h throttle 防重复，但架构上不够清晰。

方案: 移除 sweep 中的 consolidateEpisodic 调用，改为在 agentOSService.executeAgentTurn() finally 块中（session_end 之后）触发 consolidation。这样与 agentmemory 的 Stop Hook → consolidate 对齐。

中优先级

R5: Slots buildContext 扩展到有 query 路径

差异: 当 loadContext 有查询参数时（约 50% 调用），走 hybrid search 路径，该路径不调用 buildContext()。agentmemory 的 mem::context 总是包含 slots + profile + lessons。

方案: 在 loadContext 的 query 路径中，在 structuredPrompt 字符串后追加 slots.buildContext(agentId)。

// loadContext query path:
const structuredPrompt = this._slots.buildSystemPrompt(agentId)
  + '\n\n' + this._workingMemory.buildContext(agentId)
  + '\n\n' + this._slots.buildContext(agentId)  // R5: add
  + (this._consolidation.get(agentId)?.buildContext(agentId) ?? '');
低优先级

R6: Sweep timer 方案对齐

差异: agentmemory 有 5 个独立定时器（auto-forget 1h, lesson-decay 24h, insight-decay 24h, consolidation 2h, recent-searches 1h），vssaros 只有 1 个 6h sweep timer 集中处理所有定期任务。

方案: 将 sweep 拆分为独立定时器：
(1) retention sweep (6h) — 衰减 + 清理
(2) lesson decay (24h) — 教训衰减
(3) consolidation sweep (2h) — 固化兜底（如果 R4 实施则不需要）

总结

建议优先级改动量影响
R1: per-tool-call observe高~10 行提升 BM25 搜索精度，增加观察数据源
R2: memory_remember + slot_id高~30 行LLM 可自主管理记忆槽位
R3: lesson extract 提前到 session_end高~20 行新经验立即纳入上下文
R4: 简化 consolidation 触发中~30 行消除双触发路径
R5: slots buildContext 到 query 路径中~5 行50% 调用场景受益
R6: 拆分 sweep timer低~40 行更精细的定时任务控制
