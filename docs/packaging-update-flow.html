00总览与判定

一句话：打包侧有三条链路，升级侧有四条通道；只有新增的「插件补丁」链路同时满足「产物只含 dsh 插件」和「客户端只更新插件」。

读图约定：每条泳道自上而下是执行顺序，箭头表示串行；彩色边框区分链路；虚线表示复用或异步触发。所有流程图均以结构化 HTML 绘制，完全离线可用，不依赖 Mermaid CDN。可复制的 Mermaid 源码见附录。
层诉求现状判定
编译层仅 dsh 改动时不重新编译 vscode 侧主流水线无条件全量；EXE 快包复用上次 staging，跳过 npm ci / 全量 tsc / 逐扩展编译部分满足
产物层产物只含 dsh 插件新增补丁包链路只出 tgz + manifest；EXE 快包仍走 ISCC 出完整包满足
升级层只更新插件、不整装 EXE新增 PatchManager 独立通道；原生 update feed 仍是整包 EXE代码完成 待装机实测

01打包流程

入口由「差异范围 + 用途」决定。主流水线无条件串行，是唯一对外发版链路；EXE 快包只服务内部验证；插件补丁包是新增的产物层链路。

统一入口（方案 A）：.ci/scripts/pack.ps1 把上面的判定自动化——git diff 只含 dsh-plugins/** 时走补丁包；出现 src/、extensions/、build/、product.json 等内核改动时走全量构建；显式 -Mode exe 才走 EXE 快包。-DryRun 只打印 route=... 与将执行的命令。分流规则由 pack-diff.ps1 单一维护，pack-dsh-plugins.ps1 复用同一份守门口径，避免两处规则漂移。

02升级流程

四条通道彼此独立：通道一是 VS Code 原生 update feed（唯一"自动升级主链"），通道二/三是首启后台行为，通道四需要用户手动操作。只有通道三满足「不整装 EXE、仅更新插件」。

通道一 · update feed
整包 EXE · 唯一自动升级主链
全量安装
1 检查GET /api/update/{platform}/{quality}/{commit}
2 响应返回 version/productVersion/url/sha256hash 或 204
3 下载AvailableForDownload → 用户确认 → 下载 CodeSetup-*.exe 并校验 sha256
4 应用spawn /verysilent /update=… 静默运行安装器
5 全量替换code.iss Source: "*" 铺整个 app 目录 + inno_updater.exe --gc
约 800 MB 下载与整包安装manifest 无 files / plugin / delta 字段；无 bsdiff 差分
通道二 · 可选组件
局部更新，但不是插件
首启 2s 自动
1 拉清单GET /api/components
2 只认三个 idmedia / office / whisper
3 落盘<userData>/components/<id>/current
4 消费方式只注入 PATH 或 Office 运行时目录，不进 dsh plugin add
二进制资源与插件补丁刻意分开：语义、幂等与校验都不同
通道三 · 插件补丁
P1 / P2 新增 · 满足诉求
仅更新插件
1 触发Host 首次 running → GET /api/dsh-plugins
2 安全校验Ed25519 验签 + bundled pin + minClient + platform
3 下载落盘逐包 tgz 到 <userData>/dsh-plugin-patches/ + sha256
4 安装installPluginSpec('file:<tgz>', name) → dsh plugin add 进 profile
5 原子写覆盖表全部成功才写 dsh-plugin-overrides.json；失败保留旧版
6 下次启动startupPackages 摘除覆盖包防降级重装；effectivePackages 提升界面版本消除 downgradable
7 回滚删 overrides.json + 重启即回随包版本
几十至几百 KB，无 EXE落点必须是 userData：system setup 装在 Program Files 不可写
通道四 · 插件中心
运行时手动安装
需用户点按钮
1 来源商城 tgz / npm spec / GitHub tarball
2 装进 profile经 installPluginSpec 或商城 installBundle
3 局限不经过更新服务器；<appPath>/dsh-plugins/ 随包真源不变，启动时可能被判 downgradable
手动、非自动升级dsh 版本随应用发版，运行期不切换 runtime
为什么通道三要改"版本真源"：_ensurePlugin 在 installed !== bundled 时会按随包目录的旧版本重装，把刚装进 profile 的新版本冲掉。补丁链路把被覆盖的包从启动清单里摘掉（dir: undefined 走"保留已装版本"分支），并让界面清单用提升后的版本，因此不需要改动 3000+ 行的 HostSupervisor。

04门禁链条

阶段门禁拦截对象
补丁生成差异白名单、bump 规则、禁止 file: 依赖与安装脚本、归档必须含 package/package.json内核改动混入补丁包、改内容不 bump、坏归档
服务端Cache-Control: no-store、/downloads/** 路径穿越防护、部署时过滤 .pem陈旧清单、越权文件、私钥外泄
客户端Ed25519 验签、runtime pin、minClient、platform、逐包 sha256、原子写 overrides篡改、跨版本、半装状态
全量打包checkBundledSeed、--check-staging 哨兵 sha256、staging-verified.json、check-pack-contents、--record-exes 体积预算缺件包、残留暂存、超体积
EXE 快包quick-baseline.json 内核哨兵比对、版本 / 模式 / 开关一致性新版本号配旧内核
安全前提：product.json 的 updateUrl 目前是明文 HTTP。插件包内含可执行 JS，生产启用前必须切 HTTPS，或依赖已实现的 Ed25519 验签并把生产公钥注入客户端；未签名清单仅在 VSSAROS_ALLOW_UNSIGNED_PLUGIN_PATCH=1 开发开关下放行。

05当前状态与未闭环项

入口自动分流
脚本层已做 新增 .ci/scripts/pack.ps1 统一入口，按 git diff 自动路由到补丁包 / EXE 快包 / 全量构建，支持 -DryRun 预演；CI 触发层未做 on.push 仍无 paths 过滤，push 不会自动调用该入口（方案 B 需先确认蓝盾 PAC 语法）。
重复编译
未修 compile-build.ps1 与 gulp vscode-win32-x64 各跑一次全量 tsc。
HTTPS / 生产密钥
未配置 需生成生产密钥对、注入公钥与 PATCH_SIGN_KEY、切换 updateUrl。
装机实测
待验收 已通过 tsgo 类型检查、生成端与服务端端到端、验签一致性验证，但启动期应用补丁尚未在真实 EXE 上跑过。
省时幅度
数据作废 全量基线在 compile-src 阶段被终止，留痕 .build/pack-reports/baseline-cancelled.json。
装机验收清单
  • 装旧 EXE → 只改一个插件并 bump → 推补丁 → 重启后 profile 版本为新版本、页面 ?rev 变化；
  • resources/app/dsh-plugins/ 与 dsh-runtime/ 字节不变，进程里无 CodeSetup-*.exe / ISCC；
  • 验签失败 / 坏包 / pin 不符 / minClient 不满足时保留旧版，日志点名原因；
  • system setup（Program Files 只读）与 user setup 均生效；删 overrides.json 后能回滚；
  • npm run check:dsh-plugins 与 check-dsh-release.mjs 仍全绿。
