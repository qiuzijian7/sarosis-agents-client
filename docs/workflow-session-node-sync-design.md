# 工作流会话（Session）与节点修改的同步设计

> 2026-09-11 · 状态：**待决策**（方案 A 可立即落地；方案 B/C 需拍板后再实施）
>
> 关联需求：「会话下拉框允许重命名」（已实现，见 §6）+「用户修改工作流中的节点后，其他会话中的节点如何处理」

---

## 1. 现状：会话到底隔离了什么

工作流会话（2026-09-11 引入）的定位是**隔离不同聊天会话生成的内容**，不是隔离工作流定义。代码事实如下：

| 数据 | 是否按会话隔离 | 存储位置 / 依据 |
|---|---|---|
| 节点参数 values（提示词、尺寸…） | **否** | `workflow.json` 的 `nodes[].data`（单份，无 session 维度） |
| 节点位置 / 连线 / 图结构 | **否** | 同上，`store.ts` 的 `toWorkflowData` / `loadWorkflow` |
| **生成的产物（图片/视频快照）** | **是** | 快照库 key 前缀 `{sid}::`（`mediaSnapshotStore.ts` `_scoped`） |
| 节点缩略图 | **是**（读被隔离的快照库） | `nodeCard` → `useMediaSnapshotRef` → `store.get` |
| 运行状态 / 历史 | **否** | 内存 `CardStateStore`（按 nodeId，画布重建即清空） |

**会话与聊天会话的绑定**：`chatSessionId` 字段精确匹配（`pickSessionForChat`），未命中则新建 `wfs_xxx`。会话 id 与聊天 sessionId **解耦**，只是元数据字段。

**会话索引**：`{workflowsDir}/{workflowId}/sessions.json`，字段见 `IWorkflowSessionMeta`（id / name / chatSessionId / runCount / updatedAt…）。

### 1.1 由此产生的实际行为

> 在「会话 2」里把某节点的提示词从 A 改成 B → 切到「会话 1」→ **看到的是 B**（参数共享），
> 但该节点的**缩略图/产物变成会话 1 自己的**（或为空）。

这个组合容易让人困惑：**参数看起来"跟着人跑"，产物却"各管各的"**。

---

## 2. 问题定义

用户心智模型有两种可能，二者互斥：

| 心智模型 | 期望行为 | 对应方案 |
|---|---|---|
| **M1：会话 = 一次运行的存档** | 工作流定义（节点/参数/连线）全局唯一；会话只记住"这次跑出来的产物" | 方案 A（= 现状） |
| **M2：会话 = 独立副本（像 git 分支）** | 每个会话有自己的参数，改 A 不影响 B | 方案 B / C |

当前实现是 M1，但 UI 只有一句 tooltip 说明，**用户很容易按 M2 理解** → 于是产生「改了节点，其他会话怎么办」的疑问。

---

## 3. 三种方案

### 方案 A：定义共享 + 产物隔离（保持现状，补齐表达）

**语义**：工作流定义唯一；会话仅隔离产物与运行记录。

- 改节点参数 → **所有会话立即生效**（因为只有一份定义）
- 其他会话的产物**不受影响**（快照按会话隔离，不会被覆盖）

**优点**：零实现成本、无同步问题、符合"工作流是一份定义"的常规直觉；改一次全生效，避免维护 N 份副本。

**缺点**：与 M2 预期不符时用户会惊讶。

**必须补的表达**（低成本、收益高）：
1. 会话下拉的 tooltip 明确写清：「会话只隔离**生成的内容**；节点参数与连线是**所有会话共用**的工作流定义」
2. 节点参数面板顶部加一行说明（或首次打开时的一次性提示）
3. 改名后的会话名（已支持）能让用户区分"跑什么"的场景

**适用**：绝大多数场景——同一工作流的多个会话通常是「同一流程跑不同输入/产出」，而不是「同一画布的分支开发」。

---

### 方案 B：参数按会话覆盖（分层：共享定义 + 会话级 overrides）

**语义**：图结构（节点/连线/位置）共享；**节点参数可在会话级覆盖**。

- 存储：`sessions.json` 或独立文件里存 `{ sessionId: { [nodeId]: Partial<values> } }`
- 读取优先级：会话覆盖值 > 工作流默认值
- 改参数时提供选择：**「仅本会话」/「所有会话」**（默认"仅本会话"）
- UI 反馈：被覆盖的节点在卡片/属性面板上打**角标**（如「本会话已覆盖」），可一键"恢复为共享值"

**优点**：兼顾共享基线与会话特化；改动量可控（不动图结构，只加一层 values 合并）。

**缺点**：
- 存储与合并逻辑变复杂（每处读 values 都要走合并函数）
- 用户需理解"覆盖"概念；忘记自己覆盖过会导致"为什么改了没生效/生效了"的新困惑
- 执行时（`WorkflowEditorPanel` 全图执行读值处）需同步走合并逻辑

**适用**：确实存在"同一流程、不同会话要不同参数"的稳定诉求时。

---

### 方案 C：会话 = 完整快照（含定义）

**语义**：每个会话持有完整工作流副本（参数 + 连线 + 位置）。

- 切换会话 = 切换整份画布
- 优点：完全隔离，语义最直白
- 缺点：**代价最高** —— 存储膨胀、定义演进要在 N 个会话重复改、跨会话对比/合并困难、与"工作流文件唯一"的现有存储模型冲突

**不推荐**：本项目的会话是"运行产物隔离"的轻量概念，升格为完整副本会让整个存储与编辑模型重构。

---

### 方案对比

| 维度 | A 定义共享 | B 参数覆盖 | C 完整快照 |
|---|---|---|---|
| 实现成本 | 0（仅文案） | 中 | 高 |
| 存储开销 | 无 | 小 | 大（每会话一份） |
| 用户理解成本 | 低 | 中 | 低 |
| 改一次全生效 | ✅ | 可选（"所有会话"） | ❌ 需逐个改 |
| 支持会话特化参数 | ❌ | ✅ | ✅ |
| 与现有存储模型契合 | ✅ | ✅ | ❌ |

## 6. 会话重命名（已实现，2026-09-11）

与本设计独立、已落地，记录于此便于对照：

- **只改 `name`，不动 `id`**：id 是快照库隔离 key 前缀（`{sid}::`）与产物目录名（`sessions/{sid}/`），改 id 会让已有产物失联。
- **不动 `updatedAt`**：列表顺序派生自 `updatedAt`（`sortSessionsByRecent`），改名不应改变排序。
- **改动清单**：
  - `common/workflowSessions.ts` — 新增纯函数 `renameWorkflowSession(meta, name)`
  - `common/workflowStorage.ts` — 接口新增 `renameWorkflowSession(workflowId, sessionId, name): Promise<boolean>`
  - `browser/workflowStorageService.ts` — 实现（读 sessions.json → 改 name → 写回）
  - `browser/messageProtocol.ts` / `webview/src/bridge/messageClient.ts` — 新增请求类型 `workflow.sessions.rename`（两侧同步，受 `messageProtocolConsistency.test.ts` 守卫）
  - `browser/agentStudioWebviewController.ts` — 新增 case + `_handleWorkflowSessionsRename`（返回更新后的完整列表，省一次 list 往返）
  - `webview/.../WorkflowEditorPanel.tsx` — 会话下拉旁新增 ✏️ 按钮，`window.prompt` 输入新名（与既有 `renameLink` 交互一致）
