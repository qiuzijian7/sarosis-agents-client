1架构与工作原理

本工具集不是 MCP 实现，而是一层直接访问本地 Bridge 服务 的 HTTP 客户端。 工具本身运行在 Agent Studio 进程内，通过 fetch 调用编辑器侧 Bridge 暴露的 /bridge/* 端点。 

┌──────────────────────┐        HTTP (127.0.0.1:8765)        ┌────────────────────────────┐
│  Agent Studio        │                                     │  Unreal Editor 进程        │
│                      │                                     │                            │
│  unreal_health       │──── GET  /bridge/health         ───▶│  BunnySeekAgent 插件       │
│  unreal_exec         │──── POST /bridge/exec           ───▶│  (Python Editor Script     │
│  unreal_wait         │──── POST /bridge/wait_probe     ───▶│   Plugin + EditorScripting │
│  unreal_help         │──── POST /bridge/help           ───▶│   Utilities)               │
│  unreal_dump         │──── POST /bridge/dump           ───▶│                            │
│  unreal_build        │──── POST /bridge/build          ───▶│  内嵌 Python 解释器        │
│  unreal_find_asset   │──── POST /bridge/find_asset     ───▶│  (GameThread 上执行)       │
└──────────────────────┘                                     └────────────────────────────┘
关键设计点：所有工具共用同一个 callBridge 函数。它把「调用方 AbortSignal」与 「工具自身超时计时器」合并为一个 AbortController， 因此无论是上层取消还是工具超时，都能干净地中止请求而不会挂死。

统一行为约定

  • 失败不抛异常：连接失败、HTTP 错误、超时全部转成普通文本结果返回，保证对话不会因此中断。
  • 响应格式化：返回 JSON 时会走 formatPayload 美化；解析失败则原样返回文本。
  • 地址规范化：Base URL 末尾的多余 / 会被剥离，避免拼出 //bridge/health。

2前置条件与配置

必须先在 Unreal Editor 中启用插件，否则所有工具都会返回「无法连接 Bridge」。 需要在编辑器中启用：
  • BunnySeekAgent 插件（提供 /bridge/* 端点）
  • Python Editor Script Plugin（提供内嵌 Python 解释器）
  • EditorScriptingUtilities（提供编辑器脚本 API）

修改 Bridge 地址

默认地址为 http://127.0.0.1:8765。如需修改（例如端口冲突），在 设置 → 工具配置 → Unreal Engine 工具 → Bridge 地址 中填写： 

配置键：sessions.agentStudio.unreal.bridgeUrl
默认值：（空）→ 回退到 http://127.0.0.1:8765

示例：
  http://127.0.0.1:9000
  http://localhost:8765

留空即表示使用内置默认地址，无需手动填写默认值。

3七个工具详解

unreal_health5s 超时无参数

检查 Bridge 是否可达，返回状态、项目名、进程 PID 与运行时长。

用途：当任何其它 unreal_* 工具失败时，应当第一个调用它来定位问题。

// 无需参数
{}
为什么不是空 schema？该工具使用 _no_params 占位属性。 因为部分模型网关（如 IOA）要求 object 至少包含一个属性，否则整份 schema 会被判为不兼容。

unreal_exec120s 超时code 必填

在 Unreal Editor 内嵌 Python 解释器中执行代码（运行于 GameThread）。 状态跨调用持久保留（Jupyter 风格），最后一个裸表达式的 repr 会被回显。 unreal 模块已预先导入。

参数类型说明
code 必填string要执行的 Python 源码，可跨多条语句
reset 可选boolean为 true 时先丢弃此前所有全局变量再执行
timeout_seconds 可选integer硬超时秒数，默认 60，最小 1
 
// 基础：列出当前关卡中的 Actor
{
  "code": "import unreal\nacts = unreal.EditorLevelLibrary.get_all_level_actors()\nlen(acts)"
}

// 复用上一次调用定义的变量（状态持久）
{
  "code": "[a.get_actor_label() for a in acts[:10]]"
}

// 清空状态重新开始
{
  "code": "acts = None",
  "reset": true
}
严禁 sleep / 忙等待。unreal_exec 运行于 GameThread， 阻塞会直接冻结整个编辑器 UI。需要等待异步条件时请改用 unreal_wait。

unreal_wait最长 30 分钟

等待异步 Unreal 条件，且不会阻塞 GameThread。 可提供 condition（Python 表达式，轮询直到为真）和/或 log_pattern（对新增日志行做正则匹配）。二者谁先满足谁生效。

参数类型说明
condition 可选string在 unreal_exec 命名空间中求值的 Python 表达式
log_pattern 可选string与新增项目日志行匹配的正则表达式
timeout 可选number总等待预算（秒），默认 300，最大 1800
poll_interval 可选number探测间隔（秒），默认 2
 
// 等待构建完成（条件轮询）
{
  "condition": "unreal.get_editor_subsystem(unreal.EditorActorSubsystem) is not None",
  "timeout": 600,
  "poll_interval": 3
}

// 等待日志中出现特定行（正则匹配）
{
  "log_pattern": "Build completed successfully",
  "timeout": 1200
}
这是本工具集相对「在 exec 里 sleep」的核心优势。 它把等待动作从 GameThread 挪到轮询探针上，编辑器在等待期间保持可响应。

unreal_help30s 超时

内省编辑器中的 unreal Python 模块：返回指定符号的文档字符串、成员与方法签名。 传入空 symbol 描述顶层模块。

参数类型说明
symbol 可选string相对 unreal 模块的点分路径；空字符串返回顶层摘要
filter 可选string对成员名做大小写不敏感的子串过滤
 
// 查看顶层模块
{ "symbol": "" }

// 查看某个类，并用 filter 收敛结果
{
  "symbol": "unreal.EditorLevelLibrary",
  "filter": "actor"
}
强烈建议对大型类使用 filter。 Unreal 类动辄数百个成员，不加过滤会洪水般淹没你的上下文窗口。 在不确定 API 形状时，应在调用 unreal_exec 之前先调用本工具。

unreal_dump60s 超时code 必填

利用反射元数据递归导出 UE 对象/结构体的每一个可达编辑器属性为 JSON。 相比手写 get_editor_property 循环，它能捕获到被遗漏的嵌套 USTRUCT。 传入的 Python 代码，其最后一条语句必须是要导出的表达式。

参数类型说明
code 必填stringPython 代码，最后一句为待导出表达式
depth 可选integer嵌套值的递归深度
 
// 导出某个 Actor 的全部属性（最后一句是表达式）
{
  "code": "unreal.EditorLevelLibrary.get_all_level_actors()[0]",
  "depth": 4
}
注意最后一句的写法。若写成 a = get_all_level_actors()[0]（赋值语句），则没有可导出的表达式结果。 应直接写表达式本身。

unreal_build15 分钟超时mode 必填

在 Unreal Editor 中触发构建。两种模式二选一。

参数类型说明
mode 必填string (enum)live_coding = 编译并热重载 C++ 改动；ubt = 执行完整 UnrealBuildTool 构建
 
// 快速热重载（日常改动首选）
{ "mode": "live_coding" }

// 完整构建（耗时很长，配 long timeout）
{ "mode": "ubt" }
模式选择：修改了 C++ 源码做增量验证用 live_coding（秒级~分钟级）； 发布前或改动了构建文件用 ubt（可达数十分钟）。 工具侧为 ubt 预留了 900 秒（15 分钟）超时。

unreal_find_asset60s 超时

在 Unreal AssetRegistry 中按名称或路径检索资产。所有参数均可选（无参调用返回全部/默认结果集）。

参数类型说明
search_term 可选string名称或路径的子串
name 可选string资产名过滤
path 可选string包路径过滤，如 /Game/BluePrints
class_names 可选string[]限定返回的资产类型
max_results 可选integer返回命中数量的上限
 
// 按路径 + 类型精确检索
{
  "path": "/Game/BluePrints",
  "class_names": ["Blueprint", "StaticMesh"],
  "max_results": 20
}

// 模糊搜索
{ "search_term": "Character" }

4推荐工作流

标准调用序列

  1. unreal_health — 确认 Bridge 在线、拿到项目名与 PID。
  2. unreal_find_asset — 定位目标资产，拿到确切路径。
  3. unreal_help（配合 filter）— 确认 API 形状，避免凭记忆臆造 API。
  4. unreal_dump — 读取对象当前完整属性状态。
  5. unreal_exec — 执行修改。
  6. unreal_wait — 若改动触发异步任务（构建、导入、编译），用它等待。
  7. unreal_build — 需要编译 C++ 时调用。
黄金法则：先内省，后执行。 第 3 步的 unreal_help 是防止「幻觉 API 名」的关键。 Unreal Python API 面积极大，模型凭记忆写出的类名/方法名错误率很高； 一次 unreal_help 的成本远低于一次失败的 unreal_exec。

典型场景：批量修改资产属性

1. unreal_find_asset  { "path": "/Game/Characters", "class_names": ["StaticMesh"], "max_results": 50 }
     → 拿到资产路径列表

2. unreal_help        { "symbol": "unreal.StaticMesh", "filter": "lod" }
     → 确认 LOD 相关 API 的准确名称与签名

3. unreal_dump        { "code": "unreal.load_asset('/Game/Characters/Hero')", "depth": 3 }
     → 查看当前属性值

4. unreal_exec        { "code": "..." }
     → 批量修改

5. unreal_wait        { "log_pattern": "Saved.*Hero", "timeout": 300 }
     → 等待保存完成

5错误处理与超时

超时分级

工具超时设计意图
unreal_health5 秒健康检查应当快速失败
unreal_help30 秒反射内省，中等耗时
unreal_dump60 秒深递归可能较慢
unreal_find_asset60 秒AssetRegistry 查询
unreal_exec120 秒GameThread 执行，不宜过长
unreal_build900 秒（15 分钟）完整 UBT 构建可达数十分钟
unreal_wait1800 秒（30 分钟）长时异步等待专用通道

三类错误形态

场景返回文本应对
HTTP 非 2xx [Unreal] <tool> failed: bridge returned HTTP <status>. 查看附带的响应体，通常是 Bridge 侧参数校验失败
工具超时 [Unreal] <tool> timed out after Ns. 缩小操作范围（如减小 depth、加 max_results），或改用 unreal_wait
连不上 Bridge [Unreal] <tool> cannot reach the Unreal bridge at <url> 启动 Unreal Editor 并启用 BunnySeekAgent 插件；确认端口配置一致
用户/上层取消 [Unreal] <tool> cancelled. 正常中断，无需处理

连接失败排查清单

  1. Unreal Editor 是否已启动？
  2. BunnySeekAgent 插件是否已启用？
  3. Python Editor Script Plugin 与 EditorScriptingUtilities 是否已启用？
  4. Bridge 实际监听的端口是多少？与设置中的 Bridge 地址是否一致？
  5. 是否有其它服务占用了 8765 端口？

6与 UE 官方 Unreal MCP 对比

Epic 在 UE 5.8 中引入了官方的 Unreal MCP 插件（引擎内标识为 ModelContextProtocol）。 它把 MCP server 内嵌在编辑器进程里，默认监听 http://127.0.0.1:8000/mcp。 下面从多个维度对比它与本工具集的差异。

6.1 核心参数对照表

维度本项目 unreal_* 工具集UE 官方 Unreal MCP
协议 直接 HTTP REST（/bridge/*） 标准 MCP（JSON-RPC：initialize / tools/list / tools/call）
Server 位置 外部 Bridge 进程/插件（BunnySeekAgent），客户端在 Agent Studio 内 MCP server 内嵌于 Unreal Editor 进程
默认地址 http://127.0.0.1:8765 http://127.0.0.1:8000/mcp
工具数量 固定 7 个（通用元工具） 数百个（由 Toolset Registry 动态提供）
工具粒度 粗粒度：unreal_exec 可执行任意 Python 细粒度：单个 Tool 只做一件事（spawn actor、改光照、建材质实例…）
能力边界 无限 —— 受限于 Python API 而非工具定义 受限于已注册的 Toolset（SceneTools / ActorTools / MaterialInstanceTools / ObjectTools…）
功能未覆盖时 直接写 Python 绕过 需自行撰写 Toolset（Python 或 C++）并 RefreshTools
扩展性 改工具集源码 一等公民：继承 unreal.ToolsetDefinition + @tool_call 装饰器即可
类型/schema 质量 弱：unreal_exec 的 code 只是 string，无参数结构 强：类型提示 + Google 风格 docstring 自动反射为 JSON Schema
工具发现 unreal_help / unreal_dump 运行时反射内省 Tool Search 三个元工具：list_toolsets / describe_toolset / call_tool
上下文体积控制 天然小（仅 7 个工具） 依赖 Tool Search 折叠（默认开启），否则 schema 体积巨大
线程模型 exec 在 GameThread；unreal_wait 走轮询探针不占 GameThread 所有 Tool 调用在 GameThread 串行执行，客户端不应并发调用
超时控制 分级超时（5s ~ 30min）＋ 外部 signal 合并 未暴露等价的分级超时机制
状态管理 exec 命名空间跨调用持久（Jupyter 风格，可 reset） 无状态 Tool 调用
客户端耦合 仅 Agent Studio 内置可用 任意 MCP 客户端：Claude Code / Cursor / VS Code / Gemini / Codex / MCP Inspector
成熟度 稳定实现 Experimental：许多功能不完整，API 与数据格式随时可能变更
依赖插件 BunnySeekAgent + Python Editor Script Plugin + EditorScriptingUtilities Unreal MCP + All Toolsets（依赖 Toolset Registry，自动启用）
可服务 cooked build 否（需编辑器） 是：runtime 模块可在打包版本中启动 server
安全模型 任意代码执行（等同授予编辑器内完全 Python 权限） 受限 Tool 集合（但仍无认证层，仅本机绑定）

6.2 本质差异：两种截然不同的哲学

本项目：通用执行器

把 Unreal 编辑器当作一个可编程的 REPL。 7 个工具本质是「连接 + 执行 + 等待 + 内省」四个原语的封装， 真正的业务能力由运行时写出的 Python 代码决定。

  • 优点：能力上限高、不受工具定义迭代速度限制、上下文占用极小
  • 缺点：schema 弱（模型不知道该传什么）、无参数校验、错误只能靠运行时反馈、安全风险高

官方 MCP：结构化能力目录

把编辑器功能逐项声明为带类型的 Tool， 由 Toolset Registry 在启动时收集，MCP 包装后对外广告。 模型面对的是一份「菜单」而非一台「解释器」。

  • 优点：schema 精确、参数有校验、模型不易犯错、跨平台客户端通用、可扩展
  • 缺点：能力受限于已注册 Toolset、工具多时 schema 体积大（需靠 Tool Search 缓解）、目前仍是 Experimental

6.3 一个值得注意的趋同点

两者都选择了「元工具 + 按需发现」来对抗上下文膨胀，只是层级不同。
  • 官方 MCP：默认开启 bEnableToolSearch = true，tools/list 只返回 list_toolsets / describe_toolset / call_tool 三个元工具， agent 走发现路径按需展开，避免数百个 schema 一次性灌入。
  • 本项目：unreal_help 就是「按需查 API」的等价物 —— 用一次内省调用换取准确的 API 形状， 而不是预先把所有 Unreal API 塞进提示词。
结论：「不要预先广告全部能力，让模型按需查询」已是这类集成的共识做法。

6.4 能力覆盖差异（官方明确列举的能力）

Epic 文档点名的官方能力包括：生成 Actor、配置光照、创建材质实例、检查 Slate 控件、运行自动化测试。

官方能力本工具集是否覆盖如何达成
生成 / 操作 Actor间接unreal_exec 调 EditorLevelLibrary
配置光照间接unreal_exec + unreal_dump 读改属性
创建材质实例间接unreal_exec
检查 Slate 控件间接unreal_exec（需相应 Python 暴露）
运行自动化测试间接unreal_exec + unreal_wait 等待结果
资产检索原生支持unreal_find_asset 专用工具
C++ 构建 / 热重载原生支持unreal_build（含 live_coding 模式）
反射式属性导出原生支持unreal_dump（含嵌套 USTRUCT）

可见：官方有的能力本工具集大多能「曲线达成」，但需要模型自己写出正确的 Python； 而资产检索、构建、属性导出这三项在本工具集中有专门的原生工具，官方侧反而要依赖对应 Toolset。

7选型建议

优先用本工具集 unreal_* 的场景：
  • 已在 Agent Studio 中工作，不希望额外配置 MCP 客户端
  • 任务需要超出官方 Toolset 覆盖的能力（自定义 Python 逻辑）
  • 需要长时异步等待（构建、导入）—— unreal_wait 的 30 分钟预算与 GameThread 保护是硬优势
  • 需要反射式排查对象真实属性（unreal_dump 对嵌套 USTRUCT 的捕获很实用）
  • 关注上下文体积，不希望数百个工具 schema 进 prompt
应改用 / 补充官方 MCP 的场景：
  • 需要在 Claude Code / Cursor / VS Code 等多个客户端中复用同一套能力
  • 希望模型调用有强 schema 校验，降低参数写错的概率
  • 不想承担「任意 Python 执行」的安全风险
  • 需要为团队沉淀可复用、有文档的 Tool 资产（Toolset 扩展机制成熟）
  • 需要在 cooked / shipping build 中托管 server
两者并非互斥。官方 MCP 的 server 与本项目 Bridge 监听不同端口（8000 vs 8765）， 完全可以同时启用：日常结构化操作走官方 Toolset， 遇到 Toolset 未覆盖或需要长时等待 / 深度内省的任务再用 unreal_* 兜底。
