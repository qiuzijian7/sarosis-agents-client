# 设计方案：知识库根目录改名（`库`→`数据源`、`笔记`→`知识库列表`）+ 每库可关联飞书

> 结论先行：
> **可以做，而且成本比想象低** —— 目录名已经是**单一真源**（`core/kb.js` 的 `NOTES_DIR` / `LIBRARY_DIR`），
> 但**不能直接 sed 改名**：有 **322 处 / 56 个文件**引用这两个名字，且 **`.feishu-sync.json` 的键是路径前缀**
> （改错会导致飞书**重复建文档**）。建议按「抽象层 → 双名兼容 → 幂等迁移 → 每库绑定」四步走。

---

## 1. 现状（**实测**）

### 1.1 真实库的目录形态（`E:\VsSarosVault`）

```
E:\VsSarosVault\
├── 笔记/        101 文件 · 83 md · 0.34 MB
│   ├── 01_学习/      77 md（AI_Agent / UnrealEngine / 游戏设计 / AI应用 / ComfyUI技术 …）
│   ├── 02_工作/ · 03_生活/ · 导入/ · 技术架构/   （空）
│   └── 散文件：index.md / insights.md / log.md / overview.md
└── 库/          134 文件 · 81 md · 7.08 MB
    ├── raw/          92 文件 · 6.96 MB（PDF/PNG 素材）
    └── 实体/ 方法/ 概念/ 源/ 综合/   （56 md，**是"提炼条目"，不是原始素材**）
```

### 1.2 目录名的真源

```js
export const LIBRARY_DIR = '库';    // L132

```

### 1.3 引用面（改名的影响半径）

| 范围 | 「笔记」 | 「库」 | 合计 |
|---|---|---|---|
| KB 插件（`lib/`） | 55（`NOTES_DIR`） | 32（`LIBRARY_DIR`） | **87 处 / 7 文件** |
| 全仓（含 IDE 侧 / 测试 / 守卫） | 223 | 99 | **322 处 / 56 文件** |
| 守卫脚本硬编码 | 14 个脚本里都有（`check-kb-*.mjs`） | — | 改完全要跟着更新 |

热点文件：`lib/index.js`（72 处）、`kbNavigationParity.test.ts`（14）、`check-kb-feishu-args.mjs`（13）、
`kbCommandService.ts`（13）、`store.js`（10）。

### 1.4 两个**最贵的风险点**（先说，免得踩）

**① `.kbkernel.json` 里是绝对路径**

```json
{ "docs": [ { "path": "e:\\VsSarosVault\\笔记\\_图表验证.md" }, … ], "totalDocs": 169 }
```
⇒ 改名后索引**全部失效**（可重建，成本 169 篇，可接受）—— 但必须**主动删掉重建**，
否则会命中"路径不存在"分支产生一堆脏记录。

**② `.feishu-sync.json` 的键就是路径前缀**

```json
{
  "spaces": { "笔记/01_学习/AI_Agent": { "spaceId": "7688351135437982979" } },   // 6 条
  "files":  { "笔记/01_学习/AI_Agent/01 智能体是什么.md": { "token": "NvBCd7U9to35" } }  // 79 条
}
```
⇒ 键不改 = 同步器认为"这些本地文件从没同步过" ⇒ **会在飞书里重复建 79 篇文档**（最贵的错误）。
必须**逐键重写前缀**，并在迁移前后**核对数量**（spaces 6→6、files 79→79）。

## 2. 目标模型

### 2.1 新目录树

```
<vault>/
├── 知识库列表/                      ← 原「笔记」：**每个子文件夹 = 一个知识库**
│   ├── AI_Agent/                    ← 知识库（可关联一个飞书空间）
│   │   ├── .kb-feishu.json          ← 该库的飞书绑定（新增）
│   │   ├── index.md · log.md …      ← 库内文档（现状不变）
│   │   └── 01_xxx/                  ← 库内子目录 → 映射成飞书空间内的节点层级
│   ├── UnrealEngine/
│   └── 0-Inbox/                     ← 原 `笔记/` 根下的散文件归口（推荐）
└── 数据源/                          ← 原「库」：原始素材与提炼层
    ├── raw/                         ← PDF / PNG / 视频 / 网页快照（现状）
    └── 提炼/                        ← 原 实体/方法/概念/源/综合（**建议**，见 §2.3）
```

### 2.2 语义定义（这次改名的实质）

| 术语 | 含义 | 对应旧结构 |
|---|---|---|
| **知识库** | 一个**可独立拥有/分享/关联飞书**的知识单元 = `知识库列表/` 下的一个文件夹 | 旧 `笔记/<类别>/<子类>`（如 `01_学习/AI_Agent`） |
| **数据源** | 喂给知识库的原始材料（文件/网页/视频/PDF） | 旧 `库/raw/` |
| **提炼条目** | 从数据源加工出的实体/方法/概念… | 旧 `库/实体|方法|概念|源|综合` |

⚠ **现在的层级和旧数据对不上**：旧 `笔记/01_学习/AI_Agent` 是**三层**，新模型要求知识库在**第二层**
（`知识库列表/<库>`）。两种收敛方式（§2.3 决策 1）。

### 2.3 三个必须先定的语义问题

| # | 问题 | 选项 | 建议 |
|---|---|---|---|
| 1 | `01_学习/AI_Agent` 这类三层结构怎么变成"一个库"？ | **A** 把 `01_学习` 当库（`AI_Agent` 变成库内子目录）<br>**B** 把每个 `AI_Agent` 提升为库（拍平） | **A**：改动小、和现有飞书空间映射（按 `AI_Agent` 建的）冲突小；B 会让 6 个飞书空间变成 6 个库，概念更清晰但迁移重 |
| 2 | 旧 `库/实体|方法|概念|源|综合`（56 md，是提炼条目）放哪？ | **A** 留在 `数据源/提炼/`<br>**B** 移进对应知识库<br>**C** 只改名不动 | **A**：先不动内容，避免语义大搬迁；`数据源` 也确实是"原料+提纯"的同一件事 |
| 3 | 旧 `笔记/` 根下的散文件（index/insights/log/overview）怎么处理？ | **A** 收进 `知识库列表/0-Inbox/`<br>**B** 留在 `知识库列表/` 根（视为"未归类"） | **A**：否则"每个子文件夹=一个库"这条规则会被散文件破坏 |

## 3. 兼容层设计（先做这层，改名才安全）

### 3.1 单一解析入口

```js
// 新增 dsh-plugins/vssaros-kb/lib/core/kbLayout.js
export const LAYOUT_FILE = '.kb-layout.json';

/** 解析一个库实际用哪套目录名（新名优先，旧名兜底，两者并存 ⇒ 明确报错） */
export async function layoutOf(vaultRoot) {
  const has = async (n) => existsSync(join(vaultRoot, n));
  const v2 = (await has('知识库列表')) || (await has('数据源'));
  const v1 = (await has('笔记')) || (await has('库'));
  if (v2 && v1) { throw new Error('半迁移状态：新旧目录同时存在，请先跑 `kb-migrate-layout`'); }
  return v2
    ? { mode: 'v2', notesDir: '知识库列表', libraryDir: '数据源' }
    : { mode: 'v1', notesDir: NOTES_DIR,   libraryDir: LIBRARY_DIR };
}
```

### 3.2 改造方式（关键：不要 sed）

- `core/kb.js` 的 `NOTES_DIR` / `LIBRARY_DIR` 保留为**旧名常量**（供迁移与兼容判断用）
- 所有"拼路径"的地方改成 `const L = await layoutOf(vaultRoot)` 后用 `L.notesDir`
- 87 处常量引用里，**大多数是 `join(vault, NOTES_DIR, rel)` 形态** ⇒ 机械替换为 `join(vault, L.notesDir, rel)` 即可
- IDE 侧（`kbCommandService.ts` / `kbBlocksEditorPane.ts` / `kbSideview`）不直接拼目录，多数是**文案与校验**，
  改成"从 `/api/view-data` 拿回来的 `layout` 字段"驱动

### 3.3 迁移脚本（幂等 / 可回滚 / git 友好）

```bash
node dsh-plugins/vssaros-kb/scripts/kb-migrate-layout.mjs --vault E:/VsSarosVault [--apply]
```

步骤：

| # | 动作 | 幂等性 |
|---|---|---|
| 0 | **预检**：新旧名是否并存、库是否被其他进程占用（Obsidian/编辑器）、是否 git 干净 | 只读 |
| 1 | `git mv 笔记 知识库列表` / `git mv 库 数据源`（无 git ⇒ `fs.rename`） | 已迁移则跳过 |
| 2 | 散文件 → `知识库列表/0-Inbox/`；`库/实体|方法|…` → `数据源/提炼/` | 已存在则跳过 |
| 3 | **重写 `.feishu-sync.json` 键前缀**（`笔记/`→`知识库列表/`、`库/`→`数据源/`），先备份 `.bak` | 按键前缀匹配，重复跑无副作用 |
| 4 | **重写 md 内相对链接**：`](../库/raw/x.png)` → `](../数据源/raw/x.png)` | 只处理命中旧前缀的相对路径 |
| 5 | 删 `.kbkernel.json` + `.kb-html-cache/`（都可由重建产生） | 幂等 |
| 6 | 写 `.kb-layout.json` `{version:2, migratedAt}` | 幂等 |
| 7 | **校验**：文件数/md 数不变、飞书 spaces 6→6 & files 79→79、重建索引后 `totalDocs` 一致 | 只读 |

回滚：`--rollback` = 反向 rename + 恢复 `.feishu-sync.json.bak` + 删 `.kb-layout.json`。

### 3.4 兼容窗口

`layoutOf` 支持 v1/v2 双读 ⇒ **迁移不是"一刀切"**：用户可以先升级版本，某个库不迁也能正常用；
真正落盘改名由用户点一次「迁移」或首次打开时提示。市场装来的旧结构包（仍含 `笔记/库`）也能直接跑。

## 4. 每库关联飞书（新模型的核心增量）

### 4.1 绑定文件就近存

```
知识库列表/AI_Agent/.kb-feishu.json
{
  "spaceId": "7688351135437982979",
  "name": "AI_Agent",
  "syncMode": "upload",              // upload | two-way
  "ignore": [".git", ".tmp-media"],
  "lastSyncAt": "2026-11-02T09:00:00Z",
  "files": { "01 智能体是什么.md": { "token": "NvBCd7U9to35", "hash": "…", "rev": "…" } }
}
```

**为什么就近存**：库可以被单独拷贝/发布/分享，绑定关系跟着库走；也天然支持"一个 vault 里多个库各连各的空间"。

### 4.2 与现有全局映射的关系

- 现有 `.feishu-sync.json` 的 `spaces`（`笔记/01_学习/AI_Agent` → spaceId，6 条）**迁移时下沉**：
  - 若该路径在新模型里对应一个库 ⇒ 写成 `知识库列表/<库>/.kb-feishu.json`
  - 找不到对应库 ⇒ 留在全局作为默认值
- 现有 `files`（79 条 token）按同一规则下沉到各库的 `files`

### 4.3 同步语义（沿用已有机制）

- **hash 去重**（相同 ⇒ 零 API 调用）
- **rev 乐观锁**（远端变了就提示，不静默覆盖）
- **限速**：800ms/篇（导入 API 100 次/分钟）
- **方向**：先保持 **upload（本地→飞书）**；`two-way` 作为下一阶段（需 §5 的缓存层）

### 4.4 "新建知识库 = 建文件夹"的交互

```
知识库列表/  [+ 新建]  →  输入名称 → 建 知识库列表/<名称>/
                          ├─ 默认写 index.md + .kb-feishu.json 模板（未关联）
                          └─ 「关联飞书知识库」→ 选空间 / 新建空间 → 写 spaceId
```

## 5. 影响面与风险

| 项 | 影响 | 对策 |
|---|---|---|
| **绝对路径索引** | `.kbkernel.json` 全失效 | 迁移时删除重建（169 篇，秒级） |
| **飞书 token 映射** | 键不改 ⇒ **重复建 79 篇** | 迁移脚本重写 + 前后数量核对（硬性） |
| **md 内相对链接** | `../库/raw/*.png` 全断 | 迁移脚本重写相对路径（只匹配旧前缀） |
| **Obsidian 双链** | `[[文件名]]` 不受影响 ✓ | 无需处理 |
| **Obsidian 配置** | `.obsidian/` 里可能记了目录名 | 一般自动跟随；极端情况提示用户重开库 |
| **Windows 文件锁** | Obsidian/编辑器正在用时 rename 失败 | 预检进程占用，失败给出明确提示 |
| **市场包** | 装来的旧结构包仍是 `笔记/库` | `layoutOf` 双读兜底 ✓ |
| **守卫** | 14 个 `check-kb-*.mjs` 硬编码 `笔记` | 改为读 `layoutOf` / 或断言两套名都支持 |
| **IDE 侧** | `kbCommandService` 等 13 处文案与校验 | 从 `view-data` 的 `layout` 字段驱动 |
