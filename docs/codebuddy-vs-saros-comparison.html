01执行摘要

两侧本质上都是 「代码 Agent 的系统提示词 + 工具协议」，且共享同一套设计基因（反幻觉、并行工具调用、子代理委派、内容安全边界）。但二者的工程化路径截然不同：

🔷 CodeBuddy — 单体式、指令密集

  • 提示词为 单一巨型文本块，约 220 行，用 XML 标签分区（<communication>、<tool_calling> 等）
  • 工具集为 固定枚举 + JSON Schema 内联，全部直接下发
  • 强调「极度简洁」："minimize output tokens as much as possible"
  • 有独立的 automations（定时任务）与 working memory（Markdown 文件）机制
  • 明确的代码引用格式规范 ```12:15:file.tsx

🔶 Saros Claw — 分层式、条件化装配

  • 提示词 拆成常量段落，由 systemPromptComposer.ts 按 stable / context / volatile 三层组装
  • 工具集为 toolset 优先级注册表（Always/High/Medium/Low）+ 可折叠进 tool_search 桥接
  • 按 模型族动态注入格式指令与工具使用强制约束
  • 强调 「Act, don't describe」——工具调用强制显式执行
  • 拥有代码知识图谱工具族（search_graph / query_graph / trace_path）
核心结论：CodeBuddy 是「把提示词写给模型看」——文本密度高、容错靠指令； Saros 是「把提示词当运行时资源装配」——分层缓存、条件注入、按需发现工具。 前者胜在直给、低门槛，后者胜在 token 经济性与可扩展性。

04工具集对比

4.1 工具下发机制（最根本的差异）

🔷 CodeBuddy：全量静态下发

  • 工具定义（name + description + parameters）以 JSON 形式全部内联在提示词尾部
  • 已观察到：list_dir、search_file、replace_in_file、read_file、write_to_file、automation_update、use_skill、Task、WebFetch
  • 无「按需发现」层 —— 模型在任何时刻都看到全部工具

  • 工具清单段落带 缓存键（含 focus / toolset / 模型族签名）

4.3 并行工具调用策略对比

🔷 CodeBuddy：强推并行，几乎无例外

"DEFAULT TO PARALLEL: Unless you have a specific reason why operations MUST be sequential … always execute multiple tools simultaneously. This is not just an optimization - it's the expected behavior."

主张：批量读、批量搜、独立编辑全部同批。没有区分"真并行"与"批处理"，也未说明 token 成本。

🔶 Saros：区分「批处理」与「真并行」

"Direct tool calls in your main loop run inside a SINGLE round-trip when you emit several at once … They execute in order within that round-trip, not concurrently; for true parallelism delegate to sub-agents."

主张：批处理省往返；真并行靠 delegate_task / plan_explore。 并解释了成本动因："Every extra round-trip re-sends the whole conversation to the model"。

这是最有价值的差异点。CodeBuddy 的表述更简洁有力，适合驱动模型行为； Saros 的表述在技术准确性上更进一步——它明确划清了「同批调用」与「并发执行」的界限， 避免模型误以为一次发 5 个调用就是 5 路并发，从而在需要真并行的场景主动走子代理。

05设计哲学差异

哲学维度CodeBuddySaros Claw
提示词的定位 一次写就的静态说明书——所有约束同时在场，靠模型自行取舍 可编程的运行时资源——分段、分层、按模型族条件装配
工具与提示词的关系 工具 Schema 嵌入提示词，二者强耦合 工具清单与 Schema 解耦：提示词只给名字，Schema 走 FC 通道
对模型能力的假设 假设模型会犯格式错 → 反复强调输出格式、行号剥离、并行偏好 假设模型有能力选择正确工具 → 提供 tool_search 发现层与「何时不用」反向清单
上下文预算观 已关注输出 token（"minimize output tokens"），但输入侧未做裁剪 输入侧同步优化：可折叠工具集、缓存键、冻结前缀
可扩展性路径 新增能力 → 修改提示词 + 添加工具定义 新增能力 → 注册 toolset + 常量段落，不影响既有缓存签名
记忆的归属 交给模型自己用文件工具维护（提示词里反复强调"MUST write memory"） 交给运行时系统管理（提示词明确："Memory persistence is handled by the system"）
记忆机制这一条尤其值得注意。CodeBuddy 把跨会话记忆的正确性责任压给模型——提示词出现三次强制写记忆的指令 （"before ending your turn"、"NEVER skip this"）。这是一种脆弱但透明的设计： 记忆对用户可见可编辑，但漏写就会丢上下文。 Saros 反过来把责任交给运行时，模型只需调用 memory_list / session_search 读取， 更可靠，但用户不可直接干预。

06各自优势与风险

CodeBuddy

类型条目说明
优势指令密度高、直给XML 标签分区让模型易于定位规则，无需理解装配逻辑
优势输出极简导向明确反复强调 token 经济，适合成本敏感场景
优势Automations 设计完整scheduleType / rrule / validFrom / validUntil 语义完备，支持一次性任务
风险 输入 token 无裁剪全量工具 Schema 内联，工具数量增长时成本线性上升
风险 缓存未优化整个提示词随会话重发，未见分层缓存设计
风险 记忆依赖模型自觉漏写即丢上下文；且提示词三次重复强调，侧面说明此前存在漏写问题
风险 并行表述技术不严谨"DEFAULT TO PARALLEL" 未区分批处理与真并发，模型可能高估并行收益

Saros Claw

类型条目说明
优势分层装配 + 缓存友好冻结前缀命中 provider cache，易变层隔离
优势工具集成本可控deferrable 折叠机制，源码注释显示为其节省约 3–4k token/请求
优势代码图谱能力独有结构化检索优于纯文本 grep，对大型仓库（UE/Unity）噪声抑制明显
优势反幻觉规则显式且强硬独立 6 条，直接封堵「假装已完成」这一高频失效模式
风险 提示词体量偏大~330 行，含大量环境/工具细节，可能稀释关键指令的注意力权重
风险 工具命名风格不统一源码中同时存在 renderMermaidDiagram（驼峰）与 rendermermaiddiagram（全小写，bundled 定义），易引发匹配歧义
风险 toolset 注册易踩「分类遗漏」坑源码注释记录了多次「未登记 → 落入 utility → focus 模式整条剔除」的历史坑（image_gen、vision_analyze、video_generate、cronjob 均曾中招）
风险 输出简洁度要求弱于 CB未设「minimize output tokens」级别的强约束，长回答风险更高

07可借鉴建议

Saros 可向 CodeBuddy 借鉴

#建议理由与落点
1引入代码引用格式规范 CodeBuddy 规定 ```12:15:path 为唯一可接受的引用格式。Saros 当前无引用格式约定， systemPromptComposer.ts 的 buildCompactToolSection() 中可加入一节。
2补强输出 token 经济性指令 CB 有 "minimize output tokens as much as possible" 的强约束；Saros 的 "Be concise but thorough" 偏软。
3自动化任务支持一次性 + 有效期 CB 的 scheduleType="once" + validFrom/validUntil 语义完备； Saros 的 cronjob 目前仅见 cron 表达式路径。
4为关键规则加显式反例 CB 在 <making_code_changes> 中给了具体量化边界（"不要连续 replace_in_file 超过 3 次"）。 Saros 的规则多为定性描述，可补量化阈值。

CodeBuddy 可向 Saros 借鉴

#建议理由与落点
1工具 Schema 移出提示词 改为仅下发工具名清单 + function-calling Schema 通道，大幅降低输入 token 与增长斜率。
2引入提示词分层缓存 拆出稳定前缀命中 provider prompt cache，把环境/状态类信息放入易变层。
3修正并行表述 区分「同批调用省往返」与「子代理真并发」，避免模型高估批处理收益。
4记忆写入门槛从模型转向运行时 当前提示词三次强制写记忆，属于把系统正确性压给模型；可改为运行时自动持久化， 模型仅负责读写接口调用。
5补充子代理反向清单 Saros 的「When NOT to use」+ 单任务默认策略，能有效抑制过度拆分导致的超时。

08结论

这不是「谁更好」的问题，而是两种工程阶段的取舍：

如果关注…更优选择原因
快速上线、行为可控CodeBuddy 路线静态提示词无需装配基础设施，规则直观可读，调试成本低
token 成本、规模化Saros 路线分层装配 + 工具折叠 + 缓存，成本随能力增长更平缓
大型代码库理解Saros代码知识图谱（search_graph / trace_path）优于纯文本 + LSP 检索
输出简练CodeBuddytoken 经济性指令更硬性、更早、更反复地出现
可扩展能力接入Sarostoolset 注册 + 统一 MCP 桥接，新增工具不需改动提示词主体
一句话总结：CodeBuddy 把提示词当作给模型的说明书，Saros 把提示词当作给运行时装配的资源。 二者共享同一套安全边界与行号规范谱系，但在 token 经济性、条件化程度与工具发现机制上走了完全不同的路线。 理想形态可能是两者的交集：Saros 的装配架构 + CodeBuddy 的输出简洁约束与量化规则边界。
