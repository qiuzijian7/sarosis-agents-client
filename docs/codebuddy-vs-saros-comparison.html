01执行摘要

三者本质上都是 「通用 Agent 的系统提示词 + 工具协议」，且共享同一套设计基因（反幻觉、并行工具调用、子代理委派、内容安全边界）。但三者的产品定位与工程化路径截然不同：

🔷 CodeBuddy — 单体式、指令密集

  • 定位：IDE 内结对编程
  • 提示词为 单一巨型文本块，约 220 行，用 XML 标签分区
  • 工具集为 固定枚举 + JSON Schema 内联，全部直接下发
  • 强调「极度简洁」："minimize output tokens as much as possible"
  • 有 automations 与 working memory（Markdown 文件）机制
  • 明确代码引用格式 ```12:15:file.tsx

🟠 WorkBuddy — 交付导向、结果呈现强制化

  • 定位：通用任务执行 + 文档交付（非纯编码）
  • 提示词约 370 行，XML 分区 + 强制结果呈现协议
  • 三层记忆体系：云端 profile / 用户级 / 工作区级
  • 独有 Visualizer（read_me + show_widget）流式内联可视化
  • 独有 个人文件安全章节（桌面/下载目录 8 条硬规则）
  • 专家（Expert）/ 连接器（Connector）/ 插件生态
  • 托管运行时隔离（managed python / node）

🔶 Saros Claw — 分层式、条件化装配

  • 定位：代码 Agent 工作台（Agent Studio）
  • 提示词 拆成常量段落，按 stable / context / volatile 三层组装
  • 工具集为 toolset 优先级注册表 + 可折叠进 tool_search
  • 按 模型族动态注入格式指令与工具使用强制约束
  • 强调 「Act, don't describe」
  • 独有代码知识图谱工具族
核心结论：CodeBuddy 是「把提示词写给模型看」——文本密度高、容错靠指令； WorkBuddy 是「把提示词当产品契约」——用强制协议保证交付物可见、可下载、可复用； Saros 是「把提示词当运行时资源装配」——分层缓存、条件注入、按需发现工具。 三者分别代表指令密集、流程强制、运行时装配三种范式。
三者的定位差异决定了提示词重心： CodeBuddy 与 Saros 同为编码 Agent，所以提示词大量着墨于代码风格、检索策略、行号剥离； WorkBuddy 是通用交付 Agent，所以提示词的重心在「成果如何呈现给用户」（present_files、Visualizer、outputs 目录）， 对代码风格几乎不作要求。比较时须留意这一不可直接对齐的维度。

04工具集对比

4.1 工具下发机制（最根本的差异）

🔷 CodeBuddy：全量静态下发

  • 工具定义（name + description + parameters）以 JSON 形式全部内联在提示词尾部
  • 已观察到：list_dir、search_file、replace_in_file、read_file、write_to_file、automation_update、use_skill、Task、WebFetch
  • 无「按需发现」层 —— 模型在任何时刻都看到全部工具

🟠 WorkBuddy：全量下发 + ToolSearch 桥接

  • 同样全量内联，且体量最大：片段中工具 Schema 约 96KB
  • 同时提供 ToolSearch + toolName/params 调用形态（见 automation_update 后的 schema 片段）
  • 工具族极广，跨编码 / 文档 / 可视化 / 专家 / 连接器
  • 大量能力不内置而走 Skill：agent-browser、find-skills、Office 系列
  • MCP 在 ~/.workbuddy/mcp.json，需用户手动 "Trust" 才生效

🔶 Saros：注册表 + 分级 + 桥接发现

  • TOOLSET_DEFINITIONS 按 优先级注册（Always / High / Medium / Low）
  • deferrable 标记的工具可折叠进 tool_search
  • MCP 工具完全不内联，走 tool_search → tool_describe → tool_call 三步桥接
  • 工具清单段落带 缓存键（含 focus / toolset / 模型族签名）
工具下发策略的两种极端。 CodeBuddy 与 WorkBuddy 都走「全量内联」路线，其中 WorkBuddy 的 Schema 体量最大（约 96KB）； Saros 走「只给名字 + 按需发现」路线。 值得注意：WorkBuddy 虽已提供 ToolSearch 工具，但同时仍把全部 Schema 内联—— 桥接层存在却未被用作省 token 的手段，这与 Saros 把 tool_search 当作折叠机制的定位不同。

4.3 并行工具调用策略对比

🔷 CodeBuddy：强推并行，几乎无例外

"DEFAULT TO PARALLEL: Unless you have a specific reason why operations MUST be sequential … always execute multiple tools simultaneously. This is not just an optimization - it's the expected behavior."

主张：批量读、批量搜、独立编辑全部同批。没有区分"真并行"与"批处理"，也未说明 token 成本。

🟠 WorkBuddy：条件式并行，措辞务实

"If tool calls are independent, run them in parallel; if one depends on another, run them sequentially."

主张：按依赖关系决定并行与否，表述最简洁克制。 同时提示 "If the user asks for tools to run in parallel, send multiple independent tool calls in a single response"—— 把并行作为可选能力而非默认行为。同样未说明批处理与真并发的技术区别。

🔶 Saros：区分「批处理」与「真并行」

"Direct tool calls in your main loop run inside a SINGLE round-trip when you emit several at once … They execute in order within that round-trip, not concurrently; for true parallelism delegate to sub-agents."

主张：批处理省往返；真并行靠 delegate_task / plan_explore。 并解释了成本动因："Every extra round-trip re-sends the whole conversation to the model"。

三家并行策略形成清晰梯度： CodeBuddy「默认必须并行」（最强推动）→ WorkBuddy「有依赖就串行」（务实中立）→ Saros「批处理省往返、真并行走子代理」（技术最精确）。 只有 Saros 明确划清了「同批调用」与「并发执行」的界限， 避免模型误以为一次发 5 个调用就是 5 路并发。三家中 CodeBuddy 的表述最激进，也最容易让模型高估并行收益。

提示词的定位 一次写就的静态说明书——所有约束同时在场，靠模型自行取舍 产品契约——用强制协议保证交付物对用户可见（present_files） 可编程的运行时资源——分段、分层、按模型族条件装配

对模型能力的假设 假设模型会犯格式错 → 反复强调输出格式、行号剥离、并行偏好 假设模型会遗漏"呈现"步骤 → 四处反复强制 present_files 假设模型有能力选择正确工具 → 提供发现层与「何时不用」反向清单
上下文预算观 关注输出 token（"minimize output tokens"），输入侧未裁剪 关注输出长度（50–70 行硬上限）+ 记忆字符配额（4000/3000），输入侧未裁剪 输入侧同步优化：可折叠工具集、缓存键、冻结前缀
可扩展性路径 新增能力 → 修改提示词 + 添加工具定义 新增能力 → 做成 Skill（还要求模型自动积累/纠正技能） 新增能力 → 注册 toolset + 常量段落，不影响既有缓存签名
记忆的归属 交给模型自己用文件工具维护（3 次强调"MUST write memory"） 三层分工：云端（服务器）/ 用户级（模型写）/ 工作区（模型写，有字符上限） 交给运行时系统管理（"Memory persistence is handled by the system"）
交付责任边界 产物落在工作区即完成 产物必须显式呈现——不调用 present_files 视为未完成任务 产物落在工作区即完成（由用户自行查看）
安全观 内容层（content_policy）+ 局部操作约束 内容层 + 数据资产层（个人文件 8 条）+ 供应链层（技能安装 P0/P1/P2 审计） 内容层 + 身份层 + 可信度层（反幻觉 6 条）
记忆机制这一条值得展开——三家给出三种答案。 CodeBuddy 把跨会话记忆的正确性责任全压给模型（提示词出现三次强制写记忆的指令： "before ending your turn"、"NEVER skip this"）。脆弱但透明：记忆对用户可见可编辑，漏写即丢上下文。 WorkBuddy 做了三层分工 + 字符配额，是三者中设计最精细的： 云端 profile 由服务器维护（模型只读）、用户级 MEMORY.md 限 4000 字符、工作区日志限 3000 字符， 并额外提供 conversation_search 做历史检索——用配额强制"记忆必须精炼"。 Saros 反过来把责任交给运行时，模型只需调用 memory_list / session_search 读取， 更可靠，但用户不可直接干预。
WorkBuddy 的「交付责任边界」是其最根本的产品假设。 它不把「文件已写入磁盘」当作完成——「用户能看到文件」才算完成。 这解释了为什么它用四个章节反复强调 present_files， 甚至规定「必须作为 turn 内最后一个工具调用」。 这是面向非技术用户的设计：用户可能不知道 outputs 目录在哪。 相比之下 CodeBuddy 与 Saros 面向开发者，默认用户有能力自己查看工作区。

07可借鉴建议

Saros 可向 CodeBuddy 借鉴

#建议理由与落点
1引入代码引用格式规范 CodeBuddy 规定 ```12:15:path 为唯一可接受的引用格式。Saros 当前无引用格式约定， systemPromptComposer.ts 的 buildCompactToolSection() 中可加入一节。
2补强输出 token 经济性指令 CB 有 "minimize output tokens as much as possible" 的强约束；Saros 的 "Be concise but thorough" 偏软。
3自动化任务支持一次性 + 有效期 CB 的 scheduleType="once" + validFrom/validUntil 语义完备； Saros 的 cronjob 目前仅见 cron 表达式路径。
4为关键规则加显式反例 CB 在 <making_code_changes> 中给了具体量化边界（"不要连续 replace_in_file 超过 3 次"）。 Saros 的规则多为定性描述，可补量化阈值。

Saros 可向 WorkBuddy 借鉴

#建议理由与落点
1补个人文件安全专章（最高优先级建议） Saros 有 execute_code / terminal 全权访问能力，却无 WorkBuddy 级别的 No-Go Zones、扫描只读、先备份、走回收站、每批≤10 文件的硬约束。这是实质性安全缺口。
2考虑交付呈现机制 WorkBuddy 的 present_files 保证产物可见。Saros 可在报告/图表类产物上引入等价的 "必须显式告知产物路径"要求，降低用户找不到文件的情况。
3记忆字符配额 WorkBuddy 用 4000/3000 字符上限强制记忆精炼，避免记忆无限膨胀。Saros 的 memory_list 目前无明确体积约束。
4技能安装安全审计 WorkBuddy 在安装技能前强制跑 skills-security-check 并做 P0/P1/P2 分级。 Saros 的 skill_manage 支持 create/edit，无等价审计流程。
5运行时隔离纪律 WorkBuddy 禁止 pip install 全局安装、禁止 npm install -g，包必须装进隔离目录。 Saros 可考虑类似约定，避免污染用户环境。
6不采纳：技能强制积累条款 WorkBuddy 的「8+ 次工具调用后 MUST 保存技能」「发现任何问题 MUST 立即修改」纪律过重， 实测易产生无价值技能churn。Saros 当前按需创建更克制，建议保持。

WorkBuddy 可向 Saros / CodeBuddy 借鉴

#建议理由与落点
1工具 Schema 移出提示词 约 96KB 内联是三家最大。既然已有 ToolSearch，应把非高频工具折叠进去， 而非全量内联。
2引入提示词分层缓存 参考 Saros 的冻结前缀设计，把 <binary_context> 等机器相关细节移出稳定层。
3机器细节外部化 <binary_context> 硬编码绝对路径与用户名，应改为配置文件或环境变量注入， 避免换机失效与信息泄露。
4补反幻觉硬规则 参考 Saros 的 6 条独立规则（尤其"未调用工具不得声称已完成"）， 弥补当前仅有"不要占位符"单条的不足。
5并行表述技术澄清 参考 Saros 明确区分批处理与真并发，避免模型高估同批调用的并发收益。
6技能纪律降级为建议 「MUST 保存技能 / MUST 立即修改」等强制条款建议改为按需触发， 减少无价值产物；同时保留其"技能过时即负债"的正确判断。

08结论

这不是「谁更好」的问题，而是三种产品定位下的不同取舍：

如果关注…更优选择原因
快速上线、行为可控CodeBuddy 路线静态提示词无需装配基础设施，规则直观可读，调试成本低
token 成本、规模化Saros 路线分层装配 + 工具折叠 + 缓存，成本随能力增长更平缓
大型代码库理解Saros代码知识图谱（search_graph / trace_path）优于纯文本 + LSP 检索，且三家唯一
输出简练CodeBuddy / WorkBuddyCB 有 token 经济性指令；WB 有 50–70 行硬上限
交付物可见性WorkBuddy唯一强制 present_files，保证用户看得到产物
非技术用户 / 办公场景WorkBuddyOffice 技能路由 + 专家生态 + 可视化，编码非其重心
本地文件安全WorkBuddy唯一有个人文件 8 条硬规则；CB/SR 均缺
记忆设计精细度WorkBuddy三层分工 + 字符配额，兼顾自动学习与人工可编辑
能力扩展的工程性Sarostoolset 注册 + 统一 MCP 桥接，新增工具无需改动提示词主体
反幻觉严格度Saros唯一有独立 6 条硬规则章节
一句话总结： CodeBuddy 把提示词当作给模型的说明书（指令密集，推动力强）； WorkBuddy 把提示词当作产品契约（强制交付闭环、安全纵深、生态路由）； Saros 把提示词当作给运行时装配的资源（分层缓存、按需发现、结构化检索）。
三方互补关系最清晰的地方： 在「安全」这一个维度上，三家的覆盖互不重叠—— CodeBuddy 管内容安全（policy），WorkBuddy 管数据资产安全（个人文件）， Saros 管输出可信度（反幻觉）。 任何一家单独看都有缺口，这也解释了为什么横向对比本身就是有价值的工程输入。
本次对比最值得 Saros 立刻行动的一条： Saros 拥有 execute_code / terminal 的完整文件系统权限， 却没有 WorkBuddy 那套「个人目录 No-Go Zones + 扫描只读 + 先备份 + 走回收站」的硬约束。 这是三者中唯一一处"能力越强、约束越弱"的不匹配，建议优先补齐。
