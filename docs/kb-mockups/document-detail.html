Workbench 与 webview 双轨架构决策记录（ADR-018）

背景

Agent Studio 在 2026 年初引入知识库能力时，面临一个基础选择：新的界面能力应当落在 workbench 原生视图，还是落在 webview 中。两种宿主在渲染、生命周期、与主进程通信方式上差异显著，因此需要一次明确的架构决策记录。1

决策结论：导航与轻量列表放在 workbench 原生视图，富文本编辑与图谱渲染放在 webview，两者通过统一的 KB 服务层共享数据。

方案对比

  • 纯原生：启动快、跟随主题天然，但富文本编辑器需自行实现大量控件，维护成本高。
  • 纯 webview：可复用 React 生态与既有组件，但列表页常驻会有内存与启动开销。
  • 双轨（采纳）：各自承担擅长的部分，代价是需要一层数据同步契约。

数据同步契约

两轨通过 KnowledgeBaseService 暴露的只读查询与命令式写入接口通信，禁止跨轨直接引用对方模块。2

typescript// 两轨共享的唯一数据入口（webview 侧同样经 RPC 调用）
interface KnowledgeBaseService {
  queryNotes(notebookId: string, filter: KbFilter): Promise<KbNote[]>;
  readNote(noteId: string): Promise<KbNoteDoc>;
  saveNote(noteId: string, patch: KbNotePatch): Promise<KbSaveResult>;
}

影响与约束

采用双轨后，样式规范需同时覆盖两套环境：原生视图优先使用 --vscode-* 主题变量，webview 内的 kbblocks 使用固化 token，并在两者之间保持视觉一致（详见 [[CSS 设计 token 规范：kbblocks 变量表]]）。

此外，命令的权限校验必须收敛在服务层，避免两轨各自实现导致的不一致；无权限调用统一返回结构化错误，由前端决定提示形式。相关检索链路见 [[kb_search 混合检索打分公式与调参记录]]。3

后续事项

  • 补充双轨边界在「批量导入」场景下的性能基线。
  • 沉淀 KnowledgeBaseService 的契约测试用例。
  • 评估图谱视图在大规模节点（>2,000）下的降级策略。
