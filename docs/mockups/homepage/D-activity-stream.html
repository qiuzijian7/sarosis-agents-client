设计说明 · D 活动流（与现有框架的对应关系）
项说明
定位把主页做成 Agent 运行监控台：第一屏回答「现在跑到哪 / 哪里卡住」，而不是「总共有多少会话」。
信息架构3 张运行中卡（运行 / 待回答 / 已完成任务）→ 左活动流（可按来源筛选）+ 右本周活动 / 用量趋势 / 待处理 → 底部工作台紧凑条。
复用 widgetkpi 的 tally 清点（待办 / 待回答 / 重试 / 排队 / 子代理）直接撑起「运行中」与「待处理」；usage 撑起趋势；workbench 改成底部条；sessions 折进活动流事件。
新增数据最重的一项：需要 liveServices 的实时进度 + 近 7 天变更事件（mtime 聚合 / 快照）。现有 buildDashboardPayload() 只有会话投影缓存，data-vssaros-dashboard-* 的口径里没有事件流 ⇒ 这是新增取数，不是换皮。
落地代价最大。建议分两段：一期只做「运行中 3 卡 + 最近更新 Top N」（复用 tally 与 summary.sorted，零新数据）；二期再上按天分组的活动时间线。
风险live 状态没覆盖到的会话不能伪装成 0（沿用 catalog.js 的「未知不伪装」口径）；事件流若按文件 mtime 拼，容易与会话真实顺序不一致，必须在卡里标明来源（live / cache / 快照）。

原型里的「全部 / 仅 Agent / 仅系统」页签演示事件筛选；柱状图与趋势线是静态示意，落地时图表类型应按「趋势=折线、按天比较=柱状」选取，并给数据表替代以满足可访问性。
