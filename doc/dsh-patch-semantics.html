§1 分层 patch 模型

空 profile 根
  └─ base bundle patch     ── 单条 insert：~60 行插件行（{id, name, config?, disabled?}）
       └─ mode bundle patch ── 按 id 覆写 / 禁用部分行（web-app 禁 25 行）
            └─ 用户 profile 的 cordis.patch.yml ── 按 id 覆写
                 └─ VsSaros --patch 覆盖层 ── 注入管道/token（不改用户 profile）

原文头注（base patch L1-13）的四句话定义了整个模型：

  • base 作为一条 insert 打在空 profile 根上；之后的 patch 按 id 寻址这些行
  • 每行 last write wins（后打的 patch 赢）
  • 覆写是整行 config 替换，不是 merge
  • 行顺序不承载加载语义——激活是服务可用性驱动的；行的分组只是给人看的

§2 五条核心语义

#语义证据 / 后果
1按 id 寻址，last write wins同 id 的后 patch 行胜出；我们的 agents 插件用此把官方 agent-preset-registry 的默认 preset 切到 vssaros-standard
2config 整份替换（不 merge）base L6-10 明文："A patch replaces the targeted row's whole config rather than merging into it"。含义：只想改一个字段也必须重写整份 config——漏写的字段会回到 undefined 而不是保留 base 值。base 因此把「随模式变化的行」下放给各 mode bundle 完整重述
3行序无加载语义base L12-13："Row order carries no load semantics (activation is service-availability driven)"。激活顺序 = cordis fiber 的服务 inject 等待，仅此而已；dsh.client.inject 的包名边是 informational only，不参与排序（client/AGENTS.md L140）
4寻址不存在的行 = 静默忽略上游官方行改名后，我们的覆写行无声失效（真实事故教训）。⇒ 覆写官方行必须配守卫（断言目标行存在）
5insert 与覆写同构同一个 - insert: 列表，打新行 = 挂载，打已有行 = 覆写；语义统一，无独立的 update/remove 操作（禁用用 disabled: true 表达，见 §5）

§3 !!js 表达式配置

dsh 对 cordis patch 的扩展：YAML 自定义标签 !!js 内嵌 JS 表达式，在 Loader 层求值（不是 YAML 解析期）。

# base/cordis.patch.yml
- id: session-fs
  config:
    root: !!js dshHomePath('sessions')                    # L113：路径解析函数
- id: tool-fs
  disabled: !!js process.platform === 'win32'             # L216/222：平台条件挂载
- id: permissions
  config:
    policy: !!js "(process.env.DSH_PERMISSION_MODE ?? 'default') === 'danger-full-access' ? 'never' : 'ask'"  # L227：环境变量分支

# web-app/cordis.patch.yml
- id: webserver
  inject: [webStartup]
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'         # L139：读另一个插件的服务
    port: !!js ctx.webStartup.port ?? 3080
优点代价
组合层可编程：平台分支、环境变量、跨服务取值都不需要写新插件patch 不再是纯数据——审计成本高，文本 diff 看不出行为差异，表达式错误在 Loader 求值期才炸
表达式可访问 ctx 的服务（配合行级 inject 门控，见 §4）配置与运行时状态耦合，形成隐式时序依赖
对第三方（我们）的含义：!!js 是 dsh Loader 的扩展，不是 cordis 标准。我们的 patch 里可以用（Host 是我们的 Loader 求值），但每条 !!js 都是一处「纯数据审计失效点」，应有注释说明求值时机与依赖的服务。

§4 行级 inject 门控（配置时序编排）

行的 inject: [...] 字段（注意：这是行级字段，与插件代码里的 export const inject 是两个层面）使该行的求值/挂载等待所列服务可用：

# web-app/cordis.patch.yml:135-141
- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject: [webStartup]                        # 等 webStartup 服务就位后才求值 config
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'   # 所以这里读得到 webStartup

# :181-188
- id: connection
  inject: [webRuntime]                        # 等 webRuntime（webserver bind 后才 provide）
  config:
    trustedHosts: !!js ctx.webRuntime.trustedHosts

这构成一条配置级时序链：web-startup（解析命令行）→ webserver（bind）→ web-runtime（provide webRuntime 服务）→ connection（读 trustedHosts）。链中每一环的 !!js 表达式能读到上游服务，靠的就是行级 inject 门控把求值推迟到服务就位之后。

精妙与隐晦并存：这是官方处理「配置依赖运行时事实」的正规机制，比我们在插件里防御性读取干净。但它把时序藏进了数据文件——读 patch 的人必须同时看 inject 字段与 !!js 表达式才能重建依赖图。

§5 disabled 语义与 preset 化

  • disabled: true 是保留行但禁用，与「删除行」不同——web-app patch L354-359 明确注释 "disabling rather than deleting is deliberate"
  • web-app patch L367-470 显式禁用 ~25 个 base 行（tool-bash/tool-fs/tool-todo/tool-web/tool-subagent…）：agent 平面从「base 固定工具集」移到「per-session preset」之后。对第三方读者的含义：base patch 里挂着的行不等于激活的工具集；要看「当前 profile 实际激活什么」必须叠完所有层再看 disabled 终态
  • 我们侧的行级启停（dshPluginActivation.ts 的 setRowDisabledOverride）与官方 pluginManager 同口径，语义一致 ✅

§6 对 VsSaros 插件的约束与建议

#规则 / 建议性质
1我们的 cordis.patch.yml 只 insert 自己的行；覆写官方行是例外（现有唯一先例：agents 覆写 agent-preset-registry），覆写时必须重述整份 config（语义 2）官方纪律 G + 语义 2
2覆写官方行必须配守卫：断言目标 id 的行存在（语义 4 静默忽略）事故教训
3不要依赖行序表达加载顺序；需要顺序就声明服务 inject（语义 3）。「启用追加到 bundles 末尾」只是组合顺序，不是激活顺序承诺语义 3
4patch 里使用 !!js 时注释求值时机与依赖服务；能用静态值就不用表达式§3 代价
5需要「读另一个插件的服务来定 config」时，用行级 inject: [...] 门控（§4），而不是在插件代码里启动后再改官方机制
6禁用官方行用 disabled: true 而非删行——保留可恢复性与 diff 可见性官方先例
7评估「当前激活了什么」时永远看叠完所有层的终态，别看单层 patch§5
