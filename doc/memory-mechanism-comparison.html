Memory Mechanism Deep-Dive Comparison

记忆机制对比 MiMo-Code × Sarosis × agentmemory（原始项目）

主体：MiMo-Code vs Sarosis 六维对比（分类 · 存储 · 沉淀 · 召回 · 遗忘 · 注入时机）｜ 附录：agentmemory 原始项目 vs 本项目移植版 ｜ 2026-07-24

0. 总览：两种范式

MiMo-CodeSarosis（本项目）
范式 Prompt-first：记忆 = 提示词内容，文件即记忆 Engine-first：记忆 = 带生命周期的结构化数据
载体 单个 MEMORY.md 文件 + session JSONL 网关托管 KV（SQLite/JS-KV）+ BM25/Vector/Graph 索引
写入者 Agent 自己（经受约束的 file-edit 工具） 引擎自动 + LLM 半自动（标签/抽取管线）+ 记忆工具
复杂度 极简（~200 行逻辑） 重型引擎（40+ 模块：索引/图谱/保留策略/审计）
一句话总结：MiMo 把记忆当作「提示词的一部分」——单文件全文注入，极简可移植但只增不减；Sarosis 把记忆当作「带生命周期的数据」——检索式注入 + 自动沉淀管线 + TTL/衰减/驱逐，可扩展但依赖网关进程与检索质量。

1. 记忆分类

MiMo-Code — 4 个 prompt 槽位，无类型化记忆库

  • identity：SOUL.md / AGENT.md，会话启动一次性读取
  • skills：技能目录，随会话注入
  • project instructions：AGENTS.md/CLAUDE.md（findUp 发现），每轮就近挂载
  • personal memory：~/.config/opencode/saros/memory/MEMORY.md 全文，每次 LLM 调用注入

对话侧只有 fork lineage（[summary]-[text] 段）+ compaction 摘要，没有 episodic/semantic/procedural 概念。

Sarosis — 多维度类型体系

  • 9 类原生类型：workingpatternfactpreferencearchitecturebugworkflowsemanticprocedural
  • 8 个固定槽位：persona / user_preferences / project_context / tool_guidelines / guidance / pending_items / session_patterns / self_notes
  • 短/长程划分：loadContext 返回 shortTermMemories（working）与 longTermMemories（episodic/semantic…）两组
  • Lessons：带 confidence + reinforcements 的经验条目（独立 KV scope）
  • 辅助结构：sessions 摘要、checkpoints、relations 知识图谱、skill 提炼物、audit log

3. 记忆沉淀（原始观察 → 持久记忆）

MiMo-Code — 无自动管线

  • MEMORY.md 只能由 agent 主动调 memory_edit / memory_append / memory_replace 修改（本质是受约束的 file-edit）
  • compaction 产生 continue.txt 摘要保留对话连续性，但不沉淀进 MEMORY.md
  • 无蒸馏层级

沉淀质量完全取决于模型意愿——容易「什么都不记」。

Sarosis — 五级沉淀管线（自动 + 半自动）

  • 0turn observations：每轮把非 system 消息写为 episodic（hash 去重，≤1500 字符）
  • 1L1 episodic 提取：LLM 抽取 durable facts（{content, type:persona/episodic/instruction}），每 3 turn 阈值
  • 2L2 scene 提取：近期记忆 → scene 摘要（scene_name/summary/keywords → semantic），L1 后延时触发
  • 3L3 skill 提炼：workflow/pattern 记忆 → 带步骤的 skill（维护扫描时）
  • Tmemory_extract 标签：LLM 回复末尾自发输出 <memory_extract>{...}</memory_extract>，driver 流式剥离写入
# Sarosis 引擎侧 ConsolidationPipeline 原始写入 ──▶ dedup（Jaccard ≥ 0.95 判重） ──▶ supersede（同主题新版替代旧版，旧版 isLatest=false） ──▶ merge（相似条目合并） ──▶ promote（working 重复 ≥ 3 次 → 晋升 pattern） session ──▶ autoCrystallize（结晶为长期记忆） 定期 ──▶ runMaintenanceSweep（fullSweep + extractSkill + autoCrystallize）

MiMo-CodeSarosis

关键差异：MiMo 是 always-on 全量注入（记忆 = prompt 前缀的一部分，随记忆增长线性膨胀）；Sarosis 是 检索式注入（按预算取相关子集，可扩展但依赖检索质量）。

5. 记忆遗忘

MiMo-Code — 基本无遗忘机制

  • 无 TTL / decay / eviction / GC
  • MEMORY.md append-only + 手动编辑
  • 索引自动重建；靠 compaction 和人工清理对冲膨胀

长期会积累过时结论污染 prompt——它用「手动编辑」对冲。

Sarosis — 完整生命周期

  • TTL：forgetAfter 字段；recall 时过滤；autoForget 物理删除过期项
  • 矛盾淘汰：autoForget：Jaccard > 阈值 → 旧条目 isLatest=false（软删除）
  • 低价值清理：strength ≤ 2 && 超 180 天 → 删除
  • 保留评分：retentionScore = salience（类型权重 + 访问频次）× 时间衰减（exp，λ=0.01）+ 强化增益 → hot/warm/cold 分层
  • 驱逐：retentionEvict 清 cold 以下（≤50 条/次）
  • Lessons 衰减：decayRate=0.05，重复强化则 confidence 回升
  • 手动遗忘：forgetMemory（memory_forget 工具入口）

6. 记忆注入时机

MiMo-Code

  • 每次 LLM 调用（主循环 / subagent / fork / 标题生成全部）都把 MEMORY.md 全文拼进 system prompt，位置在静态手册之后、project instructions 之前
  • hook 系统把动态指令作为 hook message 注入
  • subagent 默认关闭记忆
  • 无「session 首次注入」概念——是「每调用注入」

Sarosis — 多入口、分层注入

时机内容形式
session 首次 turn loadContext → <agentmemory-context>（短/长程 + systemPrompt + 最近文件） 独立 system 消息，冻结前缀之后；AGENTMEMORY_INJECT_CONTEXT 开关；full/longTermOnly 策略 + maxEntries 配额
每轮（volatile） Persona Memory 槽位 独立 system 消息，不进前缀指纹（防缓存失效）
每轮（context tier） memoryExtractGuide（教 LLM 何时输出 <memory_extract>） 冻结前缀内；Knot 模型补丁追加到 user 消息末尾
压缩时 RETRIEVED_CTX_PREFIX 检索上下文 独立 system 消息，压缩时被剥离由摘要接管
plan 模式 前缀警告「历史结论不阻止新规划」 <agentmemory-context> 内嵌注释
写入侧时机 turn observations 每轮后写；L1 每 3 轮；标签实时剥离 memory_injected / memory_extracted 事件 → UI 卡片
sub-agent 继承 forkContext 冻结前缀（含已注入记忆上下文） 缓存对齐

7. 核心差异总结

#差异影响
1 全量 vs 检索式注入：MiMo 每次调用注入 MEMORY.md 全文；Sarosis 按 budget 检索子集 MiMo 简单但随记忆增长 prompt 线性膨胀；Sarosis 可扩展但依赖检索质量
2 手动 vs 自动沉淀：MiMo 靠 agent 自觉编辑；Sarosis 五级管线自动 + LLM 半自动 MiMo 沉淀质量取决于模型意愿，容易「什么都不记」；Sarosis 容易「什么都记」需要遗忘对冲
3 无生命周期 vs 完整遗忘：MiMo 只增不减；Sarosis TTL/衰减/矛盾淘汰/分层驱逐 MiMo 长期会积累过时结论污染 prompt；Sarosis 自动化但复杂度高
4 文件 vs 引擎：MiMo 单文件纯文本；Sarosis KV+索引+图谱 MiMo 零依赖可移植；Sarosis 需要网关进程但有混合检索与审计
5 注入时机：MiMo 每调用全量；Sarosis session 首次 + volatile 分层 + 压缩期检索 Sarosis 与提示词缓存对齐设计耦合（volatile 层不打断前缀缓存），MiMo 靠锚定 session 日期保缓存

8. 互相可借鉴的点

Sarosis ← 借鉴 MiMo

  • 用户可编辑的核心记忆文件（MEMORY.md 式）：当前 Persona 槽位已接近，但用户不可直接编辑文件；可提供一个「核心记忆」markdown，用户/agent 都可编辑，注入优先级最高
  • 极简兜底：网关不可用时降级为单文件全量注入（当前降级是「无记忆」）

MiMo ← 借鉴 Sarosis

  • TTL / 矛盾淘汰：防止 MEMORY.md 无限膨胀、过时结论污染 prompt
  • budget-aware 检索式注入：替代全量注入，记忆增长后仍可扩展
  • 自动沉淀管线：减少对「模型自觉编辑」的依赖

9.5 差异要点

#差异评价
1 依赖：原版绑死 iii-engine（外部进程编排）；移植版自研 KV + 轻网关，0 外部服务依赖 移植版更适合桌面客户端内嵌；原版更适合多 agent 共享记忆的服务化部署

4 质量保障：原版有 benchmark/eval（95.2% R@5 可度量）；移植版无检索质量基准 移植版可补回 eval 子集以验证移植后检索质量未退化
5 多 agent：原版 teamMemory/mesh 面向多 agent 协作共享；移植版单客户端按 agentId 隔离 若未来多实例协作，teamMemory 模块已在仓内可接线

12. 注入逻辑深度审计：复刻偏差与优化建议（2026-07-25）

12.2 关键发现（按严重度排序）

严重度发现详情与影响
致命 F1 复刻的 mem::context 是注入死代码 客户端注入恒传 recallQuery（user 消息），loadContextFn 永远走 query 分支——精心复刻的 buildContext（pinned slots / profile / lessons / summaries / 重要观察 / 预算填充）从未进入注入文本。实际注入的是 query 分支：混合搜索 top10 + buildWorkingContext（core 条目 + memories 全表按 strength 灌入预算）。后者正是原版刻意避免的 MemGPT 式全量倾倒——与「召回走工具、注入只放策展块」的姿态直接冲突。第 10 节 callout 声称的「注入内容 = mem::context 策展块」实际未生效。
致命 F2 「每 session 注入一次」幂等失效——实际每轮注入 agentOSService.executeAgentTurn 在 finally 之后每轮末执行 _injectedSessions.delete()（agentOSService.ts:1534）。幂等只防 turn 内 fallback 重入，不防跨轮——注入开启时每轮都全量 loadContext + 插入 ~2000+ tokens 的 system 消息。成本是原版（session-start 每会话一次）的 N 倍（N=轮数），且每轮变化的注入块持续破坏 prompt 前缀缓存。第 10.4 节时序图「turn2 不再注入」与代码实际行为不符。
中 F3 P8 Recently Touched Files 是死代码 stash 在每轮末 _stashedFiles.delete(agentId) 清空（agentOSService.ts:1536），而消费发生在下一轮轮初（工具执行前）——消费时 stash 恒为空，「Recently Touched Files」块永远不会出现。原版的对应物是 pre-tool-use mem::enrich（文件类工具调用前实时 enrich：file-context + 文件名搜索 top5 + 相关 bug 记忆 top3，≤4000c，2s 超时），本项目无等价物。
中 F4 注入路径多次全表扫描 + 串行 await 每次注入：buildWorkingContext 全表 list ×2（core + memories）+ query 分支 topShort 再 list core ×1；即使走 buildContext，返回值构造还要全表 list ×2（仅供 UI）。SQLite 后端下每次 list = 全表读 + JSON.parse，同步阻塞网关事件循环——与此前 remember() 假死（2026-07-25 修复）同源。buildContext 观察块 per-session 串行 await（原版 Promise.all 并行）。
中 F5 ServerBM25Proxy.currentAgent 并发竞态 V2.loadContext 把 agentId 写进模块级可变静态字段再调搜索——多 agent / 多窗口并发 turn 时互相覆盖，BM25 召回可能串 agent（跨 agent 记忆泄漏，破坏 agent 作用域隔离）。
低 F6 buildContext 与 mem::context 的细节偏差 ①观察块：原版筛 title 非空 && importance≥5、按 importance 取 top5/会话；移植版无条件 recency top3（Observation 无 title/importance 字段，无法对齐）。②会话筛选：原版按 project + agentId 过滤；移植版无 project 维度。③预算：原版计入 header/footer token；移植版不计。④原版 project 属性 XML 转义；移植版直接插值。⑤原版返回 {context, blocks, tokens} 元数据供调用方展示；移植版无。
低 F7 注入无专用超时 原版 hook 硬超时：session-start 1.5s / enrich 2s + 静默失败（绝不阻塞宿主启动）。本项目注入走 proxy 通用 5s 超时——网关繁忙（大库全表扫描）时 turn 启动被拖慢数秒。

15.4.3 消息布局与缓存分层

msg[0] system base system prompt（工具/规则） ┐ msg[1] system stable 层（agent 指令/人格） │ 冻结前缀 msg[2] system 策展注入块（session 级字节不变） │ 跨轮稳定 → 前缀缓存命中 msg[3] system volatile 层（每轮可变） ┘ 冻结边界 msg[4..] user/assistant 历史（压缩器维护） 可变区 system RETRIEVED_CTX（仅压缩后首轮存在） 设计要点：注入块被刻意放在「最后一个 system 消息之后、历史消息之前」—— 它在 session 内不变，与 base/stable 共同构成跨轮字节一致的前缀； volatile 层独立成消息且每轮变化，被隔离在前缀之外，变化不打断缓存。
