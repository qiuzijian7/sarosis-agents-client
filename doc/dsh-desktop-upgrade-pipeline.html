dsh 桌面窗口 · 升级触发流水线

从「启动 desktop」到「一次升级真正执行」的完整链路梳理（2026-10-30）。 代码是唯一真源：关键一跳都标了 文件:行，行号以本次梳理时代码为准（改动后可能漂移）。

一句话结论：启动后没有任何"自动升级"。启动只做两件事 —— ① 建桌面窗口时顺手推一份缓存快照（不联网）； ② 起动后 8 秒静默查一次更新源，把结论缓存进 _appUpdate。 真正的升级动作，永远由用户在左下角那行「↑ 更新」里点出来（4 条命令）。

IDE 渲染进程（sessions workbench） Electron 主进程（dshViewHost） 通道 / preload 桥 dsh 页面插件（chat-surface） 外部（Host / 更新源 / 商城 / 插件中心）
0 应用启动 / 贡献构造→ +0.8s 开桌面窗口壳→ ~3s 壳可见、IDE 被隐藏→ Host ready 建视图→ 页面首帧 落快照→ +8s 静默查更新源→ 用户点行 强制重查→ 点击动作 执行升级

二、点击之后：四条命令、四条流水线

四条命令都登记在 DSH_PAGE_COMMANDS_WITHOUT_IDE_UI（dshPageBridgeProtocol.ts:1063）—— 否则点一下就会把 IDE 主窗口拉到前台，正好违反"只显示 desktop"。 页面桥是单向（invoke 只回 true）⇒ 所有结果都靠再推一次快照回来。

upgradeApp() · 一键升级应用 最复杂

  1. 防重入：_upgradeBusy 有值直接 return
  2. busy='checking' → 推
  3. _checkAppUpdate() → 闸门：action !== 'upgrade' ⇒ 记日志 + 直接 return，不下载
  4. 没有 _updateService ⇒ 抛「这个构建没有可用的更新服务」
  5. busy='downloading' → 推 → svc.checkForUpdates(true)（VS Code 真下载）
  6. _waitUpdateReady(180s)：轮询 Ready/Downloaded；Idle/Disabled/Uninitialized ⇒ 判失败
  7. busy='installing' → 推 → ReleaseHost（释放常驻 Host 对 koffi.node 的锁；失败只记日志）
  8. svc.quitAndInstall() ⇒ 应用重启、会话中断
行号：dshHarnessService.ts:2042-2089。
为什么必须有第 3 步：更新源可能比本地旧（真机 2.2.26080 < 2.2.26125）， VS Code 只比 commit ⇒ 不做闸门就是"一键降级"。
为什么要有第 7 步：真机曾报「DeleteFile 失败；错误代码 5」，根因就是 detached Host 持锁。

upgradeBundled(name) · 随包插件

  1. 页面侧形状校验：npm 包名正则；宿主再核对"是否在随包清单里"（不许借它装任意包）
  2. getDshPluginCenterHost()（全局函数取，不是 DI）
  3. installBundledPlugin(name) ⇒ 主进程 dshHostSupervisor：先把插件目录暂存到 <profile>/.vssaros/plugins/<name>-<ver>/，再 dsh plugin add（跨盘符安全：仓库 G: / userData C: 时 file: 直装必失败）
  4. ok 的判据是实装版本 === 随包版本（"报了个错然后继续"不许显示成成功）
  5. 装完 Host 可能自动重启（日志「a bundled plugin changed while the Host was running — restarting」）
  6. finally → _pushUpgradeToAll()：成功显示"已装 ✓"，失败带原因
行号：dshHarnessService.ts:2023-2040；协议：dshPageBridgeProtocol.ts:1462。

upgradeAsset(kind, slug) · 商城资产

  1. 短路：kind 是 skill / workflow ⇒ 直接返回"由 dsh 侧负责"（页面本来就不画按钮）
  2. runMarketplaceAction({ op:'upgrade', kind, slug }) —— agent / mcp / workbench 走 IDE 台账
  3. finally → 再推一次状态
行号：dshHarnessService.ts:2091-2115。
为什么 skill/workflow 不能走这里：2026-10-22 起它们由 dsh 侧插件自持， IDE 的 install/upgrade/uninstall 会被下线闸直接抛。

「全部升级」页面聚合

  1. 只遍历 state === 'upgradable' 的随包插件（missing 不算"升级"）
  2. 再遍历 assets 里 via === 'ide' 的那几件
  3. 逐个 call() 发出 —— 宿主侧各自防重入/串行
行号：client.upgrade.js:381-387。
未安装的插件仍列在面板里（各有「安装」按钮），只是不参与计数、也不进"全部升级"。

2026-10-30 同时下线了启动弹窗：原来 `DshUpdateCheckContribution` 会在 Host 变 running 后 每 24h `discoverUpdates()` 并向用户 `notification.prompt`（"dsh X 可用（当前 Y）。"）—— 用户要求"启动时不要弹出" ⇒ 整段下线。现在**没有任何启动期自动检查 + 弹窗**， 检查只发生在：desktop 那行点开后（S7）、IDE 面板点「检查更新」、或手动命令。

补充：为什么状态必须"推"而不是"查"（协议层的硬约束）

页面桥 DSH_PAGE_IPC_INVOKE 是单向的 —— 主进程只回 true / 'pong'， 没有返回值通道。dshPageBridgeProtocol.ts:205-211

所以四件事只能靠推：主题、worktree / 工作区列表、登录态、升级状态。 好处是页面打开前数据就在 dataset 里了（不会先看到"加载中"）； 代价是必须处理"推的时候监听还没注册" —— 于是有了 lastUpgrade + did-finish-load 补发。

校验也在主进程做（validateUpgradeState）：页面会把 dataset 当可信数据解析， 所以"值域越界一律丢弃"（宁可少一行，也不要拿到脏数据）。

补充：为什么 8s 这个数字、以及为什么静默不置 busy

8s 是"避开首启高峰"的折中：Host 冷启动要十几秒、页面首帧也在抢资源， 这一跳既要尽早拿到结论（用户开面板前就该有信号），又不能和首帧抢 IO。 dshHarnessService.ts:2165-2168

不设 _upgradeBusy 的原因：busy 会让页面显示「正在检查更新源…」并禁用按钮 —— 启动时的后台检查不该让用户以为"有人在操作"。失败也只在 info 级别记一行，不影响启动。

定时器 timer.unref?.() 且注册进 _register：不阻止进程退出、随服务一起释放。
