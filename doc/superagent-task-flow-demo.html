③ 两处容易踩的口径坑

	

		
别混两个同名仓库。本次对比对象是 DeepSeek-Bot（带连字符，ds-bot 插件，Apache-2.0，每个 Bot 一条 DSH Session）；另有 DeepSeekBot（无连字符，pnpm monorepo / botharness，MIT）。Orchestrator↔Assignment 会话分离、并发上限 8、Inbox Admission、report_to_orchestrator 属于后者；当前 ds-bot 里这些词 0 命中，群聊是严格串行、没有 8 个并发槽（ds-bot/src/host/groups.js:5,141,338）。vssaros-agents/lib/assignments.js:42-43 注释的「BotHarness 默认 8 同构」借的是 botharness 的口径。

		
「superagent 移植了 DeepSeek-Bot 的 delivery/turns 运行骨架」要收窄。incubator/dsh-superagent/src 里 DSB 移植代码 0 行，模块头全是 VsSaros addition / VsSaros patch；它的运行骨架是 DSH 原生 agent/status / agent/error + 自研 AgentDelivery / Outbox / Assignments。真正同构落地的是 vssaros-agents 侧的 5～6 个机制（且是「同构重写 / v1 收窄版」，不是搬代码）。

	


	
④ 对「能否仅保留 superagent 侧」的影响

	
    
		
  • 结论不变，且不需要动 DeepSeek-Bot：它是外部参考仓库，从未安装进本工作区，不存在「下线」问题。
    • 
		
  • 但「仅保留 superagent 侧」准确说是保留两层：incubator/dsh-superagent（任务治理）+ dsh-plugins/vssaros-agents（Bot 名册 / 会话 / 团队总线 / 记忆）。后者已吸收 DSB 的 delivery/turns 收窄版，删掉它 superagent 起不来。
    • 
		
  • 代价要合并看：只留 superagent = 放弃 TeamFlow 的「研发阶段门禁与验收证据」和 DSB 的「长驻 Bot 身份、群聊轮次、上下文治理、每回合记忆 review」，换来一个纯粹的任务治理层。三者是互补的层，不是三份重复实现。
    • 
		
  • 若要收口：把 DSB 定位为「运行时参考实现」保留在仓库外；把 TeamFlow 降为 v2 第 8.4 节 ③ 的可选执行器（executor: "teamflow" 目前尚未实现，teamflow_start 在 superagent 全 src/ 0 命中），superagent 专管「谁做、怎么授权、怎么沉淀」。

1 tick ≈ 一次 Effects.dispatch() + TeamSteps.kick() 调度轮；工单、步骤、耗时为示意值，调度判据与上限按源码。理论上限是 maxWorkers 张工单 × 每单 budget.parallel 个步骤会话，两层相互独立，所以「同时活跃 / 峰值」可以明显超过 maxWorkers（本沙盘受依赖与写串行约束，会低于理论值）。把 maxWorkers 或 budget.parallel 调成 1，可直接看到排队与串行如何拉长时间线。勾选「对照组」是反向突变：模拟「假如 step 会话也占全局槽」—— 当 maxWorkers=3 时领队会占满槽、步骤永远拿不到槽而无法推进，正说明源码为何不让 step 计入全局槽；该项不是可配置行为。
