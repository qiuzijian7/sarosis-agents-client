# 增量图（incremental graph）设计方案 —— **先设计，后动代码**

> 2026-10-21 · 目标：把"每次索引都要复原整张图"改成"只重算受影响的部分"。
> ⚠ 本文件**不含任何代码改动**；它是一份可评审的设计 + 验收指标 + 回滚路径。
> 前置阅读：`doc/codebase-handover-measurements.md`（交接现状、坑、不变量）。

## 0. 为什么要做（用今天量到的数说话）

单次索引的**写侧**成本分解（13,300 文件的真机工作区，0.6.80/0.6.81）：

| 阶段 | 耗时 | 能否被"增量"消掉 |
|---|---|---|
| 扫描（只列目录） | 0.4–0.6s | 已是下限 |
| **读 + 解析 `index-cache.json`（135.7MB JSON）** | ≈2–3s | ✅ L1 可消（分片，只读变更那片） |
| **从缓存复原整张图**（38 万符号节点 + 80 万边） | ≈2–3s | ✅ L2 可消（分片 + 补丁） |
| 真解析变更文件（tree-sitter） | 1.4s（3 个文件） | 已是按需 |
| gzip 编码图（19.7MB） | 4.7s | ✅ **已由 A 档指纹短路**（空跑跳过） |
| 写 meta + 缓存 | 0.3s | — |

⇒ 现在**空跑一次 ≈ 5.6s**（实测 0.6.81：5,622ms，`encodeSkipped=true`、缓存 0 次重写）；
**有变更一次 ≈ 10s**（实测 10,223ms）。剩余成本几乎全在"**把整张图从缓存里重新拼一遍**"。

**别忘了读侧**（工具每次调用都要读图）：`loadGraph` 实测 **2.9s（热）~ 18s（冷）** ——
解压 19.7MB zstd + 解析 38 万节点/80 万边。**分片图对读侧的收益可能比写侧更大**（按需只读需要的片），
这一点在原方案里被低估了 ⇒ 设计必须**同时考虑读写两侧**。

## 1. 目标与非目标

**目标**
1. 空跑一次 ≤ **1.5s**（P50）；有变更（改 1 个文件）≤ **3s**。
2. 增量产出的图与全量重建的图**逐字节相同**（sha256 相同）⇒ 这是最硬的验收 ✓。
3. 任一判据不满足 ⇒ **自动回落全量**（宁可慢，不可错）。
4. 读侧能按需只读分片（工具查询不必加载全部 38 万节点）。

**非目标（明确不做）**
- 不改"图的语义"（节点/边类型、ID 规则）⇒ 产物格式对 IDE 仍然兼容。
- 不追求"毫秒级"（要 100ms 级得走常驻内存，代价见 §5 L3）。
- 不动 `GRAPH_RECIPE_VERSION` 语义（配方变了 ⇒ 一切增量作废 ⇒ 全量）。

## 2. 现状的数据流（增量方案要替换的部分）

```
collectSourceFiles(扫目录)                     0.5s
      ↓
parseCache(读 index-cache.json 135.7MB + JSON.parse)   2~3s   ← 全部都读
      ↓
buildImportGraph(用缓存里的 hashes/symbols/calls/usages 复原整张图)  2~3s
      ↓
变更文件真解析（tree-sitter）                    1.4s
      ↓
encodeGraph(gzip 19.7MB) → 写盘                   4.7s   ← A 档已能在"没变"时跳过
      ↓
写 index-cache.json（135.7MB）                  0.3s   ← 0.6.78 已能在"没变"时跳过
```

**关键观察**：缓存里已经有**每个文件的 `size` + `mtimeNs` + `sha256`**（`indexer.js` 的 `hashes`）
⇒ "哪些文件变了"这一判定**不需要读文件内容**（读 stat 即可）⇒ 这是整条增量化路线的地基 ✓。

## 3. 三层方案（按风险/收益排序，建议只做 L1）

### L1：缓存分片（**低风险**：不动图格式 ⇒ 失败只会"多算一次"，不会让图变旧）

- 把 `index-cache.json`（单文件 135.7MB）改成 **N 个分片**（按文件的哈希桶分，或按目录前缀分），
  每片 ~5–10MB；另存一份**清单**（shard index：片名 → 文件数、字节数、生成时间、总体版本）。
- 一次运行：读清单 ⇒ 用 `stat` 比对 mtime/size ⇒ 得到**变更文件集合** ⇒ 只读**覆盖这些文件的片** ⇒ 只解析那几片。
- 写回：只写**变了的片**。
- **判据（缺一即回落全量）**：
  ① `GRAPH_RECIPE_VERSION` 相同；② 清单版本/根/文件集合与本次扫描一致；③ 每片校验（字节数 + 摘要）通过。
- **失败模式**：片损坏/缺失 ⇒ 该片回退"重新解析它覆盖的文件"（而不是全量）⇒ 仍是正确的 ✓。
- **回滚**：保留"单体缓存"读路径；分片目录不存在或校验不过 ⇒ 读单体/全量重建 ⇒ **一个开关即可退回** ✓。
- **收益**：空跑的"读+解析缓存"2~3s → ~0.2s；写回从 135MB → 只有变了的片。

### L2：图分片 + 补丁（**中风险**：动图结构 ⇒ 判据失误会"算错边"）

- 图按**模块/目录**分片持久化（每片自己 gzip），另存**片间边**（跨片的 IMPORTS/CALLS）。
- 一次运行：只重算**受变更文件影响**的片 + 重新解析**跨片边**。
- **难点（必须先解决，否则别做）**：
  ① **依赖影响面**：改一个文件可能改变别的文件里"具名导入解析到哪个定义"的边
     ⇒ 需要一张**反向引用索引**（符号 → 引用它的文件/片）⇒ L2 的前置工作。
  ② **跨片边的一致性**：拼接顺序必须与全量构建完全一致 ⇒ 否则"逐字节相同"验收会红。
  ③ **ID 稳定性**：全量构建里节点 id 由"文件顺序 + 符号序号"决定 ⇒ 分片化后 id 分配规则要保持一致
     （否则同一份代码两次构建出不同 id ⇒ 图不可比对、增量不可验收）。
- **收益**：写侧"复原整图"2~3s → ~0.5s；**读侧**按需只读片 ⇒ `loadGraph` 2.9~18s → 亚秒级（**最大的收益在这**）。

### L3：常驻内存索引器（**高风险/高代价**）

- watcher 进程内长期持有已解析的图与缓存切片，改动即更新 ⇒ 不再每次复原。
- 代价：内存（135MB JSON → 结构化后 1GB+ 量级）、落盘一致性（进程崩溃 ⇒ 与磁盘脱节）、
  多进程（IDE 也在读同一份）的一致性协议。
- 结论：**先不做**；等 L1/L2 的数据说话（如果那时 1.5s 目标已达成，就没有必要）。

## 4. 判据总表（"什么时候可以只算局部"）

| 条件 | 不满足时 |
|---|---|
| `GRAPH_RECIPE_VERSION` 相同 | ⇒ 全量（配方变了 ⇒ 旧解析结果不可信） |
| 缓存/分片清单的 **root** 与本次一致（win32 忽略大小写 ✓ 已有） | ⇒ 全量 |
| 文件集合（增/删/改名）已知 | 有删除 ⇒ 相关片重算 |
| 变更文件的 `size`+`mtimeNs` 与缓存一致 ⇒ 该文件**不用读内容** | 不一致 ⇒ 该文件重解析 |
| 依赖影响面（谁引用了被改的符号）已算出 | ⇒ 算不出 ⇒ 相关片全重算 |
| 产物（片）的摘要校验通过 | ⇒ 重建该片 |

**一条纪律**：**任何"算不出"都往"全量"回落**，绝不猜 —— 增量图算错边比图旧更隐蔽（用户看不出来 ✗✗）。

## 5. 验收指标（可量化、可自动判定）

1. **等价性（最强）**：同一工作区，"增量产物" vs "全量重建产物" 的 `graph.db.zst` **sha256 相同**。
   仓库里已有先例：`indexer.selfCheck` 的 `delta.equal`（增量 ≡ 全量，逐字节）✓ —— 直接复用它的判据形状。
2. **性能**：空跑 P50 ≤ 1.5s；有变更（1 个文件）P50 ≤ 3s；`loadGraph` P50 ≤ 1s（读侧按需）。
3. **不变量守卫**：交接那 18 条不变量（`check-codebase-handover.mjs`）**继续全绿** ⇒ 增量不得绕过安全闸/档位/预算。
4. **失败模式可测**：人为删掉一个分片 / 改坏一个分片 / 杀进程 ⇒ 重启后**自愈**且图与全量一致。
5. **灰度**：新产物先写**影子目录**（`indexTarget=shadow`），比对通过再切工作区 ⇒ 出问题能一键回退。

## 6. 回滚路径（每一步都能退）

| 开关 | 作用 | 退路 |
|---|---|---|
| `config.incrementalGraph`（默认 **false**） | 总量开关 | 改回 false ⇒ 立刻回到今天的实现 ✓ |
| 产物目录分离 | 分片放 `.codebase-memory/shards/`，与 `graph.db.zst` 并存 | 读侧先读单体、失败读分片 ⇒ 删掉分片目录即可回退 ✓ |
| 缓存格式分离 | 分片缓存放 `.codebase-memory/cache-shards/` | 同上 ✓ |
| 写侧顺序 | 先写分片 → 校验 → 才更新单体/元信息 | 任一步失败 ⇒ 元信息不动 ⇒ 下轮重来 ✓ |

## 7. 建议的推进顺序（每步都可单独交付、单独验收）

| 阶段 | 内容 | 风险 | 预期收益 |
|---|---|---|---|
| **0** | 本设计落文档 + 在 meta 里加"上次空跑/有变更耗时"字段（基线更细） | 零 | 0（但让后续每一步都有尺） |
| **1** | **L1 缓存分片**（图格式不动） | 低 | 空跑 5.6s → ~3s |
| **2** | **反向引用索引**（为 L2 铺路；本身也能加速"谁调用了它"类查询） | 低~中 | 查询侧提速 + 解锁 L2 |
| **3** | **L2 图分片 + 补丁**（先影子目录灰度） | 中 | 空跑 → ~1.5s；读侧 18s → 亚秒 |
| **4** | 评估 L3（常驻） | 高 | 视 L1/L2 结果 |

## 8. 一句话总结

**地基已经有了**（缓存里就有 `mtime+size+sha` ⇒ "谁变了"不用读内容），
**读侧才是更大的鱼**（`loadGraph` 18s → 分片按需读），
**风险可控的关键**是：先做**不动图格式**的 L1，并用"逐字节等价 + 全量回落"两条铁律兜底 ⇒ 判据失误只会"多算一次"，不会让图变旧 ✗✗。
