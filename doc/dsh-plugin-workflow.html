dsh 插件：开发 · 打包 · 升级 全流程

把「改一个插件」到「用户机器上真的跑着新代码」这条链拆成三段，每段给出真源、闸门与已踩过的坑。基于 2026-10-28 的仓库实测。

仓库 sarosis-agents-client 随包插件 33 + 官方 bundle 2 dsh 0.2.1-rc.2 流水线 Build #241 现场

0. 一页概览

1开发

在 dsh-plugins/<name>/ 写主机侧 lib/index.js 与客户端 lib/client.js；清单、patch、files 三处必须一致。改完用 dsh-plugin-deploy 同步进 profile 再重启宿主。

2打包

CI 16 步：编译 → 权限插件 → 扩展 → prepack-dsh-runtime（运行时 + profile 种子）→ gulp 拷贝 → 四道闸门 → Inno 出 EXE → 归档 / 上传 / Release。

3升级

三条独立链：运行时（兼容清单 + 闸门 + 快照回退）、插件（版本 + 入口指纹，缺则 dsh plugin add）、应用本体（EXE）。

一句话记住判据：宿主决定「要不要（重新）装某个插件」的口径是 版本号 + 入口文件内容指纹（_planPluginInstall / _installedEntryMatches）。所以「改了 lib/** 却没 bump 版本、也没动 lib/index.js」会导致新包装上、旧代码在跑——这是本项目最高频的「改了没生效」根因。

1. 三层资产与真源

层真源（仓库内）装机后的位置 / 谁读
dsh 运行时 dsh-plugins/dsh-compat.json 的 bundled：构建期由 build/prepack-dsh-runtime.mjs 装到 dsh-runtime/<bundled>/（gitignore，不入库） <appPath>/dsh-runtime/；DshRuntimeManager 按 setting → managed → bundled → global 解析
随包插件 dsh-plugins/<name>/（包名须为 @vssaros/* 或 vendored @tt-a1i/*） <appPath>/dsh-plugins/；宿主自动发现并暂存安装进 profile
profile 构建期种子 dsh-runtime/<ver>/profile-seed/profiles/vssaros/ 整目录复制到 DSH_HOME/profiles/vssaros，首启零下载；profile 名真源是 DSH_DEFAULT_PROFILE = 'vssaros'
IDE 侧桥 src/vs/sessions/contrib/dshHarness/（electron-main 通道 + supervisor） 控制桥、会话绑定、工作区上下文、升级闸门、插件中心
「三处声明必须一致」是插件的核心契约：① dsh-plugins/<x>/package.json 的 vssaros 清单；② IDE 侧聚合表 common/dshModuleContainers.ts；③ 插件自己注册的页面路由。任一漂移的表现都是「图标在但页面 404」或「容器 ID 撞车」，编译期完全看不出来。

2. 开发流程

2.1 目录与清单

dsh-plugins/<name>/
├─ package.json          # 清单：name/version/files/dsh/vssaros
├─ cordis.patch.yml      # patch 型插件：往宿主 profile 插一行
├─ lib/
│  ├─ index.js           # 主机平面（Node 侧）：服务、工具、路由
│  ├─ client.js          # 客户端平面（浏览器侧 ESM）：UI 槽位
│  ├─ client.<chunk>.js  # 按需加载的换皮/页面 chunk
│  └─ foundationRef.js   # 消费 foundation 共享服务的引用
└─ skills/ · test/ · scripts/

最小清单（以 vssaros-kanban 为例，节选）：

{
  "name": "@vssaros/dsh-kanban",
  "version": "0.8.15",
  "type": "module",
  "main": "lib/index.js",
  "exports": { ".": "./lib/index.js", "./client": "./lib/client.js" },
  "files": ["lib/index.js", "lib/client.js", "lib/client.kanban.js", "cordis.patch.yml", "..."],
  "peerDependencies": { "@deepseek-ai/dsh": ">=0.1.7-0 <0.3.0-0" },
  "dsh": {
    "bundle": { "patch": ["./cordis.patch.yml"] },
    "client": { "platform": "web", "inject": ["@deepseek-ai/dsh-client-ui-slots"] }
  },
  "vssaros": {
    "manifestVersion": 1,
    "module": "kanban",
    "activityBar": { "containerId": "agentStudio.tasks", "title": "Tasks", "icon": "codicon:tasklist", "order": 70 },
    "view": { "kind": "page", "route": "/x/kanban/" },
    "ideCapabilities": ["taskboard", "browser"],
    "workbench": { "repository": "vssaros:kanban", "title": "Tasks", "customFrame": true }
  }
}

必守的四条

  • 包名前缀：@vssaros/*（vendored 用 @tt-a1i/*），否则种子发现会跳过且点名。
  • 依赖面：运行期依赖只能挂 peerDependencies 里的 @deepseek-ai/dsh；随 dsh 分发的包不许写成依赖。
  • files 要覆盖全部产物（含 lib/*.js chunk、cordis.patch.yml、skills/**）。漏了就是「本地能跑、装出来缺文件」。
  • patch 只插一行且 name 等于包名；patch 声明与文件必须同时存在。

两类插件

  • 模块插件：有 vssaros.module，进插件中心「随包」段、进模块容器、进种子自发现。
  • 伴生 / patch 型：没有 vssaros.module（如 foundation、bridge、chat-surface、workbenches、archify）。它们只能靠宿主清单显式安装——所以 dshHostSupervisor 里那份顺序表是「必须列出」的第二真源。

2.2 双平面挂载与 patch

平面入口跑在哪 / 能做什么
主机平面lib/index.jsdsh Host（Node）进程：注册服务、工具、路由、读写文件。读不到 DOM。
客户端平面lib/client.js + chunk浏览器（dsh web）侧 ESM：往 slots 里注册 UI。不能 require Node 模块（iii-sdk 就是因此被踢出客户端）。
 
# cordis.patch.yml —— 往宿主 profile 里插一行（patch 型插件唯一的挂载方式）
- insert:
    - id: vssaros-kanban
      name: '@vssaros/dsh-kanban'
      config: {}
两个必然踩的坑：

① ctx.provide 必须幂等：插件可能被双平面各挂一次，不幂等会令 preset invalid，会话全线起不来。可选服务一律用 ctx.inject([...])，直接 ctx.get 未声明服务一定抛。

② 工具 schema 是受限子集：写错字段插件会静默不挂载（白屏无报错）；additionalProperties 只能给布尔。守卫见 check-tool-definitions.mjs。

2.3 客户端 chunk 与「改了没生效」

宿主的 client-modules 契约：require.async("./client.<name>.js")，服务端按 dirname(clientPath) 取文件。URL 带 ?rev=<sha1(mtime,ctime,size)[:12]>，且响应头 max-age=31536000, immutable——同一 rev 永久缓存，不回源校验。

repo dsh-plugins/<x>                       ← 你编辑的地方（页面不读这里）
  │ node scripts/dsh-plugin-deploy.mjs --changed
  ▼
~/.vssaros-dev/dsh-home/profiles/<p>/node_modules/@vssaros/<pkg>   ← 宿主真正读、并据此算 rev
  │ activation 时 stat 入口 exports["./client"]
  ▼
/plugins/@vssaros/<pkg>/<chunk>?rev=…    ← 一个插件的所有 chunk 共用「入口」的 rev
「改完没生效」只有三种可能：① 只改了 repo、没进 profile ⇒ 服务端字节没变；② 只改了 chunk、入口元数据没变 ⇒ rev 不变 ⇒ 浏览器吃旧缓存（重启也没用）；③ 没重启宿主（rev 在 activation 时才抓）。

--changed 直接整包复制 + 刷新入口 mtime（毫秒级生效，但绕过 pnpm ⇒ 锁文件会漂移）；--bump 只改仓库版本号、把安装交回官方 dsh plugin add（提交前跑一次）。

2.4 工具、技能与服务声明

工具注册
主机平面里注册；同名工具注册会抛错（画布类插件曾与上游重名 4 个）。工具名必须与 agent 的 tools[] 名单对得上，写 legacy 名不报错也不生效。守卫：check-agent-tools.mjs。
技能
技能是插件负载的一部分（skills/<name>/SKILL.md），必须出现在 files 与 gulp 的资源 glob 里，否则本地正常、装出来空壳。dsh 只认顶层技能目录。
共享服务
@vssaros/dsh-foundation 是 dataRoot / dshHome / pageShell / lock 的唯一真源。消费者用 lib/foundationRef.js；它缺席时消费者直接抛「vssaros-foundation 服务未绑定」。所以 foundation 必须排在模块插件之前安装。
自定义 UI（页面 / 工作台）
自托管页要自带 UMD 依赖（宿主不传 CSS 变量，必须自备底色）；工作台要同时登记「主页卡片」与「route 白名单」，并 bump 版本 + 动入口 stamp。

2.5 开发闭环（日常四步）

  1. 改代码主机平面改 lib/index.js，客户端改 lib/client*.js；新增文件记得补 files 与 gulp glob。
  2. 同步进 profilenode scripts/dsh-plugin-deploy.mjs --changed（快通道）；或 --bump 走官方安装通道。
  3. 重启宿主KeepAlive 的 Host 不会随 IDE 退出：装/改插件后必须按 host.json 的 pid taskkill 再启动，否则跑的还是旧进程。
  4. 跑该插件的自检node dsh-plugins/<name>/test/run-<name>-check.mjs；再跑 npm run check:dsh-plugins（约 50 条链）。

2.6 守卫链（提交前必须全绿）

守卫抓的是什么
check-plugin-files.mjsfiles 是否覆盖真实产物（漏 chunk / 漏 patch / 漏 skills）
check-tool-definitions.mjs工具 schema 是否落在 dsh 允许的子集内、是否留空壳
check-agent-tools.mjsagent 的 tools[] / skills[] 是否为 dsh 真实名与可见技能
check-lib-imports.mjs插件 import 面是否越界（客户端混进 Node 模块等）
check-workbench-catalog.mjs工作台两份清单（主页卡片 + route 白名单）是否都登记
check-host-config.mjsHost 配置 / 单例约束
check-spawn-hide.mjs子进程是否带 windowsHide（否则弹一叠 console 窗口）
dshPluginPackages.test.ts包结构三处一致、patch 一行、依赖面、打包链闸门
build/saros/check-dsh-release.mjs发布前：改了 lib/** 却没 bump；随包版本低于 profile（会触发降级重装）；bundled 不在 versions 里；产物与仓库版本不一致
bump 规则（最容易被漏）：只要 插件内容有变化（哪怕只改一个 chunk），就必须 bump 版本，判据是「版本 + 入口内容」；只改 chunk 不改入口 ⇒ 指纹不变 ⇒ 打新包也不重装。

纯工具函数级改动也想免 bump，就必须让 lib/index.js（入口）字节发生变化。

3. 打包流程

3.1 十六步流水线（Build #241 实测顺序）

  1. 拉取源码Checkout main；.gitignore 里排除 /dsh-runtime/ ⇒ 干净检出没有运行时。
  2. 设置版本号写 package.json 版本（本次 2.2.26207）。
  3. 安装依赖npm ci + tree-sitter 原生编译 + 各扩展 npm install + 装 pnpm（种子需要）+ vendored rg.exe 兜底（GitHub 403 时用仓库里那份）。
  4. KB 渲染 bundlebuild-agent-studio-kbblocks（esbuild）。
  5. 生产编译compile-build-with-mangling：tsgo 编译 → 符号混淆 → NLS 抽取。失败会自动回退 npm run compile（无混淆）。
  6. 复制 kbblocks 资源产物进 out-build。
  7. 构建能力插件transpile-plugins → out/vs/extensions/capability-plugins.js（运行时按路径加载，属高危漏拷项）。
  8. 编译扩展compile-extensions-build：内置扩展打包（fromLocalNormal 会带生产依赖）。
  9. 打包暂存目录gulp vscode-win32-x64：拷 dsh-plugins/、dsh-runtime/<bundled>/（含 seed）、源码与依赖 → VSCode-win32-x64/resources/app。
  10. 内置 ffmpeg可选依赖，失败只降级（抽帧 / 视频理解回退 PATH）。
  11. 内置 whisper可选依赖（本地 ASR），失败只降级。
  12. 校验关键构件verify-staging.ps1：硬性清单 + 自愈（agent-studio/out、typescript、tree-sitter wasm、dsh-plugins、运行时、种子）。
  13. 生成 EXEgenerate-exe.ps1：调 Inno 前先硬判运行时在包里。
  14. 归档构件抓 .build/win32-x64/**/*.exe；抓不到就是 0 file ⇒ exit 100001 ⇒ Job 失败。
  15. 上传升级服务器前一步失败则 skip。
  16. 创建 Releasetag + changelog + woa.git / GitHub 双端；前一步失败则 skip。

3.2 四道闸门

级别闸门判据 / 缺失后果
硬 strip-before-pack.mjs 2.5d 暂存目录缺 dsh-runtime/<bundled>/node_modules/@deepseek-ai/dsh/lib/bin.js ⇒ 从仓库整目录自愈；仓库侧也没有 ⇒ criticalMissing ⇒ exit 1 禁止出包。
硬 verify-staging.ps1 $required 约 40 项：rg.exe、三个自定义扩展产物、out/vs/sessions/**、capability-plugins.js、resources/.agents/**、dsh-plugins/*、运行时 bin.js + sherpa-onnx.node、profile 种子三条。
2026-10-28 收紧种子从「只告警」升为硬性。
硬 generate-exe.ps1 调 Inno 之前判 <appPath>/dsh-runtime/<bundled>/…/bin.js。因为流水线「失败也继续」，这里是最后能拦住坏包的点。
诊断 prepack-dsh-runtime.mjs 各种失败只记录不抛（除安装/版本不符）。但种子缺失现在会在第 12 步被判死，所以失败必须打全 stderr（2026-10-28 补）。

3.3 运行时与 profile 种子（打包的难点）

  1. 装运行时npm install --prefix dsh-runtime/<bundled> @deepseek-ai/dsh@<bundled>；版本核对 --version 必须相等；装完幂等 prune（裁掉 LibreOffice 内核 ~182MB，不裁 sherpa 语音）。
  2. 确保 pnpm三级兜底：PATH → corepack enable pnpm → npm i -g pnpm。因为 dsh plugin add 直接 spawn pnpm。
  3. 建种子DSH_HOME=<seed> npm_config_package_import_method=copy ⇒ profile 用 web 模板初始化 ⇒ 逐个 dsh plugin add file:<staged>（repo 全部 @vssaros/* + 官方 web-app / voice / schedule bundle）⇒ 起一次 Host 让 web 模板依赖落盘。
  4. 去绝对路径把 profile 的 package.json / pnpm-lock.yaml 里 file:<构建机绝对路径> 改写成 file:.vssaros/plugins/…（相对 profile，可搬运）。
  5. 清凭证删掉试启动生成的 .credentials.yaml（否则全体用户共用构建机 grant）。
  6. 对账后写 marker按「期望插件表」逐个查 node_modules/<name>/package.json 的版本，缺/不符就 throw ⇒ 先对账再写 seed.json（写早了等于给残缺种子盖章）。
种子是「加速项」但现在是出包硬门。它的价值是「首启零下载、零 pnpm」：宿主 _ensureProfile 整目录复制种子 → _repairSeededStoreMetadata 修 .modules.yaml 的 virtualStoreDir/storeDir（跨盘 / 8.3 短名都会踩）→ _planPluginInstall 发现版本与指纹都对 ⇒ 一次 pnpm 都不跑。

缺种子的包能装，但首启要用户自己跑 pnpm 装 profile（多数机器没有）⇒ 表现为「首启很慢 / 插件缺失 / 工作台空白」。

3.4 已修的三处断点（2026-10-28）

问题现场修法
EMFILE
已修		 extensions/agentmemory-memory/package.json 的 dependencies 带 vssaros: file:../..（junction 指向仓库根）⇒ npm ls 把整个仓库当生产依赖（1907 项）⇒ 打包并发 open 耗尽句柄，两步双双失败 ⇒ 无 exe。 build/lib/extensions.ts 只认物理位于扩展自身 node_modules 下的依赖；dependencies.ts 加 omitOptional；小文件改缓冲拷贝。

种子把 182MB 装回来

名不副实的运行时
已修		 工作区残留一份引擎自报 alpha.3、目录却叫 0.2.1-rc.2 的旧安装 ⇒ 它自带的官方插件声明 rc.2、引擎却是 alpha.3 ⇒ profile 里每装一个插件都被 dsh「版本闸门」拦（to accept the risk…）⇒ 种子建不出来。旧写法「目录在就跳过安装」⇒ 一份坏安装被静默复用。 prepack 的「已安装就跳过」路径现在核对引擎自报版本，对不上就重装；种子里再出现版本闸门会自动 accept-and-retry（上限 400，带汇总日志）；失败时把 dsh 的启动诊断读出来并留痕到 seed-build-fail-logs/。
rc.4 是回归
已排除		 同期试过 next 通道的 0.2.1-rc.4：版本串自洽、种子也能建，但 host 组 p0-01 / p0-04 / p0-08 在 rc.4 上启动即崩（webServer/connection 不起）；rc.2 基线同组全绿。 留在 rc.2。升级 bundled 必须做基线对照（同一组探针跑新旧两个运行时），不能只看「版本自洽」。

4. 升级流程

4.1 运行时升级（兼容清单 + 闸门 + 回退）

dsh-plugins/dsh-compat.json
├─ bundled : "0.2.1-rc.2"          # 构建期预装进包的版本（必须在 versions 里）
├─ versions: [{ version, verifiedAt, checks[], bridgePlugin, notes }]
├─ canary  : [{ version, testedAt, checks[], notes }]
└─ blocked : [{ version, reason }]  # 明确"有问题"，禁止作为升级目标
环节口径
解析顺序setting（runtimePath）→ managed（用户显式装/升）→ bundled（pin）→ global（npm i -g）
更新发现discoverUpdates：stable 只看 versions；preview 额外看 canary；locked 不升。blocked 的版本永不作候选，当前版本被 blocked 时给明确 note。
闸门步骤检查运行中任务（忙 ⇒ blocked）→ 停 Host → 快照（profiles/<p>、sessions、storages；不含凭证）→ 切指针 → 启动 → 健康检查 → 失败自动回退指针
快照时机Host 停止之后，避免复制到写了一半的会话文件

4.2 插件升级（三条来源，同一判据）

① 随包插件（exe 自带）

  • 启动时 _planPluginInstall 比对 版本 + 入口内容指纹。
  • 不一致 ⇒ 暂存到 profile/.vssaros/plugins/ ⇒ 一条 dsh plugin add spec1 spec2 …（N 次进程收敛成 1 次）。
  • 批量漏装会回退逐项 _ensurePlugin；有不降级保护（exe 版本低于 profile 时不降级重装）。

② 第三方插件（插件中心 / 商城）

  • listThirdPartyPlugins 只读 profile 的 package.json（不碰 Host）⇒ 列出非随包依赖。
  • upgradeThirdPartyPlugin(name) 走同一套 pnpm 安装通道。
  • 商城安装：下载 → 校验 → 落 profile → 重启或热重组。
两个真机事故（务必记住）：

① 降级重装风暴：exe 里随包版本低于用户 profile ⇒ 每次启动都尝试降级（8 个包跑满 4 分钟超时、桌面窗口卡在「正在启动后台服务…」）。现在运行期有不降级保护，发布前由 check-dsh-release.mjs 拦。

② 同版本内容变了：pnpm 认为 file: 依赖没变化 ⇒ 一个字节都不替换；宿主判定又只看版本 ⇒ 新旧代码混杂。判据因此改成「版本 + 入口内容」。

4.3 应用本体升级

应用（EXE）与运行时、插件是三条独立升级链：应用走更新服务换安装包；应用内的 dsh-runtime/<bundled>/ 随包而来（新版 exe 会带新的 bundled）；profile 在用户机器上独立演进（managed 指针优先于 bundled）。

升级后的自愈顺序（启动时）：_ensureProfile（缺才复制种子）→ _repairSeededStoreMetadata（修 pnpm 虚拟店元数据）→ _auditBundledVersions（profile 已装 vs 随包，逐条点名）→ 计划安装 → 起 Host。
