移除 executeAgentTurnDirect 分支 · 默认 runPiKernelTurn · 风险评估与重构设计

版本 v1.0 · 2026-09-20 · 依据：doc/agentloop-pi-core-redesign.md §5（P0–P3） · 状态口径：当日真机实证 + 测试全绿

结论（TL;DR）

现在移除 legacy 分支 = 高风险，不建议立即执行；但方向成立，存在一条四阶段、每阶段有量化准入门槛的可达路径（估 1.5–2.5 周）。

差距不在内核机械正确性 —— 流式 / 工具 / 续跑 / 记忆注入 / token 记账 / 循环护栏 / 压缩 / UI 卡片契约已在真实聊天框两轮实测全绿；差距在覆盖面（3 类形态仍被硬排除 + 4 项能力缺口）与证据量（真机 3 轮，全是"单工具短会话"形态）。本文给出：风险分级清单、测试先行的补全计划（已落地 7 个新用例）、目标目录结构、分阶段推进图、以及与 8 个开源方案的横向对比。

1.3 门控机制（当前安全网）

  • 开关（2026-09-20 E2 已翻转：默认开 = pi 内核）：显式回落 legacy ⇒ window.__SAROSIS_PI_KERNEL = false / env SAROSIS_PI_KERNEL=0（排障逃生门）；每 turn 判定 ⇒ devtools 翻转即时生效、即时回退，无需重启。
  • 自动回落 legacy（piKernelSupports）：已无排除项——resumeFrom（D2 checkpoint）/ plan（D1 批后拦截）/ subAgent（软预算+审批路由）/ chatOnly 当日全部接入，函数保留作为将来新增不支持形态的单点门。
  • 对拍入口：window.__SAROSIS_PI_RUN(prompt)（独立最小链路，只读工具，不写会话）——sessions 与 agents 两种窗口布局均已接线。
  • 测试面：准入套件（149 例）在文件头部显式 __SAROSIS_PI_KERNEL=false 钉 legacy 行为；pi 行为钉由 piTurnKernel/piLoop/矩阵套件承担（翻转后 30+20+15+3+5+7+3+7 = 90 例全绿）。

2风险评估（移除分支 = 触发以下全部条目）

2.1 R1 · 致命（移除即功能回退）

#缺口影响与证据处置路线
1resumeFrom 断点续跑pi 路径不读不写 checkpoint ⇒ 长任务崩溃即全部丢失（agentRunState/checkpoint 体系作废）。阶段 1
2plan 模式编排plan_enter/exit/explore 是被 _handlePlanModeTools 拦截编排（DAG + 审批），不是普通工具执行；pi 路径会把它们当普通工具执行 ⇒ 语义全错。scope 决策
3subAgentsoftDeadlineMs 超时语义 + background 任务 + 委派台账。24h 日志 11 行 subAgent 活动（高频形态）。阶段 1
4steering 队列用户中途插话（executor 形参 steeringQueue?: DeliveryQueue）；pi 路径目前完全忽略 ⇒ 生成中无法插话，体验硬回退。阶段 2

2.2 R2 · 高（行为漂移）

#风险说明
5证据量过薄真机 3 轮全是"单工具短会话"。未覆盖：多工具批、长会话压缩实触发、HTTP 400 overflow 的 force 压缩恢复、工具并发、invalid-tool 熔断、XML 泄漏重试、孤儿 tool_call 补偿（endedToolIds）、reasoning streak、取消语义。
6护栏语义微差legacy ping-pong 是整批拦截；pi beforeToolCall 只能拦单个（收敛相近、语义不同，需对拍豁免或补批次层）；no-progress（同签名+同结果）护栏未接。
7测试资产旧行为套件钉的是 legacy 实现细节（loopState/endedToolIds/xmlToolLeak）而非纯契约 ⇒ 移除=重写或删除整个套件，回归网出大洞。必须先建 pi 契约套件再评删。

2.3 R3 · 中（工程）

  • 并发碰撞：turnKernel 收口（common/turnKernel/turnPartContext.ts）刚由并发会话完成，移除是对同一文件的又一次大手术 ⇒ 动手前必须正式对齐。
  • 回退能力丧失：门控的价值就是一秒翻回；移除后回退只剩 git revert + 重发。
  • 宿主瘦身连锁：agentOSService 有 26 个 private 成员为 legacy 服务，移除后需同步清理，波及面大（ITurnHost 64 成员 ⇒ pi 实际消费约 30）。

6.4 原生 pi 如何处理这四个能力（G:\CustomWorkspaces\AIProjects\pi 源码实证）

我们 fork 的只是 packages/agent/src/agent-loop.ts + types.ts（轻内核）；这四个能力在原生 pi 里全部不在这个内核层——它们的归属恰好给本方案的阶段 1/2 提供了架构判据。

能力原生 pi 的机制（文件实证）对我们的判据
steering 队列内核层、轮询模型：agent-loop.ts:173/203/263 —— 宿主提供 config.getSteeringMessages?.() 异步 getter，loop 在①起始（"user may have typed while waiting"）②长准备阶段后（如压缩）③每个 turn 边界 各轮询一次，取到的消息排进下一次模型调用之前推入 transcript；agent.ts:246 的 PendingMessageQueue 默认 one-at-a-time 模式。直接可借 模型极简：把我们的 DeliveryQueue 包装成 getSteeringMessages 挂在同一三个轮询点即可（fork 的 config 已有 steeringMode 字段，需补 getter 的轮询调用——阶段 2 工作量确认为 小）。
plan 模式内核外扩展：packages/coding-agent/examples/extensions/plan-mode/index.ts（390 行）—— 本质是工具集切换（plan 模式只放 read/grep/find/ls/白名单 bash，禁 edit/write）+ 从模型输出提取编号步骤（"Plan:" 段）+ [DONE:n] 标记 + 进度 widget。内核对此一无所知。验证 D1 建议 pi 官方就是"plan = 独立编排器，不进内核"。我们的 plan 更重（DAG 编排 + 审批 + 计划文件），更不该塞进内核 ⇒ D1 选 (b) 获得原生架构背书。
subAgent内核外扩展：packages/coding-agent/examples/extensions/subagent/index.ts（1038 行）—— spawn 独立 pi 子进程（node:child_process）换隔离上下文；支持 single / parallel（≤8 任务、并发 4）/ chain（注入 previous）；每任务输出截 50KB；JSON 模式收结构化输出。内核同样一无所知。模型不同，无可借 pi 用进程级隔离，我们用进程内 + softDeadlineMs 轮级超时（更轻、共享宿主服务）。原生没有可抄的超时机制 ⇒ 按原计划把 softDeadlineMs 接 shouldStopAfterTurn/abort（阶段 1），架构上"subAgent 不进内核"与 pi 一致。
resumeFrom 断点续跑harness 层的会话 DAG：packages/agent/src/harness/session/* + runtime/drive/checkpoint.ts —— append-only 的 entry 日志（MessageEntry/insertEntry/branchTip/chainEntries，类 git 分支模型）；run 是带 intent 的 operation，checkpoint 是被提交的 operation；恢复 = 重放 entry 到分支尖。后端可插拔（packages/session-backends）。层次不同，映射即可 这是 pi 的生产 harness 层（我们刻意没 fork —— 会话持久化本仓已有 agentRunState 体系）。我们的需求更轻（轮级快照 ⇒ 恢复消息+计数）⇒ D2 选 (a) 轻映射（pi transcript ⇒ AgentRunState 快照），不引 DAG；pi 的 entry-log 是 P2 远期可选项，不是移除 legacy 的前置。
§6.4 的一句话：原生 pi 的架构答案是「内核只做 ReAct 循环；plan/subagent 是扩展；steering 是宿主轮询；续跑是 harness 的会话 DAG」。本方案的取舍与之逐项同构 —— 唯一本质差异是续跑持久化（它用 DAG，我们用轮级快照，映射兼容）。这意味着阶段 1/2 的所有工作都不需要发明新架构，只需按原生边界接线。
