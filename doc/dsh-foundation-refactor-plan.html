设计红线

  1. 不 fork、不 patch、不锁版本：dsh 以外部运行时方式托管，VsSaros 不打包、不修改 dsh 源码，不使用官方保留的 desktop profile。
  2. 全链路零翻译：Agent 循环、工具执行、审批、会话持久化由 dsh 原生完成；聊天框作为 dsh 前端插件运行，直接使用 dsh 前端的原生数据模型。VsSaros 与 dsh 之间只传 VsSaros 自定义的界面命令（打开文件、主题、插入引用等），不搬运 dsh 的事件或数据结构。事件镜像仅作为 P0 失败时的备选方案保留。
  3. 依赖面收敛：VsSaros 核心代码（src/vs/**）只依赖 dsh CLI、dsh 页面整体和 VsSaros 自有的两条桥；所有对 dsh 插件 API、前端 Slots / hooks 的依赖都封装在 dsh-plugins/ 内的插件里。
  4. 单写者：任一数据文件同一时刻只有一个写者，迁移期由「所有权开关」保证。
  5. 可降级：任一插件或桥失败，不影响其他模块；聊天框换皮失败时回落为官方样式，内容不丢。

3.2 托管运行时：版本并存、指针切换、可回滚

  • 安装位置：~/.vssaros/dsh-runtime/<version>/，通过 npm i --prefix 安装 @deepseek-ai/dsh，不污染用户全局环境；state.json 记录当前指针与历史版本。
  • 来源优先级：托管运行时（默认）＞ 用户在设置中指定的路径 ＞ PATH 中的 dsh。Node 运行时：由 VsSaros 托管一份便携 Node，与 dsh 运行时并列安装（官方要求 22.19.x 或 24+）。P0 已证实不能用 VsSaros 自带的 Electron 以 ELECTRON_RUN_AS_NODE 运行：dsh 依赖的 node-addon-require-builtin 只支持 Electron 43 及以上，VsSaros 当前为 39.8.8。
  • 专属 profile：vssaros，用 --from-default-profile web 初始化。插件集合与用户自己的 web profile 隔离；会话、凭证、设置共享同一个 $DSH_HOME，在浏览器里打开 dsh web 也能看到同样的会话。
  • 覆盖层：运行时配置（桥地址、IDE 能力开关等）通过 --patch 覆盖层注入，不改用户的任何配置文件。

3.3 升级闸门

  1. 发现：查询 npm dist-tags（latest / next），叠加 VsSaros 兼容清单（CI 产出的签名 JSON，列出已验证版本）。
  2. 预检：① 已装插件的 peer 范围（dsh 自带检查）；② @vssaros/* 插件声明的范围；③ @vssaros/* 插件对新版 dsh 类型声明的编译结果与 Slot 目录比对（来自 CI 兼容清单）；④ Node 版本；⑤ 安装身份校验（见下）。
  3. 并列安装：新版本装入独立目录，当前版本保持运行。
  4. 快照：只读备份 $DSH_HOME/profiles/vssaros 与会话目录。原因：dsh 升级可能迁移会话格式，迁移后的会话旧版 Host 无法读取，不快照就无法真正回滚。
  5. 切换：经控制桥询问 host.hasRunningWork，无运行中任务（或用户确认）后切换指针并重启 Host。
  6. 健康检查：握手成功；全部 @vssaros/* 插件激活；聊天框 instance（agentPart）内页面冒烟通过（发送一条消息并收到流式回复、DOM 断言 mainPart 无 dsh 页面）。
  7. 失败自动回滚：指针回退并恢复快照，保留诊断日志与失败原因，提示用户；「Host 根本起不来」这一类不走本步骤，见下面的启动失败诊断与恢复。

升级闸门的三条硬约束

  • 诊断路径绝不触发升级：自检/诊断入口（DSH: 诊断环境、日志导出、兼容性检查）只做只读探测，永不下发安装、切换或回滚动作。理由：诊断通常发生在"已经坏了"的时候，此时动版本会二次破坏现场。
  • 每次启动最多提示一次：升级提示在每个 Host 生命周期内去重；用户拒绝后不再反复弹窗，直到用户主动检查或下次冷启动。企业/演示环境的"锁定"通道（第 3.4 节）下完全不提示。
  • 安装身份校验后才允许升级：只对可验证的托管安装执行升级——校验包目录 package.json 的 name === "@deepseek-ai/dsh"、bin 指向的可执行文件 realpath 落在该包目录内、Windows 上比对命令 shim 内容、并校验 npm CLI 自身身份；未知或无法解析的安装永不覆盖，只给"复制目标版本号"与"跳过"两个选项。这条同时保护用户手工安装或用其它包管理器装的副本。

运行时发现与交接的容错约定

多实例复用（第 7.5 节）与升级切换都建立在"发现层"之上，因此发现层必须满足一条总原则：它只提供提示，永远不阻塞启动。

  • 写失败即降级：host.json 写不进去（权限、并发、磁盘满）只记日志，本实例照常起自己的 Host——不因为"登记不了共享端点"就拒绝启动。
  • 读失败/损坏即自起：文件缺失、JSON 损坏、字段不全、pid 已死、端口不通，一律视为"没有可复用的 Host"，直接自起，不阻塞、不报错弹窗。
  • 探活判据是"能用"而不是"端口通"：认证成功 + 一次真实 RPC 调用成功（例如会话列表返回一个数组）才算可用；只探测端口是否监听不算。
  • 撤广告只认"明确被拒"：只有对具体 127.0.0.1 端点收到连接被拒时，才撤回本实例登记的 Host 记录；超时、连接成功但无响应、localhost 别名等模糊结果一律保留记录。这条对我们尤其重要：过早判定"Host 已死"会让第二个实例另起 Host，触发第 7.5 节的跨进程单写者冲突（SessionAlreadyOwnedError），代价远大于留一条过期记录。
  • 启动期互斥互为 best-effort：拉起 Host 前的互斥（命名管道或回环端口）只用于降低"两个实例同时拉起"的概率，等待与持有都设很短的上限，抢不到就照常自起，不排队、不失败。
  • 归属证明先于终止：只有本实例亲手拉起的进程树才能被终止；进程身份无法证明时（POSIX 进程组号已被复用、Windows 上 launcher 先退出导致后代归属不明）明确报错并交给用户处理，绝不"猜着杀"；复用/收养来的 Host 永不终止，只断开连接。
  • 收养要严格：意外退出后尝试复用已存在的 Host 时，必须全部一致（版本、profile、覆盖层/组合哈希）才收养；有一项不一致就继续搜索或另起，避免复用一个"看起来一样但覆盖层不同"的 Host。

启动失败诊断与恢复（recovery）

上面的闸门覆盖"升级失败"，但更常见的是 Host 根本起不来：插件组合损坏、profile 补丁层不兼容、宿主注入的覆盖层与当前 dsh 不匹配、认证凭据失效。此时用户看到的是一个起不来的会话而不是一条错误。因此需要一个独立流程，而不是只把日志丢给用户：

  1. 失败分类：把启动失败归入有限几类——进程启动即退出 / 启动超时 / RPC 不通 / RPC 协议不符 / 认证失败 / 沙箱构建或清理失败 / launcher 异常，每类给出不同的下一步。
    v1.2.12 十九补（README 4.68）：其中"启动超时"原先是一根**固定 60s 的秒表**，真机实测冷启动时 Host 正在"安装伴生插件（1/3）"（合法 pnpm 耗时）就被判失败 ⇒ 用户看到"启动失败"。改为**进度感知**（dshStartupDeadline）：安静预算 60s（没有任何进展才算卡住）+ 总时长上限 5 分钟（有进展也不放过）；报错文案分开"没有进展 vs 有进展但不结束"，两者都带最后一行日志——这正是本节"每类给出不同的下一步"要求的落地。
  2. 隔离沙箱复现：在临时 $DSH_HOME 与临时工作区内做真实启动探测；剥离敏感环境变量，结束前清理临时凭证文件。
  3. 有界变体：按固定顺序试少量变体（原样复现 → 移除全部用户插件包 → 半量/单例插件组合 → 移除宿主覆盖层 → 确认元凶），变体数与总启动次数设硬上限（建议 ≤8），并为"确认元凶"与"回滚验证"预留次数。
  4. 归因：把结果归到插件包 / 宿主覆盖层 / profile 补丁 / home 文件 / 环境 / 偶发，并给出证据行。
  5. 候选修复 + 还原说明：修复动作只限可逆操作（移除宿主覆盖层、停用 profile 中的插件包），必须携带还原指令与前置条件（如"必须先停止 Host"）。
  6. 台账与并发保护：修复记录落盘并带租约，防止两个窗口同时改同一个 profile。
  7. 诊断导出：一键导出诊断包（失败分类、变体结果、日志尾部），密钥脱敏，单次启动日志设大小上限且只留尾部。
  8. 入口：入口放在聊天框宿主的错误态里（v1.2.3 后不再有独立面板），提供「取消恢复 / 查看状态 / 导出诊断 / 恢复上一次状态」；恢复进行中禁止同时升级。
这四块的共同判断是：运行时治理的失败成本高于功能缺失的成本。社区实现 dsh-vsc-integration（v0.10.3）已把发现层容错、归属证明与启动失败恢复做成独立子系统；我们的方案不能只有"升级失败就回滚"一句。

尝鲜任意 latest / rc，显式风险提示开发者、内测
锁定固定某一版本，不提示升级企业环境、演示环境

版本判定与能力探测降级（两者的分工）

通道决定"允许升到哪些版本"，运行期则不要按版本号写行为分支。两者分工如下，这也是把第 12 节的"待确认能力"变成可提前落地的关键：

  • 版本只做一件事：拒绝太旧。设一个最低可用版本，低于它直接判为不兼容并给出升级指引；不建"版本号 → 行为"的映射表（那种表每来一个 rc 都要改一遍）。
  • 能力按特性探测：每个可选能力（某个端点、某个投影、清单里的某个可选字段、某个 Host 服务）在首次使用时探测一次，缺失即降级而非报错；探测结果缓存，只在重连、插件组合变化或显式刷新时失效。
  • 同一投影的多种格式都要接受：dsh 在版本间改过字段返回形态（例如某投影从"自带选项集合"改成"只返回当前值、选项另取目录"），消费方同时兼容两种，而不是锁死新版写法。
  • 上游删掉的接口不许留调用：每次适配都清理已删除 RPC 的调用点；CI 矩阵第 1 项（类型契约编译）就是它的兜底。
  • 缺省即降级，但要有可观测性：降级路径打一条诊断日志（哪个能力、哪个版本、降级到什么行为），否则用户看到的是"功能时有时无"。
这条直接缩小第 12 节的阻塞面：凡"dsh 文档未说明"的能力，一律先按可选 + 降级设计并落地，验证结论只决定默认开关与顺序，而不是决定功能是否存在。

3.5 CI 兼容矩阵（dsh-compat 流水线）

  • 频率与对象：每日对 dsh 的 latest、next、上一稳定版各跑一遍；参照社区 openma-ai/deepseek-harness-acp 的 dsh-update.yml 模式。
  • 检查项：
    1. 类型契约：全部 @vssaros/* 插件对新版 dsh 的类型声明编译（Slot 与 hooks 签名变化在此暴露）；
    2. Slot 目录比对：用 dsh 生成的 Client inspect catalog，检查 chat-surface 占用的 Slot 仍存在、基数与作用域未变；
    3. 运行冒烟：建 profile → 安装全部 @vssaros/* 插件 → 启动 → 握手 → Electron 加载聊天模式页面与完整面板；
    4. 聊天冒烟：提问 / 流式 / 工具 / 审批 / 取消 / 插队；
    5. 视觉回归：聊天模式关键界面截图比对；

  • 产出：全部通过的版本写入兼容清单；红灯自动开 issue，并阻止该版本进入稳定通道。

换皮时必须保留的两条行为约定

  • 未保存编辑保护（审批）：审批卡放行前，若目标文件在当前窗口仍有未保存编辑，拒绝放行，在卡片上点名这些文件并提示「先保存或撤销，再重新批准」。关键在实现顺序：检查必须发生在"认领该审批"之前——这样被拒的审批从未被认领，卡片保持等待状态、按钮可再次点击，而不是变成一个需要重开会话才能恢复的死卡片。脏文件判据只取审批卡实际展示的路径，不推断工具可能写哪些文件。
  • 样式只认宿主主题变量：换皮组件不要另建「注入一套 token + 主题变更推送」的通道，直接使用宿主既有的 CSS 变量（--vscode-* 同名映射，见第 5.6 节）。主题切换因此自动跟随，页面桥只需传会话、工作区、引用这类真正必要的状态，少一条需要长期维护的同步链路。

这两条与"换皮"本身无关，是行为契约：只要聊天框里的审批卡是 VsSaros 样式，就应当同时满足。社区实现 dsh-vsc-integration 的审批路径把命令行、工作目录、目标文件与提案 diff 一起呈现，脏文件时让审批保持 pending —— 可直接作为验收样本。

5.13.2 实现（v1.2.4：隐藏而非停用）

踩坑记录：不能停用 dsh 的前端插件。最初按"在 Host 的 --patch 覆盖层里按 entry id 停用非聊天插件"实现，实测客户端直接 boot 失败：页面显示 "Failed to load plugin / web boot: 23 entries did not activate"，其中 ui-theme 等条目的原因是 pending (waiting for service: locale, configForm)、sidebarRight、uiWorkspace —— 聊天本身依赖被停用插件提供的服务（locale / configForm 来自设置类插件，sidebarRight 来自侧栏，uiWorkspace 来自工作区插件）。所以改为保留插件、只隐藏界面。
  • 机制：preload（electron-browser/preload-dshView.ts）在 surface=chat 且开关打开时注入一段样式表：隐藏 [data-slot=sidebar]（含品牌行、会话列表、文件 / 工作区 / 浏览器 / 终端 / 文档预览）、[data-slot=rightbar]、[data-rightbar-col]（轨迹 / 任务 / 交付物）、以及 [data-sidebar-right-expand]（右侧栏折叠后留在聊天列里的"展开右侧栏"按钮——实测会发现，不隐藏就能把面板拉回来），并把 [data-sidebar-collapsed][class] 的三栏栅格收成 0 minmax(0,1fr) 0，让聊天主列占满。选择器一律用 dsh 布局的 data-slot / data-* 属性（不用哈希类名）；document.head 未就绪时用 DOMContentLoaded + MutationObserver 补注入并随即断开观察器。
  • 裁剪后的功能核对：实测聊天框里可见控件共 7 个 —— Choose workspace、输入框（[data-composer-input]）、Add files or run commands、Access mode（权限模式）、Select model（模型 + 推理强度）、发送按钮等，且没有可见的侧栏开关。New session / 会话列表 / 文件树 / 设置 / 插件入口原在侧栏内，随侧栏一起归还给 VsSaros（见 5.13 表）；chatId → dsh 会话的绑定仍属 P2。
  • 为什么是 preload：preload 就是"这个视图里的展示层"，只影响 VsSaros 的 dsh 视图，不改 dsh 源码、不改用户 profile；P2 的 @vssaros/dsh-chat-surface（dsh 原生 Slot 替换）到位后取代这段样式。
  • 开关：sessions.dshHarness.chatOnlyUi（默认开）→ CreateView 参数 → webPreferences.additionalArguments（--vssaros-dsh-chat-only=1）→ preload。关掉即回到官方整页形态。

5.14 能力补齐方案：chat-surface 用 Slot 贡献补齐 VsSaros 聊天框独有能力（v1.2.6）

依据：dsh 0.2.0-rc.2 的真实 SlotMap（87 个 Slot，已逐条核对 kind/scope/所属包，扫描脚本 poc/dsh-p0/.out/slotmap-scan.mjs）。本节的 Slot 名、kind、scope 均可由 CI 用 SlotCore.snapshot() 的运行时输出复核。

5.14.1 机制要点（SlotCore 契约）

  • 遮蔽（single / keyed / list）：同 cell 条目按 priority 升序、最低者渲染，官方条目默认 0 → 插件用负优先级遮蔽；条目崩溃时 abdicate，自动回落到下一个（官方样式，内容不丢）。同 cell 同 priority 注册会 throw。
  • 选举（chain）：conversation.composer 与 shell.quota-notice 由 selector 决定（返回非 null 即接管）；conversation.composer 的 overlay 选项让官方 fallback 保持挂载（接管时草稿不丢）。
  • 新增（list）：用唯一 id 加条目即可与官方共存；keyed 槽用未占用 key 加新类型，或占用已有 key 做遮蔽。

5.15 聊天框切换 Agent（preset）（v1.2.11，2026-10-10 用户决议）

机制结论（全部实证）：dsh 的"切换 agent" = 切换 agent preset（standard / ptc / minimal / cordis / 自定义）。preset 在会话创建时绑定（sessionController.create({cwd, agentPreset})）；空白会话可切换（agentPresets.select，投影经 agent-preset/selected 推进）；已有会话 Host 拒绝热切换（ApiSessionPresetConflict）。官方 hero chip 在聊天框空白会话开箱即用（e2e 57/57 实证）；已有会话的官方 UI 只有会话头部的只读 AgentPresetLabel。

5.15.1 切换语义（用户决议）

  • 空白会话：直接热切换（官方通路 remote.agentPresets.select(sessionId, id)），历史为空无损失。
  • 已有会话：切到 preset X = 打开/创建该 preset 的专属会话，各自历史独立保留，切回来还能看到原对话——对齐 legacy 聊天框"切 agent = 切到该 agent 自己的 session"的既有语义。
  • 明确不做：同会话热切换（dsh 架构拒绝；且已有历史是在旧 preset 的工具集/提示词下产出的，硬切会让会话日志失真）。

5.15.2 会话 id 派生与状态持久化

  • 派生规则（确定性）：默认 preset 沿用 vssaros-chat-<chatId>；非默认 preset 用 vssaros-chat-<chatId>--<presetId>。确定性 id + session.start 幂等接管 = 切回时重开同一会话（历史原样回来），跨重启恢复也直接可用，无需另存映射表。
  • 当前 preset 持久化：NativeChatEditorInput 序列化字段新增 dshPreset（缺省 = 默认 preset），窗口重载/重启后恢复到切换后的 preset 会话。
  • 切回默认 preset = 重新绑定无后缀 id 的会话。

5.16.5 安全与语义（必须在 UI 上讲清楚）

  • 安装即全权代码：profile 层插件在 Host 进程内运行，不受工作区沙箱限制（官方对 agent 触发的要求是 danger-full-access 或逐次批准）。用户手点安装/卸载必须有一次明确确认对话框（写明"将以当前用户权限运行插件代码"）。

  • 重启语义：HMR 开 → 立即重载；关 → restart-required（UI 给"重启 Host"按钮，复用已有重启通道）。替换同名包后必须重启才能换 JS 版本。

  • 不自动更新：当前版本升级需先卸载再装新版（官方同样如此），UI 明示。
  • 兼容闸门：安装后仍可能因 dsh peer 范围被拒（incompatible），列表要给"已装但启动被拒"的异常标签，与 VsSaros 自己的 dsh 兼容清单（第 3.4 节）区分开。

6.4 动态开关时序

  1. 用户在插件中心打开开关（内置模块首次启用时从 resources/dsh/plugins/ 离线安装 tgz）。

    1. 工具的 parameters / output.schema 必须落在 dsh 的受限 JSON Schema 子集内：type / oneOf / properties / required / additionalProperties / items / enum / const + 注解。写子集外的键（实测：integer 上的 minimum / maximum）在注册时不报错（ToolRuntime.register 只 assertSupportedJsonSchema(output.schema)），只会在模型调用时才失败——所以范围约束要写进 description、由插件代码夹紧。另一条边界：裸对象定义的参数不代校验（参数校验只在 defineTool 的闭包里），execute 必须自己容忍脏参数（类型错、越界值）；输出侧由 dsh 强制执行（execute 后用同款校验器判违规并抛 ToolOutputError）。
    2. 插件必需依赖要收敛：把只在 web 模板里存在的 webServer / connection 写进 export const inject，会让插件在 headless / tui profile 里永久 pending（实测 pending (waiting for services: webServer, connection)），连只依赖 tools 的工具一起失效。正确写法：inject = ['tools']，页面用 ctx.inject(['webServer','connection'], …) 做可选依赖（Cordis 4 的延迟注入）。
      推论（第二个模块实测）：只允许访问声明过的服务——inject 之外写 ctx.tools.xxx 会抛错（?.get?.() 也救不了）；需要"探测某个可选服务在不在"时，用 ctx.inject(['tools'], child => …) 并让状态跟着服务的事件更新（如 tools/change）。
    3. 插件自托管页面的写头顺序（同一个实测坑的另一半）：处理器里先 res.writeHead(200) 再渲染，一旦渲染抛错就会在 catch 里二次写头 → ERR_HTTP_HEADERS_SENT → socket 被切断（浏览器侧只看到 fetch failed: other side closed，不是 500，现象极难定位）。正确：先渲染再写头，catch 里判 res.headersSent，已发出就只 end。
    4. 一个 patch 文件只能有一个顶层 - insert:：写多个 insert 时加载器只认**第一个**，后面块里的行静默消失（实测：MCP 两台服务器时第二台的行不见了，且不报错——"某台服务器莫名没挂上"的典型来源）。所有行挂在同一个 insert 的列表里。生成覆盖层的代码要有断言/单测盯住这一点。
    另两条运维事实：① 装机的变更单位是版本——dsh plugin add 在版本未变时是 no-op（pnpm "Already up to date"），profile 里跑的还是旧拷贝（与 _ensurePlugin「版本相同则跳过」一致），改代码必须 bump 版本；② dsh --profile <p> --dump-config 可直接验证"组合是否采纳 + --patch 覆盖是否生效"（P3-1 探针即以其输出做断言）。

7.5 多窗口与多实例

  • 同一 VsSaros 进程的多个窗口：全应用一个 Host（主进程 DshHostSupervisor 单例），所有窗口的视图都连这个 Host。各窗口打开不同工作区互不影响（第 8 节）。
  • 多个 VsSaros 实例共享同一个 $DSH_HOME（--instance 多开等）：
    • 约束：dsh 会话持久化是跨进程单写者。同一会话只能被一个 Host 写入，第二个 Host 以写方式打开会抛 SessionAlreadyOwnedError；读可以并存，但跨进程不保证读到最新内容。
    • 方案：复用 Host。第一个实例启动 Host 后写入 ~/.vssaros/dsh/host.json（端口、pid、dsh 版本、profile、控制桥管道名与一次性 token，文件仅当前用户可读）。后续实例先探活，通过就直接复用。做法与记忆网关 3111 的多开复用一致。
    • 控制桥方向调整：为支持多个实例同时连接，v1.2 改为由 vssaros-bridge 监听命名管道，各 VsSaros 主进程作为客户端连接。连接后用 client.register 登记自己的窗口与工作区，ide.request 按会话 cwd 所属工作区路由到对应实例。
    • 复用失败（版本不同、探活失败）才另起 Host。此时打开另一实例正在运行的会话会失败，界面提示「此会话正在另一个 VsSaros 实例中运行」并提供只读查看（P0 第 18 项确认 dsh 的具体行为）。
    • dev 版与安装版默认使用不同的 $DSH_HOME，沿用 VsSaros 已有的数据目录隔离规则，避免互相争用会话。

多视图订阅方式的取舍

第 7.3 节把"同一会话在多处打开"定为每个可见视图各自 follow()。另一种做法是集中订阅 + 多视图分发：由一个常驻订阅者读取会话，再把状态分发给所有视图。两者取舍如下，P0 第 16、17 项量化时按这两列分别采数：

维度每可见视图各自 follow()（本方案）集中订阅 + 多视图分发
订阅份数每视图一份（3 个视图 = 3 份流）1 份，与视图数无关
视图成本每视图一个渲染进程（P0 第 16 项：约 150 MB/视图，重建约 550 ms）每视图仍是一个渲染进程，但数据加工只在宿主一份
数据加工由 dsh 前端在各视图内完成（分页、懒加载、断线重连内置）宿主自己把事件投影成 UI 状态，需自己实现分页、窗口化与截断
一致性由 follow() 保证逐 token 无缺口由宿主分发保证，需自己实现序号连续性与重连补齐
大会话成本由 dsh 前端的渲染策略决定随事件数线性增长（全量投影 + 全量下发），必须自己做窗口化
未知节点dsh 自己渲染，新增类型自动可见需自己维护映射，并为未知类型准备保底展示
结论倾向不变（保留每视图 follow()，即"分页与重连交给 dsh"），但仍应实测"同一会话开 3–4 个视图"时 Host 侧的 CPU / 内存增量：如果增量主要来自 Host 对同一会话的重复序列化，而不是视图渲染本身，可以只对同一会话的额外视图做"复用同一数据源"的折中，而不必整体改路线。

8. 多工作区兼容分析

结论：dsh 的模型是「会话创建时显式绑定工作区，cwd 不可变，可写边界等于 cwd」，比 VsSaros 现状的「每个窗口一个活动工作区」更明确，也消除了现状两处口径不一致的问题。一个 Host 能同时服务所有工作区，多窗口各开不同工作区没有冲突。
主要缺口有两个：多根工作区只有一个根可写；worktree 会话的 git 写操作可能被沙箱拒绝。另有一个功能缺口：dsh 会话没有按轮回滚文件的 checkpoint。

8.2 映射方案

  • 真源分工：VsSaros 注册表仍是 VsSaros 工作区概念的真源（agents、bindings、relatedFolders 只有 VsSaros 有）；dsh 注册表只承载「目录 + 会话账本」。
  • 以规范路径为连接键：
    • vssaros-bridge 提供控制桥命令 workspace.ensure(paths[])，在 Host 内调用 ctx.workspaceRegistry.create(path)。同一规范路径重复调用返回既有实体，天然幂等；查询用 resolveByPath。
    • VsSaros 不维护 id 映射表，也不在自己这边比较路径字符串。Windows 盘符大小写、junction、符号链接统一交给 dsh 的 realpath 规范处理。
  • 注册时机：Host 握手完成后、页面首次打开之前，注册所有已打开窗口的工作区（主根加各 worktree 路径）。注册表非空后，dsh 就不会再自动创建 default-workspace。
  • 删除与重命名：VsSaros 删除工作区时不自动删除 dsh 登记（dsh 的删除本来也只移除登记、保留会话，会话变为未分组）；标题按需同步。
  • 窗口与页面：窗口的活动工作区经页面桥 onBindSession({ workspace }) 传给聊天视图。新建会话默认落在该工作区；会话列表默认按该工作区过滤，可切换到「全部工作区」。
  • 切换工作区：仍沿用「重开窗口」，视图随之重建。但会话运行在 Host 进程，窗口重载与切换工作区都不会中断正在运行的会话。

8.4 worktree

  • 映射：每个 worktree 路径注册为独立 dsh 工作区，「在 worktree 中执行任务」即在该工作区新建会话（cwd = worktree 路径）。cwd 在创建时就固定，现状 AgentBinding.worktreePath 的临时覆盖与加锁机制不再需要。
  • 收益：现状同一工作区同一 agent 的多个会话共用一个 worktree；engine=dsh 后每个会话可以各选一个 worktree 工作区，并行任务互不干扰。
  • 缺口（推断，文档未提）：worktree 里的 .git 是一个文件，指向主仓库的 .git/worktrees/<name>，index、HEAD、对象库都在 cwd 之外。workspace-write 下 git add / commit 写这些位置可能被拒绝。
  • 对策（P0 第 21 项定）：
    1. 若追加可写根（8.3 方案 D）可行，为 worktree 会话追加主仓库的 .git；
    2. git 写操作改由 VsSaros 源代码管理执行：agent 只改文件，提交由用户或 VsSaros 完成；
    3. git 命令走 dsh 的单次提权审批（审批通过后按更宽的模式执行一次）。

按轮回滚与 diff 重建（IDE 侧实现，不依赖 dsh 提供能力）

社区实现 dsh-vsc-integration 已经证明：不依赖 dsh 的 checkpoint 能力，也能在 IDE 侧做到"看改动 + 回滚到某一轮"。两条手段可直接借用：

  • 按轮快照 + 整轮回滚（对应上表 checkpoint 行）：监听轮次的开始与结束事件，在轮次边界用 git 底层命令抓快照——git diff --raw -z 取改动清单、git cat-file blob 取改动前后内容、git cat-file --filters 取工作区形态；回滚时要求全部文件可还原、冲突检测做两遍（进入前一次、落盘前再一次）+ 用户确认；二进制、重命名与文件模式都要处理。这样"回滚到某一轮"就是"把该轮之后的快照依次回退"，粒度是一轮而非"单个工具调用"。
  • 不依赖 Git 的"修改前"重建（用于 diff 卡与审批预览）：工具结果里通常只带改动片段（hunk 的旧文本与新文本），而不是整文件旧内容，因此"修改前"的还原方式是把当前文件按 hunk 逐个逆向换回旧文本（倒序撤销）。三条硬约束：① 每个 hunk 的新文本必须在文件里恰好命中一次，命中 0 次或多次就放弃并提示"该处已变化，无法还原可信 diff"——一个错误的 diff 比没有 diff 更糟；② 先做行尾归一化，并把"文件是否随后又被改过"作为能否采用磁盘真实内容的条件；③ 结果缓存设条数上限，淘汰后明确提示"此 diff 已不再可用"。这同时覆盖了非 Git 仓库、被 gitignore 的文件，以及"新建文件时左侧为空"的情形。

两条都落在 VsSaros 侧，不增加对 dsh 的依赖，也不构成翻译层（只读取工具结果与工作区文件）。

本节多数项的阻塞点是"需要模型凭据，或要在真实工作台里手点"，导致验证被一直往后拖。社区实现 dsh-vsc-integration 的做法值得照搬：把能离线判定的部分全部脚本化，只在真正需要模型或 UI 的地方留人工冒烟。

  • 隔离状态跑真进程：脚本用临时 $DSH_HOME、临时工作区与临时端口启动真实 Host，不碰用户会话与凭据；结束即清理（可选保留现场供排查）。
  • 不需要模型的替身：用一个本地、返回固定流的假模型端点替代真模型，就能跑通"建会话 → 发消息 → 收到流式回复 → 工具调用 → 审批 → 取消"整条链路；脚本参数支持指定真实 CLI 路径与目标版本。
  • 按项映射：第 1、4、7、8、11、18、19、21、22、23、25 项都适合做成这类脚本（多实例复用、端口回退、承载位置的 DOM 断言尤其适合）；第 9、10、12、13、14、15、17、20、24 项中需要真实前端/UI 的部分保留人工冒烟，其余仍尽量脚本化。
  • 脚本进 CI：除每日兼容矩阵外，这些脚本要能在本地一条命令跑完，作为改动 Host 生命周期或承载位置代码后的回归门禁。

能力授权与审计（新增守卫）

第 4.4 节把 IDE 能力按清单逐项授权；对写入、执行、浏览器控制、调试这类高危能力，授权之外还要"每次调用可审计、可归责"。可直接借用社区实现对调试桥的做法：

  • 每次调用一个临时令牌：能力端点（或 ide.request 的高危方法）按会话或按启动生成一次性令牌，长度设下限、比较用恒定时间；令牌不落盘（经环境变量传入），确需写盘时权限收紧且每次用独立文件名——避免"另一个窗口因为组合相同而复用到一个带着他人能力端点的 Host"。
  • 只绑回环 + 校验 Host 头：端点只监听 127.0.0.1，并校验 Host 在白名单内（防 DNS rebinding）；请求体设大小上限；无状态、拒绝批处理请求。
  • 只允许用户已配置的动作：例如"启动调试"只允许选择工作区里已存在的启动配置，参数 schema 禁止额外字段，不允许模型发明配置；找不到就明确报错并让用户去补配置。
  • 敏感值按名脱敏：变量/参数名命中口令、密钥、令牌、凭据、授权、会话一类关键词时替换为占位符再送出；正文按字节预算截断。
  • 审计：每次高危调用记一条（时间、能力名、会话、目标路径或命令、结果），落在会话诊断里，并随诊断导出可见。

打包期守卫

与验证脚本同级的是打包期门禁：随产品分发的 dsh 插件包与清单必须在出包时就被证明完整，而不是等用户首次启用才失败。

  • 必需文件清单：对 resources/dsh/plugins/*.tgz 逐个校验主入口、前端入口（dsh.client）与 vssaros 清单存在且可解析；缺失即阻断打包并提示如何重建。
  • 传递依赖也要在：不能只查入口文件——被入口 import 的辅助/策略文件同样必须在包内（"入口还在、依赖缺失"是最容易漏的一类）。
  • 对真实产物再查一遍：既检查按发布清单（含排除规则）算出的文件集，也对最终产物再列一遍文件核对，避免"清单里有、产物里没有"。
