工作台（dsh 插件）经 GitHub 发布 → 上传 → 他人下载安装：全链路数据流转

以 https://github.com/Tencent/BrowserSkill 为例 · 代码基线：@vssaros/dsh-marketplace 0.2.41 · saros-marketplace（server）· 2026-10-26
一句话结论：工作台与插件在商城里是同一件事——都是一个 dsh 插件包，商城只登记「去哪里取」； 安装的本质是 dsh plugin add <spec>（= pnpm 装进 profile + 写 bundles 选择 + 打 cordis 补丁）。

BrowserSkill 不能直接发仓库根地址：它的根 package.json 是 {"name":"browser-skill","private":true}（无 version、无 dsh 字段）， 而真正的 dsh 插件是 monorepo 子包 packages/dsh-plugin-browserskill，已发布为 @wxg-prc-cpg/browser-skill-dsh-plugin@0.3.3。 ⇒ 正确形态是 distribution.type = npm，不是 github-source。

3. 阶段 B：落库（服务端处理哪些字段）

接收侧 schema（parser.ts:17 DistributionSchema）

{ type: 'npm' | 'github-release' | 'github-source',
  name?: string,      // npm 包名 或 owner/repo
  url?: string,       // github-release 直链
  sha256?: string,    // 64 位 hex，可选
  bytes?: number,
  commit?: string,    // 分支 / tag / sha
  peerRange?: string }

⚠ 没有 subdir / path 字段 —— monorepo 子目录无法表达（见第 7 节）

写入的两张表

表关键字段值（workbench + github-source）
packages kind / slug / name / description / category / tags / status / visibility / distribution_type / distribution_meta / latest_version / updated_at workbench · browserskill · 浏览器技能 · github-source · {"type":"github-source","name":"Tencent/BrowserSkill"} · 由 recomputeLatest() 回填
package_versions version / changelog / asset_path / asset_size / sha256 / manifest / is_latest / published_by 0.3.3 · ''（空字符串，表示无包体）· 0 · distribution.sha256 ?? '' · 合成 manifest（见下） 
// versions.ts:355 合成的 manifest（与 bundle 通道同形，客户端解析逻辑可共用）
{ kind, id: slug, name, version,
  description?, category?,
  author: <发布者用户名>, files: [] ,
  distribution: { type, name?, commit?, url?, sha256? } }
审核策略（routes.ts:239）：管理员发布 ⇒ status='active' 直接上架； 普通用户且开启审核 ⇒ pending_review，需管理员在后台「资源审核管理」通过。

7. 反面案例：把仓库根当发布源会发生什么

如果按字面填 https://github.com/Tencent/BrowserSkill 作为 github-source： 
① 发布：成功。落库 { type:'github-source', name:'Tencent/BrowserSkill' }
   （服务端只校验域名与 name 形态，不校验这个仓库里有没有插件）

② 安装：pnpm 会去 clone 该仓库 根目录的 package.json：
     {"name":"browser-skill","private":true}   ← private:true，且没有 version
   ⇒ pnpm 拒绝（私有包 / 无法确定版本）
   ⇒ 用户侧看到「安装失败」，而商城里这条商品显示得完全正常

③ 即使 pnpm 放行：根目录没有 dsh 字段 ⇒ 没有 cordis.patch.yml 可打、没有 client 注入
   ⇒ 装上了也不会出现任何 bsk_* 工具（"装了但没效果"）
根因：DistributionSchema 里没有 subdir 字段， github-source 只能表达「owner/repo + ref」，表达不了 「这个仓库的 packages/xxx 子目录」。

三种可行做法

做法可行性说明
用 npm 发布源（推荐）现在就能用仓库作者已经把子包发到 npm；{type:'npm', name:'@wxg-prc-cpg/browser-skill-dsh-plugin'} 即可
用 github-release不适用该项目没有 Release 资产包（Release 区块为空）
给 github-source 加 subdir需开发要改三处：server DistributionSchema、客户端 specForDistribution（pnpm 不支持子目录 ⇒ 需自行下载 + 取子目录打包成 file:）、安装器定位逻辑

9. 本次修复：publish 带 source 被转 IDE 丢弃

现象：工作台/插件在详情里填了 GitHub 地址点提交，看起来成功，但库里没有 distribution， 或者报「打包失败」。

根因：dispatch.js 的 publish 只看 kind（workbench/plugin 不在 PUBLISHABLE_KINDS ⇒ 一律 'ide'）；而 IDE 侧的 marketplaceActionService.ts:377 的 publish 分支只读 version / changelog， 把 source 静默丢掉了。于是「登记外部源」退化成「打包上传」。

// dispatch.js（修复后）
if (name === 'publish') {
    if (PUBLISH_LOCAL_KINDS.includes(kind)) { return 'local-publish'; }
    // ★ 带 source（GitHub 地址）的登记留在 dsh 侧：服务端 external 接口不限 kind
    if (String(params?.source ?? '').trim()) { return 'local-publish'; }
    return 'ide';   // 真正的"打包上传"才交 IDE
}

回归验证（14/14）

publish(workbench)                        ⇒ ide                 ✔ 保持原行为
publish(workbench, source=https://…)      ⇒ local-publish       ✔ 修复点
publish(plugin,    source=…)              ⇒ local-publish       ✔
publish(plugin)                           ⇒ ide                 ✔
publish(skill | mcp)                      ⇒ local-publish       ✔ 未回归
install/upgrade/uninstall(workbench|plugin) ⇒ local-plugin      ✔ 未回归
install(skill) ⇒ local-write · list ⇒ local-read · pluginState ⇒ local-plugin ✔
publish(workbench, source='   ')          ⇒ ide                 ✔ 空白不算 source

守卫：check-plugin-files 101/101 · marketplace 0.2.40 → 0.2.41（profile 副本已同步）

10. 风险与待补能力

项现状影响 / 建议
github-source 无完整性校验服务端不存 sha256（只有 github-release 必填）同一 ref 被 force-push 时内容会变；建议对 github-source 也记录 commit sha（现在会自动写入 distribution.commit）并可选校验
monorepo 子目录不支持（无 subdir 字段）像 BrowserSkill 这样的仓库必须靠作者发布 npm 包；否则装不上
peerDependencies 兼容商城不校验插件要求 @deepseek-ai/cordis ^4.0.2、dsh-llm ^0.1.5-rc.3 || ^0.2.0-rc.1，宿主版本不匹配时安装成功但加载报错 ⇒ 建议在详情里展示 peerRange
发布原子性两次 HTTP（建包 → 发版本）第二步失败会留下「无版本的空包」；服务端已有「无版本」过滤，但商品会出现短暂空壳
生效条件无 hmr 需重启 Host用户容易误判为「装了没用」⇒ 安装结果里已如实返回 restartRequired，页面应显式提示
外部依赖不在商城表达靠商品描述写BrowserSkill 还需要 bsk CLI + 浏览器扩展；建议在描述第一行写「需先安装 …」（REA 商品已用此做法）

11. 发布校验机制（preflight）

分两层：① 字段校验（早就有，保证"长得对"）；② 可装性体检（2026-10-26 新增，保证"装得上"）。 第 7 节那个反面案例，正是只有第 ① 层时的漏网。

① 字段校验（既有）

层校验内容
客户端表单商城标识符合 ^[a-z0-9][a-z0-9_-]*$（插件包名会先被压成 slug）；版本非空；登记外部源必须有地址
dsh 侧 publishslug 规则、version 非空、distribution.type 在枚举内、description 截断 2048、npm 包名格式
服务端 zodDistributionSchema（type/name/url/sha256 64hex/bytes/commit/peerRange）、slug 唯一、kind 枚举、审核状态机
安装期bundle 包校验 manifest.id === slug 与 kind；github-release 必须 sha256 且校验一致才装

② 可装性体检（新增，op:'preflightPublish'）

在点「提交」之后、真正 publish 之前自动跑一次，全部走不占 GitHub API 额度的通道：

发布源检查项判定
npm 包名 registry 上是否存在该包不存在 ⇒ error（阻断）
package.json 是否有 dsh 字段（workbench/plugin 必须）没有 ⇒ error（"装了也没工具"）
商城填的版本与 npm latest 是否一致不一致 ⇒ warn + 建议改版本
peerDependencies 数量与版本范围有 ⇒ warn（宿主版本不匹配会装得上但加载报错）
repository.directory（是不是 monorepo 子包）是 ⇒ pass 并说明"用 npm 名是对的"
GitHub 地址 根目录有没有 package.json没有 ⇒ error（有 SKILL.md 会额外提示"这更像技能"）
private:true是 ⇒ error（pnpm 不装私有包）
有没有 version没有 ⇒ error（无法确定版本）
有没有 dsh 字段没有 ⇒ error（不是 dsh 插件）
是不是 monorepo（pnpm-workspace.yaml / workspaces）是且根不是插件 ⇒ error + 指引去子包的 npm 名
版本一致性不一致 ⇒ warn

三种结果的处置：

pass  → 直接发布
warn  → 列出提醒，window.confirm 让用户确认后才发
error → 拦住，不发布；逐条列出原因；若有可行修法给「按建议修正」按钮（一键回填 npm 名 / 版本）
