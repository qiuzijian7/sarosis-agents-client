1 目标、非目标与成功标准

先框定范围，避免把「多模型兼容优化」做成一次大重构。本次只解决收发链路上的上下文与能力协商，不动协议转换矩阵本身，也不实现服务端会话存储。

做（In scope）

  • 把 Model.Extra 能力表接入 relay 热路径，提供带缓存的查询入口
  • 新增「出站窗口预算」策略：按 contextWindow 估算、按消息边界裁剪、保留关键语义
  • 声明式灰度开关（按渠道 / 渠道类型 / 模型正则），默认全关
  • 裁剪可观测：诊断、消费日志、AgentLens 属性、可选响应头
  • 配套单测与灰度验证流程

不做（Out of scope）

  • 不实现 Responses 对象存储：本站无响应存储，且展开历史后仍要全量发给上游，解决不了窗口问题（上轮已论证）
  • 不做「透传 /responses/compact」：上游实测 404，路径已判死
  • 不动 12 条协议转换矩阵、toolconv IR、计费公式
  • 不改造 37 分支 GetAdaptor 为插件化（列为 P3 长期方向）
  • 不做「模型生成摘要式压缩」：需定义 prompt 与 output 契约，未知量太多

成功标准

0

0

0

明确的性能约束

裁剪发生在每次请求的热路径上，必须默认关闭、按渠道灰度；开启时对未超预算的请求要做到零额外序列化（先走便宜的粗估，超阈值才做逐条精确计数）。能力表查询必须走内存缓存，不能每次打 DB。

3 总体架构：三层 + 一条旁路

新增代码集中在 service/context_budget/ 一个包，对主链路的侵入只有一个调用点。

Layer 1 · 能力数据层
CapabilityResolver
按「映射后的上游模型名 → 原始模型名 → 家族兜底」查 Model.Extra，产出 {ContextWindow, MaxOutput, SupportsTools...}。
  • 内存缓存 + 版本号失效，热路径零 DB
  • 缺失 / 0 值 → 返回 unknown，跳过裁剪
  • 可选 option 覆盖表，支持人工修正
Layer 2 · 策略层
BudgetPolicy
决定是否启用、预算多少、保留几条、裁剪模式（trim / reject / observe）。
  • 复用灰度范式：渠道 ID / 类型 / 模型正则
  • 默认 Enabled=false
  • 安全余量吸收 tokenizer 误差
Layer 3 · 执行层
ContextTrimmer
按 RelayFormat 分派 4 个裁剪器，原地改 info.Request，返回裁剪统计。
  • OpenAI Chat / Claude / Gemini / Responses
  • 整条消息为最小粒度，不做字符级截断
  • 保留 system、最近 N 条、工具调用配对

数据流

入站请求解析→ GenRelayInfo
relay.go:134→ ContextBudget.Apply
新增唯一调用点→ PrepareRequestBilling
relay.go:160→ 重试循环 / TextHelper→ 协议转换→ RemoveDisabledFields / param_override→ 出站 body
为什么必须放在计费预扣之前

PrepareRequestBilling 在重试循环之外、TextHelper 之前，用 info.Request.GetTokenCountMeta() 估算预扣额度。若裁剪只写在 TextHelper 内，预扣按裁剪前的量算，会出现临时多扣甚至「余额不足」误拒（虽然最终按上游 usage 结算会修正）。放在 relay.go:134~160 之间，计费、param_override、日志、每次重试看到的都是同一份裁剪后的 request。

5 核心算法

5.1 预算公式

budget = contextWindow
       − reservedOutput      // max_tokens / max_output_tokens，缺省取 max_output_tokens 或窗口的 15%
       − safetyMargin        // 固定 10~15% 或 max(4096, contextWindow*0.1)，吸收 tokenizer 3~5% 误差
       − toolsTokens         // 工具定义通常计入 prompt，按 tokenkit.Count 估
       − systemTokens        // system / instructions / systemInstruction 永不裁剪

used  = Σ tokenkit.Count(upstreamModel, messageText) + perMessageOverhead
if used <= budget → 直接返回（不裁剪）
else → 从最旧的可丢弃消息开始整条移除，直到 used <= budget 或触到保留集下限

6 分阶段路线

每阶段独立可上线、独立可回滚。P0/P1 解决线上实际问题，P2/P3 是能力建设，不阻塞前者。

P0能力表接线 + 观测模式建议先做
内容：新增 service/context_budget/ 包；实现 CapabilityResolver（读 Model.Extra + 内存缓存 + 映射模型名回退）、BudgetPolicy（照抄灰度结构，默认 Enabled=false）、只统计不裁剪的 observe 实现；在 relay.go:134~160 加一个调用；诊断与日志字段。
价值：不改任何请求内容，先在 observe 模式拿到线上真实分布 —— 有多少请求会超预算、超多少、哪些模型能力表缺值。这些数据决定 P1 的安全余量取多少。
验收：灰度范围内所有请求 100% 不变（出站 body 字节一致）；诊断日志能看到触发率与能力表命中率。
P1出站窗口裁剪（核心收益）根治 100001 报错
内容：实现四协议裁剪器与保留集；trim / reject 模式；passthrough 互斥约束（禁用透传或替换 BodyStorage）；统计可视化。先在 CodeBuddy(type=64) + 长会话高频模型 单渠道灰度。
价值：长会话不再把全量历史顶到上游 100k 窗口；100001 tokens 类 400 在网关侧被消解；compact 支持从「必须做」降级为「可选增强」。
验收：构造 120k+ tokens 的历史，验证出站 body 消息数下降、system 与工具配对完整、重试各轮 body 一致、计费预扣按裁剪后 token 计算。
P2能力声明外扩 + 管理入口
内容：把 OpenAIChatCapabilities 的 5 个硬编码布尔位改为「能力表优先、代码兜底」；新增 option 覆盖表与 PUT /api/option/ 热更新；系统设置页加只读能力表视图与裁剪策略配置；补全 supports_tools / vision / reasoning / streaming 的通用声明。
价值：新模型不用改 Go 代码；为后续按能力路由（例如把带图请求只路由到支持 vision 的渠道）打基础。
注意：本阶段触及计费相关字段时，需遵守仓库 AGENTS.md:130-134 规定先读 .agents/rules/billing.md。
P3compact 支持 / provider 配置化（长期，可选）
compact：P1 落地后窗口已受控，compact 不再是阻塞项。若仍要做，按上轮调研的路径 B（本站把 compact 转成一次 chat 请求生成摘要，再包装回 response.compaction），且必须先抓 Codex 真实请求/响应确认 output item 结构 —— 目前仓库无真实抓包，盲目实现容易做出「不报错但客户端不认」的版本。
provider 配置化：对标 LiteLLM「OpenAI-compatible 一个 JSON 文件」，把纯兼容渠道从 37 分支 switch 里抽成配置注册。改动面大（前后端 75 个文件），建议单独立项，不并入本次。

8 风险、规避与回滚

风险成因规避 / 回滚
裁剪破坏语义删掉 tool_use / tool_result 配对、thinking 签名块、Claude System 等，上游直接 400 或答非所问。四协议各自保留集 + 配对校验；裁剪后做结构自检，不通过则放弃裁剪并记 warn；P0 observe 模式先跑一周核对数据；灰度从单渠道单模型开始。
tokenizer 误差Claude / Gemini / Unknown 为加权估算，平均误差 3–5%，短文本更大；Unknown 权重未校准。固定 10–15% 安全余量；只做整条消息粒度；未知家族默认不裁剪；reject 模式给明确提示而非静默失败。
能力表数据缺失max_input_tokens 可能为 0 / 缺失，模型别名与映射后上游名不一致。缺失即跳过并记 capability_unknown；按「映射后模型名 → 原始名 → 家族」三级回退；P2 提供 option 覆盖表人工修正。
计费不一致裁剪放在 TextHelper 内会导致预扣按裁剪前算，临时多扣 / 额度误拒。强制插入 relay.go:160 之前；单测断言预扣 token 与裁剪后 body 一致。
重试 / 透传不一致passthrough 直接发原始 BodyStorage；relay.go:208 每轮复位 c.Request.Body。裁剪与 passthrough 互斥；端到端单测覆盖「首次 + 重试」各轮出站 body 一致。
性能回归热路径逐条 token 计数、能力表查 DB。默认关闭；粗估未超阈值就跳过精确计数；能力表内存缓存 + 版本号失效；observe 阶段量测 P99 延迟。
回滚路径

策略走 config.GlobalConfig，PUT /api/option/ 把 Enabled=false 即可本机立即生效、无需重启、无需回滚二进制；跨节点 ≤60s 收敛。极端情况下 Apply 保持默认关闭，代码本身对未灰度流量零影响。

9 验收与测试计划

单元测试
  • 能力解析：正常值 / 0 值 / 缺失 / 模型别名 / 映射后名回退；缓存失效
  • 灰度判定：全关 / 全渠道 / 指定 ID / 指定类型 / 模型正则 / 优先级
  • 预算计算：under_budget / 恰好触顶 / 超大量 / max_output 缺省
  • 四协议裁剪：system 保留、N 条保留、工具配对、thinking 块、Responses RawMessage 重组、带 previous_response_id 跳过
  • 统计与诊断：字段完整、跳过原因准确、诊断去重上限
端到端 / 回归
  • httptest 假上游，断言实际出站 body 的 messages 数量与顺序
  • 首次 + 渠道级重试 + transport 重试，三轮 body 一致
  • passthrough 开启 / 关闭两种配置下的行为
  • 计费预扣 token 与裁剪后 body 一致
  • observe 模式下出站 body 字节级不变
  • 回归：go test ./... 、go vet、前端构建、read_lints

灰度上线顺序

① 全量 observe（默认关，按渠道开）→ ② 收集 3–7 天触发率 / 能力表命中率→ ③ 校准安全余量→ ④ 单渠道 trim 灰度→ ⑤ 双协议 200 与长会话复测→ ⑥ 逐步扩面
复测要用真实故障样本

线上那次报错的请求（user 11、POST /v1/responses、耗时 1m38s、prompt_tokens 峰值 32 万）在 log_contents / logs 里没有记录，拿不到原始出站 body。灰度验证需自行构造 120k+ tokens 的长会话，或在 P0 observe 阶段通过 AgentLens 的原始 body（属性上限 128 KiB）留档。

10 请确认的决策项

① 实施范围
是先只做 P0（观测、零风险、拿数据），还是 P0+P1 一起做（直接解决 400）？建议先 P0，用真实数据校准余量后再开裁剪。
P0 单独 / P0+P1 / 仅出方案不实施
② 默认模式与灰度对象
trim 模式默认是否只作用于 CodeBuddy(type=64)？其它渠道（Claude/Gemini/DeepSeek）上游窗口更大，误裁风险更高，建议 P1 不纳入。
仅 type=64 / 含 OpenAI 兼容渠道 / 全渠道
③ 裁剪 vs 快速失败
超预算时是静默裁掉旧历史（保成功率、有语义损失），还是返回明确错误让客户端自行压缩（语义无损、用户可感知）？也可按渠道配置。
trim / reject / 按渠道分别配置
④ passthrough 冲突
裁剪时禁用整包透传是最小改动，但会影响依赖私有字段透传的渠道。是否接受该约束，或需要实现 BodyStorage 替换方案（改动更大）？
禁用透传（推荐） / 替换 BodyStorage
确认后的执行顺序

按选定范围实施 → 单测 + 端到端 → 本地实例验证（严格 TOF 环境）→ 交叉编译部署 anydev → observe 灰度观测 → 再决定是否开 trim。当前仓库累计约 31 个改动 + 4 个新单测未提交（通用注册、登录态缓存等），实施前建议先确认这批改动是否一起提交，避免混在一起难以回滚。
