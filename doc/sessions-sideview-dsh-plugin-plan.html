把左栏「历史会话」SessionHistoryViewPane 的**绘制与能力**整体搬到 dsh 插件里， 并保留今天刚落地的口径：按工作区分组、每组 5 条空闲配额、运行中不占配额、行首无圆形图标。

本轮最重要的两个发现（都与"能不能搬"直接相关）
  1. 数据不用开新通路：dsh 插件 host 半边能直接读会话投影缓存 <DSH_HOME>/storages/session_projcache/sessions/<id>.json（**明文 JSON**，会话 id 就是文件名）， 还能可选注入 sessions / sessionProjections 把活会话**逐字段**合并进来。 vssaros-dashboard 已经这么做了，是可直接抄的活样板。
  2. 「人格」在 dsh 侧白拿：它本来就是 dsh 的会话投影（key vssaros-persona）。 上一轮卡住的那件事（VsSaros 侧拿不到 persona）**搬到 dsh 页后自动消失**。

三、核心待验证分叉：页面形态（决定第 2 期能不能做写操作）

这条我还没验证，且它决定"改名/删除/归档"能不能直接搬。dsh 插件页是一条**独立文档** （dshPluginViewPane.ts:10-12：页面由插件在自己的 Host 前缀路由上服务），不是 dsh SPA 的一部分。 所以有两条路，各有取舍：

七、我要替你定的假设（不对就推翻）

A1 列表画哪份会话：按 dsh 自己的会话（投影缓存 + 活会话）。理由：数据零新通道、人格白拿、且符合"能力全落 dsh 侧"的方向。代价：内容会变——VsSaros 侧那些没被 dsh 建过的会话不在列表里，且 dsh 会话按 preset/worktree 派生 ⇒ 可能出现"一个 VsSaros 会话对应多行"。
A2 popout 本轮不做：第 5 期再实验；失败就保留 DOM 版。
A3 飞书绑定交互留壳侧：徽标只读搬过去，绑定/解绑仍走壳（避免把跨系统耦合变成两次跨进程）。
A4 第 1 期先用"甲"（host 渲染 + 自绘）：因为它是 dashboard 已证可行的形状，风险最低；第 1 期顺手把"乙能不能 boot dsh client"证掉，若可行则在第 2 期切到官方那套以白拿写操作。
