search_code path_filter 错误过滤 HIGH L1382, L1495

问题表现

LLM 传入格式错误的 path_filter 参数，底层 grep 找到 1030 个匹配（502+528），但因 path_filter 格式错误被全部丢弃，LLM 收到空结果。

行号path_filter 值底层匹配数耗时问题
1382 "GarbageCollection/.cpp" 502 13.6s / 被当正则字面量，.cpp 前缺通配符，全过滤
1495 "GarbageCollection.cpp" 528 2.6s 精确文件名匹配，但实际文件路径为 .../Private/UObject/GarbageCollection.cpp，只匹配根目录

根因分析

// codebaseTools.ts L859-865: path_filter 是原始正则匹配，不做 glob/前缀魔法 .filter((e: any) => { if (!pathFilter) { return true; } try { return new RegExp(pathFilter).test(e.filePath); } catch { return true; // invalid regex → pass all } })

path_filter 被作为原生 RegExp 测试文件路径。对于 "GarbageCollection/.cpp"： - / 是正则字面斜杠（需 \/ 转义），导致不匹配任何文件 - .cpp 匹配单个字符+cpp，不具备 glob 语义

同类工具排查

工具有类似过滤参数风险
search_code path_filter, filePattern ✗ HIGH — 直接 RegExp 匹配，LLM 传 glob 语法必失败
search_files pattern ⚠ MEDIUM — 无 path_filter，仅文件名 glob，相对安全
search_graph namePattern, filePattern, label ✓ LOW — namePattern 支持 glob，有容错处理
list_dir ignore_globs ✓ LOW — 仅 glob，无正则风险
terminal 无内置过滤 ✓ NONE — 命令由 LLM 自行构造

结论：search_code 的 path_filter 是唯一受影响的参数。LLM 天然倾向用 glob 语法构造 path 过滤器，但实现期定义为 "正则"，两者语义不兼容。

修复建议

  1. P0 — 将 path_filter 从 RegExp 改为 glob：修改 codebaseTools.ts L859-865，将 new RegExp(pathFilter) 替换为 picomatch / minimatch 等 glob 匹配器，自动处理 **、*、? 等通配符。这样 "GarbageCollection*.cpp" 可直接匹配
  2. P1 — 失败时返回诊断建议：当 path_filter 过滤掉所有结果时，除了返回 "X match(es) filtered out" 外，再附带 "Hint: path_filter is RegExp, not glob. Try --filePattern for glob filtering."
  3. P2 — 自动检测路径模式类型：检测 path_filter 中是否含 **、* 等 glob 通配符，如检测到则发出 WARN 日志并自动转译为正则，避免静默失败

模型调用错误: fetch failed (连接超时) HIGH L897, L2386-2492

问题表现

向 copilot.tencent.com:443 发起请求时，3 次连接失败：

行号迭代上下文压力错误结果
897 1 低 AbortError: This operation was aborted 可能是用户取消或初始连接建立失败
2403 11 136% (realPromptTokens=184411, window=136000) ConnectTimeoutError: Connect Timeout Error (copilot.tencent.com:443, timeout: 10000ms) 系统正确触发 Incomplete turn retry (attempt=1/2)
2487-2492 12 (retry) 136% TypeError: fetch failed 第二次重试仍失败，但最终第19秒时收到文本delta（可能第三次隐式重试成功）

根因分析

  • 直接原因：TCP/TLS 连接到 copilot.tencent.com:443 超时（10秒 timeout）
  • 触发条件：上下文压力 136% 时发生 — realPromptTokens=184,411，远超模型 window=136,000
  • 级联效应：超大请求体可能被网关限流/丢弃/TLS 握手超时，或因请求太大导致网络传输中断
  • 重试机制：系统有 Incomplete turn detected → safe retry (attempt 1/2) 和 Network error on attempt 1, retrying... 两套重试，但用相同的超大请求体重试，大概率仍失败

修复建议

  1. P0 — 上下文压缩先于重试：当 ContextManager 检测到 tokens > window 时，先压缩再重试，而非用相同大 prompt 重试。当前压缩冷却（60s）可能阻止了及时压缩
  2. P1 — 模型故障切换：3 次 fetch failed 应触发 _executeWithFallback() 切换到备用模型（如 deepseek-v4-pro-ioa），而非耗尽重试
  3. P2 — HTTP 连接超时自愈：ConnectTimeoutError 是网络层面的瞬时故障，应指数退避（当前固定 10s timeout → 建议 10s → 20s → 40s）
  4. P3 — 请求体大小监控：在 modelProvider.chat() 前记录 requestBodySize，超过特定阈值（如 500KB）时发出 WARN

大量终端空结果 (no output) MEDIUM L2581-3595

问题表现

Agent 在 iteration 13-21 期间发出 14 次 terminal 命令，全部返回 (no output)。Agent 陷入空结果循环中无法脱离。

行号命令耗时问题
2581grep -n "ProcessAsync\|SpinUntilAllStopped..." "F:/.../LevelStreamingGCHelper."13.8sWindows 上 grep 不可用或路径末尾缺通配符
2589grep -n "PrepareStreamedOutLevelForGC..." "F:/.../LevelStreamingGCHelper."10.9s同上的 grep 问题
2691powershell -Command "Select-String -Path '...GarbageCollection.cpp' -Pattern 'ProcessAsync|SpinUntilAllStopped'"3.9s符号在目标文件中不存在（但 LLM 应该知悉这点）
2699powershell Select-String (类似)9.5s继续重复搜索相同符号

核心问题：Agent 使用 terminal 搜索 UE5 符号 ProcessAsync、SpinUntilAllStopped、PrepareStreamedOutLevelForGC。当这些符号在任何文件中都不存在时，LLM 不应继续用 terminal 搜索 — 应该改用 search_code（利用 graph 索引）或接受事实。

根因分析

  • Windows grep 不可用：前 2 条命令用 grep，但 Windows 默认没有。Agent 在发现无输出后切换到了 powershell Select-String（行 2690），但搜索的符号仍不存在
  • 连续失败未注入提醒：terminal 返回 (no output) 时，LLM 将其解读为 "可能 grep 没安装"，而非 "符号不存在"。缺少系统注入的 consecutive failure reminder
  • 迭代预算耗散：14 次空 terminal 消耗了 14 次迭代中的约 70% 时间（每次 2-14 秒），上下文从 136% 增长到 142%，但无实质进展

修复建议

  1. terminal 连续空输出检测：当 terminal 连续 3 次返回 (no output) 时，注入 system-reminder: "Terminal returned (no output) 3 times in a row. Possible causes: command tool missing, symbol not found, or incorrect path. Use search_code for codebase search instead."
  2. Windows grep 自检：当 LLM 的 tool description 提示 grep 的同时，提示 Windows 上可用 findstr 或 powershell Select-String。或者 terminal 工具在 Windows 上自动检测并提示
  3. terminal 超时优化：当前 timeout=30s hardCap=60000ms，对于搜索不存在的符号浪费大量时间。建议对于 grep/powershell 搜索命令使用更短的 timeout（10s）
