它解决什么

把「同一类活反复来」变成无人值守：定时抓一批待办、筛掉不该做的、逐个处理、跑完睡下，明天继续。

  • 不是 cron 替代品：它比 cron 多的是「按条挑活 + 去重 + 失败退避 + 熔断 + 审计」。
  • 不寄生官方 schedule：官方 schedule 只负责「到点往会话投一句话」；loop 自己有 30 秒 ticker。
  • 每条 item 是独立会话：上下文由轮数与墙钟决定，不是「这个进程活了多久」。
触发权在 loop、任务列表在官方 schedule —— 两者互链不合并，避免「两套任务 UI」。

三步跑起来

  1. 建目录与定义：<数据根>/loops/<名字>/loop.json （目录名 = loop 的身份，不用在 json 里重复写）。
  2. 先干跑：loop_dry_run —— 真采集、列出「会做哪些 / 其余为什么排除」， 不建会话、不花 token。
  3. 确认后让它跑：schedule 写 every 4h 就会自动轮；或随时 loop_run 手动跑一轮。 
{
  "title": "TAPD Bug 自动修复",
  "schedule": "every 4h",
  "maxItemsPerRound": 1,
  "itemTimeout": "45m",
  "harvest": { "command": "node bug-report.mjs --json" },
  "identityFields": ["id"],
  "work": {
    "taskHeader": "单号 {id}（优先级 {priority}）",
    "prompt": "按模板处理这张单……"
  },
  "notify": ["web"]
}
harvest.command 默认不执行：插件 config.allowCommands 默认 false （命令 = 本机代码执行）。干跑会明白告诉你「未执行」，要真跑得由部署方显式打开。

loop.json 字段

字段默认硬上限说明
schedulemanual—every <dur> / daily HH:MM / manual；最小轮间隔 120s
quietHoursoff—23:00-07:00，本地时间，支持跨午夜
maxItemsPerRound320每轮最多几条（超出如实标 round-cap）
itemTurnCap60500⚠ 当前只解析不生效，实际靠墙钟兜底
itemTimeout45m6h单条墙钟超时（abort）
harvestTimeout2m—采集命令超时（超时不算本轮失败）
maxAttempts25同一条活最多试几次
retryBackoff30m24h失败后的退避
consecutiveFailureLimit310连续失败粘性熔断：只能人工恢复
roundCostCeiling0（关）—⚠ 当前只记录不生效；建议生产环境填正数
onAskblock—block=存起来等人答；assume=让模型自己声明假设
identityFields["id"]—账本 key 由这些字段拼成（必须稳定）
harvest.command空—stdout 必须是 JSON 数组或 {rows:[...]}
work.prompt / template空—支持 {字段} 替换（taskHeader 同理）
work.allowedTools[]—声明用；实际放行看 config.allowTools（全局白名单）
completion.onMissingMarkerfailed—没签字算失败（防假绿）
notify["web"]—⚠ 目前只记录，通道未接
越过硬上限一律报错而不是夹紧 —— 夹紧会让「我写了 500 轮」静默变成 60 轮。

调度三型

写法语义
every 30m每 30 分钟一轮。从本轮开始时间起算（不是结束时间），否则跑 40 分钟的活会把 every 30m 变成 70 分钟一轮
daily 02:20每天本地 02:20。当天该时刻已过 ⇒ 明天；睡过头⇒不补跑
manual不自动跑，只能 loop_run

刻意不做 cron 表达式：它需要时区故事，而 every 已覆盖真实需求。

完成契约

每条 item 的最后一行必须是：

[item:done]
[item:failed:编译不过]
[item:blocked:缺服务器日志]
  • 没签字默认算失败（onMissingMarker=failed）—— 把「没签字」当成功是无人值守最常见的假绿。
  • blocked = 需要人介入：不再自动重试，用 loop_answer 放回队列。
  • 与 [plan:ready] 是不同命名空间，两个解析器永不互读。

护栏与去重

账本怎么判

状态下一轮
done永久不再做（dedupe = forever）
blocked等 loop_answer 放回
failedattempts 没用完 + 退避到点 ⇒ 可重试
running启动时一律归正为 failed（保留 attempts）
崩溃安全：每次状态变化都原子落盘；进程被杀时没有机会写「我死了」，靠启动时这条规则把账算清。 错过的轮次不补跑 —— 补跑会在「睡了一夜」后一次性放出 N 轮。

并发与互斥

  • 一轮互斥：ticker 与手动 loop_run 不会同时跑（忙时明确回报 busy，不排队）。
  • 串行执行：maxConcurrent 恒为 1，一轮没跑完不开下一轮。

五个工具

工具用途
loop_list列表 + 调度 + 账本计数 + 下次到期 + 是否熔断 + 配置错误
loop_show单个 loop 的护栏 + 账本明细（含每条为什么被跳过）
loop_dry_run不花 token 的预演：会做哪些 / 其余为何排除
loop_run立刻跑一轮（runs 服务不可用会明确报错，不假装跑了）
loop_answer把 blocked 的条目放回队列（可带一句回答）

群聊 #task（与 loop 对齐）

群聊与 loop 共用 @vssaros/dsh-workitem 内核：同一套去重、退避、完成契约。

  • 群里的活靠显式 #task:<key> 标记（不用隐式文本指纹 —— 改两个字就会重复派）。
  • key 归一化小写，#task:Bug-1 与 #task:bug-1 是同一件事。
  • 没有标签的消息行为完全不变（增量接线，不伤现有群聊）。
  • 回环闸门：loop 通知进群后那条系统消息不参与 @ 解析（判来源在 @ 之前）。
  • 风暴预算：20 事件 / 60 秒 / 冷却 60 秒（loop 没有、群聊必须有）。

账本单独存 <数据根>/agent-group-tasks.json —— 群 transcript 封顶 200 条会裁最旧，拿来当账本会把「做过了」裁掉。

装机与排错

装机（两个插件都没 vssaros.module）

它们走 archify / ego 同款伴生路径：common/dshHarness.ts 包名常量 → dshHostSupervisor.ts 的 workItemPluginDir / loopPluginDir → dshHarnessChannel.ts 解析目录。workitem 必须排在 loop 之前（loop 用 ctx.inject 等它）。

排错清单

  • loop_list 抛「组合里缺 @vssaros/dsh-workitem」：内核没装/没激活。看 profile 的 node_modules/@vssaros/ 里有没有 dsh-workitem。
  • 干跑说「harvest 未执行」：正常 —— allowCommands 默认关。
  • loop_run 说「runs 服务不可用」：bridge 没装或版本过旧，loop 的 ticker 不会启动（list/show/dry_run 仍可用）。
  • 改了 loop.json 不生效：spec 是每轮读的，但 state.json 的 lastRoundStartedAt 决定下一轮时间；想立刻跑就 loop_run。
  • 日志里看不到 loop：正常 —— 它只在 warn 时打日志。验证看落盘（loops/<name>/state.json 与 profile 目录），不看日志。

坑与边界

  • itemTurnCap 与 roundCostCeiling 当前是死字段（解析/展示但不生效）—— 别以为有护栏。
  • approval.allow 是全局白名单：给一个 loop 放开写权限 = 对所有 loop 放开。
  • harvest.command = 本机命令执行，等同代码执行：只给信任的 loop 开。
  • notify 目前不真发通知（只记录）。
  • 一条 item 的会话 id = loop:<名字>:<key 的 sha1 前 12 位>，重跑复用同一条历史。
  • loop.mjs（脚本回调形态）未实现：当前只支持 harvest.command 声明式采集。
