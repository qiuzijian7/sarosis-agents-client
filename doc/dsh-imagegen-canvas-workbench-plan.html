3. 目标形态

① 插件 @vssaros/dsh-imagegen（dsh-plugins/vssaros-imagegen/）

  • 上游源码钉 commit + 补丁队列构建出的 lib/index.js / lib/client.js（+ P2 起 lib/client.studio.js 懒加载块）
  • 清单：module: 'imagegen'，容器 vssaros.dsh.imagegen（page-only），图标 codicon:paintcan，侧栏页 /x/imagegen/
  • 入口 id 保持 image-gen（客户端设置读写写死了它，shared.ts:141）

② 画布 = 我们自己的插件页（/x/imagegen/canvas/）

  • 为什么不塞进 dsh 聊天页/右栏：画布引擎产物 3.4MB（§5.6）⇒ 放进 dsh 客户端包就变成"每个聊天框都加载 3.4MB"——那正是当初 tldraw（4.89MB）被否掉的原因
  • 插件页是独立 webview（打开才加载）⇒ 体积只在这一个视图里付
  • 页面完全自控（不依赖 dsh 的 slot 机制，也不用碰 dsh 布局 CSS ⇒ 不脆）
  • 聊天仍在 Agent 栏（画布页在编辑区页签）⇒ 两个界面切换；"并排"是后面的体验增强

③ Host 侧：画布状态镜像 + 两个工具

  • 画布页把场景/选区推到 Host（POST /x/imagegen/canvas/state，按会话分键 ⇒ 不会跨会话串）
  • canvas_state（摘要）/ view_canvas（选区截图 → attachment）两个工具给 Agent 读
  • edit_image 增加 source:'canvas_selection'（拿选区原图去改）
  • Agent 出的图回写画布：Host 记"本会话最近出图"⇒ 画布页拉取后落位
ActivityBar「画布」→ 侧栏页 /x/imagegen/（状态 + 打开按钮）→ 编辑区页签：画布页（Excalidraw，独立视图）↕ Host 画布镜像（按会话）↔ canvas_state / view_canvas / edit_image(canvas_selection)

5. 交付形态：自研第一方插件（已改）

原方案是"钉住上游 commit + 补丁队列 + 本地构建产物 vendored"。G1 拍板 B 之后这条路不划算，理由三条：

  1. 画布换 Excalidraw ⇒ 上游 tl/* 那 8 个文件（tldraw 封装 / 状态推送 / 选区导出 / 落图桥 / 画廊拖入）全部作废，要重写成 Excalidraw 适配层 ⇒ fork 下来的代码有一半用不上。
  2. fork 剩下的 provider 层（11 个 provider / 订阅登录 / ComfyUI 工作流 / 灵感库）与我们"复用 IDE 侧模型 provider"的路线方向相反：我们要的是"经控制桥回 IDE"（凭据只有一份），上游是"插件自己持 Key"。
  3. 补丁队列的长期成本（上游当天还在合 PR ⇒ 每月 rebase）换来的只是 provider 层的抄写 ⇒ 不如自研：代码在我们手里，许可干净（只有 Excalidraw MIT + 我们自己的 MIT），那些坑（摘要毁缓存 / 镜像跨会话 / 路由无鉴权 / ~/.dsh 写死）从一开始就不存在，而不是"打了补丁才不犯"。
决策选择理由 / 代价
包名@vssaros/dsh-imagegen（目录 dsh-plugins/vssaros-imagegen/，模块 id imagegen）与仓库里上一轮已登记的迁移台账一致（migration-ledger.json 的 media-gen 族已写明"@vssaros/dsh-imagegen（vssaros-imagegen 0.1.0，image_generate 工具）"）⇒ 沿用它的命名与版本
入口 idimage-gen（设置命名空间）客户端设置读写写死了它（shared.ts:141）
与 npm dsh-image-gen 共存插件中心对它标"已内置"并拦装两份都会注册同名工具
许可与署名我们自己的 MIT + 后续随包带 Excalidraw 的 MIT 原文与第三方声明（P2）tldraw 那份许可问题整体消失（不随包 ⇒ 不分发）
