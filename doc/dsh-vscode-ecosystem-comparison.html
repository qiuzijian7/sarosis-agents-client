「dsh × VS Code」开源生态调研与方案对照

2026-10-16 · 7 个样本（6 个本地 checkout，1 个外部）· 目的：为「多根工作区 / 文件写根边界 / Host 生命周期」三件事找现成答案 只读调研 + 1 项已落地
一句话结论：dsh 阵营里没有任何项目真正做了多根工作区（全部退化到 workspaceFolders[0]）⇒ 这是我们最容易做出差异化的点； 而 Host 生命周期我们其实已经不薄（拥有者记录 + 孤儿回收 + 启动锁 + 端口复用 + 客户端计数自退都在）⇒ 上一轮"最薄的一环"的判断需要修正。

真正做过多根的是非 dsh 阵营：
  • claude-dev（Cline）：WorkspaceRootManager 注释直写 "from host-provided workspace folder paths (multi-root aware)"，维护 workspaceRoots[] + primaryRoot + currentRoot，resolvePathToRoot() 按路径长度排序处理嵌套根（apps/vscode/src/core/workspace/WorkspaceRootManager.ts:44-64,99-101,122-133）。
  • continue：直接取全部 folder（extensions/vscode/src/util/ideUtils.ts:68-75），协议层 getWorkspaceDirs: string[] 天然多根。
⇒ 这两份可以直接借形状（尤其"嵌套根按路径长度定归属"这条）。

3. 三个缺口的方案对照

3.1 多根 / .code-workspace / 视图关联

与我们的稿 B（单向 dsh⇒IDE）最相关的是 dsh-vs-sidebar，它把同一问题的反方向做全了：

  • 不重启 Host 的重新绑定：onDidChangeWorkspaceFolders 与 onDidChangeActiveTextEditor 都入队；rebindToWorkspace 明确"切根不杀 dsh 子进程"（extension.js:1067-1096,1516-1520）。
  • dsh 侧工作区注册表客户端：POST /api/workspace.list / workspace.create（ch2/workspaceClient.js:22-25,83-146）。
  • 会话↔工作区绑定状态机：unbound → matching → consent → creating → ensuring → bound，含缓存与 250ms 去抖；非自有 Host 需用户同意才注册工作区；"粘性根会话"复用该工作区最新 root 会话 ⇒ 防会话爆炸（context/workspaceBinding.js:23-33,136-147,176-217,242-364）。

⇒ 它回答的正是我们还没拍的 ②（多根时会话跑哪个根）与 ③（切工作区要不要顺带换会话）：根会话粘性复用是现成的第三条路，比"每次新建会话"省得多。

3.2 文件写根边界（三条路线，强度递增）

路线样本代价 / 局限
扩展侧拦工具参数 dsh-vscode 的 tool-write-guard.ts:17-23,34-52,81-84：识别 write/edit/str_replace_editor/apply_patch，按 dsh 解析相对路径的方式归一化到 cwd 下再校验；另有 dirty-file-guard.ts:5-13 写前拦未保存文档 便宜、立即可用；但覆盖不到 bash / 脚本写文件，是"检查点"而非围栏

这条最有价值：MiMo 那份自我承认的软链局限，正好佐证我们已拍的方向是对的 —— 我们计划覆盖 SandboxedFileSystem.checkedTarget（dsh-fs-sandbox/lib/index.js:153）并把多个根逐个交给官方 super.checkedTarget， 从而复用官方 containment（含 Windows 8.3 长短名 / 大小写身份回退，isPathUnder 未导出）。自己写词法判定就会重蹈 MiMo 那个洞。
旁证：opencode 是 ask/allow/deny + external_directory 围栏（tool/external-directory.ts:35-43）；continue 是"工作区外强制需批准"（core/tools/policies/fileAccess.ts:10-26）——两者都是权限降级，不是路径囚笼。

3.3 Host 生命周期 —— 修正：我们并不薄

上一轮口述的"这是我们最薄的一环"是错的（那是根据样本反推、没核我们自己的代码）。核对后：样本里被点名的机制我们基本都有：
  • 拥有者记录（= dsh-vs-sidebar 的 dsh-instances.json owner 标记）：common/dshHostRunOwnership.ts 的 owner-<runId>.json，带 appPid / hostPid / instanceId / profile / startedAt / files。
  • 只回收"拥有者已死或就是自己"（= "绝不跨窗口接管"）：planOrphanHosts（dshHostRunOwnership.ts:115-138）——拥有者活着 ⇒ 一律不动，且有 grace 保护期。
  • 结束整棵进程树（= dsh-vscode 的 taskkill /T）：dshHostReaper.ts:88-98。
  • 启动锁（= dsh-vsc-integration 的 install lock）：DshHostLeaseStore.acquireStartLock（dshHostSupervisor.ts:904）。
  • 客户端计数自退（= dsh-vsc 的 clientCount 引用计数关停）：桥插件里 clients.size ⇒ 无 IDE 客户端即起空闲计时器（dsh-plugins/vssaros-bridge/lib/index.js:125-140,274）。
  • 端口复用：dshHostPortManager.ts 的 host-port.json（这也是缓存命中率调查的修复）。

因此真正剩下的缺口只有一条：我们的空闲自退 TTL 是 12 小时（DSH_HOST_IDLE_TTL_MS），而 IDE 崩掉后 Host 仍会攥着会话写租约到 TTL 到期； 样本 dsh-vs-sidebar 用 心跳文件 + Host 侧看门狗（DSH_VSCODE_HEARTBEAT_PATH）把这段缩到分钟级。 未做 建议

4. 本轮已执行

环回地址强制绕代理（electron-main/dshRuntimeManager.ts 的 ensureLoopbackNoProxy + 接进 sanitizedEnv）—— 这是对照里唯一"我们确实缺、且改动面小"的一条。
  • 为什么：Host 的插件页经 http://127.0.0.1:<port> 加载，用户环境若配了系统代理而 NO_PROXY 没排除环回 ⇒ 页面被劫持（白屏 / /x/... 全 404），而日志里看不出是代理干的。样本 deepseek-harness-for-vscode 专门为此强制了这一条。
  • 语义：追加而非覆盖（用户条目原样保留）；NO_PROXY=* 视为已满足；★ 把 NO_PROXY / no_proxy 两个写法合并成一个键（Windows 环境变量名大小写不敏感，两个键并存会让"谁生效"说不清）。
  • 验证：新增 test/node/dshHostEnv.test.ts 7/7 通过；反向突变 7/7 变红（其中"幂等"那条第一版是假守卫——只比"两次相等"，摘掉整段追加逻辑仍然绿 ⇒ 已补钉期望值）；--common 回归 607 passing 与基线一致；tsgo exit 0。
