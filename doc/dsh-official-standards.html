以下是官方成文纪律的逐条镜像（编号对应原文行号），标注 已对齐我们无等价物口径冲突：

#官方纪律（原文出处）VsSaros 现状
L5导出形态：服务包 default-export 服务类；函数插件 named-export name/inject/Config/apply 且无 default export。混用会让 Loader 丢弃函数插件（有 postmortem：0001-acp-default-export-drops-inject）已对齐（dsh-plugins 全部 named-export）
L6可选服务用 ctx.get(name)；ctx.<name> 只留给已声明的 inject——属性代理是拓扑敏感的，ctx.get 读全局服务表已对齐（我们用 ctx.inject([...], scope) 动态声明，等价；曾踩过 try{ctx.foo}catch{} 恒抛的坑）
L7产品可见插件必须有 REAL-composition 测试：走 Loader 启动真实 cordis.yml，禁止纯手搭 ctx.plugin(...)；断言模型可见/持久化/用户可见输出我们缺这一层（守卫多为静态扫描 + 真机探针，无"真组合"测试）
L8initiator 私有链「先 derive 再 capture」：编排入口恢复 Agent、derive agent.session，不为藏参数把 Session 放宽成 Context无等价物（我们的 agents 插件未涉此层）
L9一个异步操作 = 一个生命周期控制器/事务；readiness/cancellation/disposal 分离需要独立 owner 或 settlement 点原则一致（workflow 引擎的事务边界）
L10服务定义为所有现存消费者设计；反向坏味道：公共方法只有一个内部调用者 ⇒ 改私有 capability 闭包vssarosBridge 符合（多个消费者）
L13模型可见契约从模型视角写：prompt/工具 schema/结果不含 UI、传输、实现词汇；稳定的模型可见文本要逐字钉住（快照/e2e）已对齐（工具 description 口径）
L14决策在执行点强制：schema 省略、prompt 过滤、facade 都不是强制——要经 executor 测试拒绝路径部分对齐（审批闸在组合层 ✓；但路径围栏等靠插件自觉）
L15状态只在 commit 点发布；派生缓存/prompt/UI 回声从单一权威源派生已对齐（kanban 指纹 CAS + 原子写）
L16对完整结果施加边界：byte/token/item/time 上限在含包装与元数据的完整值已知处强制；测试微小与精确边界、多字节截断部分（memory 双层截断口径互相掩盖是已知偏差）
L17注册表贡献必须证明 disposal：HMR-safety 测试——dispose fiber 后观察到移除缺（我们靠 ctx.effect 自觉，无 dispose 断言）
L18spec 并发运行于 forked worker：端口/路径/子进程都要有 teardown 归属；"只在单独跑时过"的 spec 是 spec 缺陷部分（真机探针有孤儿 Chrome 假回归的前科）
L24-25src/types.ts 只放类型；测试在包级 tests/ 而非 src/__tests__/已对齐

§2 官方纪律镜像（客户端，packages/client/AGENTS.md）

2.1 槽位与 props 纪律（7 条）

#官方纪律VsSaros 现状
1唯一 API：ctx.slots.register({name, children?, store?, inject?}, Component)；没有单独的槽位定义调用；只有壳渲染 'root'已对齐（chat-surface 等全部走 register）
2children = 声明＋授权：渲染未声明的槽、或声明别人已声明的槽，load 期即报错；槽名镜像组合路径 <domain>.<entry>.<hole>已对齐（我们只 register 进官方已声明的槽，不自声明）
4hook 只有框架造的五个席位（useSession/useSessions/useWorkspaces/useStore/renderSlot）＋ inject hooks 舱绑定的 use<Name>；业务代码永不自制 hook已对齐
6store 必须工厂化：createXXXStore() 导出工厂，模块级单例禁止；生产代码只在 apply 里调工厂已对齐（chat-surface chunk 无模块级单例）
7inject 只返回 plain data + callbacks；私有响应式事实走保留的 hooks 舱；插件只能碰 inject 声明过的依赖已对齐

2.2 导出纪律（3 条红线）

  • UI 插件除 apply/inject/Config ＋ 类型外不导出任何值；新增值导出需要 user sign-off
  • 同包测试直接相对路径 import 内部文件，永不为测试扩公共 API
  • 功能插件禁止 runtime-import 或 re-export 另一个功能插件的值，禁止用 dsh.client.external 拿别的功能插件；行为跨包走 cordis 服务，UI 跨包走 slots——都不适用就停下来升级讨论，不许加导出解围。这条与我们「插件间无 npm 级互相依赖」的现状完全一致

2.3 组件永远看不到 ctx

ctx 只属于 apply 世界；组件经「四份 props」（PropsRuntime & PropsRenderSlots & PropsStore & inject face）拿一切，不读 React context、不 import 服务类。我们的 chat-surface chunk 遵守。

2.4 依赖声明与模块图（重要澄清）

官方明确：dsh.client.inject 的包名边是 informational only（preflight 展示、HMR diff），不参与激活排序。激活顺序只由 cordis fiber 的服务 inject 等待决定。三种「依赖」不可混用：cordis 服务 inject（运行时、缺则 PENDING 无超时、可替换、允许环）vs 模块图 external（物化时、缺则当场抛、唯一供应者、禁环）vs dsh.client.inject（纯信息）。
  • client 包必须 cordis 同时进 peerDependencies 与 devDependencies（版本一致）
  • 浏览器/类型关系只进 devDependencies；Host 值 import 需分类导出（safeHostDependencyExports / peerRequiredHostExports）
  • files 必须闭合发布载荷（publint 检查）——与我们「漏 files 会加载即失败」的教训同源
  • 基线 external（React、Cordis、client/store、ui-primitives、ui-slots、ui-dockkit）隐式，禁止在清单里重复声明

2.5 新插件包三注册面

缺一不可（各缺一个会在不同的更晚时点炸）：① tsconfig.client.json 聚合 references；② web-app/cordis.patch.yml 的 dsh.client 行；③ web-app/package.json 依赖。我们的单插件分发形态只涉及 ② 的等价物（patch insert）。

2.6 测试与检查阶梯

  • client 源码包在 per-file 100% coverage 门内；防御分支要 /* v8 ignore -- 真理由 */
  • 组件 spec 用真实 props 或驱动 fixture，断言用户可见行为（不断言 class 名/hook 内部/渲染次数）
  • 检查阶梯：test:gui（秒级内循环）→ DSH_SNAPSHOT=replay test:web（改动会改变装配输出时）→ PR 前 dsh-pre-push-checks 选最窄检查集——与我们「验证范围按改动面选」的反馈记忆同向

版本 bump 纪律 / files 守卫官方（L67 + plugin add no-op 语义）完全同源

§5 结论与行动项

结论：dsh 官方源码（在场部分）自身执行纪律严格，且 packages/AGENTS.md 就是一份成文的官方设计标准。我们的 A–I 合规基准大方向与官方一致；两处需要修正认知：①「slots 禁区」不是官方禁令而是宿主裁剪的经验结论；②「owns 单写者」是我们自加的机制，官方对应物是 persistence-catalog。
