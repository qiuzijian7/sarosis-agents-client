工作台 ⇄ 聊天框 交互关联 · 调研与优化方案

对象：VsSaros（VS Code fork）+ dsh 宿主上的四个工作台（知识库 / 记忆库 / 代码库 / 媒体库）与 Agent 聊天框。 本稿回答三件事：① 现在有哪些交互通道、缺什么；② 开源项目怎么做（含优缺点对比）；③ 我们该按什么次序补。

结论速览
  • 本仓底层 seam 全都已具备：dsh 官方的 @ 触发源注册（ctx.inputTriggers.registerSource）、引用 codec、dsh-resource:// 活值资源、IDE 页面桥 + 插入引用推送通道、用户消息富化标签。
  • 但四个工作台一个都没接上去：现在只有两条互不相干的通路 ——「文件/选区 → 聊天」与「Agent 用工具读写知识库」。
  • 缺的三件事：① 工作台条目 → 聊天的引用入口；② 聊天 → 工作台的定位回跳；③ 引用在发送时"变成什么"的统一语义（指针 / 内容 / 快照）。
  • 生态的取舍很一致：入口用 @ 扩展源 + 知识源作用域；出口用引用回跳；内容默认走"指针 + 工具检索"而不是"把正文塞进去"。

3. 开源方案调研

3.1 显式引用体系（@ / #）—— 已高度收敛的共识

项目机制值得抄的点
VS Code Copilot Chat #-mention（files / folders / symbols / tools / terminal / source control 等）+ Add Context 选择器 + 拖放 + #codebase；@ 是聊天参与者，扩展可贡献 显式引用与隐式工作区索引并存；响应侧另有 stream.reference / filetree / button / anchor —— 让回答能点回源头
Cursor @：Files & Folders / Terminals / Chats / Git diffs（@Commit / @Branch）/ Browser 官方口径"知道是哪些文件才用 @，不知道就别用，Agent 自己会找"；上下文环 + 自动压缩把预算做成可见 UI
Zed @：文件 / 目录 / 符号 / 历史线程 / 技能 / 诊断 / 分支 diff / URL；选区快捷键；粘贴代码自动转成带文件上下文的 @mention；/compact 写侧闭环：Review Changes 多缓冲 + 逐 hunk 接受 + Checkpoint + Follow（编辑区跟随 agent 跳文件）
Continue context providers 注册进 @ 菜单（@File / @Code / @Diff / @Tree / @Problems / @Repo-Map / @HTTP）；自定义走 @HTTP（POST → ContextItem{name,description,content}）或 MCP 已废弃 @Codebase / @Folder / @Docs，官方推荐统一改走 MCP ⇒ "每家自己造引用类型"不可持续
Roo Code / Cline @file / @folder / @problems / @terminal / @url / @git-changes 候选由文件系统事件驱动实时刷新；踩过"被引用文件正文里的 @ 误触发解析"的坑 ⇒ 解析只作用于用户输入层
共性：生态收敛为「@ = 参与者/源，# 或 @文件名 = 上下文项」；上下文项可拖放、可粘贴自动识别、可点回源头；并且必须有上下文预算的可见性。

3.2 知识源作为一等公民

项目机制对我们的启发
Open WebUI 两条接入：① 聊天里用 # 引用知识库；② 把知识库挂到模型上（作用域隔离）。两档检索：Focused Retrieval（默认 RAG） vs Full Context（全文注入每条消息） 最重要的教训：开 native function calling（现为默认）后，挂在模型上的知识库不会自动注入，模型必须自己调知识工具；官方解药是"在系统提示里点名要求用 list_knowledge / query_knowledge_files"。这正是我们 kb_overview 常驻注入与 kb_* 工具两条路的分工问题
Open WebUI 工具链 query_*（语义定位文档）→ grep_*（精确到行）→ view_file（行范围），回执带文件名 + 1-indexed 行号 与 kb_search(mode=fulltext) 同构；引用溯源要落到"文件+行"粒度才有用
Obsidian Copilot V4 已从"Chat + Vault QA 检索"整体转向 Agent + Projects / Skills；针对选中文本的 Quick Ask 是"选区 → 对话"的等价入口 "知识库插件内置一套 RAG 聊天"正在被"接 Agent"取代 ⇒ 与本仓"能力全部落 dsh 侧"的方向一致

3.3 引用即什么 —— 最值得做的取舍（三家口径完全不同，且都是深思熟虑的结果）

形态代表语义优点代价
指针 dsh 官方 dsh-file-reference README 原话：「选中候选绝不读取或附带文件内容；模型必须调用文件系统工具才能查看文件」 ⇒ 引用只是提示词里的 @path 文本 零 token 浪费、永不过期、KV Cache 友好 模型可能"声称看过了"却没真读 ⇒ 需提供方注入 FILE_REFERENCE_PROMPT 约束
发送时快照 dsh 官方 dsh-session-reference @[label](dsh-session:…)，在 agent/pre-step 校验并捕获快照进模型上下文 上下文可控且可审计；历史不被后续改动污染 需要一条 pre-step 校验/捕获链；引用失效会终止该轮（不是静默降级）
内容附件 VS Code Add to Chat / Continue ContextItem{content} / 本仓 addFileToChat 直接塞正文 模型一定能看到 大文件截断（本仓就是 100KB 静默截断）、token 不可控
两档可切 Open WebUI（Focused / Full）、Zed（/compact 自动压缩） 用户按文档大小选档 兼顾准确与成本 多一个用户要理解的开关（必须如实标注）
对知识库这一路，生态的答案是"指针 / 快照 + 工具检索"，不是"把笔记正文塞进去" —— 恰好我们的 kb_* 工具面已经很完整。

3.4 反向通道：工具、回跳、活值资源

机制代表要点
活值资源 dsh 官方 dsh-client-resources（最该用的一条） dsh-resource://<protocol>/… + ctx.resources.register({protocol, async *open(address,{signal}){…}}) + slot 组件的 useResource(address) + ctx.resources.pin()；失败是帧（{ok:false}）不是抛错，且是活值流。官方自己就用它承载"已打开 tab 的地址"
发送时捕获 dsh 官方 dsh-session-reference agent/pre-step 校验 + 快照捕获 ⇒ 引用能真正进入模型上下文
逐条双向 Zed Follow（编辑区自动跳到 agent 摸过的文件）+ Review Changes + Checkpoint ⇒「聊天 → 工作区」是双向、逐条的
协议标准化 MCP resources resources/list / read / templates/list / subscribe / listChanged，带 annotations{audience, priority, lastModified}。但规范明确 application-driven：UI 由宿主自定，客户端支持度参差不齐 ⇒ 不能假设"暴露成 MCP resource 就自动有引用 UI"
本仓现状 缺口 — 全仓（排除 node_modules）搜 resources/list|resources/read|listResources = 0 命中；MCP 只有 tools 那半边（dsh-plugins/vssaros-mcp 读 mcp.json，每台服务器一个 @deepseek-ai/dsh-mcp-client 组合行）⇒ "用 MCP resources 一把梭"在本仓目前不成立，工具面才是既有资产

扩展点真实契约能干什么

4. 优缺点对比（按机制范式）

范式代表实现优点缺点 / 风险适配度
A. @ 扩展源（注册新 source） VS Code participant、Continue providers、Roo mentions、dsh registerSource 与用户心智一致；可搜索 / 可下钻 / 可加图标；官方已支持第三方注册；候选可实时刷新 每个源要自己实现候选排序、缓存、失效；引用多了会挤爆上下文（需预算 UI） ★★★ 首选
B. 知识源"挂载 / 作用域" Open WebUI（挂到 model / # 引用）；本仓可做"会话级知识作用域 chip" 一次设定、多轮受益；天然做权限隔离 native function calling 下不自动注入（Open WebUI 实测）；作用域与工具参数容易分叉 ★★★ 配 A 用
C. 引用即指针（不读内容） dsh dsh-file-reference 的既有口径 零 token、永不过期、KV 友好 模型可能假装读过（需 prompt 约束）；用户体感"我引用了它却没看见内容" ★★ 默认档
D. 引用即发送时快照 dsh dsh-session-reference（agent/pre-step） 上下文可控、可审计；历史不被污染；失效终止本轮而非静默降级 需要 pre-step 链；实现比 C 重 ★★ 显式开关
E. 内容附件（现有 addToChat） VS Code Add to Chat；本仓 addFileToChat（100KB 截断） 实现最省；模型一定看得到 token 不可控；截断静默；不适合"整库" ★ 单篇短笔记
F. 工具检索（agent 主动查） 本仓 kb_* 全套；Open WebUI 的 query → grep → view_file 最省上下文；可溯源到"文件 + 行"；已有资产 模型不一定主动调（需系统提示点名）；每轮多一次往返 ★★★ 已有
G. 聊天 → 工作台回跳 VS Code stream.reference/filetree/button；Zed Follow；dsh openModulePage / openFile 闭环感最强，引用才有价值 本仓 chat-only 隐藏右栏 ⇒ 必须走 IDE；route 不支持查询串 ⇒ 要加命令 ★★★ 缺口最大
H. MCP resources 统一暴露 MCP spec（resources/* + annotations） 协议标准化、可跨客户端复用、订阅能力现成 规范 application-driven，客户端支持不齐；本仓 MCP 只有 tools 半边，等于要先补上游 ★ 长期方向
取舍一句话：A + B + F 做"进入上下文的入口"，G 做"出来的回跳"，C / D 做成用户可见的一个开关； H 只作为将来对外复用的形状参考，不作为本期依赖。
