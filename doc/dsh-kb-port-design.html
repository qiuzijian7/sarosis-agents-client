0. 一句话与两条订正

知识库不需要"移植"了 —— dsh-plugins/vssaros-kb（@vssaros/dsh-kb）已是完整 dsh 插件：自托管页 /x/kb/、 活动栏容器 agentStudio.knowledgeBase、12 个工具、与 IDE 侧同一份 vault 数据面、写侧已挂审批闸 ✓。 剩下的是三块未搬（原因各不相同）＋两块搬不动或不该搬。本方案按"改动的可控性 × 收益"排成三期，并给出每期的证据要求。

★ 订正我上一轮的两条判断（都是"读源码才看清"的）
  1. 订正 ①（结论不变，原因变了）：我说 kb_suggest_links "缺整条 embedding 链" —— 读侧不成立 ✗。 source 原话（kbVectorIndex.ts:420）："纯本地向量运算（不需要 embedding provider）" ✓ （findSimilarDocs = 双方块两两 cosine 取 max ✓ 纯数学）。真正的阻塞是向量索引只活在内存里： rebuildVectorIndex()（knowledgeBaseView.ts:3237-3276）只调 buildVectorIndex()， 没有任何落盘调用 ✗；本机实测两个数据根下都不存在 .kbrag.json / .kvindex ✓（见 §2）。 ⇒ 结论仍是"当前搬不了"，但出路有两条，其中一条只需 IDE 侧加一步落盘。
  2. 订正 ②（新发现的既有缺陷）：.kbkernel.json 在真实机器上有两种形态 ✓（实测）： 生产库是元数据形态（uri/title/type/created/…/text），dev 库是 FTS 形态（uri/name/path/section/…/text）。 dsh 侧 normalizeDoc 只按元数据形态取 title/type/created ⇒ 在 FTS 形态的库上 标题退化成文件名、type/created 全丢 ✗（页面与 kb_search 的类型过滤都受影响）。 ⇒ 第 1 期顺手修（一行回退），属"发现的真实缺陷"，不是新需求。

由盘点得到的三条硬结论
  1. 正文检索有现成数据源 ✓：.kbkernel.json 里就有 text ⇒ 不必扫盘、不必引新依赖，口径还能与 IDE 侧索引器天然一致（同一份 text ✓）。
  2. 语义那半没有数据源 ✗：向量不落盘 ⇒ 要么改 IDE 侧（构建后落盘），要么 dsh 侧自己算 embedding。两条都不是"在 dsh 插件里加个工具"的量级。
  3. 大库后端是另一条路 ◻：kb.db 存在时正文在 FTS5 里，读它不是"顺手"，要先有 >2000 docs 的夹具才能验。

4. 三期方案

4.1 第 1 期：正文检索（kb_search 加 mode）+ 双形态兼容 —— 已落地 2026-10-12（见 §8）

工具形态（决策点 D1）：给同一个 kb_search 加 mode 参数，而不是新开工具名。

kb_search({ query, mode?, type?, tag?, limit?, vaultId? })
  mode: 'index'    // 缺省 = 现状行为（标题 / 标签 / 类型 / uri 匹配）⇒ 零行为改变 ✓
      | 'fulltext' // 正文 BM25（本期新增）
  // 明确不支持 'semantic'（IDE 侧枚举里那个）：显式报错并指路，绝不静默退化成 fulltext ✗
  • 理由：IDE 侧同名工具本身就是"同名不同义"的分叉点（已登记在 toolOwnership.ts）✓； 用一个入口 + 一个参数描述两种检索，模型只看描述就能选，比多一个 kb_grep 少一份漂移面。
  • 缺省必须是 index：现有 12 个工具的行为、tools-snapshot、探针全部不动 ✓（B1 那次"缺省 = 现状"的同一纪律）。

实现落点（全部在 dsh-plugins/vssaros-kb/，不碰 src/）

文件内容性质
lib/core/kbFulltext.js 新 tokenize(text) —— 逐字照 kbIndex.ts:369-386：小写 → ASCII 词 /[a-z0-9][a-z0-9_'-]*/g + CJK / 假名 /[㐀-䶿一-鿿豈-﫿぀-ヾ゠-ヿㇰ-ㇿ㆐-㆟]+/g 单字 + 相邻二元；
buildPostings(docs) → {postings, avgLen, totalDocs}（length 取 kernel 里的值，缺则现算）；
searchFulltext(index, query, {limit}) —— BM25 k1=1.2, b=0.75、 idf = ln((N-n+0.5)/(n+0.5)+1)、gatherTerms 前缀展开（仅 ASCII 且长度 ≥2）、 文件名命中 +10 / 标签命中 +5、matchedBy、snippet（命中位置前后 40/80 窗口，与 kbIndex.ts:739-752 逐字同形） 		纯函数、零 I/O、零 dsh 依赖 ✓（与 core/kb.js 同层，便于单测与探针直取）
lib/store.js 扩展 新增 loadFulltextSource(vaultDir)：① 读 .kbkernel.json 的 docs[].text（首选 ✓ 实测两形态都有）； ② 缺 text（老索引）⇒ 回退读 .ftindex.json；③ 都缺 ⇒ 抛"该库还没建索引"的可读指路（不静默空 ✗）； 返回时一并带上 source 与 indexedAt（kernel 文件 mtime） I/O 层，沿用既有围栏与 MAX_SCAN 保护
lib/core/kb.js 小修 normalizeDoc 兼容双形态：title 缺失时用 name（去掉 .md）兜底； section 存在时如实带出（不硬塞进 type ✗ —— 那是另一个字段，猜就是编） 一行回退，修订正 ② ✓
lib/index.js 改动 kb_search 加 mode 分支 + 描述改写（写清 dsh 侧支持哪两个取值、semantic 不支持、正文来自索引快照）； output.render 保持同形（结果仍回报 count / items，fulltext 额外带 snippet / score / matchedBy） 只读工具 ⇒ 不过闸 ✓（与现状一致）
package.json / tools-snapshot.json 版本 bump（读到的当前值 0.2.14 ⇒ 0.2.15，落笔前重读，并发会话可能在动）； files 加 lib/core/kbFulltext.js（漏了 = 装出来的包缺文件 ⇒ 插件加载即失败 ✗ 真出过）；跑 tools-snapshot.mjs --write 纪律项，见 §5

诚实边界（必须写进工具描述与 render）

  • 正文来自索引快照（.kbkernel.json），不是实时读盘 ⇒ 回报 source + indexedAt，让模型 / 用户能判断新鲜度 ✓（页面缓存那套"只影响计数、不影响索引条目"的诚实口径同理）。
  • 结果条数 / 扫描条数封顶时如实标 truncated（照 codebase_schema 那次的做法 ✓，不静默截断 ✗）。
  • 空查询 ⇒ 明确报错；库没有索引 ⇒ 指路"先在 IDE 里打开一次知识库 / 用 kb_topic_overviews 看结构"。

4.5 挂起：语义检索与 kb_suggest_links（两条出路，都需外部前提）

出路要做什么代价 / 归属
(a) 让向量索引落盘 IDE 侧在构建完成后调 exportBinaryToDisk(<vault>/.kvindex)（API 已存在 ✓） ⇒ dsh 侧读 Float32 + 纯 cosine 即可实现 kb_suggest_links 的完整语义（含默认 minScore 0.72、doc 级取块 max） 改 src/（知识库视图）+ 新增盘上产物格式承诺（版本 / 尺寸 / 损坏处理）⇒ 产品决策；dsh 侧只读，风险低 ✓
(b) dsh 侧自带 embedding 插件里配 Provider（BYOK）+ 自己分块 / 向量化 / 持久化 等于在 dsh 侧重建一条 RAG 链（provider 配置、配额、缓存、维度变更…）⇒ 体量与"语义检索"整块相当 ✗
(c) 结构版"关联建议" 不看向量，用 tags / 标题重合 / 正文 wikilink 给候选 不建议现在做：语义变了（那是"文本相似"的近似冒充）⇒ 违背"不许看起来答了其实答的是别人" ✓

8.1 ★ 一处设计订正（实测促成）：fulltext 是「每库一份索引」，不是「跨库合成一份」

第一版把选中的多个 vault 的正文合成一个索引再检索 —— 探针立刻报红，查出的真因是： BM25 的 N（文档总数）与 avgLen 是全局量 ⇒ 同一篇笔记的分数会随 "这次同时选了哪些别的库"变化 ✗，而 IDE 侧一次只索引当前打开的那个库 ⇒ 两侧分数对不上， 且两边都不报错（本方案开头要防的正是这一类）。 改成每库一份后：单库检索（或 vaultId 限定）的分数与 IDE 逐条相同 ✓ （黄金表就是这么钉的），跨库合并时分数不可互相比较 —— 这条写在回执里如实告知 ✓。

8.2 ★ 顺手修掉一个真·数据丢失缺陷（回归 p3-08 时抓到，非本期引入）

kb_organize 的备份目录名时间戳精度是分钟（stampOf 取 12 位，照真源 ✓）⇒ 同一分钟内的多次调用共用同一个备份目录。收尾逻辑原先只判「这次没放东西就收掉目录」⇒ 一次 只建目录（无备份需求）的调用会把上一次调用写下的唯一还原点整个删掉 ✗✗。 实测复现（固定 now 两次调用）：第一次删除入备份 ✓ → 紧接着那次调用后备份目录消失 ✗； 跨分钟则正常 ✓（所以它是时间相关的，靠"顺手跑一遍"看不出来）。 为什么这是最坏一档：dsh 侧没有聊天页签的 undoAll ⇒ 那个备份目录是唯一还原点，删掉 = 已执行的删除/移动不可挽回 ✗。 修法：判据从「这次没放东西」改成「这个目录是我这次建的」（backupDirExisted）✓。 守卫：p3-08 新增 1 条（用固定 now 保证确定性），反向突变 2/2 命中 （新守卫 + 原有「删除入备份」断言同时变红 ✓）。
