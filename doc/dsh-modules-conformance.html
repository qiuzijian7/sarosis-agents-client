§1 评估基准（dsh 插件标准的官方来源）

以下"规范"不是经验判断，全部来自 dsh 运行时自带的官方文本与运行期强制：

#规范出处
A会话日志是唯一真源：模型看到的一切必须能从已提交的会话事件重建；插件内存只是派生缓存dsh-agent-preset/skills/cordis-plugin-development/references/practices.md P1
Bprompt 文本只经 systemPrompt.section()/variable()/context()；禁止用 system-prompt/assemble waterfall 加/删文本同上 P4 / P17 / P18
Cper-session 状态用 ctx.sessionProjections 单元（纯 apply、忽略的事件返回同一引用、stateVersion）；不得订阅 session/event 自行重扫；不得新增自定义事件类型同上 P21 / P26
D最弱机制优先：tools.restrict()（只删）→ tools.guard()（只拒）→ waterfall → system-prompt/assemble（最强）。审批由组合层的 tools/pre-execute 返回 ask（→ 用户确认）给出，不是工具自带同上 P4 / Stability 17；dsh-tools 类型
EUI：React + slot；不 iframe 自服务页；用 --dsw-alias-* token；不 import 其它 Harness 客户端包；读会话数据用 selector hook；Chat 行用 uiConversation.events.register同上 P6 / UI 31-38
F性能：不轮询 agent/status；timer 唤醒用 agent.followup() 而非 inject；装配期别做重活同上 P26-29
G打包：files 覆盖运行时文件齐全；peerDependencies 与运行时装机版本兼容；cordis.patch.yml 只 insert 不覆盖他人cordis-plugin-development SKILL.md；dsh-app-boot 类型
H可诊断：激活失败 / 配置缺失要留痕（日志 / roster broken 行 / 页面诊断）preset registry 的 diagnostic() 先例
I数据落点与"启动时快照"口径一致（IDE 注入的目录、数据根）本仓启动链路

§2 总览结论

§3 逐插件评估

3.1 @vssaros/dsh-kb 知识库 合规

5 个只读/工具（kb_list/kb_search/kb_read/kb_topic_overviews/kb_feishu_sync，lib/index.js:497-770）+ 自托管页 /x/kb（服务端渲染）。数据只读 <数据根>/knowledge-base/，带路径围栏（lib/store.js:139-157）。打包只 insert。

唯一实质风险：kb_feishu_sync 的 apply:true 是有副作用的远端写（lib/index.js:739-747），目前只有默认 dry-run 兜底——模型一句话就能触发远端写（§4-1）。

3.2 @vssaros/dsh-codebase 合规2 处可收

5 个工具（codebase_overview/search/deps/hotspots/self_index）+ 页 /x/codebase + 客户端卡（tool.call.toolview，按工具名，priority -10）。读 <workspace>/.codebase-memory/；结构化数据经 codebase_overview_json: 文本行出结果——模型可见内容可重放（✅A）。轻/重分层 + mtime 缓存做得对。

两处可收：① 客户端卡的错误色用 var(--vscode-errorForeground,…)（lib/client.js:95）而非 --dsw-alias-*——这张卡跑在 dsh 原生界面里，该变量不存在，只能靠回退色（§4-2）。② 重路径 gunzipSync+JSON.parse 129MB 同步跑在 Host 主线程（lib/store.js:146-159），期间同进程其它请求停摆（§4-2 性能项）。

3.3 @vssaros/dsh-memory 记忆 合规

本评估里唯一往 prompt 注入的插件：prompt section vssaros-memory-working，order 从中央表 getSectionOrder('DEPLOYMENT_PERSONA_PREFIX')+100 取，text 是函数提供者（装配时零 I/O 读快照），完全走正门（✅B）。5 个工具经网关（单写者），读/写都有预算与失败留痕。

可重放性（规则 A）：已核实 ✅——dsh 会把每步/每序列渲染后的 prompt 写成 system/message 事件（dsh-agent-loop/lib/index.js:1052-1060 的 systemPrompt.project()），所以"当时注入的记忆文本"能从日志精确重建。

可收：memory_remember 写操作无审批闸（§4-1）；双层截断口径（插件 8000 字符 vs 网关 1024 token）会互相掩盖。

3.4 @vssaros/dsh-kanban 看板 合规

10 个工具（2 只读声明 isConcurrencySafe）+ 页 /x/kanban + 客户端卡（keyed 槽按 10 个自有工具名，priority -10，token 用 --dsw-alias-* 带回退 ✅）。写落 <数据根>/taskboard.json：同进程串行队列 + 文件锁（心跳 + pid 破门）+ 指纹 CAS + 原子写——与 IDE 同一把锁。

可收：8 个写工具无审批闸（§4-1）；无 Config schema（错型到用到才炸）。

注：看板相关 e2e 红（already-installed）是测试假设过期（"随包自动安装"已装上，用例仍假设未安装），不是产品缺陷。

3.5 @vssaros/dsh-workflow 工作流 合规2 处可收

4 个工具（workflow_update/list/get/engine_status；写只动 3 个元信息字段、保留未知字段 ✅）+ 页 /x/workflow + 客户端卡。读 <数据根>/workflows/，路径穿越防护在（store.js:35-41）。

两处可收：① 客户端卡用 --vscode-errorForeground（lib/client.js:96）——与 codebase 同病（§4-2）；② 每次页面渲染都 spawn 一个真 worker 自证再 terminate（index.js:571），刷新成本偏高（§4-2 性能项）。另：webServer/connection 是硬依赖（headless profile 会整包 pending，kanban 的注释里写过这个坑，这里没跟上）。

3.6 @vssaros/dsh-dashboard（附） 合规

纯只读聚合：2 个工具 + 页 /x/dashboard。教科书式的投影消费面——不订阅 session/event，只 sessionProjections.stateOf(session, unit) 现读（✅C 的最佳示范）；只读 dsh 自己的 session_projcache 缓存目录。可收项：单会话读取 O(n)→O(1)、上限口径统一（API 1000 vs 工具 200）、SUPPORTED_CACHE_VERSION 硬钉的降级策略。

§4 横向发现

4-1 写工具没有审批闸（唯一实质风险，需真机验证后再定）

dsh 的审批不是工具自带，而是由组合层在 tools/pre-execute 返回 ask（→ 用户确认）给出（practices.md Stability 17；dsh-tools 类型）。当前 profile（cordis.patch.yml）与我们所有插件都没有挂这条策略，而官方 preset 也没挂（standard.patch.yml 无 approval 行）。受影响工具：kanban_create/update/complete/block/unblock/comment/link/heartbeat、workflow_update、memory_remember、kb_feishu_sync(apply:true)。下一步：真机确认权限预设（composer 的 permission 档）对自定义写工具的默认行为；若默认放行，在 VsSaros 组合层挂一条 tools/pre-execute 审批策略（一条规则覆盖全部写工具），比逐插件改干净。

4-2 客户端卡的 token 口径不齐（dsh 原生界面内的偏差）

跑在 dsh 原生聊天页里的工具卡必须用 --dsw-alias-*：kanban ✅（带回退）、codebase ❌（lib/client.js:95）、workflow ❌（lib/client.js:96）。修法统一：var(--dsw-alias-state-error-primary, var(--vscode-errorForeground, #f48771))（双层回退）。

4-3 会被误读为偏差的"正确选择"（澄清）

  • 自托管 HTML 页用 --vscode-* 是对的：kb / memory / kanban / workflow / dashboard 的 /x/* 页宿主在 VsSaros 的 WebContentsView（IDE 侧托管），不是 dsh 原生 web 界面；规范的 --dsw-alias-* 约束的是 dsh 原生 UI（slot/React 组件）。若要这些页也进 dsh 原生壳，才需要换 token。
  • 无 React 客户端半 ≠ 违规：kb / memory / dashboard 没有 dsh 原生 UI 需求（工具结果走文本回执）；有卡需求的（codebase/kanban/workflow）都有 React 客户端半。
  • dsh.client 是官方字段名（不是 dsh.bundle.client）——codebase/kanban/workflow 的写法正确。

4-4 记忆注入的可重放性（关键澄清）

memory 往 prompt 注入的快照文本是否"能从日志重建"，取决于 dsh 是否把装配结果落盘——已核实落盘：systemPrompt.project() 每步/每请求序列把渲染后的 prompt 写成 system/message 事件（dsh-agent-loop/lib/index.js:1052-1060）。故规则 A 成立 ✅。

§6 存疑与边界

  • 权限预设对自定义写工具的默认行为未在真机确认（§4-1 的"下一步"）。
  • 评估环境噪声：本轮有并行会话在改 dsh-plugins/ 多个包（chat-surface 已被推到 0.2.55、kanban 到 0.4.5），e2e 的看板相关红是测试假设过期（"随包自动安装"已装上）而非产品缺陷；报告按源码与运行时类型评估，未受环境影响。
  • IDE 侧数据契约（knowledgeStorage.ts、网关 mem::* 参数形态）按插件自述的真源引用采信，未逐行复核 IDE 源码。
  • requestActionConsent 是 IDE 侧能力层的同意闸（IIdeCapabilityEnv），不是 dsh 的审批 API——评估按 dsh 的组合层模型（tools/pre-execute → ask）表述。
