dsh Dashboard → 可编排的 homepage

目标：把 dsh 侧的自托管页 /x/dashboard/（插件 @vssaros/dsh-dashboard）从 一张写死的服务端渲染长页，改成 用户可以自由增删 / 拖动 / 调跨度的组件化首页。
本稿是设计与执行方案（含可交互原型）。尚未改任何生产代码 —— 下方「要你拍板的三件事」定了我就开工。

一、现状：页面已经"半组件化"了，只是没被拆开

读完 dsh-plugins/vssaros-dashboard/lib/index.js 的 renderPage()（L311–385），现有页面其实是 5 块写死顺序的 HTML：

#现有块出处改造后的组件
1标题 + 口径说明（"两者数字不必相同"）renderPage L363–365固定页头（不可移除，锚点挂了它）
2日期范围切换（today / 7d / 30d / all）L366–368工具条（不进网格：它是全局作用域，不是一张卡）
3KPI 卡片组（5 张固定 + 最多 9 张条件出现）L369–375kpi（也可拆成 kpi.tokens / kpi.activity 两张）
4诊断行（token 明细 / 数据目录 / 工具 / live 服务）L376diag（默认关闭：它主要是给排障看的）
5会话明细列表（50 条上限 + 截断提示）L377–382sessions
结论：不需要"重写"，需要把已有块抽成组件 + 加一个布局层。这也是本方案 P1 敢承诺"视觉零变化、等价重构"的底气。

二、三个决定性前提（都已查实，其中一条直接否掉一个方案）

① dsh 的 web 端口是 --port 0 ⇒ localStorage 存不住布局

dshCli.ts:21    return [bin, ...launcher, '--no-open', '--port', '0'];

--port 0 = 每次启动由系统分配随机空闲端口（真机日志里见过 http://127.0.0.1:7313/?token=…）。 而 localStorage 按 origin（scheme+host+port）隔离 ⇒ 下次启动端口一变，布局就是空的 ✗。
⇒ 「布局存浏览器本地」这条路不成立，除非把端口固定（但 port 0 是**故意**的：避免多实例抢端口）。

② 页面桥是封闭命令集，没有通用 storage ⇒ 走 IDE 侧要扩协议

window.vssarosDsh（dshPageBridgeProtocol.ts，DSH_PAGE_BRIDGE_VERSION = 2）暴露的是 ping / openFile / reveal / notify / switchPreset / openSession / newChat / newSession / switchWorktree / openAgentMarket / sessionTitle / sessionPersona 这一组具名命令（DshPageCommand 联合类型 + validatePageCommand），没有任何 kv/storage 方法。 ⇒ 若把布局存回 IDE 的 storage，需要动协议：联合类型 + preload API + host 处理 + 校验 + 版本号，且纯浏览器打开时没有桥（必须另留回落）。

③ 仓库已有"谁能写数据根"的机制 —— 且它是被守卫钉死的决策

  • 唯一声明 owns 的是 kanban：vssaros-kanban/lib/store.js 自己 node:fs/promises 写 taskboard.json / boards.json（临时文件 + rename 原子写 + <file>.lock 独占创建）；
  • workflow 走共用的 lib/lock.js（acquireFileLock + atomicWriteFile，与 IDE 侧同一套协议）；
  • dshWriteOwnership.test.ts 把 声明集合钉死为 ['vssaros-kanban:taskboard.json+boards.json']，且"只读模块不许 import 写 API"是按 import 行判的。
⇒ 只要让 dashboard **落盘写布局**，就必须：新增 owns 声明 ＋ 显式改那条固定期望（= 一次"新增写者"的正式决策）＋ 用锁 + 原子写。 这是本方案里唯一需要你签字的技术动作。

三、设计

3.1 组件模型（服务端描述 + 服务端渲染，客户端只管布局）

// 一个组件 = 一个纯函数（与现有 renderPage 里的块一一对应 ⇒ 可平移）
{ id: 'kpi',            // 稳定 id：布局里引用的就是它
  title: '关键指标',
  desc: '会话 / turn / step / 耗时 / token',
  span: 4,              // 默认占几列（1–4）
  module: 'dashboard',  // 数据来源模块（一期只有 dashboard；见 P4）
  render(ctx) { … } }   // 返回 HTML 片段

数据全部由服务端一次查出（沿用现在那条"一次 readSessions + applyLiveSessions"）， 客户端**不再取数** ⇒ 拖拽/增删是纯布局操作，不会有"拖动时卡顿/串数"的问题 ✓。 （P4 的跨模块组件才需要按卡取数，那时再走 /x/dashboard/api/*。）

3.2 布局 schema（就是落盘的那份 JSON）

{
  "version": 1,
  "updatedAt": 1791814000000,
  "items": [
    { "id": "kpi",      "span": 4 },
    { "id": "sessions", "span": 4 }
  ]
}

版本号是给未来迁移用的；未知 id 一律忽略并保留在文件里（插件装卸导致组件暂时缺席时，不该把用户布局删掉）✓。

3.3 ★ 锚点解耦：机器可断言的东西必须与用户布局无关

这是本次改造最大的回归风险。 p3-09-dashboard-plugin.mjs 靠一批写死在页面里的属性断言： data-vssaros-page="dashboard"、data-vssaros-dashboard-sessions/active/live/turns/dir/tools/range/todo-*/waiting/retrying/running/queued/subagents…、 以及正文文案（构成（估算）、排队待发 0、来源 cache、scope="session-telemetry" …）。
一旦用户把"诊断"卡删掉、或把组件顺序拖乱，这些断言就会随机变红 ✗ —— 那等于探针在替用户的布局做假设。

对策（本方案的核心设计之一）：把这些锚点从"某张卡的内容"里抽出来，渲染成一个**永远存在、与布局无关**的隐藏元数据块：

<body data-vssaros-page="dashboard">
<div id="meta" hidden
     data-vssaros-dashboard-scope="session-telemetry"
     data-vssaros-dashboard-sessions="12" data-vssaros-dashboard-active="2"
     data-vssaros-dashboard-range="all" …></div>

⇒ 探针**不用改一行**；用户怎么编排都不影响它 ✓。只有当你想改**语义**时才动它。

六、风险与边界（每条都有对策）

  

    
#风险对策

    
①探针被用户布局搞红（最危险）§3.3 锚点解耦：meta 块永远存在、与布局无关 ⇒ p3-09 不用改

    
②坏布局 / 未知 id / 版本不认识一律回落默认并保留原文件；未知 id 只忽略、不删除（插件装卸后布局要能回来）

    
③多窗口同时编辑 ⇒ 后写覆盖沿用既有"最后写覆盖"口径（与 kanban/workflow 一致）；写入用锁 + 原子写，避免半截 JSON

    
④插件要读数据根（现在只读 DSH_HOME 的投影缓存）新引入 dataRootOf(config) —— ⚠ check-host-config 有一条"dataRootOf 实现 7 份同形"的契约，新增第 8 份必须与其余**逐字节同形**（否则它会红）

    
⑤拖拽与页面滚动冲突 / 触控板手势只在编辑态且按在 ⠿ 上才 draggable=true；键盘可达性用 ◀ ▶ 与"上移/下移"按钮兜底

    
⑥组件数据读失败（缓存目录缺失/坏文件）按卡降级：卡内显示原因，整页仍 200（沿用现有 missing/truncated/errors 的"如实说"口径）

    
⑦iframe 卡（若做）重复外壳、双重滚动默认不放；如做，iframe 卡改用"片段路由 + 无外壳"约定（需各模块配合）
