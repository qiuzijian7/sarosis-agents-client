SuperAgent 框架 v2 · 设计细则

以 superagent 的工单流水线为基础框架：四个输入源进入同一条准入与评估链路；Router 在接单后组建任务团队（查找或新建 bot），用户同意后才分发；每个 worker 是一个 VsSaros bot；每个 worker 结束时把执行证据交给记忆系统沉淀技能；整个任务结束后沉淀可复用的团队工作流，并可导出到外部工作流格式。本文状态：前 14 节是 2026-11-04 的设计基线，各节末尾标注实际落地情况；15.0 是现状（逐版本增量，以此为准）；15.1–17 是 2026-11-06 对照 0.1.55 的复核，作为历史快照保留，其中已完成的遗留项已移入 15.0。

1目标与相对现状的变化

现有的团队代码（0.1.31）是一条旁路：主会话直接派活给 bot，不产生 Trigger、不过 Policy 准入、不建工单、不经 Executor、结果也不回到原来源。v2 的核心是把团队并回工单主线，让团队成为工单的执行方式，而不是另一套系统。

四条不变的约束（沿用 superagent 的原则）
  1. 判断交给模型，护栏由代码保证：组队、拆步骤、选 bot 由 Router 模型完成；配额、风险、同意、并发、跳数由宿主代码强制。
  2. 只有人能授权：bot 发来的请求最多是 inferred；同意组队、批准高风险 bot、审核高风险技能只能由名单内的人完成，bot 的消息永远不能充当同意。
  3. 只有 Assignment 的 report 能从执行侧结束工单：团队步骤的结果汇总成工单级 report，不另开结束路径。
  4. 不另起第二套：bot 名册、技能库、回复通道各只有一份；团队复用工单的 Thread、Subscription 与 Outbox。

3.1 新增 superagent 源：两个入口

入口 A · 主管对话（人）

在 Bots 名册里点 SuperAgent，打开一条「主管对话」会话（preset dsh-superagent-desk，与路由用的主会话分开）。用户在这里提需求、看方案、回复同意。

Trigger：human=true · addressed='direct' · actor = 本机用户

入口 B · bot 求助（机器）

其它 bot 用 agent_message to=SuperAgent 求助。替换现在「直接插队进主会话」的做法，改为产生 Trigger。

Trigger：human=false · actor = 发起 bot · 最多 inferred

主管对话怎样把用户原话变成 Trigger

desk 会话的 preset 只挂一个宿主工具 superagent_submit()，不带文本参数：工具执行时宿主从会话事件里读取最近一条用户消息原文作为 Trigger.text，模型无法改写需求。工具返回后，desk 会话只回一句「已收到，交给主管评估」。后续的方案、进度和结果都由 channel.send 写回这条会话。

备选：如果 dsh 有「用户消息入列」的宿主事件，可直接拦截生成 Trigger，连模型都不用。实现前先核对事件名；没有的话就用上面的工具方案，它只依赖已知的 snapshotEvents。

bot 求助的准入

  • Policy 的 superagent 部分新增 bots 名单（默认空），只有名单内的 bot 能过 machineGate。
  • bot 请求只能是 inferred，需要 accept mode = auto 且命中一条已启用规则（建议预置规则「bot 求助：明确的子任务」，默认关闭）。
  • 即使被 accept，组队方案仍要人同意：bot 求助会出现在面板「需要你处理」和主管对话里，而不会只回给发起的 bot。
  • 沿用 6 跳上限：Trigger.meta 记录 hop，worker 再向其它 bot 求助时 hop+1，超过则拒绝。

4Router 与团队组建

Eval 与 Decision 不变（Router 仍判定 accept / attach / ignore / stop）。变化在 accept 之后：工单进入 person/staffing，不立即启动执行器；Router 在同一回合里调用团队工具产出组队方案。

4.1 组队的四步

已定：所有工单都走组队，流程统一
  • 单人能完成的工单 = 1 个角色、1 个步骤的团队，同样经过选人、方案和同意闸，不另设快速通道。
  • 为了不让简单工单变啰嗦，单角色方案用精简格式：一行「由 设计 bot（现有）处理：xxx · 只读 · 预算默认」+ 同意 / 修改 / 取消。
  • 工单详情、步骤表、报告汇总的结构对单人和多人完全一样；单人工单的「汇总」就是那一份步骤报告。
  • 原来的单会话执行（worker-<ticketId> + dsh-superagent-worker）不再作为默认路径，只作为兜底 bot（第 14 节问题 6）。
步骤谁做做什么宿主强制的规则
a · 工作流匹配宿主用工单标题与原始请求对已保存的团队工作流打分≥70% 时把命中的工作流（含参数、角色、步骤）预填进方案；草稿状态的工作流不参与匹配
b · 角色拆解Router 模型把需求拆成角色和步骤 DAG；每步标读 / 写权限、产出物步骤 ≤12；依赖必须指向已有步骤且不成环；每个工单至少 1 个角色、1 个步骤（单人工单也走这里）
c · 选人宿主打分 + 模型裁决按角色能力在名册里查找现有 bot；没有合适的就起草一个新 bot同名或同 id 返回现有 bot；新 bot 只是草稿，不写名册；每工单最多新建 3 个，主管创建的 bot 全局 20 个
d · 方案宿主组装方案 vN，按来源格式发出，等人回应方案带版本号与内容指纹；同意必须对应当前版本

4.2 选人打分

宿主对每个角色给候选 bot 打分，模型只能在前 5 名里选，或者选择「新建」：

score = 0.45 · 能力覆盖（角色描述词 ∩ bot 名称 / 描述 / 技能）
      + 0.20 · 历史成功率（同类步骤，来自 team_step）
      + 0.15 · 可委派（subagent: true）
      + 0.10 · 工作区授权匹配（workspaces-read / write 覆盖工单目录）
      + 0.10 · 空闲度（当前没有运行中的步骤）
低于 0.35 视为没有合适人选 → 允许起草新 bot

5用户同意闸

现有领域刻意不设「等待中的 Eval」状态，所以等待放在工单上：新增阶段 person/staffing，排在 person/delivery 之后、person/answer 之前。工单处于这个阶段时不创建运行中的 Assignment，执行器不启动。

5.1 什么算「同意」

条件规则
谁工单原始来源的名单内的人（与「只有人的 explicit 消息能 stop 工单」同一判据）；面板操作者视为本机用户。bot 消息、inferred 消息一律无效。
哪个版本同意绑定 version + fingerprint。飞书卡片按钮自带版本；文字「同意」默认指最新版本，但方案在该消息之后被修改过则无效并提示重新确认。
在哪里工单已订阅的任一线程都可以（原来源、主管对话、面板）。消息先按 Subscription 扇出到工单，再由 Router 识别意图后调用 orchestrator_team_confirm。
同意的范围一次同意覆盖方案里列出的全部内容：成员、新建的 bot（含高风险工具，方案里逐个列出）、写权限步骤、预算。没列出的不在授权范围内。

5.2 人的三种回应

回应结果
同意宿主依次：创建草稿中的新 bot（写 .agent.md、初始化记忆、注册 preset）→ 写入步骤 → executor.start → 回一句「开始执行」。创建 bot 失败则整体回滚到 staffing 并说明原因。
修改（「把测试换成 xx」「不要新建 bot」）Router 调 orchestrator_team_revise 出 v+1，旧版本作废；修改意见写进 exchange。
拒绝 / 取消工单以 dropped 结束，草稿 bot 丢弃，不产生任何资产。

5.3 可选：低风险自动同意（已定：默认关闭）

设置 → 团队 新增 autoApprove，默认关闭，出厂与升级迁移都不会替用户打开。关闭时每个方案（含单人方案）都要人同意。用户手动开启后，只有同时满足以下条件的方案自动通过：全部成员是现有 bot、没有写权限步骤、没有高风险工具、预算不超过默认值、来源是 explicit。其余一律等人。

自动通过时，方案消息仍照常发出，只是标「已按设置自动同意」，并写进工单的 exchange，人随时可以停止工单。

执行统一回到 DshExecutor，复用并发槽、mandate、report、attention 和回复。变化是：一个工单从「一个 worker 会话」变成「每个步骤一个 bot 会话」。

6.2 调度规则

  • 就绪：依赖的步骤都已 ready；前置步骤的报告（每份 ≤2000 字）注入本步骤的任务正文。
  • 并行：每个工单 ≤3 个运行中的步骤，同时受全局 maxWorkers 槽位限制；人的消息仍可额外占用 1 个槽。
  • 报告：每个 worker 用 orchestrator_report 回报，宿主把它记为步骤结果并以 team_report relay 给 Router；只有全部步骤完成后，宿主才把汇总写成工单级 ready report，保持「只有 Assignment report 能结束工单」。
  • 提问：worker 用 human_action 提问 → 工单 attention（person/answer），只阻塞这个步骤，其它独立步骤继续。
  • 失败：同一 bot 自动重试 1 次（带失败原因）；再失败交给 Router 决定换人、跳过或问人。等待它的步骤保持 pending，不会被提前跳过。
  • 跳数：worker 向其它 bot 求助时 hop+1，链路 ≤6 跳。
  • 预算：token / 回合超出方案预算的 90% 时提醒 Router；达到 100% 暂停新步骤并询问人是否追加。

6.3 写冲突

多个 bot 共用工单 worktree。方案里 access: "write" 的步骤在同一目录上持有写锁，同一时刻只有一个运行；read 步骤不受限制。需要并行写的工单，由 Router 在方案里把写步骤分配到不同子目录，或者拆成两个工单。

7.3 记忆系统的处理流程

收到证据→读会话日志→提炼（短期子会话）→分流：技能 / 记忆 / 丢弃→去重与版本→风险分级→自动生效 或 待审核→绑定到 bot
环节规则
提炼开一条短期子会话（模型取记忆系统配置），输入为证据 + 会话日志摘要，输出固定结构：可复用的步骤 / 检查清单 / 反例 / 适用条件。
分流可复用的做法 → 技能；一次性事实（某接口地址、某同事偏好）→ 该 bot 的记忆或工作区记忆；无价值 → 丢弃并记录原因。
去重与版本与该 bot 已有技能做相似度比较，≥0.8 时生成新版本并保留差异，否则新建。技能 frontmatter 增加 version。
风险分级正文含 shell 命令、外发（飞书 / 邮件 / webhook）、凭据或本机绝对路径 → 待审核；其余自动生效（与用户已定的规则一致）。
归属frontmatter owner: bot:<id>（执行者）/ team（跨角色）/ global；来源字段 origin: ticket-8f2c · T3、evidence。
淘汰使用后成功率 <60%，或 30 天未被使用 → 在「技能」页提示降级或删除。

8.1 时机与生成

  • 触发：工单以 completed 或 merged 结束，且团队至少 2 个步骤。失败、取消的工单不生成。
