SYSTEM PROMPT ARCHITECTURE

分层 · 字节稳定 · 缓存对齐 的系统提示词框架

从「拼一个 101K blob 再粗暴裁剪到 15K」重构为「stable / context / volatile 三层组装」， 让冻结前缀字节稳定、工具走结构化 schema、易变内容隔离在前缀之后 —— 对齐 MiMo-Code / Hermes-Agent / CodeBuddy 的 prompt cache 设计。

冻结前缀 stable + context
易变层 volatile 独立消息
工具 结构化 tools 字段
指纹 FNV-1a 前缀对齐

01概览

系统提示词按「可变性」拆成三层，稳定在前、易变在后。发给模型的第一条 system 消息是 冻结前缀（stable + context），它在同一会话内字节不变，是 provider prompt cache 命中与 fork 前缀指纹的计算对象； volatile 层作为独立 system 消息追加在前缀之后，其变化只影响自身位置之后的缓存，不打断前缀。

核心不变量：相同 agent + 相同会话 → 冻结前缀字节相等。一切每轮会变的内容（Persona Memory、本轮激活技能、记忆快照、持久上下文）都被推到前缀边界之后。

02三层架构

由 agentDriverService.executeTurn 分层组装，经 systemPromptComposer 合成，最终由 agentTurnExecutor 注入消息流。

STABLE 冻结前缀 · 参与指纹字节稳定

核心身份与行为规则。会话内对同一 agent 不变，是缓存命中的主体。

03策略提示词（Strategy Guidance）

根据 Agent 配置的 paradigm 字段，getStrategyGuidance(paradigm) 返回范式专属的策略提示词， 注入 stable 层（GLOBAL_SYSTEM_PREFIX 之后）。让 LLM 明确知道：执行模型 / 优先工具 / 工作结构。 preLoop 预分析器已移除，LLM 通过策略提示词在 ReAct 主循环中自主决策。

范式执行模型优先工具链核心行为
budgeted-react
（默认）		 ReAct + 迭代预算 + 委托编排 search_graph → delegate_task(explore) → plan_register → file_write → file_read 先探索再编码；预算低时优先总结；2+ 独立子任务并行委托；有序多步任务用 plan_register 注册队列依次执行
plan-explore 三阶段：计划 → 探索 → 执行 update_plan → plan_explore → exit_plan_mode → plan_register（可选）→ file_write 先出结构化计划文档；并行只读探索；再按计划逐步执行（plan_register 提供队列强约束）
react 纯 ReAct 单循环 同 budgeted-react，无委托 / 无预算 Reason → Act → Observe 循环；每轮一个工具调用
delegation Supervisor + 子 Agent 树 delegate_task(tasks) 为主；search_graph / file_read 仅快速检查 分解任务 → 委托子 Agent → 汇总结果；不自做执行
readonly 只读收集 search_graph / file_read / delegate_task(explore)（写工具全部禁用） 收集信息 → 分析 → 生成报告；不编辑文件 / 不执行命令
graph 声明式节点图 / BSP 超步 transfer_to_agent 路由 + 节点内 budgeted-react 一个节点做一部分；完成后 handoff 到下一节点
设计决策：移除 preLoop，改用策略提示词
原架构在 ReAct 前做 LLM 评估（assessFn）+ 并行探索（exploreFn）+ 计划生成（planGenerator）， 额外消耗 1-2 次 LLM 调用。现在通过 <strategy_guidance> + <code_explorer_subagent> + <search_graph_priority> 三段系统提示词，让 LLM 在 ReAct 主循环中自主决策何时探索、何时委托。
plan_register：工具驱动的串行执行队列（调研 → 拆任务 → 依次执行）
LLM 在调研（plan_explore / delegate_task(explore)）后调用 plan_register(tasks)， 通过 planQueueRegistry 把有序任务列表写入当前 turn 的 planTasks 队列 （agentTurnExecutor 在 turn 开始时注册句柄、finally 注销）。主循环在每轮无工具调用时自动推进队列， 并注入 CURRENT TASK (k/N) 提醒，形成强引导的依次执行。 与 update_plan（软追踪，仅 UI 卡片不回读）互补；无活动队列时降级为文本指引，永不阻塞流程。

策略提示词注入位置

┌─ STABLE 层（冻结前缀）──────────────────────────────────────────
│  [1] Agent persona（核心身份）
│  [2] caller systemPrompt（workflow / 子 agent 模板）
│  [3] GLOBAL_SYSTEM_PREFIX（并行优先 + 行号剥离 + code_explorer + search_graph_priority）

04消息流

最终发给模型的消息序列。缓存断点落在冻结前缀（第一条 system 消息）边界；其后所有内容均为每轮可变的下游，不影响前缀命中。

┌─ [0] system   冻结前缀（stable + context + enforcement）  ◄── cache_control 断点 / fork 指纹
├─ [1] system   volatile 层（Persona Memory + Active Skills）
├─ [2] system   <agentmemory-context> 记忆快照（会话内去重注入一次）
├─ [3] system   durable context（delegation ledger / 目标）
├─ [4..] user / assistant / tool …  对话历史
├─ [k] user（synthetic sidecar） 策略 reminder / TaskGate nudge / 反思 / 计划推进 / 技能激活
│        ↑ 仅发送副本，压缩与持久化前由 stripSyntheticSidecars 剥离，不污染干净 transcript

工具定义：不进入任何 system 文本，经 modelOptions.tools 结构化 schema 随请求下发（function-calling），
MCP / 超限工具经 tool_search → tool_describe → tool_call 桥接按需发现。

04.5Sidecar 注入与 user 消息隔离

框架会在发送前临时拼入数据——技能激活、策略提醒、控制流重入（TaskGate nudge）、反思、计划推进。 这些数据不是用户真实输入。若不隔离，会污染干净 transcript，并在下一轮被当作「用户消息」重放。 本框架用 synthetic 标记 + 压缩/持久化剥离，对齐 Hermes 的 api_content sidecar 与 MiMo-Code 的 synthetic: true。

注入通道：system 族（干净） vs user 族（sidecar 可剥离）

数据通道标记 / 剥离方式
冻结前缀（stable+context）system（首条，字节稳定）进缓存前缀，不参与剥离
volatile（Persona Memory + 激活技能）system（独立消息）每轮重算，不进前缀指纹
Agent Memory 快照system（<agentmemory-context>）会话内 injectedSessions 幂等一次
Retrieval 保留上下文system（## Preserved Context）INJECTED_CONTEXT_PREFIX 前缀，压缩剥离
Durable Contextsystem（<durable_context_data>）checkpoint 持久化
技能激活（auto/explicit）user（synthetic）synthetic: true + sidecar: 'skill'；HARD_MAX 修剪前 / 压缩构建器（prunedHead/Tail）/ 结构化 checkpoint 的 firstUser 全部排除 → 不持久化、不重放
策略 budget reminderuser（synthetic）synthetic: true + sidecar: 'reminder'，同上剥离
TaskGate 重入 nudgeuser（synthetic）synthetic: true + sidecar: 'nudge'，同上剥离
反思 / 计划推进提醒user（synthetic）synthetic: true + sidecar: 'reflection' | 'plan'，同上剥离
真实事故：Code Gen 技能强制注入
code-gen 曾被写死进 5 个内置 agent 的 skills 列表，经 agent.skills → required 每轮强制注入 user 消息， 导致用户仅做「GC 卡顿分析」也会被前缀 ### Skill activated: Code Gen 污染。修复：从 builtinAgents.ts 移除 code-gen， 改为仅命中 match 关键词（code/generate/write code…）的代码请求才自动激活；技能激活块现统一标记为 synthetic sidecar，压缩时剥离。

Canonical 注入顺序（保障 system 前缀字节稳定）

① [0] system   冻结前缀（stable + context）              ◄── cache_control 断点 / fork 指纹
② [1] system   volatile（Persona Memory + Active Skills）
③ [2] system   <agentmemory-context> 记忆快照（幂等一次）
④ [3] system   ## Preserved Context（retrieval，前缀剥离）
⑤ [4] system   <durable_context_data>（checkpoint）
⑥ [5..] user（真实）+ assistant / tool …  对话历史
⑦  [k] user（synthetic sidecar） 策略 reminder / TaskGate nudge / 反思 / 计划 / 技能激活
        ↑ 仅发送副本；stripSyntheticSidecars 在 HARD_MAX 修剪前 + 压缩构建器 + checkpoint 剥离

06优化前后

本次重构（P0–P2 为核心）解决了 101K 膨胀、persona 腰斩与缓存击穿三大问题。

优化前

  • persona + 工具清单 + 技能目录 + 记忆指引拼成单个 101K+ blob
  • 工具「名称+描述」大列表与结构化 tools 字段重复发送
  • executor 端用「头 35% + 尾 65%」粗暴裁剪到 15K，腰斩 persona
  • 裁剪 marker 每次内容不同 → 彻底打破 prompt 前缀缓存
  • Persona Memory 置顶进 system，易变内容污染前缀
  • fork 指纹基于未含 enforcement 的 systemPrompt，断点常落空

优化后

  • stable / context / volatile 三层组装，system 文本自然体量
  • P0：工具清单移出 system 文本，仅保留名称清单 + 行为规则
  • 删除粗暴裁剪，改为非破坏性体量告警（40K 阈值）
  • 冻结前缀字节稳定 → provider prompt cache 命中
  • volatile（Persona Memory + Active Skills）独立消息置于前缀后
  • fork 指纹 / 缓存断点 / modelOptions 统一基于 effectiveSystemPrompt

07设计原则（四方收敛）

MiMo / Hermes / CodeBuddy 高度一致的四条原则，本框架全部落地。

🧩

工具永远结构化

工具以 JSON schema 经 function-calling 下发，绝不以文本形式嵌入 system。超限工具走 tool_search 桥接。

MiMo · Hermes · CodeBuddy
✂️

靠策展而非裁剪

system 文本保持小而精，从源头不产生 101K；删除 head/tail 裁剪，只留非破坏性告警。

MiMo · Hermes · CodeBuddy
🧊

前缀字节稳定

冻结前缀（stable+context）会话内不变；易变内容全部推到前缀边界之后，不打断缓存。

MiMo · Hermes · CodeBuddy
🧠

记忆不每轮灌

记忆快照会话内去重注入一次，置于前缀之后；durable context 同为下游消息。

MiMo · Hermes · CodeBuddy
