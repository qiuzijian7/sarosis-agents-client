0.1 重构后"以 dsh 侧为准"的准确含义

三类能力的定义与实现都落在 dsh 侧插件（dsh-plugins/<name>/lib/**）：

能力dsh 侧是谁在定义宿主侧（src/vs）还剩什么
工具 各插件的 lib/index.js 里 ctx.tools.register(definition)；实现也在插件内（本地文件 / HTTP / 子进程），只有办不到的事才经反向桥回宿主 ① legacy 引擎那套工具（providers/tool/**，dsh 关闭时用）② 反向通道的被调方实现（dshIdeCapabilities.ts）
技能 @vssaros/dsh-skills 注册一个 skill provider；目录挂载由 dsh-skill-filesystem 行 + 我们的 --patch 覆盖层完成 只负责给出目录清单（_skillDirs()）与生成覆盖层（renderSkillsOverlay）
MCP dsh-mcp-client（dsh 原生）一行一台服务器；@vssaros/dsh-mcp 只做只读观察；bin/sync-rows.mjs 可在 dsh 侧自己产行 生成 renderMcpOverlay（dsh 侧未登记时的兜底）+ 配置解析镜像 + 重启闸门

权威口径来自重构方案 §6.9「契约共享、实现各自一份」：协议/清单/容器 id 的真源留在 src/vs（插件侧手写对齐 + 守卫比对）， 模块业务逻辑（core）放 dsh-plugins/<name>/lib/core 作为最终真源；src/vs 永久禁止 import dsh-plugins/。

0.2 三条通道与五个结论

通道机制谁拥有本仓库用量
① dsh 原生 插件里注册即对模型可见（ctx.tools.register），执行在 dsh 进程内 我们的模块插件 31 个工具（kanban 10 / codebase 5 / kb 5 / memory 5 / workflow 4 / dashboard 2）
② IDE 反向通道 bridge.callIDE('ide.request') → 命名管道 → 主进程授权闸门 → 渲染进程执行 我们的插件发起，VsSaros 执行 12 个工具（@vssaros/dsh-ide）+ 11 个能力名
③ MCP dsh-mcp-client 原生消费外部 MCP 服务器，工具名 mcp__<server>__<tool> dsh 原生（我们只供配置与观察） 0 行代码挂载；vssaros-mcp 提供只读可观测面
五个核心结论
  1. 工具注册已成体系：43 个工具全部用字面量定义 + 显式注册（内联或工厂返回数组后 .map(register)），没有隐式注册表/魔法发现 —— 清单可从源码穷举，这是可审计的前提。
  2. 反向通道只用于"dsh 进程里做不到的事"：编辑器诊断/选区/打开文件/reveal/diff/浏览器 CDP/画布/思维导图/Unreal —— 31 个本地工具没有一个走桥。
  3. 技能是"目录 + 按需加载"：dsh 没有 activation: always 的等价物，技能挂进去是"目录可见、模型自取"（dsh-tool-skill）；且原生 skill 工具行被随包层关掉过，必须由我们的层翻回来才有意义。
  4. MCP 是"组合行"模型：一台服务器一个组合行、重启才生效、没有运行时注册服务 —— 所以"配置变更即时生效"在这条路上不可能，只能靠覆盖层 + 重启。
  5. 代价在"两份实现"：MCP 解析/MCP 行渲染在宿主与 dsh 侧各一份（dshMcpConfig.ts ↔ mcpConfig.js / mcpRows.js），靠 p3-18/p3-24 差分与前缀守卫看守；这是"契约共享、实现各自一份"的既定成本（见第 7 章）。

2.1 注册 API 的真实形状（两种写法）

没有 defineTool 包装层、没有装饰器、没有注册表扫描：就是一个对象字面量 + ctx.tools.register()。两种写法覆盖全部 43 个工具。

// 写法 A（工厂风格 · 40 个工具）：数组字面量 + map(register)。dashboard/codebase/kb/memory/workflow/ide 都用这个形状。
export const name = 'vssaros-dashboard';
export const inject = ['tools'];            // 只依赖 tools：工具在任何模板里都该可用

function toolDefinitions(ctx, state, config) {
	return [{                               // ← 字面量数组：清单可穷举，是"可审计"的前提
		name: 'dashboard_sessions',
		description: '列出 dsh 会话及其遥测（turn/step 数、模型与工具耗时、token 用量），并给出汇总。',
		parameters: { type: 'object', properties: { limit: { type: 'integer', description: '1–200（默认 20）' } } },
		output: {
			schema: { type: 'object', properties: { summary: {…}, sessions: {…} }, required: ['summary','sessions'] },
			render: (_args, value) => [{ type: 'text', text: `会话 ${value.summary.sessions} 个…` }],  // 给模型看的短文本
		},
		isConcurrencySafe: () => true,      // 也可能是布尔 true（kanban 就用 true）
		execute: async (params) => ({ … }),  // 返回值会被 output.schema 校验
	}];
}

export function apply(ctx, config = {}) {
	ctx.effect(() => {                      // 注册随插件激活/停用自动回收（disposer）
		const disposers = toolDefinitions(ctx, state, config).map(d => ctx.tools.register(d));
		return () => { for (const d of disposers) d(); };
	});
}
// 写法 B（内联风格 · kanban 10 个工具）：每个工具一次 ctx.effect(() => ctx.tools.register({…}))
// 差别只在组织方式；同样支持 exec（用于中止信号与会话 id）。
ctx.effect(() => ctx.tools.register({
	name: 'kanban_list', description: '列出看板任务…',
	parameters: { type: 'object', properties: { status: { type: 'string', enum: [...], description: … }, limit: {…} } },
	output: { schema: LIST_OUTPUT_SCHEMA, render: … },
	isConcurrencySafe: true,
	execute: async (params, exec) => { /* 支持 exec.signal 中止 */ },
}));
三条硬约束（全部来自源码注释与实测）：
  • 参数 schema 只接受受限子集：没有 minimum/maximum —— 范围写进 description、由代码夹紧（dashboard/lib/index.js:393-394）。
  • 返回值必须与 output.schema 相符：声明为可选整数的字段要删掉而不是留 undefined（否则校验器判类型不符，dashboard/lib/index.js:466-467）。
  • 工具名是跨端契约：客户端工具卡的 key 必须与 ctx.tools.register 的名字逐字符一致（kanban/lib/client.js:24-31 用探针钉住）。

2.6 反向通道的授权模型（12 个工具的安全边界）

这是本仓库与其他 dsh 宿主最大的差别，规则全部默认拒绝（dshIdeAuthorization.ts:59-80 authorizeIdeRequest）：

  1. 能力名必须在白名单：VSSAROS_IDE_CAPABILITIES（vssarosPluginManifest.ts:88-98）—— openFile / reveal / showDiff / getSelection / getDiagnostics / browser / canvas / mindmap / unreal / taskboard / workflow；不是名单里的名字直接 MethodNotFound。
  2. 请求必须带 pluginId，且该插件已安装在 profile 里；缺 pluginId 一律拒（"逐插件授权的前提是知道谁在问"）。
  3. 该插件的清单里必须声明过这个能力（vssaros.ideCapabilities）—— 不是"某个插件声明过就全局放行"。
  4. 身份由桥盖章：pluginId 不采信调用方自报（bridge/lib/index.js:210-227），否则任何插件都能自称 IDE 插件去要那 12 个能力。
  5. 时间预算分层：ide/lib/index.js:88-98 取多档最大值（配置值、渲染侧 default/slow、需确认的 consent 档、unreal 各 tool 的实测档）。
  6. 需确认的写操作：browser / canvas 的写 op 不在插件里"偷偷做"，而是转给 IDE 侧走用户确认。
能力名为什么拆这么细（vssarosPluginManifest.ts:83-86 的原话）：把 mindmap 折叠进 canvas、把 unreal 硬塞进某个桶， 会让"一个只声明 canvas 的插件顺带拿到 mindmap 工具"——"按清单逐项授权"就退化成"整族放行"。 名字多一个的代价只是清单里多一项，换来的是"这个插件到底能驱动 IDE 到什么程度"在安装那一刻就可读、可审。

⑤ 结构性问题：平面错位让 preset 失效

官方把工具下移到 per-agent plane，本意就是让 preset 成为"能力预算开关" —— minimal 的定义是"极简，只有一个持久终端"，省掉 20+ 个工具定义常驻上下文。 但我们的 43 个工具在 host plane，任何 preset 下都会全部注入：选 minimal 的用户实际拿到 43 + 2 = 45 个工具，预期落空；cordis（创造模式，本意是"只读内省 + 改 dsh 自身"）下我们的工具也在。

  1. 会话无关的模块留在 host plane（现状正确）：不注册工具的模块（bridge / mcp 观察页 / dashboard 只读页 / canvas 页面）本就不占工具面。

4. MCP 层：配置、挂载与观察

一句话：MCP 的挂载不在我们任何插件里做 —— dsh-mcp-client 是"一台服务器一个组合行"的模型，dsh 没有供别的插件注册服务器的运行时服务。 所以配了 MCP 但没经过"启动覆盖层"这一步，就挂不上；我们做的是 ① 把配置文件解析/归一化成组合行（renderMcpOverlay）② 把"实际挂了什么、哪些被跳过、为什么"显示出来（@vssaros/dsh-mcp 只读页）。

  4. 两条路并存挂两遍 ⇒ 加归属判定与让路（4.6）。
  5. 插件 config.path 与真挂载用的文件不一致（页面看的 ≠ 真挂的），且被"探针都自己注入了数据根"完全掩盖。修：renderDataRootOverlay 写 - id: vssaros-dsh-mcp / config.path（dshCli.ts:453-472）。

  7. 工具全名写死造成假红 ⇒ 改成语义断言（4.5）。
  8. state=error 态无断言、易被伪装成 missing/empty ⇒ 造法（把 mcp.json 换成目录）+ 断言"不伪装成'还没有 MCP 配置'"（mcpConfig.js:203-211）。

export const name = 'vssaros-demo';

// 只依赖 tools：工具在任何 profile（含 headless / tui）都该可用。
// webServer / connection 只在 web 模板存在 ⇒ 写进静态 inject 会让插件永久 pending，连工具一起失效。
export const inject = ['tools'];

const ROUTE_PREFIX = '/x/demo';

function toolDefinitions(ctx, state, config) {
	return [{
		name: 'demo_list',
		description: '列出 demo 条目。',
		parameters: {
			type: 'object',
			// 注意：dsh 的参数 schema 只接受受限子集（无 minimum/maximum）——范围写描述、代码里夹紧
			properties: { limit: { type: 'integer', description: '返回条数上限，1–100（默认 20；超出会被夹到边界）' } },
		},
		output: {
			schema: {
				type: 'object',
				properties: {
					count: { type: 'integer' },
					items: { type: 'array', items: { type: 'object', properties: { id: { type: 'string' } }, required: ['id'] } },
				},
				required: ['count', 'items'],
			},
			render: (_args, value) => [{ type: 'text', text: `demo 条目 ${value.count} 个\n` + value.items.map(i => `- ${i.id}`).join('\n') }],
		},
		isConcurrencySafe: () => true,
		execute: async params => {
			const limit = Math.min(100, Math.max(1, Number.isFinite(params?.limit) ? Math.floor(params.limit) : 20));
			return summarize(await readRows(config), limit);
		},
	}, {
		name: 'demo_add',
		description: '新增一条 demo 条目（写本地文件，独占）。',
		parameters: { type: 'object', properties: { text: { type: 'string' } }, required: ['text'] },
		output: {
			schema: { type: 'object', properties: { ok: { type: 'boolean' }, id: { type: 'string' } }, required: ['ok', 'id'] },
			render: (_args, value) => [{ type: 'text', text: `已新增 ${value.id}` }],
		},
		// 写工具不声明 isConcurrencySafe ⇒ 独占执行（kanban 写族同此约定）
		execute: async params => appendRow(config, String(params?.text ?? '')),
	}];
}

export function apply(ctx, config = {}) {
	const state = { tools: null };

	ctx.effect(() => {                                   // 注册随插件激活/停用自动回收
		const disposers = toolDefinitions(ctx, state, config).map(d => ctx.tools.register(d));
		state.tools = ctx.tools;
		return () => {
			state.tools = null;
			for (const dispose of disposers) { dispose(); }
		};
	});

	// 页面（可选依赖）：不在 web 模板 ⇒ 只是没有页面，工具照常可用。
	ctx.inject(['webServer', 'connection'], page => page.effect(() => page.webServer.register({
		kind: 'prefix',
		path: ROUTE_PREFIX,
		handler: async (req, res) => {
			const rejected = page.connection.requestRejection(req);
			if (rejected) { res.writeHead(rejected, { 'content-type': 'text/plain; charset=utf-8' }); res.end(String(rejected)); return; }
			const html = `<section data-vssaros-page="demo">…</section>`;   // 渲染必须先于 writeHead
			res.writeHead(200, { 'content-type': 'text/html; charset=utf-8', 'cache-control': 'no-store' });
			res.end(html);
		},
	})));
}
