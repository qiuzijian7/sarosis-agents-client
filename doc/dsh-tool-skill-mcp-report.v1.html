0. 摘要与总体结论

dsh 的"工具"不是一套函数库，而是一张注册表 + 一条固定执行流水线；技能（skills）与 MCP 都通过"组合行声明 + 系统提示注入"与工具同构地接进来。本仓库（VsSaros）在 dsh 之上叠了两层自有扩展：

面 1 · dsh 原生
注册即可见
`ctx.tools.register(defineTool(...))` → 自动进系统提示词。read/write/edit、glob/grep、pwsh/bash、web_search/web_fetch、skill、MCP 工具都在这一面。
面 2 · IDE 反向通道
ide.request
只有"dsh 进程里做不到"的能力走这条：unreal、browser 动作、canvas、mindmap、IDE 诊断/选区/打开文件。授权默认拒绝。
面 3 · legacy 自有
builtinToolProvider
dsh 关闭时聊天框用的那一套：file_read/file_write/patch、search_files/search_code/search_graph、terminal/process、web_search/web_extract、browser_*、read_skill…
核心结论（三条）
  1. 工具 = 注册表 + 固定流水线：`tools/pre-execute`（可扩展 allow/deny/ask）→ 单调守卫 → `tools/execute`（超时/重试包装）→ 工具体 → `tools/post-execute` → `finalizeContent` → `tools/result`（只观测）。失败一律转成结构化错误，不中断当前轮次。
  2. 技能与 MCP 不是"另一套机制"：两者都是"往 profile 插一行组合（provider 行 / mcp-client 行）"，再由 dsh 把目录/工具送进系统提示与 `ctx.tools`。技能靠 `skill` 工具按需加载正文，MCP 靠 `mcp__<server>__<tool>` 直接进注册表。
  3. 两套引擎互不共享工具实现，唯一的打通是 IDE 反向通道（vssaros-ide 插件 → callIDE('ide.request') → executeIdeCapability）。同名动词（两侧都叫 `unreal_*` / `kanban_*` / `kb_*`…）靠 common/toolOwnership.ts 的 21 条漂移契约 + 守卫测试钉住。

1. 工具调用机制（dsh 侧）

1.1 注册：defineTool 一次声明四件事

面向模型的名称/描述/参数 schema、规范输出声明（output.schema + output.render）、只返回所声明 JSON 值的 execute 主体。注册即可见 —— 注册表会自动把 schema 送进系统提示词组装，没有额外的"暴露"步骤。

ctx.tools.register(defineTool({
  name: 'read_file',
  description: 'Read a file from disk.',
  parameters: { path: { type: 'string', required: true }, offset: { type: 'number' } },
  output: { schema: { type: 'string' }, render: (_args, value) => [{ type: 'text', text: value }] },
  async execute(args, exec) { return readFile(args.path, { encoding: 'utf8', signal: exec.signal }); },
}))
实测坑（本仓库踩过）：ctx.tools.register 的 output 必须带 render；只写 schema 会抛错，表现为"整个插件不挂载"（dsh-plugins/vssaros-ide/lib/index.js:177-180 即为此写的注释）。

1.2 可见性与限制

机制作用关键点
modenative / ptc / both：模型看到原生 schema、只看到 run_code+生成 SDK，还是两者纯 ptc 下直呼其它可见工具会在策略之前解析为 UNKNOWN_TOOL —— 通告面与可调用面强制一致
maxParallelSubCallsPTC run_code 内子调用的并发上限（默认 10，1 = 严格串行）只影响 PTC 模式

1.3 执行流水线（主调用图）

每次调用都跑同一条固定流水线，插件只能在这条线上挂接：

  │
  ▼
① 参数校验（执行前）              ── 无效输入 → 普通错误结果（不中断轮次）
  │  实体化 & 冻结解析后的参数，分配不透明关联 token
  ▼
② tools/pre-execute  waterfall    ── 可扩展：allow / deny / ask
  │                                  拒绝可附带 ToolErrorInfo（结构化 name/code，
  │                                  不进模型内容，只进持久投影）
  ▼

  │
  ▼
④ tools/execute  waterfall        ── 环绕分发包装层：超时 / 重试
  │                                  （只有这一层视图可以替换必填信号；

  ▼

  ▼
⑥ tools/post-execute              ── 检查 / 替换结果、附加上下文
  │
  ▼
⑦ finalizeContent（定义持有）      ── 策略之后的最终内容处理
  │
  ▼

  │
  ▼
结果回模型（追加为工具结果消息）

1.4 横切插件（四条独立组合行）

包做什么边界（重要）
dsh-tool-call-timeout-policy为每个工具执行它自己声明的协作式时间上限，超时后映射成清晰的模型错误无法硬性停止下游：忽略取消的工具仍会让调用方继续等待
dsh-user-approval一次性审批 seam：ask → 请求人类/机器应答者；never → 直接拒绝不提示应答者缺失/失败 → unavailable，fail-closed（以拒绝关闭）；每项批准只对应那一项请求；请求与结果进会话审计日志，模型只看到最终结果与当前策略
dsh-compaction-tool-result-pruner压缩触发后，超预算文本替换为「头部 + middle pruned + 尾部」原始结果仍留在会话日志；修剪不发起模型调用
dsh-repeat-tool-reminder同一工具同参数重复 3/5/8 次时提醒模型换方法纯建议，不阻止合理重复；新用户消息清零计数

1.5 UI 呈现：Host 不参与

工具可以留 presentCall() / presentResult() 给 Host 本地消费方，但内置 Web Client 不消费它们：卡片一律由 tool.call.toolview（keyed 槽，key = 工具名）的 renderer 从原始调用参数、结果内容、失败状态与持久 metadata 自行派生 props。这与本仓库 vssaros-chat-surface/lib/client.tools.js 遮蔽 write/edit 的做法一致。

10. 评估：优点、风险、建议

10.1 设计上确实好的地方

注册即可见
没有"再声明一次暴露"的步骤：register 就把 schema 送进系统提示组装，减少半死状态。
流水线可插拔
策略、超时、审批、结果修剪、重复提醒都是独立组合行 —— 换行为=换策略，不动工具。
失败不中断轮次
无效参数、未知工具、抛异常、超时全部转结构化错误，模型能自纠；工具作者不必写防御性 try。
审批与沙箱分层
沙箱策略决定"能不能写这里"，审批决定"要不要问人"；unavailable 以拒绝关闭（fail-closed）。
技能/MCP 与工具同构
都是组合行 + 系统提示注入，不需要为它们引入第二套插件模型。
能力面可裁剪
preset 逐 agent 挂工具行 + restrict() 掩码 ⇒ 同一个 Host 里不同会话拿到不同工具集。

10.2 风险与缺口（按严重度）

#风险证据 / 影响现状
1能力面由 preset 摆布dsh-web-app 关掉 base 的 tool-web/tool-skill，preset 再逐 agent 重挂；切到 minimal 就只剩 persistent bash/pwsh —— 没有 read/write/edit、没有 web、没有 skill已知，需列入产品口径

10.3 建议

  1. 给反向通道工具补 signal 通路：dshUnrealRunner 把 exec.signal 传进 callBridge（底层已支持 signal 合并），至少让"用户中断回合"能终止后续等待。
  2. 把"需重启"做成显式反馈：MCP / 技能目录 / 工具行变更后，在插件中心与聊天框给一条"改动将在下次 Host 重启生效"的提示（现在只在源码注释里）。
  3. 把 preset 能力面对用户可见：切换 agent preset 时列出"本 preset 的工具集差异"（minimal 无文件工具是强语义）。
  4. 把"来源行 + 消费者行"配对做成守卫：像 dshWriteOwnership.test.ts 那样，断言"注册了技能来源 ⇒ tool-skill 必须 enabled；装了 MCP ⇒ dsh-mcp-client 行必须存在"。
  5. dsh 侧写入若要贴近 IDE 体验：在 fs/write-intent 钩子里加"缓冲区脏检查"（IDE 侧已有 checkDirty 的桥能力可复用，见方案 5.14 批次 4）。

11.6 对本仓库可执行的四条借鉴

  1. 插件中心加"宿主可渲染性"标注（借 skymecode 的四级口径）：随包/商城插件里已有纯客户端 UI 插件，装完发现"聊天框里看不到"与 Official Web UI only 是同一类问题——按其能否被当前 surface 渲染分级，必要时禁装并给说明。判定可对齐它的做法：已装包的 row 模块名含 client-ui，或 manifest 有 dsh.client。
