dsh 聊天框的 Slot 机制

通俗版原理解析 · 依据 dsh 0.2.0-rc.2 真实源码与运行时扫描（官方 web 组合共 87 个命名槽位）· VsSaros 侧实例来自 dsh-plugins/vssaros-chat-surface/lib/*.js · 2026-10-11

0. 一句话原理

dsh 的聊天框不是「一个写死的大组件」，而是一块带插座的电路板： 官方把界面拆成几十个有名字、有规矩的插槽（slot），每个插槽自己声明「我这儿能插几个、插什么样的东西」； 任何插件（包括 VsSaros 的换皮插件）都能往这些插槽里插自己的 React 组件。 官方条目和插件条目躺在同一本账上，按优先级仲裁出「谁来渲染」。

conversation.input.dock list / session
官方：审批提示条（priority 0）
插件：队列提示条（id 唯一，priority 0）
list 槽：各占各的格子，互不遮蔽
tool.call.toolview keyed / session
插件：VsSaros 文件卡（key=write, priority −10）
官方：原生文件卡（key=write, priority 0）
keyed 槽：同 key 比 priority，数值小的赢
conversation.hero.agentPreset single / session-maybe
插件：VsSaros preset chip（priority −10）
官方：hero preset chip（priority 0）
single 槽：一个坑位，谁 priority 小谁占

1. 名词地图：谁在跟谁说话

Slot 机制一共只有三个角色。把这三个角色分清，后面的规则都不用背。

角色叫什么是什么谁负责
插座 Slot（槽位） 界面上的一个具名挂载点，带 kind（插几个）和 scope（什么作用域）。必须先被父组件声明，否则谁也别想插。 宿主组件（官方或插件）在注册自身时用 children 表声明
插头 Entry（条目 / 贡献） 插进槽里的一个 React 组件 + 选项：id（list 用）/key（keyed 用）/order/priority/select（chain 用）/children（再声明子槽）。 任何客户端插件
账本 SlotCore → ctx.slots 纯注册表（无 React）。负责校验、排序、仲裁「谁生效」、通知渲染器重绘、导出拓扑快照。 dsh 的 ui-slots（纯逻辑）+ ui-renderer（绑到 React）

术语速查

字段含义易错点
name要插的槽位 key，如 "tool.call.toolview"写错 → 直接抛 slot "X" is not declared
idlist 槽的条目身份（唯一）同 id + 同 priority 重复注册 → 抛错
keykeyed 槽的分格键（如工具名 write、节点类型）不传 → 抛 keyed slot requires options.key
priority竞争权重，默认 0，升序，数值最小的先赢想遮蔽官方（默认 0）必须用负数
orderlist 槽内部的展示排序（priority 相同才轮到它）不是权重，不参与遮蔽
selectchain 槽的选举函数，返回非 null 即「我要接管」不传 → 抛 chain slot requires options.select
children本条目要渲染的子槽声明表声明即授权，声明即独占：不声明就不能渲染，被别人先声明了就报错

2. 四种 kind：插槽分四种脾气

这是整套机制的核心。kind 决定「一个格子只能一个，还是可以很多个」，以及「怎么决定谁生效」。

single（单个占位）
list（有序条目）
keyed（按键分格）
chain（选举接管）

一个坑位，同一时刻只有一个条目渲染。后注册者若与在座条目 priority 相同，直接抛错（强迫你表态）；用更小的 priority 才能顶掉它。

single · 一个坑
A（priority −10）→ 渲染
官方（priority 0）→ 出局

真实例子：conversation.hero.agentPreset（新会话欢迎区的 agent 选择器）、conversation.approval.detail（审批卡）、sidebar / rightbar（布局）。

可以插很多条，各占各的格子，互不遮蔽。身份靠唯一 id；渲染顺序 = priority 升序 → order 升序。想遮蔽官方某个条目，就用同一个 id + 更小的 priority。

list · 多格
官方：模型选择器（id=model, p=0, order=10）
插件：用量药丸（id=vssaros-turn-usage, order=100）
插件：preset chip（id=vssaros-preset-chip, order=99）

真实例子：conversation.session.header.utilities（会话头右侧工具位）、conversation.input.dock（输入框上方横条）、conversation.input.right（输入框右侧按钮）。

先按键分格，每格再按 single 的规矩竞争。键通常是「类型」：工具名、聊天节点类型、来源 id。没被占用的 key 就等于新开一格（新增），已占用的 key 就能遮蔽。

keyed · key="write"
插件卡（p=−10）
官方卡（p=0）
keyed · key="bash"
官方卡（p=0）
没插件插入 → 官方原样

真实例子：tool.call.toolview（工具卡，key=工具名）、conversation.chat.node（消息流节点，key=节点类型）、main（布局主体）。未覆盖的 key 自动回落官方渲染器——这正是「渐进换皮」的底气。

不做格子竞争，改「选举」：每个条目带一个 select() 函数，注册表按 priority 升序逐个询问；谁第一个返回非 null，谁就接管并拿到 matched prop；全都返回 null 时，由宿主自己的 fallback 渲染。典型用途是「同一位置在不同状态下换不同 UI」。

chain · 询问顺序
① VsSaros 审批卡（p=0）→ select 返回 pending 时接管
② 官方审批 UI（p=1）→ 轮不到
③ 宿主 fallback → 无审批时渲染输入框

真实例子只有 3 个：conversation.composer（输入区：审批/提问时被接管）、shell.quota-notice（配额提示）、sidebar.right.tab.guide。chain 槽不能用普通 renderSlot 渲染子槽，要用 renderSlotChain。

3. 仲裁规则：谁渲染？（唯一需要记住的一张图）

问题答案源码依据
同格谁赢？priority 升序取第一个「还活着」的条目 → 数值最小者渲染（官方默认 0，插件用负数遮蔽）entriesOfSlot() 投影每格首个非 abdicated 条目
list 内部怎么排？priority 升序，同级再按 order 升序注册时的排序函数
同格同 priority 会怎样？抛错（single/keyed/list 都检查；chain 不检查）register() 的 occupant 校验
插件组件崩了会怎样？abdicate（让位）：把该条目从格子里撤下（一次性），下一次渲染自动轮到下一候选 → 官方样式回归，内容不丢；注册本身仍在账本上，disposer 依然有效reportEntryError({abdicate:true})
chain 崩了会怎样？不撤（选举在选择时就已定），只发错误通知abdicate:false
没声明的槽能插吗？不能，直接抛错。children 声明是唯一授权来源，且声明即独占（别人再声明同一子槽就报错）slot "X" is not declared (a parent entry's children table must declare it)

4. 授权与生命周期：插座、电闸、拔插头

插座是「声明」出来的
宿主组件注册自己时，用 children 表列出「我允许谁在我身上开洞」。插槽的拓扑就是这么长出来的一棵树： 
ctx.slots.register({
  name: 'conversation.session.header',
  children: {
    'conversation.session.header.utilities': { kind: 'list', scope: 'session' },
    'conversation.session.header.corner':    { kind: 'single', scope: 'session' },
    ...
  },
}, HeaderComponent);
子槽由父组件决定 kind/scope，插头无权修改。
拔插头是「级联」的
条目被 dispose 时，它声明的子槽、子槽里的贡献、以及它挂的 store 席位一起消失（递归）。 dsh 把 ctx.slots.register() 包在 Cordis 的 ctx.effect() 里，所以插件卸载/热更新时插头自动拔掉，不会留半截 UI。 
// renderer 侧
SlotRegistry.prototype.register = function (options, component) {
  return this.ctx.effect(() => this._register(options, component), 'slots.register()');
};

ctx.slots.inject(key, cb)：插座还没装好时先排队

插件加载顺序和宿主渲染顺序不保证一致（谁先谁后都可能）。inject 的语义是： 「等这个槽位被声明出来了，再帮我注册」。实现上盯的是槽位的声明代际（declaration epoch）—— 声明出现时执行回调并接管，声明被撤掉时把回调的产物清理掉。 

// VsSaros 的标准写法（每个换皮部件都是这个形状）
ctx.slots.inject('conversation.input.dock', () => {
  const dispose = ctx.slots.register(
    { name: 'conversation.input.dock', id: 'vssaros-queue-hint', order: 100 },
    QueueHint,
  );
  return dispose;   // 槽位消失时由 inject 负责清理
});
为什么大家不直接 register？因为槽位在页面刚挂载时可能还没声明，直接 register 会抛 is not declared。用 inject 排队，插件就能与官方解耦、各自按自己的节奏加载。

5. 数据是怎么流进组件的：scope + 五类 props

插件组件不自己去订阅会话、不 import 渲染器。它只是普通 React 组件，props 由框架「拼装」好递进来。 拼装的原料有五类（官方 README 称 five framework props shares）：

share内容例子
runtime父级渲染调用点的 owner props + 会话标准工具包 + 全局席位sessionId、phase、toolName、block（工具卡）、node（聊天节点）、openFile/cwd
child render静态收窄后的 renderSlot：只能渲染自己 children 里声明过的子槽文件卡渲染自己声明的「展开区」
factory renderrenderFactorySlot：渲染可复用装配的 occurrenceComponent Factory 场景
store声明过的 store 席位的 selector 钩子与写操作useDisclosure() → {expanded, toggle}
业务 inject父级声明的注入面（会话 hooks 等）useInput()、useChat()、useSession()、inputActions

scope 决定「能拿到什么」

scope含义会话标准工具包官方 web 组合中的数量
root全局，一份全局工具包：useSessions / useSessionStatus / useWorkspaces …40
session绑定某个会话，每个会话一份实例会话工具包：useSession / useProjection / useConversation / useInput / useChat …42
session-maybe会话可选（没有会话也能渲染）同 session，但字段可为 undefined5
scope 决定「一个还是多个」。同一个组件注册到 session 作用域的槽，聊天框开了 5 个会话就是 5 份实例。 换皮时若在组件里塞了模块级可变状态，会踩到「多个实例互相串味」的坑。

变更怎么传出去（响应式三件套）

  • version 同步自增：每次变更立刻 +1，保证 getSnapshot() 永远不会读到旧值（哪怕通知还没派发）。
  • subscribe 微任务批处理：同一 tick 内对同一个 key 的 N 次变更只通知一次。
  • onMutate 同步不批处理：事件流需要「一次变更一次事件」，所以另开一条同步通道。

渲染器在插槽出口把注册表接到 React 的 useSyncExternalStore 上——这就是「插件只写 React 组件，不懂订阅」的原因。

7. VsSaros 实际用它做了六件事

同一个机制，在聊天框里被用了六种「姿势」。这六段就是最好的教材。

① 新增（list，用唯一 id 与官方共存）—— 队列提示条

// dsh-plugins/vssaros-chat-surface/lib/client.queue.js
ctx.slots.inject('conversation.input.dock', () => {
  const dispose = ctx.slots.register(
    { name: 'conversation.input.dock', id: 'vssaros-queue-hint', order: 100 },
    QueueHint,                      // 空队列时 return null（不渲染）
  );
  return dispose;
});

要点：新 id 不会与官方冲突；order 只影响同 priority 下的展示位置；空状态直接返回 null 最省事。

② 遮蔽（keyed，负 priority）—— 文件工具卡换成 VsSaros 风格

// dsh-plugins/vssaros-chat-surface/lib/client.tools.js
for (const key of ['write', 'edit']) {
  ctx.slots.inject('tool.call.toolview', () => ctx.slots.register(
    { name: 'tool.call.toolview', key, priority: -10 },  // 官方同 key 是 priority 0
    VssarosFsToolCard,
  ));
}

要点：只覆盖 write/edit 两个 key，其它工具（bash 等）原样用官方卡——这就是 keyed 的好处：逐 key 渐进换皮。组件崩溃时会 abdicate 回官方卡，聊天不至于变砖。

③ 遮蔽（list，同 id + 更低 priority）—— 干掉「在其他 app 中打开」按钮

// 官方注册在 conversation.session.header.utilities，id="open-in-app"，priority 0
ctx.slots.register(
  { name: 'conversation.session.header.utilities', id: 'open-in-app', priority: -1 },
  () => null,                        // 同 id 更低优先级 → 官方那条被遮蔽
);                                   // 注意：同 id 同 priority 会抛错，所以必须 -1

④ 遮蔽（single，负 priority）—— hero 区的 agent chip

ctx.slots.inject('conversation.hero.agentPreset', () => ctx.slots.register(
  { name: 'conversation.hero.agentPreset', id: 'vssaros-preset-chip-hero', priority: -10 },
  PresetChip,
));

遮蔽理由很有意思：官方 chip 走「空白会话热切换 preset」，会破坏 VsSaros「会话 id 后缀 = preset」的确定性，所以必须由自己接管。

⑤ 选举（chain，抢占式同槽）—— 审批卡

// 官方审批 UI 在 conversation.composer（chain，priority 1 + select「审批时接管」）
// VsSaros 注册同槽、priority 0（升序先试）→ 先被询问，同样 select 语义 → 接管
ctx.slots.inject('conversation.composer', () => ctx.slots.register(
  { name: 'conversation.composer', priority: 0, select: (o) => (o.pending ? o.pending : null) },
  VssarosApprovalCard,
));

要点：chain 的遮蔽不是「数值小的强制赢」，而是「先被问，且同样宣布接管」；放行/拒绝仍走 dsh 原生审批流（pending.answer(decision)），只换皮不换语义。

⑥ 纯换肤（不占槽）—— 主题与样式

只做视觉改动时不必注册条目：直接用宿主主题变量（--dsw-alias-* 等）写样式、或经 ctx.theme.overrideTokens() 叠一层调色板。少一个插槽改动面，就少一处 dsh 升级时要跟的地方。

8. 为什么这么设计（四条原理）

解耦
官方不需要知道谁在扩展它，插件也不需要改官方代码。双方只依赖「槽位契约」（名字 + kind + scope + props 类型）。
可回退
单点失败不拖垮聊天：条目崩溃 → abdicate 让位给下一候选；某个换皮部件注册失败只影响它自己（VsSaros 把每个部件拆成独立 chunk，失败原因记在 window.__vssarosChatSurface.partErrors）。
类型即契约
SlotMap / SlotFactoryMap 由各包 declare module 声明合并：槽名拼错、kind 用错、props 取错，编译期就报；运行时再校验一次（未声明 / 同格冲突 / 缺 key 或缺 select）。
可观测
SlotCore.snapshot() 导出整棵拓扑（kind / scope / declaredBy / occupants{id,key,order,priority,active}），成为 Slot 目录比对、覆盖率报告和 e2e 断言的数据源。

9. 排错速查表

症状多半是怎么办
slot "X" is not declared (a parent entry's children table must declare it)槽名写错，或父级还没声明（加载顺序问题）核对 snapshot() 里的真实槽名；用 ctx.slots.inject() 排队注册
single keyed list ... already has a registration at priority 0 ...同格同 priority 撞车（官方默认 0）改 priority（遮蔽用负数）；或换唯一 id
keyed slot requires options.key / chain slot requires options.select少传必填选项补上
SlotOwnershipError: ... use renderSlotChain把 chain 槽当普通槽渲染子项chain 用 renderSlotChain；或改注册到别的槽
注册成功但界面没变化① 组件返回了 null；② 被更小 priority 的条目遮蔽；③ scope 不匹配（没有会话时 session 槽不渲染）；④ 改的是另一个同名面板看 snapshot() 里该 slot 的 occupants[].active；确认当前页面/会话
自己注册的卡突然变回官方样式组件抛错触发了 abdicate（一次性让位）查 onEntryError / 控制台报错；修好后重新注册（同一条目不会自动复活）
多开会话时状态串味session 作用域槽每会话一份实例，用了模块级可变状态状态放进组件内或 store 席位
