§0 结论

可行，但不能一次切。dsh 已接管前台聊天框，19 个插件提供 107 个工具；但所有后台入口仍跑 legacy 自研引擎（渠道、Pocket、调度器、看板自动执行、工作流、KB 导入、HTML 面板）。legacy 引擎要等这些入口全部迁走才能删。因此方案按“绞杀者”模式推进：先把入口迁进 dsh，再收工具缺口和 UI，最后删引擎。分 6 个阶段，每个阶段都能单独发布、单独回滚，预计 16–22 周。

§1 “dsh 插件范式”在本项目里落成 8 条准则

准则取自官方成文纪律（纪律镜像、A–I 合规基准）以及已经定下的方向（能力归 dsh、壳可替换）。后面每一项工作都用这 8 条检查。

#准则在本项目里的含义
P1能力归属三分法dsh 官方已有 → 删掉 legacy 实现，不再迁；与宿主无关 → 写成 dsh-plugins/ 插件；必须用 VS Code 平台（编辑器、diff、终端、webview 渲染）→ 留在壳里，经 ide.request 暴露（先例 dshIdeCapabilities.ts）
P2清单是唯一真源插件 package.json 的 vssaros.* 字段驱动壳的 ActivityBar、视图宿主、IDE 能力授权；壳里不再有按模块硬编码的表。验收标准是“新增一个模块，壳代码改动为 0”
P3跨包行为走 cordis 服务，跨包 UI 走 slot插件之间不 import；需要共享的逻辑做成服务插件（见 1.3），不再靠“逐字节拷贝 + 守卫”
P4会话日志是唯一真源后台入口发起的回合也必须是 dsh 会话；不新增自定义事件类型；按会话的状态用 sessionProjections
P5审批放在组合层工具本身不带审批；无人值守会话用 permissionPreset 加按作用域挂的 approval/request 应答者
P6最弱机制优先按 tools.restrict → guard → waterfall → assemble 的顺序选，prompt 只走 section/variable/context
P7每个插件四件套REAL-composition 测试、dispose 证明、persistence.json 登记、工具快照；外加行为级探针和反向突变（沿用本仓纪律）
P8不 fork、不 patch、官方件优先先查官方有没有：dsh-schedule / dsh-webhook / dsh-workflow / dsh-jobs / dsh-permission-presets / dsh-user-approval / dsh-goal / experimental agent-team（全都已在 0.2.0-rc.2 运行时里）

3.1 一次后台运行在目标态下怎么走

入口插件（channels / scheduler / kanban runner / workflow engine / pocket 路由）
   └─ ctx.vssarosRuns.start({ origin, sessionKey, workspacePath, agentPreset, permissionPreset, prompt })
        ├─ sessionController.create({ sessionId: 由 sessionKey 派生, ... })   // 同一个 IM 会话 / 同一个看板任务 → 同一条 dsh 会话，幂等领养
        ├─ workspace.attachSession → sessionController.prompt({ mode: 'queue' })
        └─ awaitTurn(sessionId) → { finalText, stopReason, toolSummary }     // 需要 Spike S1 确认官方的回合结束信号
   审批：permissionPreset 先挡一层；剩下的 ask 交给按 origin 挂的 approval/request 应答者
        （channels → IM 卡片；IDE 在前台时 → IDE 通知；其余入口 → 拒绝，并把原因写进结果）

vssarosRuns 是一个 cordis 服务（放在 foundation 或 bridge 插件里）。壳侧过渡期的调用方经桥上新增的 session.run 调用同一个服务。整条链只用官方已有的 session controller、approval 和 permission preset，不新增事件类型。S1 已真机验证（§10）：投递必须用 sessionController.prompt() 而不是 agent.followup(自建消息)——v4 会话格式拒绝插件自造的 source kind；结果回收用 resolveAgent → whenIdle → snapshotEvents(水位差)；恢复同 sessionId 有效。

S1 · 后台回合的“结束信号 + 结果回收” 已验证

结论：可行，且有官方先例可照抄。链路与官方两个包的手法完全一致： workspaceRegistry.create → sessionController.create（幂等收养）→ attachSession → resolveAgent → sessionController.prompt → whenIdle → snapshotEvents(seqBefore, seqAfter) → finalAssistantText + turn/end.reason。 同 sessionId 第二次调用是恢复而不是重建（seqBefore=21 实测），且只读到新回合的事件。
  • 投递必须走 sessionController.prompt()，不能 agent.followup(自建消息)：v4 会话格式要求 source kind 是“生产者自有”的，插件自造 kind:'plugin' 会被拒（format v4 message requires a producer-owned source kind，实测错误事件）。prompt() 自带 requestId 幂等去重，正好解决重试重复投递。
  • whenIdle() 是“整个 agent 停稳”（含排队工作），不是“某条消息结算” ⇒ 多生产者并发时结果归属要靠消息 id 锚点 + agent/inbox/spliced 验证消费（照 vssaros-agents/lib/relay.js 的 pending 手法）。
  • 官方先例：dsh-subagent-in-process-driver/lib/index.js:204-252（一次性子代理：followup→whenIdle→snapshotEvents→fold）；dsh-webhook/lib/index.js:148-219（建会话完整顺序：preset resolve → workspaceRegistry.create → agents.create(+setup mount preset) → attachSession → permissionPresets.set → sessionTitle.rename → followup，失败路径 detach+dispose 回滚）。vssarosRuns 照这个顺序写即可，把 followup 换成 controller.prompt。
  • ⚠ 调度 bundle 的 time-context 会给每个步骤追加一条持久时钟用户消息 ⇒ “最后一条用户文本”不一定是我们的提示词（断言和触发逻辑都不能只看末条）；同时这是 token 开销。

D4 · 无人值守审批 已验证（语义有重要订正）

  • 应答者可行：挂 approval/request 按会话策略返回 allowed-once / rejected 实测生效（Spike 5a deny、5b allow，写盘与否都与策略一致）。注册在根 ctx 即可收到全部 agent 的请求（scoped waterfall 对无标签侦听放行）。
  • 订正：“没有应答者就 fail-closed 成 unavailable”在 web 组合里不成立——dsh-api-remotes 的 Host 侦听总是接住 approval/request 转发进客户端队列，没有浏览器连着时请求挂起（Spike 5c 实测：90 秒超时、写操作未执行、回合不结束）。⇒ 我们的应答者必须充当最终应答者：背景 origin 的会话 deny-by-default + 有超时，绝不 next() 给会挂起的下游。
  • 审批结果有三个合法去向：IM 卡片（渠道）、IDE 通知（前台在跑）、按 preset 白名单自动放行；其余一律拒并把原因写进回合结果。
  • 工具侧照 vssaros-browser 先例：自己在 execute 里发起 approval.request 并判结果（拿不到 allowed-once 就抛错）⇒ 任何部署下默认拒绝，比只挂 tools/pre-execute 钩子更稳。

S3 · 官方调度 bundle 的可装性与语义 已验证

  • 往 profile 的 dsh.profile.bundles 追加 @deepseek-ai/dsh-experimental-schedule-bundle 即可（Spike 2a：--dump-config 出现 time-context / schedule / ui-schedule 三行，Host 正常启动）。
  • 运行时：schedule 服务对插件开放（ctx.schedule.create(sessionId, {title, prompt, after_seconds…}) 实测成功）；schedule_create 出现在 root agent 的模型工具表；到期提醒真的作为新回合送达原会话（mock 收到 [SCHEDULE REMINDER] 消息并跑了一轮，Spike 6c）。
  • 差异要点（写进 2.1 的实现说明）：提醒投递到原会话；cron 是五字段 Vixie 方言（最小 1 分钟，拒 L/W/#/@daily/秒字段）；投递是至少一次（崩溃可重复）；headless 组合挂不了（需要 Web Session controller）⇒ 调度页只能活在有 Web 的组合里。
  • 旧任务迁移：ctx.schedule.create 程序化创建 ⇒ 不必经模型；legacy 那 5 个文件里的任务定义读出来逐条创建（每个任务绑定一条专属会话），不支持的写法逐条报出。

S2 · 官方 agent-team / jobs / goal 与看板 源码取证

结论：官方 agent-team 接不住“看板驱动自动执行”——它的任务板只存在于 Lead 会话日志里（与 taskboard.json 不互通）、不自动派工、teammate 不能单独指定模型、且是 experimental 无稳定性承诺。看板 runner 在 vssaros-kanban 插件里自己写：ctx.agents.create + sessionController.prompt 驱动执行；要“一直做到完成”再叠加 ctx.goals + goal-round-driver；ctx.jobs 只登记取消与进度（jobs-local 进程内、不持久，重启后由 runner 按 taskboard.json 对账恢复）。Crew 直接退役（MVP + 模拟执行，只有一个视图在用）；Swarm 引擎退役，多 agent 协作交给官方 agent-team（用户可选开启）。decompose / specify 官方没有 ⇒ 用一次性 subagent + outputSchema 实现。注意 agent-team profile 会禁用普通 subagent 工具，和我们的 preset 冲突 ⇒ 默认不开。

S4 · 官方工作流能力边界与方案 B 的可行性 源码取证

  • 官方 dsh-workflow = 模型写的一次性 JS 编排脚本（agent/parallel/pipeline/phase/log）：仅前台收集、不持久化、不支持保存/嵌套/恢复、脚本里没有工具/HTTP/文件 API、agent() 的 opts 只有 label/phase/schema/provider/model（preset、工具白名单、超时都不支持）、取消 = 杀 PTC 进程。与我们的节点图（持久化 DAG + checkpoint 续跑 + Comfy/媒体/AskUser 节点）语义不等价。
  • 方案 B 可行：冲突按 cordis 服务名判定（重名 provide 抛错）⇒ 用新服务名 vssarosWorkflowEngine、直接继承 cordis Service 而不是 WorkflowEngine（基类构造器把名字写死成 workflowEngine）、不发 workflow/* 事件，就不冲突。
  • agent 节点复用官方 ctx.subagents.start（比 agent() 能力强：persona / toolFilter / outputSchema / maxDepth），不必自己开会话；script 节点可转交官方 ctx.workflowEngine.start；Comfy / 媒体 / AskUser 节点经 vssarosBridge 回 IDE（留壳）。注意：subagents.start 的 parent 必须是活的 Agent ⇒ 后台触发时先用 ctx.agents.create 建一个根会话当 parent。
  • 附带发现的存量缺陷（与本重构无关但值得记）：内置 goal-workflow.json 在宿主引擎下不能按预期运行——ifElse 的出边端口名（branch-done/branch-not-done）与引擎只认 branch-N 不匹配，会退化成走所有下游；两个 Execute/Judge 节点是 prompt 类型，只追加消息不调 LLM。
