§0 结论

可行，但不能一次切。dsh 已接管前台聊天框，19 个插件提供 107 个工具；但所有后台入口仍跑 legacy 自研引擎（渠道、Pocket、调度器、看板自动执行、工作流、KB 导入、HTML 面板）。legacy 引擎要等这些入口全部迁走才能删。因此方案按“绞杀者”模式推进：先把入口迁进 dsh，再收工具缺口和 UI，最后删引擎。分 6 个阶段，每个阶段都能单独发布、单独回滚，预计 16–22 周。

§1 “dsh 插件范式”在本项目里落成 8 条准则

准则取自官方成文纪律（纪律镜像、A–I 合规基准）以及已经定下的方向（能力归 dsh、壳可替换）。后面每一项工作都用这 8 条检查。

#准则在本项目里的含义
P1能力归属三分法dsh 官方已有 → 删掉 legacy 实现，不再迁；与宿主无关 → 写成 dsh-plugins/ 插件；必须用 VS Code 平台（编辑器、diff、终端、webview 渲染）→ 留在壳里，经 ide.request 暴露（先例 dshIdeCapabilities.ts）
P2清单是唯一真源插件 package.json 的 vssaros.* 字段驱动壳的 ActivityBar、视图宿主、IDE 能力授权；壳里不再有按模块硬编码的表。验收标准是“新增一个模块，壳代码改动为 0”
P3跨包行为走 cordis 服务，跨包 UI 走 slot插件之间不 import；需要共享的逻辑做成服务插件（见 1.3），不再靠“逐字节拷贝 + 守卫”
P4会话日志是唯一真源后台入口发起的回合也必须是 dsh 会话；不新增自定义事件类型；按会话的状态用 sessionProjections
P5审批放在组合层工具本身不带审批；无人值守会话用 permissionPreset 加按作用域挂的 approval/request 应答者
P6最弱机制优先按 tools.restrict → guard → waterfall → assemble 的顺序选，prompt 只走 section/variable/context
P7每个插件四件套REAL-composition 测试、dispose 证明、persistence.json 登记、工具快照；外加行为级探针和反向突变（沿用本仓纪律）
P8不 fork、不 patch、官方件优先先查官方有没有：dsh-schedule / dsh-webhook / dsh-workflow / dsh-jobs / dsh-permission-presets / dsh-user-approval / dsh-goal / experimental agent-team（全都已在 0.2.0-rc.2 运行时里）

2.3 壳侧偏离范式的地方（重构的首要切入点）

  • 模块表写死在壳里：新增一个模块要改 4 处，分别是 DshModuleId、DSH_BUILTIN_MODULES（dshModuleContainers.ts:41）、DSH_MODULE_CONTAINERS（:100）、MODULE_VIEW_HOSTS（dshActivityBarContribution.ts:64-79）。插件清单里的 vssaros.activityBar 不是运行时数据源，只靠测试和壳表保持一致。这违反 P2。
  • 同一个贡献注册了两次：DshActivityBarContribution 在 dshHarness.contribution.ts:545 和 dshActivityBarContribution.ts:209 各注册一次。
  • 插件之间靠拷贝复用代码：pageShell.js 7 份、dataRootOf 9 份、dshHomeOf 5 份（没有逐字节守卫）、lock.js 4 份（web-content-import 那份没被守）。这违反 P3。
  • 后台入口直接调 legacy 服务：壳里没有“发起一次 Agent 运行”这层中立抽象。
  • agentStudio 被外部依赖的面：agentStudio 外有 29 个文件 import 它；dshHarness 有 6 处反向依赖 agentStudio（EditorInput、skillRoots、canvasOpsBridge、kbVaultState、两个工厂）；app.ts:174-195 直接注册了 14 个 legacy 主进程通道。

§3 目标架构

L2 壳（VsSaros / VS Code fork）——只做 7 项契约和通用宿主 进程与运行时托管（supervisor、租约、升级闸）· 控制桥客户端 · ide.request 能力执行器（编辑器、diff、终端、canvas / mindmap、工作流编辑器、KB blocks 编辑器）· 视图宿主（聊天实例、插件页的侧栏和编辑区）· 主题桥 · provider / 凭证同步 · 工作区注册表（IAgentStudioService 迁到中立层）· 按清单驱动的 ActivityBar
L1 VsSaros 插件（dsh-plugins/），分 4 层 基座（始终开启、不可停用）：bridge · chat-surface · ide · foundation（新增）
模块（可启停，开启后出 ActivityBar 图标）：kb · memory · codebase · kanban · workflow · agents · skills / mcp · media · sessions · dashboard · scheduler（新增）
入口（无界面或只有设置页）：channels（新增） · pocket 路由（新增） · kanban runner · workflow engine
工具：browser · unreal · web-content-import · media-gen（并入 media） · archify
L0 dsh 官方运行时（不改动，跟随官方升级） agent loop · session controller · tools / skills / mcp-client · user-approval / permission-presets · schedule / webhook / jobs / workflow · web client 与 slots

3.1 一次后台运行在目标态下怎么走

入口插件（channels / scheduler / kanban runner / workflow engine / pocket 路由）
   └─ ctx.vssarosRuns.start({ origin, sessionKey, workspacePath, agentPreset, permissionPreset, prompt })
        ├─ sessionController.create({ sessionId: 由 sessionKey 派生, ... })   // 同一个 IM 会话 / 同一个看板任务 → 同一条 dsh 会话，幂等领养
        ├─ workspace.attachSession → sessionController.prompt({ mode: 'queue' })
        └─ awaitTurn(sessionId) → { finalText, stopReason, toolSummary }     // 需要 Spike S1 确认官方的回合结束信号
   审批：permissionPreset 先挡一层；剩下的 ask 交给按 origin 挂的 approval/request 应答者
        （channels → IM 卡片；IDE 在前台时 → IDE 通知；其余入口 → 拒绝，并把原因写进结果）

vssarosRuns 是一个 cordis 服务（放在 foundation 或 bridge 插件里）。壳侧过渡期的调用方经桥上新增的 session.run 调用同一个服务。整条链只用官方已有的 session controller、approval 和 permission preset，不新增事件类型。

§4 风险评估

可能性和影响按 高 / 中 / 低 三档。“触发信号”指出现什么现象就说明这个风险正在发生。

ID风险证据可能性影响缓解触发信号
R-01迁移成果不在版本控制里dsh-plugins/ 343 个文件 tracked = 0已发生极高Phase 0 第一件事就是入库（需要你确认提交）；CI 加“dsh-plugins 不得有未跟踪文件”的检查—
R-02无人值守会话卡在审批上dsh-user-approval：没有应答者就返回 unavailable 并拒绝；kanban、kb、memory、workflow、skills 等 9 个以上写工具挂了 ask高高后台专用 permission preset，加按 origin 挂的应答者，拒绝时在结果里写明原因（1.5，D4）后台任务结果里出现“unavailable / denied”

R-09数据双写 / 迁移出错taskboard.json 两端都写（共用锁协议）；bridgeStore 在主进程；legacy chat-history 格式中高persistence.json 的 owns 只允许一个写者；迁移前先备份并按内容校验；切换期间旧端只读check-persistence-catalog 报两个写者
R-10用户可见入口中断飞书 / Telegram 机器人是在线服务中中按机器人独占切换并配租约，绝不两个引擎同时连同一个机器人；先切测试机器人重复回复或掉线
R-11并行会话互相踩已发生：并发会话把 kb 改坏（uniqueCanvasPath 未导出）高中每个插件同一时间只指派一个会话改；每一刀都 bump 版本；Host 在跑时不替换仓库源码探针安装到了“陌生版本”
R-12守卫“假绿”多次出现：静态扫描没覆盖、断言 markup 存在不等于交互可达中中每一刀都要有行为级探针 + 至少 2 次反向突变；REAL-composition 测试覆盖基座插件（1.6）突变后测试仍然是绿的
R-13打包和体积dsh-runtime 310 MB 随包；dsh-plugins 31.4 MB；webview 产物 31.1 MB；“dsh-plugins 进安装包”这一步只补了代码，没有真跑过一次完整打包中高0.4 真打一次安装包，建立体积基线；删 legacy 时同步删 webview 里不再用的入口安装后模块页全部 404
R-14退役 legacy 时耦合面断裂29 个外部 import、6 处 dshHarness 反向依赖、app.ts 里的 14 个通道低高先抽中立层（5.4），删除前跑 tsgo 加全量测试编译错误
R-15插件第三方依赖现有 19 个插件都是 0 个 npm 依赖（事实上的纪律）；渠道等新插件可能想引 SDK中中保持 0 依赖：需要的库 vendor 进插件，并写进 files离线安装失败

§6 每一刀的标准作业（完成定义）

动手前

  • 台账里登记，状态从 planned 改为 dual
  • 涉及界面的改动，先出 doc/ 下可交互的 mockup，确认后再写代码
  • 认领插件所有权：同一个插件同一时间只有一个会话在改
  • Host 在跑时不替换仓库源码，先停 Host 或改用副本

交付时

  • 插件 bump 版本（最后一次改动之后再 bump）；补齐 files；tools-snapshot.mjs --write
  • REAL-composition 测试 + 行为级探针 + 至少 2 次反向突变
  • persistence.json 登记写者；有写工具的挂审批
  • 验证范围按改动面选择，不必每次全量跑
  • 开关默认值的变化单独一刀，方便回退

§9 不做 / 暂缓

  • 不 fork、不 patch dsh；不新增自定义会话事件；不通过 system-prompt/assemble 改 prompt 文本。
