kb_build 的 build 半边 —— dsh 侧编排方案

2026-10-12 · 承接 知识库续搬 dsh §4.4（第 3 期的 build 半边）· 读者：决定"dsh 里的会话能不能自己把素材构建成笔记"的人。
本文是设计方案，不含实现（真构建会写 vault、会花模型额度 ⇒ 按方案 §4.4 的约定"先出稿"✓）。

一句话结论：能由插件自己编排 ✓ —— dsh 把"起子代理"与"进后台任务名册"都做成了 插件可注入的服务（不是只有模型能用的工具 ✗）。本方案的做法是： kb_build mode="build" 里用 ctx.jobs.start() 起一个后台任务，任务里用 ctx.subagents.start() 起一个子代理去读素材、写笔记 ⇒ 立即返回 jobId， 进度/取消直接复用 dsh 已有的 jobs 面板与 job_output/job_list/job_kill ✓。

1. 取证（先证明"插件的确能这么干"，再谈方案）

#事实出处（本轮实测，均 ✓ 已核对）
E1 subagents 是一个 服务，且插件可注入；起子代理的调用是 ctx.subagents.start(provider, request) @deepseek-ai/dsh-subagent 自身注释原话："foreground one-shot delegation keeps calling ctx.subagents.start()"； dsh-tool-subagent/lib/index.js 里真的这么调 ✓；另一个包 dsh-tool-subagent 的注入面是 ctx.inject(['tools','subagents','systemPrompt'], …) ⇒ 服务名就是 subagents ✓
E2 后台任务同理：jobs 是服务，ctx.jobs.start(spec) 注册一个任务并返回 jobId dsh-tool-subagent/lib/index.js： 
const jobs = runtimeCtx.get("jobs");
jobId: jobs.start({ kind: "subagent", label, owner: parent.id,
  run: () => ({ cancel: (reason) => …, done: settleStart(subagents.start(provider, req)) }) })
⇒ kind / label / owner / run() → {cancel, done} 就是全部形状 ✓
E3 工具的 执行上下文带会话身份（owner 要用它）+ 取消信号 @deepseek-ai/dsh-tools 的 ToolExecutionInput：readonly agent?: Agent （注释原话："The agent on whose behalf the call runs (set by the agent loop)" ✓）＋ readonly signal: AbortSignal ✓ ⇒ 我们的 execute(params, exec) 里能拿到 exec.agent 与 exec.signal ✓
E4 任务名册是 按 owner 隔离的，且自带输出环 / 事件流 / 模型侧三件套 dsh-jobs README：producer 注册 kind + 一行 label ⇒ 返回 <kind>-N id； 可读输出 / 列任务 / 等结算（带超时） / 请求取消；结算时事件流广播，由 dsh-tool-jobs 转成会话内通知（不用轮询 ✓）；实现是进程内的 dsh-jobs-local ✓
E5 子代理 provider 是注册式的（fork / spawn 等），并有授权面（最大深度 / 并发上限 / 允许的模型） dsh-subagent-fork-in-process / -spawn-in-process 各自注册 provider ✓； dsh-client-ui-settings-subagent 暴露 { maxDepth, maxActiveSubagents } 与允许的 provider/model ✓
取证顺手纠正一个直觉：模型面的 subagent / job_* 工具与这里的服务面是两组包 （dsh-tool-subagent vs dsh-subagent）⇒ "模型能起子代理"并不能推出"插件也能" ✗。 本方案成立靠的是 E1–E3 那三条服务面的证据 ✓。

2. 方案（P0：最小可用形态）

kb_build({ vaultId?, mode: 'build', batch? })        // batch 缺省 20（照真源 MAX_ASSETS ✓）

execute(params, exec):
  1. preview 一遍（同一份口径 ✓）⇒ pending 清单；空 ⇒ 直接回"没有待构建素材"（不起任务 ✓）
  2. 若 ctx.get('jobs') / ctx.get('subagents') 任一缺失 ⇒ 明确报错（不是静默退回 preview ✗）
  3. jobs.start({
       kind: 'kb-build',
       label: 构建 ${n} 份素材为笔记,
       owner: exec.agent.id,              // E3：来自工具执行上下文 ✓
       run: () => {
         const ac = new AbortController();
         return {
           cancel: () => ac.abort('kb-build killed'),
           done: ctx.subagents.start(PROVIDER, {
             label: kb-build ${vaultId} ${batch} 份,
             signal: ac.signal,
             prompt: 见 §2.1,
           }),
         };
       },
     })
  4. 立即返回：jobId + 本批清单 + "去哪看进度/怎么取消"（照真源"发起即返回"的理由 ✓）

为什么不 await：真源的注释写得很清楚（构建是分钟级长任务，await 会把调用方那一轮对话卡住数分钟， 且进度发生在另一个会话里、调用方看不到）✓ —— dsh 侧同理，而且这里还多一层： jobs 本来就会把结算变成会话内通知 ⇒ 不 await 反而更贴合基座 ✓。

2.1 子代理提示词契约（要写死，不然等于没编排）

  • 读：只能读清单里那些素材（用 kb_read；素材路径与 preview 给的完全一致 ✓）。
  • 写：只能用 kb_write_note 写进 笔记/<分类>/<标题>.md —— dsh 原生 write/edit 在 vault 上会吃 FS_SANDBOX_DENIED ✗（这条已经写在工具描述里 ✓）。
  • 不许动 库/（素材区）与导航文件（index.md / 知识体系.md …）✓。
  • 收尾：回报"新建/更新了哪几篇 + 哪几份没做成 + 为什么"（子代理的最终回答会进 job 输出 ✓）。
  • 上限：本批 ≤ batch 份；剩余留给下一次调用（照真源 ✓）。

7.1 D2（审批疲劳）的取证与做法

取证结论：基座没有"记住本批"这一档 ✗ —— 本轮在 .runtime/<版本> 里逐行读了审批契约： 客户端决定只有 ApprovalDecision = 'allowed-once' | 'rejected'， 结果集 ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'， 且 dsh-user-approval 的注释原话是 "'allowed-once' is the only grant" ✓； 全局旋钮只有 ApprovalPolicy = 'ask' | 'never'（要么每次问、要么根本不问 ✗）。 ⇒ 要在我们这层实现一个有界授权 ✓（见 §7.2）。

7.2 批授权：有界 / 有时限 / 有归属（三条缺一不可）

⚠ 定性修正见 §8：这一节当初是按"解决审批疲劳"写的（"不再逐篇询问" ✓），但真机（§8）证明平台把 委派出去的孩子钉成 approvalPolicy: 'never' ⇒ 子代理根本没有审批通道 ⇒ 这份授权其实是子代理唯一能写成笔记的途径（不是"少问几次" ✗）。三条不变式本身不变，但含义更重了 ✓。

  • 什么时候开：只有 kb_build mode="build" 被用户批准之后（执行期 ⇒ 批准已成立 ✓）才开， 且在任务起成功之后才开 —— 顺序反过来的话，起任务失败会留下一个没人用的空白授权 ✗ （探针专门钉了这条：先成功起一次、再用掉 1 篇、再让下一次失败 ⇒ 剩下的必须被清掉 ✓）。
  • 有界：只覆盖本批篇数（consumeGrant 递减，只有 kb_write_note 记账 —— 建目录也是围栏内的写、同样不该狂弹窗，但它不产生"笔记篇数"⇒ 不记账 ✓）。
  • 有时限：30 分钟到点自动失效（长任务也要收敛 ✓）。
  • 有归属：只对同一个 vault ＋ 同一个会话（exec.agent.id）生效 —— 否则 A 会话的授权会替 B 会话放行 ✗；身份拿不到就一律不放行（fail-closed：宁可多问一次 ✓）。
  • 披露点：用户看到的唯一提示就是那张卡的文案 ⇒ 文案里必须写明"批准后本批写入本 vault 的笔记不再逐篇询问（上限 N 篇、30 分钟后失效）" ✓ （p3-26 专门断言这句在 ✓）。config.batchGrant=false 可整个关掉（退回逐篇问 ✓，可复核、可回退）。

7.3 本轮的三个教训（都是自己踩的）

  • 编排的正确性只能靠反向突变来验 ✓：prompt 的类型、parent 的对象同一性、 toolFilter 是白名单还是黑名单 —— 这些写错也不报错，只会"起了个没任务的子代理"或"子代理啥也干不了" ✗。 而突变要跑 6 次 ⇒ 挂在一个几分钟一轮的探针上就没人愿意跑 ⇒ 本轮实测被外层掐掉两次、 还把突变残留在源码里（第二次靠"备份 + 启动即自愈"补回 ✓）⇒ 这就是把编排面拆成 p3-44（秒级）的理由 ✓。
  • 一条断言可能"没有鉴别力" ✗：最初"起任务失败要清授权"那条只放了 1 份素材 ⇒ 授权只有 1 篇、先被正常用光 ⇒ "没清"与"清掉了"表现完全一样 ⇒ 突变 M3 抓不出来（实测 6 条只命中 5 ✓）。 改成"授权有 2 篇、用掉 1 篇"后立刻能抓住 ✓（所以突变是必须跑的：它纠正的不是实现，是测试本身 ✓）。
  • 别在模板串里嵌反引号 ✗、别在块注释里写 glob 通配（其中的斜杠加星号会提前闭合注释 ✓）—— 两条本仓都记录过，本轮又各踩一次 ⇒ 都写进注释留痕了 ✓。

8.1 真机 bug ①：maxDepth: 0 让任务起来就失败

MOCK_LLM_TOOL_RESULT "(no new output) [status: failed, SubagentDepthError: subagent depth 1 exceeds maxDepth 0]"

真源里 maxDepth 的语义是 "孩子深度的绝对上限"，不是"还能往下派几层" ✗✗ —— dsh-subagent/lib/index.js:400-403 的 resolveChildDepth() 拿"父深度 + 1"去比， 超了直接抛 SubagentDepthError；而服务自己的 config schema 缺省就是 maxDepth: 1 （同文件 L2822）✓。我原以为 0 ＝"孩子不许再派"，实际是"根本不许有孩子" ⇒ 任务起成功、jobId 也返回了，但子代理一个回合都没跑 ⇒ 现象是"看起来一切正常、笔记却是空的" ✗。
