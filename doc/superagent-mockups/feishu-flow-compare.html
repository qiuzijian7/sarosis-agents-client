04 · 一句话结论

两边共享同一套骨架：lark-cli 入站 → 确定性 Trigger → SQLite + effect 队列 → 2 秒 passes → 单一 master Session + 每工单 worker Session。原型不是简化版，它同样有 store.ts / effects.ts / passes.ts / sessions.ts。

真正的结构差异只有一条：本项目在「建单」与「启动 worker」之间插入了组队方案与人工同意闸门。原型 tickets.ts:54 建单即 executor.start()；本项目 tickets.ts:59 先写 team={state:'proposing'}，:64 的启动条件不成立，直到 :96 的 approveStaffing() 才启动。

由此派生出本项目全部新增复杂度：team_request 唤醒、orchestrator_team_bots/propose、7 天方案复用、飞书「同意」纯代码快路径、团队步骤、步骤审批、用量账本、结果回飞书；以及为了抵消模型延迟而加的 fastExplicitTasks 规则直建单。
