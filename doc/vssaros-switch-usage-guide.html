1 号池注入

把 CodeBuddy / ChatGPT 的上游凭证提交进共享号池，系统据此创建可调度渠道。提交人拥有该条凭证的查看、启停与删除权，凭证本身永不回显。老用户从旧站迁移过来的账号与 Key 已经自动复用，无需重新注入。

支持的平台与凭证

Platform 01
CodeBuddy
ck_ API Key 或三段 JWT。落到渠道类型 64，默认上游 copilot.tencent.com/v2，模型取全局 CodeBuddy 目录。
channel type = 64
Platform 02 · 订阅
ChatGPT（Codex）
粘贴 Codex OAuth JSON，必须含 access_token 与 account_id，refresh_token 用于自动续期。落到渠道类型 57。
channel type = 57
Platform 02 · API
ChatGPT（官方 Key）
sk- 开头的官方 API Key。落到渠道类型 1，默认上游 api.openai.com。系统按凭证形态自动识别，不用手选。
channel type = 1

操作步骤

STEP 1
登录并打开首页注入区
访问中转站首页，向下滚动到「号池注入」。未登录会显示「登录后注入」并禁用表单；从旧站迁移的账号可用原 sk- Key 或 TOF 登录。
STEP 2
选择平台、粘贴凭证
选 CodeBuddy 或 ChatGPT。ChatGPT 会把 OAuth JSON 重建成已知字段白名单，丢弃未知字段；sk- Key 则按官方 API Key 处理。
STEP 3
填写名称与权重并提交
名称可留空自动生成；权重 1–1000，默认 1。提交后系统做去重与限额校验，并立即建立渠道、abilities 与路由缓存。
STEP 4
在「我注入的凭证」里管理
列表只显示脱敏片段（如 ck_g****4Adk、oauth:acct****6655），可随时停用/启用或删除。同样的卡片也出现在「API 密钥」页。

规则与限制
  • 每个账号默认最多 5 条（三个平台共享，POOL_MAX_KEYS_PER_USER 可调）；完全相同的凭证会拒绝重复注入。
  • 凭证进 group=default 全局共享调度，不是仅自己可用；贡献者只拥有管理权。
  • 用户只能看/改/删自己的；「非本人」与「不存在」返回同一提示，避免探测。
  • 渠道类型 57 上游只提供 /v1/responses 等端点，不支持 /v1/chat/completions；类型 64 则相反。
  • 目前没有贡献者结算 / 审核流程；ChatGPT 不认 session token。
API 速查（给脚本 / 排障用）

GET /api/user/pool_keys 我的列表 · POST /api/user/pool_keys 注入（platform + credential + name + weight）

PATCH /api/user/pool_keys/:id 改名 / 改权重 / 启停 · DELETE /api/user/pool_keys/:id 删除

旧字段 api_key 仍兼容；响应含 platform、type、key_hint，不含明文凭证。

2 LLM 输入输出详细日志

在原有「使用日志」的计费元数据之外，按 request_id 记录每次请求发往上游的正文与模型返回的正文。正文存独立表，不塞进日志列表字段，也不写进审计日志。

原来就有
计费 / 诊断元数据
时间、用户、模型、渠道、token 数、耗时、是否流式、request_id、重试链、计费明细。日志详情里的「Content」是计费说明模板串，不是 prompt。
本次新增
请求正文 + 回复正文
请求侧记录转换后发往上游的 JSON（或 PassThrough 原始报文）；响应侧从 SSE / JSON 中提取模型最终答案。一次重试记一条 attempt。

谁能看

角色自己的请求所有人的请求入口
普通用户可查看不可使用日志 → 详情
zijianqiu可查看可查看使用日志详情 + /api/user/log_contents/all

白名单可在运行时通过 PUT /api/user/log_contents/settings 的 viewers 调整，默认 zijianqiu。

操作步骤

STEP 1
打开「使用日志」
管理员在日志列表里能看到所有人的记录，普通用户只看到自己的。列表按时间倒序，可按模型 / request_id 过滤。
STEP 2
点开某条日志的「详情」
原有详情展示 token、耗时、渠道、计费明细等。页面会按该条日志的 request_id 自动拉取正文。
STEP 3
查看「请求 & 回复正文」区块
按尝试序号分组展示：请求正文是脱敏后的 JSON，回复正文是模型答案文本；每段都有复制按钮。
STEP 4
按需关闭 / 调整保留期
管理员可关闭记录开关或调整白名单；保留期由 LOG_CONTENT_RETENTION_DAYS 控制，默认 7 天。

隐私、体积与开关
  • 落库前脱敏：密钥（sk-/ck_/Bearer/JWT）、手机号 / 邮箱 / 身份证、内联 base64 图片；请求体里的敏感键（authorization、api_key 等）整体替换。
  • 请求与回复各限 20000 字符，超出截断；上游响应捕获上限 1 MB，不影响原 handler 读取。
  • 默认开启、默认保留 7 天；LOG_CONTENT_ENABLED=false 或设置接口可一键关闭（只影响之后的请求）。
  • 正文不进入日志导出、统计聚合与 AuditLog（审计日志代码明确禁止记录 body）。
当前覆盖范围
  • 采集挂在 TextHelper 链路：chat completions，含 CodeBuddy 强制流式后聚合出的完整回复。
  • 其它 relay mode（Claude / Gemini / Responses / Audio / Images / WSS）暂不采集正文；日志导出也尚未带正文。
  • 回复正文只保留最终答案文本，推理片段与工具调用原文不单独存；错误请求会保留脱敏后的错误体摘要。
API 速查与数据位置

GET /api/user/log_contents 本人列表 · GET /api/user/log_contents/:request_id 按请求查全部 attempt

GET /api/user/log_contents/all 白名单 / root 全量列表（可按 user_id 过滤）

GET / PUT /api/user/log_contents/settings 查看或设置 enabled / viewers / retention_days / can_view_all

数据落在独立表 log_contents（字段 request_id / user_id / attempt / request_content / response_content / ...），日志主表 logs 结构未改。

3 常见问题

我是旧站用户，还需要重新注入 Key 吗？
不需要。旧站 /api/auth/users 的 9 个账号与原 sk- Key、以及 codebuddy.direct_nodes 里的 1 把 ck_ Key 已导入本项目；账号按 owner_login 复用（zijianqiu 没有重复建号），原 Key 可直接访问新中转站。注意导入账号没有迁移密码，只能用原 Key 或 TOF 登录。
为什么用原 sk- Key 调用会 401？
早期鉴权会把 sk- 之后的 key 按 - 截断，而旧站 Key 内部含 -。已修复为「完整 key 精确命中优先、截断兼容回退」。若仍 401，先确认本机 CPU / 磁盘保护没有在鉴权前拦截——它会返回 503 掩盖真实结果。
注入的凭证会被别人看到吗？
不会。列表与接口只回脱敏片段，且按 owner_id 隔离；管理员也只能通过渠道管理页看到自己有权查看的渠道。号池调度本身是全局共享的，但凭证内容不外泄。
日志详情里「请求 & 回复正文」是空的？
常见原因：这条日志产生时记录开关是关闭的；超过 7 天保留期已被清理；请求走了尚未覆盖的 relay mode（如 Images / Audio / WSS）；或者该日志根本不是 chat 消费日志（充值 / 登录 / 管理类没有正文）。
能不能关掉正文记录？
可以。管理员调 PUT /api/user/log_contents/settings 传 {"enabled":false}，或启动时设 LOG_CONTENT_ENABLED=false。关闭只影响之后的请求，已落库的正文需要等保留期清理。
