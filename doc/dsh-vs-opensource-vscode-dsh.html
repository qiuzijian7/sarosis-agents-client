VsSaros × dsh 与开源 VS Code + dsh 项目对比分析

2026-10-18 · 样本：deepseek-harness-for-vscode 0.6.1 / dsh-vsc-integration 0.10.3 / dsh-vscode 0.0.5 / dsh-vsc 0.2.6（另有 dsh-vs-sidebar / dsh-ui / dsh-cline 见既有调研）· 所有数据现取

一、一句话结论

这不是「两个都做 dsh 集成的项目」之间的差距，而是「扩展」与「宿主改造」两种形态的差距。

开源项目全部是 VS Code 扩展（package.json 里 engines.vscode + main: extension.js），在别人的编辑器里开一个 dsh 侧栏；本项目是 VS Code fork（改了 src/vs 本体），把 dsh 当插件体系内嵌进工作台。

⇒ 我们的能力上限更高，但必须精确划定高在哪：真正 fork 独占的只有三条——① 新建 workbench part（agentPart）从而用原生 WebContentsView 承载 dsh；② 替换聊天 UI 本体（扩展要 chatSessionsProvider，而它是 proposed API）；③ part 级布局与可见性联动。

常见误判：ActivityBar 一级图标（contributes.viewsContainers.activitybar 是 stable）、工具注册（lm.registerTool 无 proposed 检查）、命令/菜单（contributes.commands）、多根工作区（workspaceFolders 本就给全部根）——这四项扩展都能做，我们选了 fork 是产品取舍，不是 API 限制。把它们当成 fork 的必要理由，会让 fork 的辩护站不住脚。

三、六维逐项分析

3.1 集成深度：fork 的真正价值

真正只有 fork 能做的（已逐条核对 API 源码）：

  • 新建 workbench part——扩展的视图容器只有三个落点（activitybar / panel / secondarySidebar，见 viewsExtensionPoint.ts:77-90），没有第四个位置。我们的聊天区 agentPart 是 fork 才有的 part ⇒ 才能用 原生 WebContentsView 承载 dsh 页面（扩展只能用 iframe 化的 webview，进程模型与消息通道都不同）。
  • 替换聊天 UI 本体——扩展的 createChatParticipant 是 stable，但那是「往原生 chat 里加一个参与者」；要接管整个 chat session UI 得用 chatSessionsProvider，而它是 proposed API（extHost.api.impl.ts:1659 的 checkProposedApiEnabled）⇒ 无法面向普通用户发布。
  • 布局与可见性联动——part 级别的显示/隐藏、与编辑器区的互斥（workbench-e2e.mjs 钉住「dsh 页面不出现在 mainPart」），扩展无从干预。

看起来像 fork 独占、其实扩展也能做的（容易误判）：

  • ActivityBar 图标 + 容器——contributes.viewsContainers.activitybar 是 stable manifest 能力。我们的优势是模块化生命周期（16 个模块各自独立挂载/卸载、参与 workbench 布局持久化），不是「扩展做不出一级图标」。
  • 工具注册——lm.registerTool 在 API 里没有 proposed 检查（extHost.api.impl.ts:1828）⇒ 扩展也能注册语言模型工具。我们走 dsh 插件是为了与 dsh 生态同构，不是为了绕过 API 限制。
  • 命令 / 菜单 / 快捷键——扩展 contributes.commands 全支持。
  • 多根工作区——见 3.3，workspaceFolders 本来就给全部根。
  • 壳侧编辑器保留（工作流 litegraph / KB blocks）——扩展也能用 WebviewPanel 做，只是我们把它们做成了壳内原生编辑器。

代价：真正独占的那三条都依赖「我们在 VS Code 源码里」，上游一改就可能有冲突。

3.2 工具面：从「能聊天」到「能干活」

开源样本的定位是 「给 VS Code 加一个 dsh 聊天侧栏」——模型能读写文件、跑 bash，就这些。本项目的定位是 把 20 个业务域做成模型可调用的工具：

领域工具数开源样本有无对应
memory23无（部分样本装了 dsh-memory-plugins，但非自研集成）
codebase21无
kanban17无（这是本项目差异化的核心之一）
kb（含语义检索双向 / 飞书同步）17无
media（生成 / 视觉 / 视频）8无
workflow6无
agents / skills / mcp6 / 5 / 2部分（dsh 官方有 fs/bash/skill，无 agent 编排与市场）
unreal / browser7 / 1无

优点：模型在一个会话里能跨域操作（查图谱 → 建卡 → 写笔记 → 发飞书评论），这是扩展形态给不了的纵深。

缺点：127 个工具带来上下文压力——所以才有工具集分桶（toolsetConfig）、按需 defer、tool_search 这些机制；开源样本因为工具少，不存在这个问题。这是「功能丰富」换来的复杂度。

3.3 多根工作区：我们唯一明显领先的一维

既有调研（dsh-vscode-ecosystem-comparison.html）已确认：7 个样本全部退化到 workspaceFolders[0]，没有一个真正支持多根。最接近的 dsh-vs-sidebar 也只是「在多个根之间切换 + 粘性根会话」。

本项目有 DshMultiRootBindingService（合并 worktree / 单向 dsh⇒IDE / 视图关联），属于可对外讲的差异化。

但这不构成 fork 的理由：VS Code 扩展 API 的 workspace.workspaceFolders 本来就返回全部根、且 onDidChangeWorkspaceFolders 是 stable 事件。样本退化到 folders[0] 是实现偷懒，不是 API 限制。⇒ 这条领先是「别人没做」，扩展形态完全追得上。

3.4 Host 生命周期：我们比预想的厚

既有调研已修正过一轮误判。核对现状：拥有者记录（owner-<runId>.json）、孤儿回收（planOrphanHosts，拥有者活着就不动）、结束进程树、启动锁（DshHostLeaseStore）、端口复用（host-port.json）、客户端计数自退——这些样本里被点名的机制我们基本都有。

唯一真缺口：空闲自退 TTL 是 12 小时，IDE 崩掉后 Host 会攥着会话写租约到 TTL 到期；dsh-vs-sidebar 用心跳文件 + 看门狗把它压到分钟级。这一条是对面比我们强的具体点。

3.5 可维护性与升级路径：fork 的原罪

扩展模式（样本）

✓ 用户装到任意 VS Code 版本上

✓ 上游升级零成本（改 engines 版本即可）

✓ 发布物小（dsh-vsc 仅 3,742 行 / dsh-vscode 2.6MB 零依赖）

✓ 可多端复用（dsh-ui 把协议抽成零依赖包，Tauri/TUI/H5/VSCode 四端共用）

✗ 够不到宿主内部（ActivityBar 结构、编辑器区、命令注入深度）

✗ 多根 / cwd 控制权受限

fork 模式（本项目）

✓ 集成深度无上限（16 容器 / agentPart 承载 / 壳侧编辑器共存）

✓ 能做业务工具面（127 工具）与多根

✓ 有一整套结构性守卫（快照 / preset / 覆盖映射 / 台账）

✗ 每次 VS Code 上游更新都要手工消化冲突（这是长期最大成本）

✗ 发布物大（必须整包分发 IDE）

✗ 用户锁定在本产品，不能「装个扩展试试」

✗ 团队门槛高：要同时懂 VS Code 内核 + dsh 插件体系 + 业务域

3.6 当前最大的技术债：双引擎并存

本项目此刻同时存在两套引擎：dsh 引擎（官方 + 23 插件）与 legacy agentStudio 引擎（piLoop / providers / turn executor，248,057 行）。这是重构收口期的必然状态，但代价明确：

  • 认知成本：同一功能有两处实现（如 kanban 工具、媒体工具），排查时要先判断「哪套在跑」。
  • 回归噪声：当前 common 套件 653 passing / 1 failing，红项来自并行会话，但双轨期这类噪声更容易被误判。
  • 删除风险：executeFromChatOptions 调用方已归零（代码侧前置达成 ✓），但真删要等 5.1 真机验收——一条「真模型 e2e」读数。

开源样本没有这个问题——它们从一开始就只有 dsh 一套。

四、优缺点总表

本项目优点

  1. 集成深度：agentPart 原生承载 dsh 页面（扩展只能 iframe webview）+ 16 个模块级容器（各自独立生命周期、参与布局持久化）+ 聊天 UI 本体可改（扩展要 proposed API 才行）——体验上是「IDE 自带 AI」而非「装了个插件」。
  2. 业务纵深：127 个工具覆盖 20 个业务域，模型能跨域完成任务闭环。
  3. 多根工作区：样本全军覆没的维度上我们做了（但注意：扩展 API 并不禁止，属实现领先非形态领先）。
  4. Host 生命周期完备：拥有者语义、孤儿回收、启动锁、端口复用、客户端自退都在。
  5. 工程纪律：124 探针 + 结构性守卫 + 反向突变验证（改坏了必须变红），这套东西样本里没有。
  6. 插件范式统一：23 个插件同构（cordis.patch.yml + preset plane + 工具快照对齐），新增域有明确模板。

本项目缺点

  1. 上游脱钩：VS Code 每次大版本都要手工合并，长期成本最高，且会随时间放大。
  2. 双引擎并存：25 万行 legacy 仍在，认知成本与回归噪声双高，删除被真机验收卡住。
  3. 发布与分发重：用户必须用整个 IDE，不能「装扩展试用」。
  4. 工具面过宽带来上下文压力：需要工具集分桶 / defer / 检索来缓解，机制本身也是维护面。
  5. 可移植性差：能力绑死在 VsSaros，无法像 dsh-ui 那样一份协议供四端复用。
  6. 人力门槛：要同时维护 VS Code 内核改动 + dsh 插件 + 20 个业务域。

开源项目优点

  1. 轻：3.7K–45K 行（本项目 dsh 侧的 1/3 到 1/30）。
  2. 跟随上游：零改造宿主，VS Code 升级无痛。
  3. 可移植：dsh-ui 把协议抽成零依赖包，多端复用；dsh-vsc 21 文件纯协议客户端。
  4. 分发友好：Marketplace 一键安装，按需下载 runtime。
  5. 可组合：用户自己挑 dsh 官方插件，生态开放。

开源项目缺点

  1. 上限低：够不到 ActivityBar 结构、编辑器区、命令深度注入。
  2. 多根全部缺失（folders[0]）。
  3. 工具面薄：基本只有 fs / bash / search，谈不上业务闭环。
  4. Host 生命周期参差：多数无孤儿回收，IDE 崩溃后残留。
  5. 写根边界多为「检查点」而非围栏（tool-write-guard 覆盖不到 bash），或靠 worktree 绑定换来的结构性边界。
  6. 质量保障弱：无工具面快照 / preset 对齐这类结构性守卫，容易「注册漏了没人知道」。

五、关键取舍：什么情况下该选哪条路

如果你的目标是该选理由
快速验证「dsh + 编辑器」有没有价值扩展几天能出原型，不碰宿主；dsh-vsc 21 文件就是范例
做成产品化的 AI IDE（体验一体化）fork只有 fork 能做原生容器承接、聊天区深度承载、业务工具面

要一份协议跑多端（桌面/TUI/H5）扩展 + 协议包dsh-ui 的 @dsh-ui/protocol 是正解
要真正的多根工作区扩展就够workspaceFolders 返回全部根、onDidChangeWorkspaceFolders 是 stable 事件——样本没做是实现问题，不是 API 限制
要在聊天区里放自己的原生页面（非 iframe）fork扩展视图只有三个落点，无法新建 part

6.3 关键否定结论：删 legacy 不会缩小冲突面

我曾推测「chat 那 1.5 万行是支撑 legacy 聊天卡片的，等 5.5 删掉 legacy 就能收回」，实测否定这个推测：

  • chat 下 23 个改过的上游文件，新增 10,614 行里只有 12 行（0.1%）提到 agentStudio / dsh / saros。
  • 抽样 chatListRenderer.ts（基线 2,931 行 → HEAD 5,075 行，净增 2,144 行）的 diff 中段：checkpointRestoreToolbar、inline-progress、treePart——全是通用聊天 UI 增强，与 legacy 引擎无关。

⇒ 这批改动是产品级分叉，不是过渡期脚手架。5.5 删完 legacy 后，这 43% 的冲突面依然在。这意味着「等重构收口再考虑上游合并」的乐观假设不成立。

6.4 由此得出的三条修正

  1. 「每个 stable 版本建一次合并分支」→ 不可行，改为「只吃安全修复」。落后 5.5 个月 + 上游 sessions/chat 每月千余提交 ⇒ 全量 rebase 的冲突量已超出人工可承受范围。现实策略：建立「上游关键修复 cherry-pick 白名单」（安全 CVE、崩溃、数据损坏类），其余不上。把 fork 当冻结基线维护，而非追踪分支。
  2. 把精力从「改上游文件」转向「新增文件 + 钩子」。现状 2,161 新增 vs 277 修改，比例健康；但 26 个 >200 行的修改文件是长期负担。优化方向：凡是能用「新增文件 + 在上游文件里留一行调用」实现的，就不要在上游文件里写大段逻辑。尤其 chatListRenderer / chat.contribution 这两处（合计 8,300+ 行改动）值得专门做一次「把逻辑抽成独立模块、原处只留注册」的收编。
  3. 把 5.5 的价值重新定位。删 legacy 的核心收益是认知成本与回归噪声（25 万行双轨），不是「缩小上游冲突面」。所以不要为了「将来好合并上游」而加速删除——应按原节奏等 5.1 真机验收。反过来说，也不该因为「删了也不减少冲突」而放弃删除——双引擎并存的维护成本是独立且真实的。

七、给本项目的三条建议

  1. 把「fork 的必要性」写成可验证清单。✅ 本报告已完成（见第二节「真正只有 fork 能做的」三条 + 「容易误判」五项，每条附 API 源码行号）。维护方式：VS Code 每个 stable 版本复核一次，若某条被上游补齐（例如 chatSessionsProvider 转正、或新增第四个视图容器位置）就从清单里划掉。关键纪律：不要把「扩展也能做」的项算进 fork 理由——那会让整份辩护被一次 code review 击穿。
  2. 把「上游合并」变成常规动作而非事故。⚠ 已被 6.4 修正：实测落后 5.5 个月、上游 sessions/chat 每月千余提交 ⇒ 全量 rebase 不可行。改为「关键修复 cherry-pick 白名单」（安全 CVE / 崩溃 / 数据损坏），fork 按冻结基线维护。
  3. 把可移植的部分抽出去。通信协议、Host 生命周期管理、工具面快照守卫这三块与「fork」无关，可像 dsh-ui 那样抽成零依赖包——既能复用到未来形态（如 Electron 独立版 / Web 版），也能在 fork 崩盘时保命。
