# 游戏拆解（kb-game-teardown）

产物落到知识库 vault 的 **`库/raw`**（素材层），**随后由「构建」变成笔记** —— 这条链路是本技能的核心，
不要跳过落盘直接给一段聊天结论，也不要自己往 `笔记/` 写（见第四、五步）。

## 何时启用 / 何时不启用

- **启用**：用户说「**拆分游戏**」「游戏拆解」「拆解这款游戏」等，或发来「介绍某款游戏的视频链接」
  （小红书 / 抖音 / YouTube / B站 / 快手 / 微博…）、给出**游戏名**并要求**拆解 / 分析 / 研究**。
- **不启用**：用户只是分享链接让你**收藏 / 下载 / 转存 / 找视频**，或闲聊某游戏好不好玩（没有拆解意图）
  ⇒ 照常回答，不要套本手册的流程。判断不清时，一句话问清「是要我做拆解报告吗」。

## 第一步：先盘素材（决定这次能拆到多深）

**关键约束：Agent 不能自己触发「知识库导入」。** 视频链接要变成**入库素材**
（元信息 + 封面 + 落进 `库/raw`），必须由用户在**知识库视图**点「导入链接 / URL」
（或让用户直接口述、发截图）。

**但「看视频」不需要导入**（★ 2026-09-24 起）：ffmpeg / ffprobe / yt-dlp **随 VsSaros 自带**
（`<安装目录>/resources/saros/bin/`），两个视频工具可直接对链接工作 ——
也就是说**抽帧与字幕你自己就能拿到**，不要因为「没导入」就退回凭常识编造。

| 素材 | 有这个素材时 | 来源 |
|---|---|---|
| **字幕全文**（≤1.2 万字，若有） | 口播内容/玩法的**主要事实来源**（作者讲了什么机制、体验如何） | `video_analyze`（内部 yt-dlp 抓平台字幕/自动字幕）或 URL 导入。⚠ **抖音、小红书多数视频没有字幕** |
| 标题 / 作者 / 时长 | 定位层、题材与玩法标签的第一手依据 | `video_analyze`（`--print` 元信息）或 URL 导入 |
| **视频帧（多张 PNG）** | **画面层结论的唯一合法来源**：美术风格、UI 信息层级、战斗/反馈表现 | `video_analyze`（顺带看图）或 `extract_video_frames` → `vision_analyze` **逐张**读 |
| 封面图 / 网页正文（图文帖） | 题材氛围与第一印象；图文攻略/评测的事实来源 | URL 导入（reader-mode 抓正文）；`vision_analyze` 读 |
| 用户补充的截图 / 口述 | 抽帧覆盖不到之处（设置界面、深层菜单）的合法来源 | 用户发图 → `vision_analyze` |

**两条看视频的路（按目的选，别两条都跑）**：

1. **要整体理解** → `video_analyze`：一次调用完成「抽帧 + 抓字幕 + 多模态模型给结论」，
   返回带 `[帧 mm:ss]` / `[字幕]` 标记的分析 + 素材清单（帧路径）。**先用它**；
2. **要写进报告的证据 / 要针对某帧追问** → `extract_video_frames`（产物目录显式指定为
   `<vault>/库/raw/assets/<游戏名>/`，报告里用相对路径 `assets/<游戏名>/frame-01.png` 引用）
   → 再 `vision_analyze` **逐张**读。默认抽 6 张、限宽 1280、最多 24 张，返回路径与时间点。

**依赖与失败处理**：正常情况下**不需要用户装任何东西**（随包自带）。
若工具报「未检测到 ffmpeg / yt-dlp」——那是内置二进制缺失或被杀软拦截：
**原样转告工具的排查指引**（源码运行 ⇒ `node build/saros/fetch-ffmpeg.mjs`；
或设 `FFMPEG_PATH` / `YTDLP_PATH`），也可以让用户到**命令面板执行
「检查媒体工具链（ffmpeg / ffprobe / yt-dlp）」**自查看装在哪、什么版本；
**不要**改用"我记得这类游戏通常…"继续，那等于编造。
抽完默认**删除下载的视频本体**，只留帧图。

**仍然拿不到（不要假装有）**：
- ❌ 连续播放 / 音频 / 镜头语言 —— 只能看抽出来的**静止帧**，不能声称"看完了整段视频"；
- ❌ 全片逐帧 —— 只有抽出的那几张；**没抽到的时段等于没看过**，不要对那段时间下结论；
- ❌ 平台官方 API 数据（人数/流水等要么来自简介/字幕，要么来自 `web_search` 的外部报道，须注明来源）。

**降级路径**（按优先级，能拿到多少就拆多少）：
1. 字幕全文 + 抽帧结果 ⇒ 可做完整拆解（L1–L7，表现层有画面证据）；
2. 只有元信息 + 抽帧 ⇒ L1 定位 + L6 表现层可写，其余维度写明「素材不足」；
3. 抽帧也失败（内置二进制缺失 / 平台反爬 / 视频下架）且没字幕 ⇒ 只做 L1 定位，
   并**明确告诉用户差什么**：先把工具的排查指引原样给出（通常**不需要装东西**，
   是内置二进制缺失或被杀软拦截）、让用户在知识库视图导入、或让用户提供截图；
   也可以直接用**游戏名** + `web_search` 做外部资料拆解（并说明结论来自外部报道而非视频）。

## 第二步：七层拆解框架

按「证据可得性」从高到低逐层做，**每层都要落到可核验的具体物**，不要停在形容词。

**L1 定位与市场**：品类与子品类、题材/世界观、玩法标签（3–6 个）、目标用户画像、平台与发行、商业模式
（买断 / 内购 / 广告 / 订阅）。依据：标题、简介、字幕、封面；缺则用 `web_search` 补（注明来源）。

**L2 核心循环（Core Loop）**：分三层各写一句闭环 + 钩子 + 退出点：
- 分钟级：一次操作 → 即时反馈（打击感/掉落/进度条）；
- 小时级：一局/一次产出 → 结算与选择（下一局为什么再来一次）；
- 天/周级：成长、社交、活动的时间钩子（留存靠什么）。
产出：**一张 mermaid 循环图**（`flowchart`）。

**L3 系统拆解**：逐系统写「输入 → 处理 → 输出」+ 与其他系统的耦合。常见系统：战斗/建造/养成/关卡/探索/经济/任务/社交/赛季。
产出：**系统关系 mermaid 图** + 系统表（见 `references/report-template.md` 表头）。

**L4 数值与经济**：主要资源清单（软/硬通货、体力、时间）、产出与消耗闭环、主要卡点（时间墙/付费墙/运气墙）、
成长曲线形状（线性/阶跃/指数）。⚠ 具体数值一律 `[待验证]`，除非字幕或资料明确给出。

**L5 内容与节奏**：首 10 分钟（FTUE）做了什么、新手引导的信息投放顺序、内容产出管道（关卡/赛季/活动频率）、
难度与心流曲线（哪一段最容易流失）。

**L6 表现与体验**：美术风格、UI 信息层级（主界面第一屏放了什么）、关键反馈（掉落/暴击/失败提示）。
⚠ **必须先看画面再下结论**：整体印象用 `video_analyze`（一次拿到带时间点的画面结论），
要写成可核验证据就 `extract_video_frames` → `vision_analyze` 逐帧读并挂 `[帧 mm:ss]`；
只抽到封面、或抽帧失败时，整层标「未验证 —— 需要用户提供截图或可抽帧的视频」。
**禁止**凭封面推断实机 UI 细节，也禁止描述没抽到的时段。

**L7 借鉴与风险**：3–5 条可迁移结论，每条写「借鉴点 + 前提条件 + 风险/适用边界」。
不要写「值得学习」这类无动作结论。

## 第三步：证据纪律（硬性，违反即返工）

1. **每条结论挂来源标记**：`[字幕 12:34]`、`[帧 00:45]`、`[简介]`、`[封面]`、`[搜索:<来源名>]`、`[用户口述]`、`[推断]`。
   （`[帧 mm:ss]` 指"我确实用 vision_analyze 看了抽出来的这一帧"—— 这是画面结论的唯一合法标记。）
2. **事实与推断分开写**：推断必须紧跟一句依据（「因为字幕 08:10 提到 X，所以推断 Y」）。
3. **无法核验的不要混进结论区**：统一进文末「待验证清单」，写清「需要什么素材才能验证」。
4. **禁止用常识填补**：不要因为「这类游戏一般都…」就写成该游戏的机制。
5. **禁止描述你没看到的画面**：没有截图的 UI/战斗/镜头细节，一律不写。

## 第四步：落盘到 `库/raw`（素材层 —— 不要写进 `笔记/`）

产品的知识库是**两层**：`库` = 数据源层（原始素材），`笔记` = 知识体系层（构建产物）。
拆解报告是「加工后的素材」，**先落 `库/raw`**，再由第五步的构建把它变成笔记
（归位 / 补链 / 去抽象化门控 / 导航 / 飞书同步全部由既有管线接管，你不用管）。

落点与命名（对齐 URL 导入产物的既有约定）：

- **报告**：`<vault>/库/raw/<游戏名>-拆解报告.md`
- **帧图**：`<vault>/库/raw/assets/<游戏名>/frame-01.png`（抽帧时 `outDir` 传这个目录），
  报告里用**相对路径**引用：`![](assets/<游戏名>/frame-01.png)`
- 内容多时拆多篇，同目录并列：`<游戏名>-拆解-<系统>.md`，用 `[[双链]]` 互引。

⚠ **素材不写 frontmatter**：对齐 URL 导入产物的形态 —— 首行 `# <游戏名> 拆解报告`，紧跟一行
`> 来源：<链接或"游戏名+检索"> · 拆解时间：<YYYY-MM-DD> · 素材：<字幕/帧 N 张/封面>` 即元信息。
`type / title / sources / status / feishu:*` 都是**构建产物（笔记）**才有的字段，由管线写入 ——
你替它写只会污染构建判定。

- 报告骨架：**先读** `references/report-template.md`（省 token 的渐进披露），按它填。
- 图：核心循环/系统关系用 `mermaid` 代码块写源码即可（同步飞书前宿主会自动渲染成 PNG 并改写引用）。
- 正文**不写 HTML / `<iframe>` / html 代码块**，也不用依赖 Obsidian 社区插件的语法（Charts / Dataview 等）——
  预览与飞书都不渲染（见技能 `kb-feishu-sync` / `kb-category-feishu`）。

## 第五步：询问用户是否构建到笔记（用 `kb_build`，而不是让用户自己去点按钮）

素材落盘**不等于**流程结束。按下面两步走，别停在那里，也别只丢一段聊天结论就收工：

**1）先问用户（一句话，带事实）**

> 拆解已落盘到 `库/raw/<游戏名>-拆解报告.md`（帧图在 `库/raw/assets/<游戏名>/`）。
> 要我把它构建成笔记吗？（会归纳到「笔记」区并维护知识体系，耗时可能几分钟）

有 `clarify` 工具时**优先用它**（它会暂停本轮并等用户明确选择，避免"问完就当用户同意了"）；
没有就在对话里直接问。素材多时先用 `kb_build`（`mode:"preview"`，**只读**、不启动任何会话）
拿到准确数量与清单再问，不要用「大概有几份」这种含糊说法。
⚠ **没得到用户明确同意前，不要调用 `mode:"build"`**。

**2）用户同意 ⇒ 调用 `kb_build`（`mode:"build"`）**

- 它会在「知识库专家」agent 里**新建一个聊天会话**执行（与知识库视图「批量构建库」按钮
  **同一条路径**：agent 自己读素材、写笔记，随后补链/门控/导航并完善 `知识体系.md`，
  规则全在技能 **`kb-build`** 里）；
- **发起后立即返回**：你只转述「已开始、N 份素材、进度在那个会话里、完成后有通知」，
  **不要等它跑完**，也不要重复发起（工具会拒绝并发，并告知已有构建在进行）；
- 用户**拒绝** ⇒ 就停在这里，告诉他之后随时可以：让助理调 `kb_build`、或去知识库视图点
  **「批量构建库」**、或对素材右键 **「构建为笔记」**。

前置条件：知识库专家已配好 Provider/模型，否则 `kb_build` 会**拒绝并说明去哪配置** ——
如实转告用户，**不要**因此改走「我自己直接写 `笔记/`」（那会绕过补链/门控/导航与素材台账）。

最后给用户一段**结论摘要**（5 行以内）+ 报告路径 + 哪些维度因素材不足没做、要怎么补。
⚠ 若用户明确说「不用落盘，直接讲」，就只在对话里回答（仍守第三步的证据纪律）。

## 反模式（出现即不合格）

- 「玩法丰富、画面精美、体验流畅」这类零信息量描述；
- 把外部报道/竞品信息当成该游戏的事实；
- 没拿到字幕却复述「视频里说…」；
- 用封面图推断实机 UI 细节；
- 数值/付费点凭经验编出一组具体数字；
- 自己往 `笔记/` 写「拆解笔记」（那是构建的活，会造成素材/产物混淆与重复笔记）；
- 给素材文件写 `type/sources/status` 之类构建产物字段。

## 相关技能与工具

技能：
- `kb-build`：构建执行手册 —— 素材 → 笔记（本技能第五步交接的对象）
- `kb-category-feishu`：笔记分类、与飞书知识库建立同步关联
- `kb-feishu-sync`：笔记区 → 飞书知识库同步
- `mermaid` / `obsidian-markdown`：图表与笔记语法
- `youtube-content`：YouTube 字幕专项（可选增强）

工具（视频理解三件套，随包自带二进制，无需用户安装）：
- `video_analyze`：**一次调用**拿到带时间点的理解（抽帧 + 字幕 + 多模态模型结论）—— 默认首选；
- `extract_video_frames`：只抽帧（要写进报告当证据、或要针对某帧追问时用）；
- `vision_analyze`：读单张图（含帧图、用户截图）。
