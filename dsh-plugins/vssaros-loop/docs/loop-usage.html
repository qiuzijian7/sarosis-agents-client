vssaros-loop：无人值守循环

一个 loop = 定时去外部系统采活（harvest）→ 用共享账本挑单去重 → 每条条目在独立会话里让 agent 干活 → 按完成契约结算。它跑在 Host 里（30 秒一个 tick），不需要人盯着，也不需要模型自己记得"上一轮做到哪"。

一、30 秒上手

  1. 在数据根下建目录：<数据根>/loops/<名字>/，写 loop.json（最小配置见下）。
  2. 先干跑：loop_dry_run { "name": "<名字>" } —— 看它采到什么、会做哪几条、其余为什么被排除。
  3. 确认无误再开跑：loop_run { "name": "<名字>" }（或等 schedule 到点自动跑）。
  4. 随时查账：loop_list / loop_show { "name": "<名字>" }。
先干跑再开跑是纪律，不是建议。干跑真的执行采集命令，但不建会话、不花 token； 它能在你烧掉一轮额度之前就把"采到的行没有 id""prompt 是空的""全是已处理过的老条目"这类问题暴露出来。

二、文件与数据落在哪

路径是什么
<数据根>/loops/<名字>/loop.json循环定义（下面那张字段表就是它）
<数据根>/loops/<名字>/state.json运行状态：上次起止时间、结果、连续失败次数、轮数
<数据根>/loops/<名字>/ledger.json账本：每条条目的状态、尝试次数、原因、会话 id

数据根按共享链解析：config.dataRoot → $VSSAROS_DATA_ROOT → ~/.vssaros（dev 环境通常是 ~/.vssaros-dev）。落盘是原子写（tmp → rename），进程被杀也不会留下半截 JSON。

三、loop.json 字段

调度与安静时段

字段默认说明
schedulemanual只有三种：every 30m / daily 09:00 / manual（刻意不做 cron——cron 要时区故事，every 已覆盖真实需求）。两轮最短间隔 120 秒。
quietHours''如 23:00-07:00，跨午夜也可；留空 / none / off = 不启用

取活（harvest）

字段默认说明
harvest.command''一条 shell 命令，stdout 必须是 JSON 数组（或 {"rows":[...]}）
harvest.cwd''命令的工作目录；留空用插件 cwd
identityFields["id"]行的哪些字段进账本键；没有 id 就用别的字段组合
harvestTimeout2m采集命令超时（超时只报一轮 harvest-failed，不算条目失败）
最容易踩的一条：harvest.command 只有插件 config.allowCommands=true 才会真的执行（默认是 false）。 否则你会看到 harvest 未执行：config.allowCommands=false —— 那是安全默认值，不是故障。

干活（work）与完成契约

字段默认说明
work.prompt''每条条目要做的事；支持 {字段} 占位（取自采集到的行，如 {id}、{bug}）
work.taskHeader''拼在 prompt 前面的抬头（同样支持占位），让条目自带单号
work.allowedTools[]这条 loop 允许的工具名（与插件 allowTools 取交集）
work.model / work.template / work.cwd空可选覆盖
completion.requireMarkertrue要求条目最后一行给出标记（见下）
completion.onMissingMarkerfailed没给标记时算 failed（可设 done）

完成契约由框架自动附加到每条目的 prompt 末尾，作者不用自己写；条目收尾必须是下面之一：

[item:done]                        → 完成
[item:failed:<原因>]  → 失败（会计入重试与熔断）
[item:blocked:<问题>] → 停等人决策（用 loop_answer 回答后重跑）

护栏（都有默认值，不写也能 7×24 跑）

字段默认硬上限作用
maxItemsPerRound320一轮最多做几条（防一轮烧光）
itemTimeout45m6h单条墙钟超时
itemTurnCap60500单条最多多少轮对话
maxAttempts25失败重试几次
retryBackoff30m24h重试前的退避
consecutiveFailureLimit310连续几轮有失败 ⇒ 熔断（粘性：只能人工恢复）
roundCostCeiling0（关）—单轮成本上限
runsRetention30d365d运行记录保留期
notify["web"]—通知通道
越过硬上限一律拒绝（不是夹紧）—— 夹紧会让"我明明写了 500 轮"静默变成 60 轮，那是没法排障的。

结构化交接（handoff，可选）

开了之后，每条条目除标记外还要交一份带字段的交接块（summary / evidence / next / blocker）， 超长或字段矛盾直接判失败（不截断、不静默放过）。默认关闭，与老 loop 完全兼容。 

"handoff": { "require": true, "maxChars": 16384 }
这份交接是条目自述，不是独立验收：写 done ≠ 有人复核过。（这条口径与官方 Ralph loop 一致。）

一个能直接用的例子

{
  "name": "tapd-bug-triage",
  "schedule": "every 30m",
  "quietHours": "23:00-07:00",
  "maxItemsPerRound": 3,
  "harvest": {
    "command": "python scripts/list_open_bugs.py --json",
    "identityFields": ["id"]
  },
  "work": {
    "taskHeader": "单号 {id}：{title}",
    "prompt": "复现并定位这条缺陷，改完跑单测。收尾最后一行给 [item:done] 或 [item:blocked:<原因>]。"
  },
  "completion": { "requireMarker": true },
  "handoff": { "require": true, "maxChars": 16384 }
}

四、五个工具

loop_list只读

列出本机所有循环：调度、账本计数、下次到期、是否熔断、配置错误。参数：verbose:true 附带护栏参数。

loop_show只读

单个循环的完整定义 + 账本明细（done/failed/blocked/running 与原因）。参数：name（必填）、limit（≤100）。回答"这个循环为什么没跑"。

loop_dry_run只读

干跑：真采集 + 挑单 + 逐条说明为什么排除，不建会话、不落账本。参数：name。

loop_run需审批

立刻跑一轮（不等 schedule）。会建独立会话、写账本。参数：name。

loop_answer需审批

回答被阻塞的条目并放回队列。参数：name（必填）、key（不传=放开该循环全部 blocked）、answer。

五、安装与插件配置

  • 装机：IDE 启动时按伴生清单安装（@vssaros/dsh-workitem 先于 @vssaros/dsh-loop——loop 用 ctx.inject 等它）。它是纯 Host 插件，不声明 vssaros manifest ⇒ IDE 侧没有页签，只有 5 个工具。
  • 依赖：@vssaros/dsh-workitem（账本/去重/完成契约的唯一真源，与群聊 #task 共用）——没绑上不降级，会抛带指引的错（静默回退本地实现正是"两份判定"复活的入口）。
  • config：allowCommands（默认 false：harvest 命令开关）、allowTools（条目会话里允许的工具名数组）、cwd、dataRoot。
  • 驱动一条条目的原语：bridge 的 vssarosRuns.run({ sessionId, cwd, prompt, timeoutMs, approval })；后台回合没人审批 ⇒ approval.allow 默认全拒，必须显式放开。

六、排障速查

现象先看这里
每轮都采到 0 条harvest.command 为空，或 config.allowCommands=false（默认）
harvest 的 stdout 不是合法 JSON命令输出必须是数组 / {"rows":[...]}；别把日志打到 stdout
条目一直被重试没给 [item:*] 标记（默认 requireMarker=true、缺标记算 failed）
循环"卡住不跑"state.json 里 consecutiveFailures ≥ 上限 ⇒ 熔断是粘性的，需人工 loop_run 或清 state 后恢复
夜里还在跑配 quietHours；它在安静时段内只跳过、不算失败
状态显示 paused历史遗留值（早期版本写入）；语义等同停用（只有 active 才会触发）
同一个活被做两遍identityFields 选的字段不稳定（比如带了每次都变的时间戳）
换机器后账本对不上数据根解析链不同（config.dataRoot / VSSAROS_DATA_ROOT）——dev 与 prod 是两套根
插件激活失败看 Host 日志里是否有 vssaros-loop 的行；它默认不打日志（只在 runs 缺失或工具没注册时 warn）⇒ "日志里没有它"不等于没激活，要看 profile 目录与数据根落盘

七、它和「自动化任务 / 群聊 #task」的分工

自动化任务（schedule）

管"人看的任务列表"与定时投递一句话；/api/run 可手动立刻跑一次。

vssaros-loop

管"无人值守地批量干活"：外部采集 + 账本去重 + 独立会话 + 重试/熔断。

群聊 #task

同一套账本内核的另一条入口（显式 #task:<key>），与 loop 共享去重判定。

为什么触发权不交给 schedule：schedule 只会"往会话投一条 prompt"，拿它当哨兵等于让内部逻辑靠解析自己发出的 prompt 触发，脆得没边。 所以 schedule 只保留"人看的任务列表"，真正的循环触发留在本插件。
与 0.1.1 实现对齐；字段与默认值以 lib/core/spec.js、工具签名以 lib/index.js 为准。改动后请先跑 node dsh-plugins/vssaros-loop/test/run-loop-check.mjs（95 项）。
