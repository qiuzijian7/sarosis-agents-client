05a DSH 框架原理（讲懂版）

已审 19.2 KB · 1 260 字 · 改于 10-26 14:02

一、一句话结论

DSH 的框架本质是「一个共享 Context + 一堆平权插件」：所有能力都以服务/事件的形式挂在 ctx 上，插件之间不互相 import。

注意本段 2026-10-26 重新核对了运行时版本（0.2.1-rc.1），与旧稿的差异已标注。

二、运行时结构

ctx = { services, events, effect }
plugin.apply(ctx) → 注册服务 / 监听事件 / 声明清理

插件生命周期由 ctx.effect() 管理：返回的函数会在插件卸载时调用。这一点决定了「热重载不留定时器」。

三、为什么不用全局单例

全局单例在测试里无法隔离、在多实例下会串数据。共享 Context 把「作用域」显式化，代价是每个插件都要声明依赖。

四、与本知识库的关系

知识库插件同时挂 3 个宿主（IDE 侧栏 / 工作台面板 / HTTP 页面），靠的就是这套 Context：同一份视图、同一套 /api/*。

五、常见坑

1) 在 apply 里做异步初始化而不登记 effect；2) 事件监听忘记释放；3) 用 ctx.get 拿可选依赖、却在缺失时崩溃。

六、小结

把「共享 Context」理解成前端的 DI 容器，很多设计选择就顺了：依赖显式、生命周期可控、测试可隔离。
