# 讲懂一件事（help-me-understand）

**交付物不是"我讲了多少"，而是"你能复述多少"。**

三条硬约束：① **先 trace 真源再开口**——没读到真实路径不写解释；② **每个结论标证据等级**
（`observed/inferred/recommended/unknown`）；③ **理解靠检查点验收，不靠篇幅**。

## 何时启用 / 何时不启用

- **启用**：用户要求讲清某件事（论文 / 技术方案 / 代码链路 / 一段 AI 回答 / 概念）。
- **不启用**：只要摘要（用 summarize）、要直接改代码、要拆解游戏/产品（用 `kb-game-teardown`）、
  只是转了个链接没提要讲（先问一句）。

## 深度档位（先定档）

| 档 | 预算 | 追加框架 | 产出 |
|---|---|---|---|
| L1 快读 | 15min | SCQA、5W2H | 结构 + 核心论点 |
| **L2 标准**（缺省） | 30min | +批判性思维、逆向思维 | 论点评估 + 风险 |
| L3 吃透 | 60min | +心智模型、第一性原理、系统思考、六顶帽 | 多角度 + 本质 |
| L4 综述 | 120min+ | +跨源对比 | 多材料综合 |

按输入类型选（别全用）：论文 → 5W2H+批判+系统思考；代码/引擎机制 → trace 优先+第一性原理；
方案/架构 → SCQA+心智模型+逆向；观点文/难懂的回答 → 批判+逆向+六顶帽。框架细则见 `references/frameworks.md`。

## 执行步骤

**Step 0 定位真源**（决定这次能讲多深）：知识库先查（`kb_search` → `kb_read` → `kb_list`，
★ 库里讲过就**接着讲、别从零重讲**，冲突要指出）；否则 `file_read` 读本地文件、用抓取工具取 URL、
或直接用用户粘贴的内容。**拿不到真源就标 `unknown`，不许用常识补全。**

**Step 1 Trace**（不许跳过）：沿真实路径走一遍，每跳能说出 `file:line` 和"这一跳决定什么"，
数出 **hop 数**（后面是跟用户签的合约）。

**Step 2 定形态**：能装进 ~200 字 + 一段代码、且**无前向引用** ⇒ 一次讲完；只要有前向引用 ⇒ 分轮。

**Step 3 开场给地图**（两种形态都要，≤5 行）：一句"这东西是干嘛的" + 整条路径的箭头链
（`🗺 A → B → C → D。4 跳。`）。分轮时 hop 数就是合约。

**Step 4 讲**：
- 一次讲完：地图 → 自己的话讲机制 → 一段"做出决定的那几行" → 一个冷读时会意外的地方 → 停。
- 分轮：一跳一轮，每轮 = `Hop n/N —— 名字` + 2–4 句解说 + ≤10 行关键代码（其余 `…` 省掉）
  + 一行"抽掉这跳会坏什么" + `❓ 检查点`。
- ⚠ 代码是证据不是解释：解说必须看着片段才成立，说明解说还没到位。
- **检查点要用户预测或应用**（"第一次问会怎样？"），答错/含糊 ⇒ 换个角度重讲这一跳再问；
  用户反问说明这轮落地了。要一次问多个 ⇒ 按 **frontier** 问：只问前置已定的，每题给**推荐答案**，
  措辞让"是"即采纳。用户说跳过/点名某跳 ⇒ 直接跳。

**Step 5 视觉锚点**（需要才画，别逢讲必画）：挑 2–3 个文字说不清的概念，优先 Before/After 对比图；
一张图一个概念、≤5 元素、SVG 内联。要存档/给别人看 ⇒ 出单文件 HTML（数字卡片 + 结论块 + 风险块）。

**选哪种图**（两条路分工，别混用）：
- **结构性的**（流程 / 时序 / 状态机 / 依赖关系 —— 节点与连线本身就是信息）⇒ **mermaid 代码块**：
  Obsidian / 飞书 / GitHub 都能渲染，改几个字就行不用重画，篇幅也只有手写 SVG 的三分之一；
- **示意性的**（Before/After 对比、布局、心智模型 —— 重点是"看起来像"）⇒ **手写内联 SVG**：
  mermaid 的自动布局控制不了视觉重心与相对位置。

规范见 `references/visual-delivery.md`。

**Step 6 Recap**（收尾，≤8 行）：地图 + 每跳"它决定什么"。这是用户会留下的东西。

**Step 7 落盘知识库**（★ 默认**不写**）：只有用户明确要"存进知识库 / 记下来"才写。
`kb_write_note` → `笔记/讲懂/<主题>.md`（缺省 `create` 不覆盖；覆盖要显式 `replace`，旧正文先进备份）。
正文必须带来源、hop 清单、证据等级、recap、回链。契约见 `references/kb-integration.md`。

## 证据分级（硬约束）

`observed`（材料真写了/代码真这么走，给 `file:line`）｜`inferred`（推出来的，**必须写推导链**）｜
`recommended`（我的建议）｜`unknown`（材料没覆盖，**允许说不知道，不许用常识补**）。

两条硬约束：**相关 ≠ 因果**（要写因果需时序/机制/对照之一）；**每个结论都要写适用边界与不适用情形**。
细则与自查清单见 `references/evidence-guard.md`。

## 能力边界（如实）

- 不新增工具：只用 `file_read`、`kb_*`、平台抓取工具；没有的就说没有。
- 图是手写 SVG/HTML，不是图像生成 ⇒ 画的是示意，不是精确渲染。
- 读不到真源就标 `unknown`，不按"通常怎么做"补全。
- 落盘会改盘 ⇒ `kb_write_note` 要用户审批，被拒是正常的，别反复重试。

## 存档位置（硬约束）

产出要落进知识库时，**位置由既有分类决定，不由任务命名决定**。

- **先看已有分类**：`笔记/` 下通常已经有领域划分（如 `01_学习/AI_Agent/`、`02_工作/`、`技术架构/`）。
  用 **`kb_catalog`** 拿目录地图（`路径 + 篇数`，以磁盘为准）确认后再落。
- **放进领域分类**：同一主题的笔记应该和它**已有的兄弟笔记**待在一起。
- **不要用任务类型命名目录**：`讲懂/`、`分析/`、`摘要/`、`问答/` 这类都是错的 ——
  同一篇内容换个任务就会存成好几份，而它本质上是**同一篇**。
- **不确定就询问用户**：直接问"这篇要放进哪个分类"（并可列出 `笔记/` 下现有的目录供选），
  **不要**自己挑一个、也**不要**新建目录。宁可多问一句，也不要留下一个孤儿目录。
- 已经是同一主题的第二版时：**优先 replace 原文件**（`mode: "replace"`，会先备份），
  而不是新建一个"（讲懂版）"。

> 2026-10-20 真机教训：一次"讲懂"把 `DeepSeek Harness 框架原理.md` 写进了自建的 `笔记/讲懂/`，
> 而同一篇早在 `笔记/01_学习/AI_Agent/12 …md`。结果是**同一内容两份**，用户要手工合并。
