# 知识库构建（kb-build）

宿主（VsSaros）会发来一条消息，里面带：**素材清单**（绝对路径 + 每份的 sources 引用）、
**笔记区现有目录树**（若附带）、vault 根与笔记区路径。你按下面的两个阶段执行。

## Phase 1 —— 构建笔记（素材 → 笔记区）

**依次**处理清单里的每份素材：

1. 先 `file_read` 读原文（**不要凭文件名猜内容**）。
2. 读 schema：`file_read <vault 根>/kb-schema.json`（宿主已确保它存在；`type` **必须取自**其中的类型集合）。
3. **落点规则（严格遵守）**：
   - **优先**把笔记放进现有目录树里最匹配的「已有目录」（领域层级是首选，例如 `01_学习/UnrealEngine/09_UI与Slate/`）；
   - **能复用就绝不新建目录**；目标文件已存在 ⇒ 用 `patch` **就地更新**它（不要新建 `xxx_2.md`）；
   - 实在没有合适目录时才新建：**优先在已有领域层级下新建子主题目录**，命名风格与**同级目录一致**
     （例：同级已有 `01_核心系统`…`08_音频系统` ⇒ 新目录用 `09_xxx`）；完全无从归属才落在笔记区根目录；
   - ⚠ 不要为 schema 的每个 type 各建一套并行目录树（schema 的 `dir` 只在以上都不可行时兜底）；
    新建/调整**分类目录**（以及它与飞书知识库的关联映射）见技能 `kb-category-feishu`。
4. 每篇笔记用 `file_write` 写到「笔记区」`<笔记区路径>/<目录>/<笔记名>.md`，frontmatter **必须**含：

   ```yaml
   ---
   type: <schema 类型 id>
   title: <笔记标题>
   sources:
     - "[[raw/素材名.md]]"
   ---
   ```

   （`sources` 用宿主清单里给出的引用 —— 它是相对「库」的路径，宿主靠它建立「素材 → 笔记」的溯源。）
5. 正文里引用本地图片**必须用相对路径** `assets/<素材名>/<文件名>`（写绝对路径会导致预览与飞书同步都失效）；
   若素材同目录存在 `assets/<素材名>/` 下的图片，用 `vision_analyze` **逐张**总结并并入笔记（该工具一次只接受一张图）。
6. 素材含视频原始链接 ⇒ 笔记里保留该 URL；含「字幕」段 ⇒ 据此总结视频内容。
7. ⚠ 工具约束：只用 `file_read / file_write / patch / search_files / vision_analyze / kb_organize`；
   **不要使用 terminal**；不要用 `file_write` 复制一份再想办法删旧的（曲线搬运禁止 —— 搬运走下面的重构通道）。

## 可视化优先（让笔记不止文字）

判定：内容里只要出现**流程 / 调用链 / 状态机 / 数据流 / 层级结构**，就必须配一张图，
不要用纯文字段落硬讲。

可用的图块（宿主已支持渲染，你只写源码）：

- **流程 / 判定 / 步骤分支** → mermaid 代码块 + `flowchart TD`
- **调用链 / 请求时序 / 消息交互** → mermaid 代码块 + `sequenceDiagram`
- **状态机 / 生命周期** → mermaid 代码块 + `stateDiagram-v2`
- **实体关系** → mermaid 代码块 + `erDiagram`
- **主题地图 / 知识空间叙事** → `![[<主题>.canvas]]`（该 `.canvas` 文件用 json-canvas 技能产出）
- **已有 mxGraph 源码** → drawio 代码块

mermaid 代码块的写法（用 `mermaid` 作为代码块的语言标记）：

    ```mermaid
    flowchart TD
        A[开始] --> B{判定}
        B -->|是| C[处理]
    ```

规则：

- 图表**源码**就是你要写的东西：同步飞书前，宿主会**自动**把 mermaid / drawio / canvas
  渲染成 PNG 并改写引用 —— 你不需要、也不应该手动贴图。
- ⚠ 不要写裸 HTML 标签、`<iframe>`，也不要用 html 类型的代码块：笔记渲染端会做白名单过滤，
  飞书同样不认。
- ⚠ 不要使用依赖 Obsidian 社区插件的语法（Charts、Dataview、DataviewJS 等）：
  飞书同步与客户端预览都不渲染，画了等于没有。
- 克制：一篇笔记 1 张主图（确有必要再加 1 张），配合少量 callout，不要堆图。

## Phase 2 —— 维护知识体系（宿主会随后发「收尾」消息）

1. `search_files` 列出笔记区当前目录与文件（必要时 `file_read` 若干笔记了解内容）。
2. 创建或**完善** `<笔记区路径>/知识体系.md`（已存在 ⇒ 保留既有结构、补充新增内容，不要整体重写），内容必须包含：
   - ① **目录结构总览**：有哪些主题目录、每个目录下有哪些笔记（用 `[[笔记名]]` wikilink 引用）；
   - ② **阅读 / 学习路径建议**：先读什么、再读什么（按依赖与难度排序，并说明理由）；
   - ③ **知识缺口**：哪些主题只有零散笔记、建议补充什么；
   - ④ **结构评价**：现有分类体系是否合理（层级过深/过浅、同类散落、命名不一致…），以及你建议怎么改。

   文档必须按**真实目录层级**组织（含用户手写目录），不要凭空发明目录。
3. **结构重构（可选）**：
   - **小规模（≤10 项）⇒ 直接调用 `kb_organize` 工具**（只能在笔记区内操作；「删除」= 移入 vault 外备份目录；
     执行前自动 checkpoint + 备份，用户可在聊天页签一键 undoAll 回滚）。
   - **大规模（>10 项）⇒ 不要直接动手**，而是输出下面这段**机器可读**的 `KB_REORG` 计划块
     （宿主会**先备份、再请用户确认后执行**）：

     ```html
     <!-- KB_REORG
     {"reason":"把散落在笔记区根目录的 UI 笔记归入 UnrealEngine/09_UI与Slate；理由：…",
      "moves":[{"from":"笔记/UI优化技巧.md","to":"笔记/01_学习/UnrealEngine/09_UI与Slate/UI优化技巧.md"}]}
     -->
     ```

     约束：`from` 必须**已存在**、`to` 必须**尚不存在**（避免覆盖）；两者都必须落在**笔记区**内（**不要动「库」**）；
     路径用**相对 vault 根**（形如 `笔记/…`）；**改目录名 = 对该目录下每个文件各写一条 move**。
     若无需重构，就输出 `<!-- KB_REORG {"moves":[]} -->`。

## 完成标准

- 每份素材至少产出 1 篇笔记；
- 全部处理完后，用一句话列出**你写入 / 更新的全部文件路径**（含 `kb_organize` 的移动结果）。
